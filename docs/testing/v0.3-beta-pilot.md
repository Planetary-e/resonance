# v0.3 beta volunteer test

This beta is for a small, consent-based test of installation, background relay operation, and volunteer-network repair. It is a research prototype. Use invented needs and offers only: relay operators can observe network addresses, timing, message sizes, and fingerprints, and v0.4 private transport is not implemented.

## What the installers can test

The release includes an Apple Silicon macOS DMG, a Windows x64 NSIS installer, and Linux x64 Debian and RPM packages. Each desktop can run an outbound-only relay in the background after its window closes. Keep its storage, bandwidth, CPU, power, and schedule limits at values you are comfortable contributing. Previously accepted records may still require traffic for repair, acknowledgements, and withdrawals after a limit stops new work.

The desktop app cannot expose a public inbound relay endpoint. To connect friends on separate home networks, at least one trusted volunteer must run the standalone relay with a reachable `wss://` endpoint and share that URL with the others. A local-only `ws://127.0.0.1` address will not connect another household. If everyone is behind NAT without a reachable volunteer, the apps can test installation and local behavior, but not the cross-household network. Do not expose the desktop's local admin or backend ports to the Internet.

## Test sequence

1. Install the beta for your operating system. Note the exact release version and installer filename. The Apple Silicon app has an ad-hoc bundle signature, not an Apple Developer ID signature or notarization, so macOS may require per-app approval in Privacy & Security. Report the warning and do not disable Gatekeeper globally. Windows and Linux may also warn about unfamiliar or unsigned packages.
2. In the dashboard, enter the trusted volunteer relay URL under **Volunteer relay contacts** before enabling **Act as Relay**. Set resource limits, enable the relay, and verify that the dashboard reports a running service and an outbound authenticated link. A blank contact list is local-only mode.
3. Close the graphical app and leave the computer awake for a few minutes. Reopen it and check that the relay service is still running and reconnects. Test sleep, wake, and a normal restart separately.
4. On two devices, publish complementary **invented** needs and offers, search, and check that a match notice appears once. Record whether the result survives closing and reopening the app.
5. With consent from the volunteers, take one participating relay offline and bring it back. Record the time to reconnect and whether accepted records, match notices, and withdrawals converge. A placement count below three receipts is a shortfall, not a guarantee of recovery.
6. Report the operating system, app version, network type, steps, expected and observed behavior, and approximate times in a GitHub issue. Share only sanitized logs. Never post relay identity files, keys, journals, personal text, fingerprints, or unredacted network addresses.

## What this test does not prove

Five containers or five relays on one computer share a physical failure domain. Five friends provide stronger evidence, but even five signed receipts only show past durable writes; they do not establish continuous availability or independent operators. The direct-endpoint counter is recent peer testimony and needs a separate real-network check. Windows and Linux background-service installation in release packages is part of this beta's test, not a previously validated result.
