# Actual local application exercise — October 18, 2026

## Result

Two separate Node application processes, each with its own identity and encrypted
storage, complete the desktop backend workflow with the actual cached Nomic FP32
model. No embedding, cryptography, API handler or transport is mocked.

The run creates two offers from one account and one need from another, finds the
complementary offer by text, delivers encrypted mailbox notices to both accounts,
then locks/unlocks both and checks their mailboxes again without duplicating
matches. Ten distinct request bindings use ten distinct blind tokens:

| Operation | Accepted presentations |
| --- | ---: |
| Publication write | 3 |
| Search | 1 |
| Mailbox fetch | 4 |
| Mailbox acknowledgement | 2 |

The two publications from one account have different signing keys and publication
IDs. Captured WebSocket frames contain neither account's root DID, none of the
three input texts, and none of the redeemed token strings. These are concrete
field-exposure checks, not a proof against timing or similarity correlation.

## Reproduction

With the existing local model cache, from the repository root:

```sh
npm run eval:v04-real-app -- --out /tmp/resonance-real-app.json
```

The harness disables model downloads, uses temporary profiles, two loopback
relays and actual authenticated desktop APIs. It issues bounded blinded batches
through a durable local permit ledger. It closes its child processes and relays
and removes only its generated temporary directory. Output paths must be new.
No native installer, operating-system service or release is created.

## Resource discovery and correction

The [first run](v04-real-app-2026-10-18.json) took 32.6 seconds and observed
568,280 WebSocket payload bytes. Application lifetime peaks were 1,997 and
1,616 MiB RSS. Inspection found that account setup loaded and abandoned a model
instance, while lock/unlock created more without explicitly releasing native
sessions.

The engine now has idempotent disposal. It rejects new inference immediately,
waits for initialization and active inference to settle, then calls the native
pipeline's disposal. Setup releases its probe before creating the identity;
failed/cancelled unlocks release their model; locking queues cleanup; a new
unlock waits for that cleanup. Failed cleanup prevents another allocation until
the application restarts. Authentication revocation remains immediate.

The [repeated run](v04-real-app-model-cleanup-2026-10-18.json) passes the same
workflow in 32.9 seconds with identical payload-byte counts. Peaks remain high:
2,019 and 1,565 MiB. **This run does not demonstrate a peak-memory reduction.**
Native resource ownership is now explicit, but allocator/model-loading peak
costs remain an open optimization and device-budget issue. These are runtime
memory observations, not installer sizes. Per-process peaks do not establish
simultaneous total memory, and CPU seconds do not measure energy.

## Important negative result

The Python need also produces a candidate notice for the gardening offer.
The test records that behavior instead of treating all delivered notices as
relevant matches. This is consistent with the excessive candidate false-positive
rate in the [labeled fingerprint evaluation](scoped-fingerprint-real-2026-10-18.md).
The matching-quality gate remains open; this exercise validates delivery and
credential handling, not semantic precision.

## Protected policy composition

The [protected-policy run](v04-real-app-protected-policy-2026-10-18.json) repeats
the workflow with five protected observers, 25 durable history services and
freshness enforcement at the wallet, issuer and relay. It completes ten private
policy queries. After two history replicas per observer become unavailable, an
actual application search fails before reserving another wallet token or
accepting another spend. The run takes 55.9 seconds and records 2,361,088 WebSocket
payload bytes; these include the local infrastructure exchanges.

```sh
npm run eval:v04-real-app -- --protected-policy --out /tmp/resonance-real-app-policy.json
```

This composition exposed slow batch signing outliving its three-second policy
observation. The issuer now retains prepared signatures in its encrypted ledger
and requires a fresh observation before approving them. The explicit command
refreshes once; it does not extend the deadline or bypass a newer policy. Both
applications successfully finalize their sixteen-token batches in this run.

## Protected witnesses and durable spends

The [complete protected run](v04-real-app-protected-admission-2026-10-18.json)
adds five actual witness relays, a coordinator and 30 more durable history
services, for **55 local history services** in total. Each witness checks current
policy before retaining its vote; the destination retains its quorum certificate
and spend before accepting the operation. All original application checks pass.

```sh
npm run eval:v04-real-app -- --protected-admission --out /tmp/resonance-real-app-admission.json
```

All six admission owners close and reopen their existing stores. An exact retry
remains accepted as a replay; a different binding using the same token is rejected.
After two witnesses each lose two history replicas, an actual application search
fails and its uncertain token stays reserved. Losing two history copies per
policy observer then refuses a further search before another token reservation.

The run takes 88.2 seconds, including an explicit 17.4-second cooldown before
fault injection. All simulated clients share one transport address, so the
negative tests wait for the next existing one-minute IP allowance; production
rate limits are not raised. Without that separation, the test correctly exposed
a discovery refusal rather than exercising the intended witness failure.
The report records 7,615,634 WebSocket payload bytes and per-API durations:
publication at most 4,828 ms, successful search 4,686 ms, and mailbox release
at most **9,111 ms**. That mailbox result has little margin under the ten-second
deadline and does not establish Internet responsiveness.

This composition exposed two implementation issues: concurrent witness queries
were refused by single-operation policy observers, and JavaScript signatures
consumed substantial CPU. The bounded observer queue keeps each caller's own
freshness budget and history query. Native Ed25519 signing preserves exact
signature bytes and flushes while removing that JavaScript arithmetic cost.
See `../developers/v0.4-native-signature-verification.md` for the profile and
compatibility tests. Runtime model peaks remain high (about 1,998 and 1,636 MiB).

## Selected 500 ms collection windows

The [follow-up run](v04-real-app-protected-admission-500ms-2026-10-18.json) passes
the same eight checkpoints after reducing request/reply collection windows from
750 to 500 ms. Maximum mailbox release falls from 9,111 to **7,137 ms**;
publication is at most 3,808 ms and search is 3,599 ms. Payload traffic remains
7,615,634 bytes. Total duration includes 27.5 seconds of rate-window cooldown, so
it is not used to compare interactive latency. Model peaks remain about 2,011
and 1,804 MiB; no memory improvement is claimed.

The [separate 192-request timing comparison](private-windows-500-2026-10-18.md)
and [predeclared screening criteria](../developers/v0.4-quiet-period-decision.md)
support selecting 500 ms as the experimental default. This does not establish
quiet-period anonymity or protection against cooperating hop operators.

## Concurrent protected application searches

```sh
node --import tsx scripts/eval-v04-real-app.ts --protected-admission \
  --concurrent-searches --out /tmp/new-concurrent-app-report.json
```

The [initial run](v04-real-app-concurrency-before-2026-10-18.json) completed only
3/6 searches across three paired trials: the policy responder refused the second
simultaneous caller before its wallet reserved a credential. Its other application
and recovery checks passed; the concurrency gate correctly exited unsuccessfully.

The responder now queues at most eight exchanges while preserving its existing
one-collector default (two when explicitly configured), each caller's challenge,
original expiry and the charge for undrained transports. Protected admission
serializes the complete valid-token decision before reading or updating the
shared history. Waiting consumes the existing three-second default allowance;
each operation obtains a separate fresh observation. Invalid tokens do not enter
the queue or cause observer requests. An exact retry and a conflicting binding
are rechecked against the retained state after waiting.

The [corrected run](v04-real-app-concurrency-2026-10-18.json) completes **6/6**
paired searches, consumes exactly six credentials and retrieves the expected
offer each time. Latencies range from **3,834 to 5,562 ms**. This phase adds
3,464,084 WebSocket payload bytes and 5.25 process CPU seconds. All **nine**
application checkpoints pass, including six-owner restart and both quorum-loss
checks. The complete run records 16 distinct spent tokens, 11,075,766 payload
bytes and 33.64 CPU seconds. Its 155.6-second duration includes 71.8 seconds of
explicit cooldown to isolate the unchanged shared loopback-IP allowance; it is
not an interactive-latency measurement. Per-application peaks remain roughly
2,010 and 1,907 MiB.

An intermediate rerun exposed a measurement defect: the capture hook threw after
10,000 retained frames, thereby causing transport failures. It now always passes
traffic through and explicitly fails the privacy gate if capture is incomplete.
The concurrency variant retains at most 20,000 parent frames and 32 MiB per
process; children retain their 10,000-frame ceiling. The completed run captures
10,969 parent frames plus 107 application frames, explaining why the old hook
interfered. No production connection, payload, freshness or rate limit was raised.
Intermediate runs affected by that hook are not evidence of a relay failure.

This is three paired trials on one computer, not a saturation or independent
Internet-capacity result. Larger concurrency, total TCP/TLS traffic, energy and
representative device budgets remain open.

## Scope still missing

- IPv4 and IPv6 loopback simulate different address domains on one computer;
  they do not establish independent operators or Internet/TLS deployment.
- The actual desktop backend is exercised through HTTP. No graphical-interface
  interaction or installed executable is certified.
- Protected observers, witness quorum and spend durability are composed with
  the real application in the optional modes above. Eligibility distribution,
  membership/authority migration and independent operator availability remain
  separate gates.
- Static fingerprint and timing leakage remain. No global anonymity claim is
  supported by absence of an account identifier or repeated token alone.
