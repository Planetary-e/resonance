# Actual local application exercise — October 18, 2026

## Result

Two separate Node application processes, each with its own identity and encrypted
storage, complete the desktop backend workflow with the actual cached Nomic FP32
model. No embedding, cryptography, API handler or transport is mocked.

The run creates two offers from one account and one need from another, finds the
complementary offer by text, delivers encrypted mailbox notices to both accounts,
then locks/unlocks both and checks their mailboxes again without duplicating
matches. Ten distinct request bindings use ten distinct blind tokens:

| Operation | Accepted presentations |
| --- | ---: |
| Publication write | 3 |
| Search | 1 |
| Mailbox fetch | 4 |
| Mailbox acknowledgement | 2 |

The two publications from one account have different signing keys and publication
IDs. Captured WebSocket frames contain neither account's root DID, none of the
three input texts, and none of the redeemed token strings. These are concrete
field-exposure checks, not a proof against timing or similarity correlation.

## Reproduction

With the existing local model cache, from the repository root:

```sh
npm run eval:v04-real-app -- --out /tmp/resonance-real-app.json
```

The harness disables model downloads, uses temporary profiles, two loopback
relays and actual authenticated desktop APIs. It issues bounded blinded batches
through a durable local permit ledger. It closes its child processes and relays
and removes only its generated temporary directory. Output paths must be new.
No native installer, operating-system service or release is created.

## Resource discovery and correction

The [first run](v04-real-app-2026-10-18.json) took 32.6 seconds and observed
568,280 WebSocket payload bytes. Application lifetime peaks were 1,997 and
1,616 MiB RSS. Inspection found that account setup loaded and abandoned a model
instance, while lock/unlock created more without explicitly releasing native
sessions.

The engine now has idempotent disposal. It rejects new inference immediately,
waits for initialization and active inference to settle, then calls the native
pipeline's disposal. Setup releases its probe before creating the identity;
failed/cancelled unlocks release their model; locking queues cleanup; a new
unlock waits for that cleanup. Failed cleanup prevents another allocation until
the application restarts. Authentication revocation remains immediate.

The [repeated run](v04-real-app-model-cleanup-2026-10-18.json) passes the same
workflow in 32.9 seconds with identical payload-byte counts. Peaks remain high:
2,019 and 1,565 MiB. **This run does not demonstrate a peak-memory reduction.**
Native resource ownership is now explicit, but allocator/model-loading peak
costs remain an open optimization and device-budget issue. These are runtime
memory observations, not installer sizes. Per-process peaks do not establish
simultaneous total memory, and CPU seconds do not measure energy.

## Important negative result

The Python need also produces a candidate notice for the gardening offer.
The test records that behavior instead of treating all delivered notices as
relevant matches. This is consistent with the excessive candidate false-positive
rate in the [labeled fingerprint evaluation](scoped-fingerprint-real-2026-10-18.md).
The matching-quality gate remains open; this exercise validates delivery and
credential handling, not semantic precision.

## Protected policy composition

The [protected-policy run](v04-real-app-protected-policy-2026-10-18.json) repeats
the workflow with five protected observers, 25 durable history services and
freshness enforcement at the wallet, issuer and relay. It completes ten private
policy queries. After two history replicas per observer become unavailable, an
actual application search fails before reserving another wallet token or
accepting another spend. The run takes 55.9 seconds and records 2,361,088 WebSocket
payload bytes; these include the local infrastructure exchanges.

```sh
npm run eval:v04-real-app -- --protected-policy --out /tmp/resonance-real-app-policy.json
```

This composition exposed slow batch signing outliving its three-second policy
observation. The issuer now retains prepared signatures in its encrypted ledger
and requires a fresh observation before approving them. The explicit command
refreshes once; it does not extend the deadline or bypass a newer policy. Both
applications successfully finalize their sixteen-token batches in this run.

## Scope still missing

- IPv4 and IPv6 loopback simulate different address domains on one computer;
  they do not establish independent operators or Internet/TLS deployment.
- The actual desktop backend is exercised through HTTP. No graphical-interface
  interaction or installed executable is certified.
- Protected observer freshness is composed with the real application in the
  optional mode above. Spend-witness quorum durability and eligibility
  distribution still have separate gates.
- Static fingerprint and timing leakage remain. No global anonymity claim is
  supported by absence of an account identifier or repeated token alone.
