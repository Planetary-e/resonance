## Decision in plain language

The product goal remains worthwhile. Continuing the current implementation by
serially optimizing historical replay is the wrong default. Replace the parts
that require custom global coordination with an established protocol structure;
preserve useful application code and tests. Search confidentiality still needs a
feasible multi-owner access model. A recent fast private-search paper is not a
complete substitute for that missing design.

Recommend a **selective architectural pivot**, not a wholesale rewrite and not
another cache/timer/fingerprint-tuning round. This review does not demonstrate
that all K1–K8 can be satisfied simultaneously. In particular, malicious
multi-owner semantic matching and sparse/colluding-observer privacy within the
joint resource envelope remain feasibility decisions.

## 1. Recovery: preserve history without replaying all of it for every decision

### What established systems do

[PBFT §4.3](https://pdos.csail.mit.edu/archive/6.824-2009/papers/castro-practicalbft.pdf)
uses periodically certified execution states to release older protocol-log
messages and bring lagging replicas up to date. Its certificates attest to a
state reached by the protocol, not merely that some storage nodes saved a hash.
This is a design pattern, not permission to import its thresholds into our
five-member/four-confirmation model.

[BFT-SMaRt](https://github.com/bft-smart/library) implements replicated state and
group reconfiguration; its [state-transfer interface](https://bft-smart.github.io/library/javadoc/bftsmart/statemanagement/ApplicationState.html)
combines checkpoint state and subsequent batches. These are concrete references
for replacing repeated custom ownership/history protocols. The Java runtime,
resource footprint, membership authorization and application semantics would
need evaluation before selecting this library. No library is selected here.

### What we should change

Separate three objects that are currently too tightly coupled:

1. **Authoritative current state:** unexpired rights, spent bindings, permanent
   denial/fence semantics, unresolved proposals/votes, conflicts, retry results,
   policy head and membership/activation state.
2. **A bounded journal after a certified state boundary.** Replay only changes
   after that boundary for ordinary recovery, while preserving all obligations.
3. **Historical audit evidence and authorization continuity.** Keep required
   originals and authenticated configuration transitions separately. A durable
   reference is not permission to forget unavailable proof bytes.

Our encrypted files already use the word checkpoint. Adding another file with
that name changes nothing. The missing property is a justified semantic cut:
why the next member can use this state without reconstructing every historical
business image and without losing a possible earlier acceptance.

Proposed proof obligations before code:

- The existing authoritative roles validate the full semantic state and bind its
  canonical digest, sequence, original context, membership and policy cutoff.
  Opaque storage acknowledgements alone cannot certify completeness.
- The old cohort is fenced before a successor may authorize; acknowledge no
  mutation before durable state protection. Include uncertain/partial decisions,
  already acknowledged work, exact retries and permanent refusals.
- New members authenticate the state, necessary suffix and configuration chain,
  reserve real storage, install atomically and establish freshness before serving.
- An original-genesis or stale node must still establish authorization continuity.
  A locally trusted recent checkpoint may accelerate an already enrolled node;
  it cannot silently become a new trust root for everyone else. Authority-chain
  work can still grow with transitions even when business replay is bounded.
- Bound every certificate/transition and the suffix, measure cold and warm paths
  separately, and retain rollback/conflict evidence. This does not claim constant
  total storage when the number of live obligations or permanent fences grows.

[CometBFT's light-client specification](https://github.com/cometbft/cometbft/blob/main/spec/light-client/verification/README.md)
illustrates why fast synchronization has explicit initial trust and time-validity
assumptions. Do not import a fresh trusted hash, staking assumption or trust period
as a hidden solution to our original-genesis/rejoining-node requirement.

### Simplify coordination, not safety

Assess one coherent replicated control state per authorized shard/community,
instead of multiple independently reconstructed control histories required for
one operation. Order quota spends, policy transitions and reconfiguration there.
Keep encrypted publication/mailbox replication outside consensus where their
owner-signed sequence/tombstone rules permit it. Keep the logical authority
partitioned so consolidation does not expose client identities or create a new
global cross-operation identifier. Do not merge entry, honest mix and exit roles
or confuse storage replication with confidential-compute membership.

This is an architectural hypothesis: fewer dependent quorums and fewer nested
proofs may help K1/K2/K3/K8. A malicious model rules out replacing these decisions
with ordinary Raft/etcd crash-only consensus or eventual-consistency merging.
An eventually merged spend can already have authorized two conflicting actions.

**Recommendation:** stop tuning the current replay family as the default path.
First justify a state-transfer and reconfiguration protocol against the actual
five/four/one-fault model and retained-rights requirements. Reuse existing storage,
cryptography and regression fixtures where compatible. Do not start a new BFT
implementation from a paper summary.

## 2. Search: newer systems help, but several solve a different problem

There are at least three distinct guarantees: hide a query from the host, hide
publishers' data from that host, and hide non-authorized publication information
from another searching user. Our product needs all three in the declared model.

| Reference | Demonstrated direction | Boundary for Resonance |
| --- | --- | --- |
| [PACMANN, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/391d50b3fe1c59b3e2b8b644e0c8fe81-Paper-Conference.pdf) | Client-side graph traversal with private retrieval of graph data; protects query from a semi-honest server | Malicious extension is explicitly future work. A server holding database vectors and a client retrieving graph content do not establish publication privacy under our access model. |
| [PANTHER](https://eprint.iacr.org/2024/1774.pdf), §3.1 | Optimized private ANN with batched PIR and mixed cryptographic operations | The inspected version specifies a static semi-honest two-party model. It is not our malicious, changing multi-owner volunteer service. PDF fetch was restricted; the threat-model passage was available in indexed primary-source text. |
| [Compass, OSDI 2025](https://www.usenix.org/system/files/osdi25-zhu-jinhao.pdf), §3 | Encrypted semantic search with integrity against a malicious host, including access-pattern protection | The searching client owns and is trusted with its database; cross-owner sharing is not its target. Timing, operation type, data size and availability have explicit exclusions. Giving every searcher this trusted-client role would violate publication confidentiality. |
| [BiSON, EuroS&P 2026](https://www.microsoft.com/en-us/research/publication/bison-billion-scale-oblivious-nearest-neighborsearch-in-milliseconds/) and [author artifact](https://github.com/r-dott/bison/blob/artifact/README.md) | Newer ORAM/DiskANN work reports encrypted billion-scale search; code exists | Read the primary abstract and artifact, not the complete security proof. Neither establishes our multi-owner authorization, churn, total-resource or malicious configuration. The artifact exposes a semi-honest mode: benchmark mode must never be confused with stronger security. |
| [SANNS, USENIX Security 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/chen-hao) | Secure scan/selection and approximate search | Useful algorithmic baseline, but its semi-honest guarantees do not complete our protocol. |

The important correction to the October 18 review is to include Compass and the
newer BiSON direction. It would be wrong to conclude that efficient encrypted
semantic search is generally unavailable. It would be equally wrong to replace
our multi-owner matching service with one of these systems based on its latency
headline. Multi-owner authorization is the unresolved bridge.

### Most direct compatible direction to examine

Keep publication/query vectors confidential using a named, existing actively
secure computation protocol; expose only the approved opaque match references,
not vectors, exact scores or stable publication IDs. Split secrets over the
permitted independently operated compute roles, preserving encrypted bodies and
mutual-consent disclosure. [MP-SPDZ](https://github.com/data61/MP-SPDZ) supplies
concrete malicious-security implementations; each has its own party/fault,
preprocessing and abort assumptions. It is a benchmark/protocol reference, not
an already selected dependency or a five-of-four drop-in service.

At our target, start by costing a simple confidential full scan and top-k
selection before building oblivious ANN indexes. 10,000 × 768 is 7,680,000
coordinate products; FP32 input alone is 30,720,000 bytes (29.30 MiB). Those are
arithmetic/raw-storage figures, not secure-compute time, traffic or acceptable
precision. Quantization, authentication, comparisons/top-k, preprocessing, share
delivery/refresh and offline members all need accounting. There is no measured
claim that this fits K1/K7. If it fails joint bounds, reject it before integration;
only then consider a more complex index with a demonstrated cost advantage.

Offline publishers, malicious clients and dynamic members are mandatory cases.
A multi-client ORAM service or a permanently online trusted client holding all
keys would add a new protocol or trust dependency. A TEE would add hardware trust.
None is silently authorized by this review.

### Fix the experiment's question before its implementation

No useful search system can conceal every fact that its authorized answer
intentionally reveals. Define separately: representation/dictionary recovery,
cross-scope linking, and inference available through approved chosen queries.
Freeze the attacker view, query allowance, entitlement acquisition and allowed
outputs. Existing output-consent rules do not automatically exempt count/existence
leakage. Preserve K5's 5% targets and prior failures; if their intended game is
incompatible with useful output, present that exact conflict for an owner decision.
Do not improve a score by silently redefining the adversary or labels.

## 3. Observer privacy: reuse a mixing design rather than adding hop patches

[Loopix](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/piotrowska)
combines independently delayed packets, client/relay cover and offline reception
roles. It is a concrete design reference for asynchronous private communication,
not evidence that our volunteer topology meets its assumptions or costs.
The [2024 metadata-systems SoK](https://petsymposium.org/popets/2024/popets-2024-0030.pdf)
shows why similar-looking honesty assumptions can yield different guarantees
depending on placement and topology. A named honest mix is insufficient without
the required indistinguishable traffic, anonymity population and behavior.

Recommend one existing mix design and packet construction as a reference, with
the owner's approved honest independently operated middle role. Preserve separate
activity-detection and source-linking experiments. An extra forwarding hop,
TLS padding, fresh IDs or relay-only noise does not solve a client-link observer
who sees one isolated operation. Do not replace that observer with a weaker one.

Declare connected sparse-mode daily bytes, wakeups and physical power separately
from nominal bytes/completion. Any positive continuing cover traffic makes
bytes/useful-operation diverge as useful traffic approaches zero; this does not
contradict K7's nominal-workload definition. It means a sparse envelope is still
needed before activating cover. Schedules must include handshakes, reconnects,
bidirectional segments, computation and the original deadline.

The [Anonymity Trilemma](https://conferences.computer.org/sp/pdfs/sp/2018/AnonymityTrilemmaStrongAnonymityLowBandw.pdf)
motivates joint latency/bandwidth/security evaluation in its specified model; it
does not prove our exact AUC/byte/power targets impossible. Sleep or no usable
volunteer route means no delivery. Report that outage rather than declaring a
fast privacy-preserving operation.

## 4. Two dependencies no cryptographic substitution removes

**Eligibility.** [Privacy Pass, RFC 9576](https://www.rfc-editor.org/rfc/rfc9576.html)
separates attestation from anonymous authorization. Reuse the separation and
established token primitives; do not rebuild their purpose with a permanent user
ID. It does not decide who is eligible or establish one human per entitlement.
Our independently adjudicated source, federation issuance budgets and K4 fairness
evidence are still missing. Fixed-period token retirement can reduce live state
only with irrevocable authenticated cutoffs; it cannot erase required fences or
make a replayed backup current.

**Availability.** Replicate encrypted application data widely, while avoiding
unnecessary *simultaneously required* quorum dependencies. This can improve
availability but does not prove 99% service from arbitrary volunteer schedules.
The existing two-independent-4/5-cohort model gives 84.372% at individual p=0.9;
that is a conditional model, not measured volunteer uptime. Offline owner-free
search adds compute availability too. Measure the complete dependency graph and
retain K8's real pilot; do not replace volunteers with an unapproved fixed service.

## One finite next decision, not another auxiliary roadmap

The next deliverable should be **one executable architecture decision**, before
product implementation, using the same persistent blocker IDs and remaining
authorized resources. No repeated broad survey or fourth renamed alternative:

1. Specify the checkpoint/state-transfer invariant and every retained obligation,
   its freshness path from original pins and a concrete existing consensus model.
   Compare current replay against this semantic structure, not just cache speed.
2. Specify one confidential matching protocol/access model and one mix reference,
   with exact malicious/offline roles and permitted outputs. Reject incompatible
   schemes on paper before obtaining or porting artifacts.
3. Show one full publish/search/mailbox dependency path and cost table at the
   accepted load, including steady, sparse, recovery and membership-change modes.
   Mark measured quantities, analytic bounds and unknowns separately.
4. Admit an isolated benchmark only when it can resolve the remaining decisive
   uncertainty. Predeclare its hypothesis, meaningful result, acceptance/stop,
   exact candidate and cumulative allowance. Use the existing frozen lifecycle
   fixtures for regression; no campaign rerun is authorized by this document.
5. If it fails a structural invariant, needs an unapproved trust/cost change, or
   reaches the existing stop boundary, return a concrete go/no-go decision. Do
   not open another importer, exporter or optimization to avoid that decision.

Full-scope closure still requires **the same integrated candidate** passing K1–K8,
including independent operation. A successful architectural decision is not a
KPI pass. A replacement recommendation must precede any new implementation;
abandoning an approach is not abandoning the product or lowering its requirements.
