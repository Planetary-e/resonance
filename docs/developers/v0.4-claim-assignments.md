# One approved claim, one assigned issuer

An allocation with `version: 2` and
`claimPolicy: 'authority-assigned-v1'` requires a signed assignment before an
issuer can grant a permit. The requirement is part of the community's signed
plan. An operator cannot disable it by omitting a local command option.

The authority's retained journal assigns one opaque approved claim to one issuer
in a community epoch. Repeating the same assignment recovers the identical signed
result; assigning that claim to another issuer is refused. Each new assignment
reserves one permit from the selected issuer's signed allocation, even if delivery
fails. This adds coordination across honest issuer ledgers that share that plan
and authoritative journal.

## Trust and privacy boundary

The claim handle is the existing operator-approved, canonical base64url encoding
of 32 opaque bytes. It represents the same approved claim throughout its period.
Generating a fresh handle for each attempt would defeat the intended uniqueness;
the software does not determine whether different handles belong to one person.
Eligibility evidence and the process that supplies these handles remain external.

The assignment binds the authority, complete allocation digest, community, epoch,
claim handle and selected issuer key. The signed allocation determines the batch
size and issuer limit. Assignment files are private provisioning material: the
authority and selected issuer can associate a claim with its grant. Keep them
out of public repositories, logs and relay messages. Permits, blinded requests,
issuance responses and redemption capabilities carry no assignment or claim
identifier. This does not hide provisioning timing or operator knowledge.

The guarantee requires one authoritative retained journal and honest issuers
enforcing the signed mode. Copied keys, cloned issuer ledgers, restored snapshots,
another authority journal or signatures made outside this workflow can bypass
local accounting. The component does not establish federation consensus,
malicious-issuer resistance, one person per claim or cross-community uniqueness.
It does not qualify the K4 automation/fairness targets.

## Retained state and availability

The [protected authority API](v0.4-protected-allocation-authority.md) adds
four-of-five volunteer retention for new authority journals. The commands below
still use the local-only authority workflow; they cannot silently downgrade a
protected file. Protected creation/enrollment and exact pending resumption are
separate explicit operations. Reviewed owner-loss restoration is available through
the development API; resumable operator orchestration remains pending.

The authority retains at most 64 allocation plans and 2,048 assignments in its
existing 8 MiB encrypted journal. The assignment count is global across retained
periods. New work is refused at capacity; exact retained recovery remains
available. There is no pruning, reassignment, refund or automatic reset.

New assignments require the allocation's issuance window before signing and
before persistence. The journal commits before releasing a signature. Cached
assignments remain exportable after expiry; this does not extend an issuer's
permission to grant or sign. The existing signed policy, active-key rules,
allocation window and any enrolled policy-observation requirements still apply.
An already allocated permit or completed response is recoverable only under the
existing recovery rules.

Allocation v1 retains its previous manual claim behavior. Existing signed plans
cannot be replaced within a period, so a community that has already signed v1 for
an epoch must choose a new period and corresponding issuer profiles for v2.
This is a separately approved allowance, not a refund of the previous period.
The policy still selects one active issuer at a time; an assignment alone does
not activate another key.

Issuer active/retired formats 8/9 retain the required mode. Active ledgers retain
authenticated assignment evidence and validate it on reopen. Retirement removes
per-permit details while preserving the signed allocation and lifetime totals,
and permanently refuses further grants or recovery. Older software refuses these
new formats. No missing history is treated as an empty new account.

The authority can distribute assignments in advance and then go offline. The
selected issuer must be available to issue tokens, and relevant quorums must be
available for configured checks. Previously issued valid tokens do not require
the authority or issuer to remain online for redemption. Losing an assigned
issuer does not authorize reassignment or a second allowance; loss recovery
without duplication remains a separate requirement.

## Operator workflow

Start with the [allocation workflow](v0.4-issuance-allocations.md), using
`version: 2` and `claimPolicy: 'authority-assigned-v1'` in the unsigned plan.
The authority signs and retains it through the same review/sign commands.
`init-allocation` automatically derives the issuer's required mode from that
signed manifest; it accepts no override to permit unsigned grants.

Prepare a private `assignment-request.json` from an existing approved claim file
and the intended issuer profile. The claim file uses the
[existing operator claim format](v0.4-admission-decision.md#optional-operator-approved-claim-binding).
The profile must belong to the retained signed plan and match its epoch.

```sh
node --import tsx --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
import { admissionKeyFingerprint } from '@resonance/core/admission-policy';
const claim = JSON.parse(readFileSync('operator-claim.json', 'utf8'));
const profile = JSON.parse(readFileSync('issuer-profile.json', 'utf8'));
const request = {
  community: 'public', epoch: profile.scope.epoch,
  claimHandle: claim.handle,
  issuerKeyFingerprint: admissionKeyFingerprint(profile.issuerPublicKey),
};
writeFileSync('assignment-request.json', JSON.stringify(request), { flag: 'wx', mode: 0o600 });
JS
node --import tsx scripts/admission-allocation.ts assignment-review authority.pub authority-private.json allocation-journal.json assignment-request.json
```

Inspect the private request and selected allocation, then copy the returned
approval digest into the next command. Unlike public allocation-plan review,
assignment review opens the encrypted retained journal and therefore requires
the authority secret. The placeholder below is not a valid digest.

```sh
node --import tsx scripts/admission-allocation.ts assign --approve '<approvalDigest>' authority.pub authority-private.json allocation-journal.json assignment-request.json signed-assignment.json
```

Give the signed assignment privately to its selected issuer. After the issuer
has installed its signed allocation and current community policy, it grants
through the assignment path:

```sh
node --import tsx scripts/issue-admission-tokens.ts grant --approve --assignment-file signed-assignment.json issuer-profile.json issuer-private.pem issuer-ledger.json permit.json
```

`--assignment-file` and `--claim-file` are mutually exclusive. An unsigned claim
file or omitted assignment cannot grant from a v2 allocation. Continue with the
existing blinded request, `issue --approve` and wallet response-import workflow.

All exports create new files exclusively. After a failed assignment export,
repeat the approved assignment to a new output path or re-export the retained
result with the same request:

```sh
node --import tsx scripts/admission-allocation.ts assignment-reexport authority.pub authority-private.json allocation-journal.json assignment-request.json recovered-assignment.json
```

After a failed permit export, repeat the issuer's `grant --assignment-file` with
the same signed assignment and a new output path. Preserve both journals and
the wallet's original blinded request; do not reinitialize to recover lost output.

## Validation and completion boundary

Local TypeScript compilation and 67 tests across ten files pass: 25 core and
authority tests, plus 42 issuer allocation, assignment, ledger, freshness,
retirement and crash tests. The three new files contribute 18 tests. A final
seven-test issuer assignment rerun covers the reviewed secret/binding tamper
assertions. Astra reviewed runtime, tests and this guide; Sol implemented the two
bounded parts and Luna checked operational command consistency.

Checks cover one retained assignment after 100 retries, cross-issuer reassignment
refusal through restart/concurrent requests, signed scope and authority validation,
the 2,048-assignment global bound, issuer capacity, persistence/export failures,
expiry/recovery, prepared issuance, policy freshness and sealed retirement. The
actual authority CLI assignment runs through issuer CLI grant and blind issuance
to verified token redemption; downstream formats are inspected for metadata
leakage. The new files are included in Linux, macOS and Windows CI; local success
does not establish the result of a new cross-platform run.

These checks establish this component's boundary, not completion of
[v0.4's acceptance contract](v0.4-acceptance-kpis.md).
