# Prepare and operate volunteer history replicas

`scripts/admission-history.ts` prepares an opt-in protected admission owner and
enrolls explicitly selected volunteers. The service retains and routes complete
certified ancestry across successive generations and restarts. These commands
make initial setup usable without writing application code; recovery agreement,
owner restoration and protected maintenance still need their operator commands.

Five identities/endpoints are pins, not proof of independent devices or operators.
Use independently verified public keys and the existing fixed-membership trust
assumptions. New admission needs four durable responses. Running five processes
on one computer tests the protocol but does not provide independent redundancy.

## 1. Collect keys, policy and member endpoints

Use the existing `scripts/admission-policy.ts` key-generation commands to create
the owner's participant signing key and owner storage key. Each volunteer creates
its own participant signing key and independent local storage key, keeping both
private. Volunteers never receive the owner's encryption key or signing secret.
The owner independently pins the community authority and current signed policy.

Collect exactly five public records in `members.json`:

```json
[
  { "publicKey": "<member 1 public key>", "endpoint": "wss://<member 1>/history-checkpoint" },
  { "publicKey": "<member 2 public key>", "endpoint": "wss://<member 2>/history-checkpoint" },
  { "publicKey": "<member 3 public key>", "endpoint": "wss://<member 3>/history-checkpoint" },
  { "publicKey": "<member 4 public key>", "endpoint": "wss://<member 4>/history-checkpoint" },
  { "publicKey": "<member 5 public key>", "endpoint": "wss://<member 5>/history-checkpoint" }
]
```

The placeholders must be replaced with verified values. For a one-computer test,
use distinct loopback ports with `ws://127.0.0.1:<port>/history-checkpoint`. Public
endpoints require `wss:`. These commands do not discover, replace or establish the
independence of volunteers. Endpoint edits preserve identity pins and do not
authorize changing the context or replacing lost histories.

## 2. Prepare a genuinely new owner

Run from the repository root with Node 24 or later:

```sh
node --import tsx scripts/admission-history.ts owner-config \
  owner-private.json authority.pub policy.json members.json owner-config.json

node --import tsx scripts/admission-history.ts owner-prepare \
  owner-config.json policy.json owner-storage.hex owner-data enrollment.json
```

`owner-config` authenticates the signed current policy against `authority.pub`,
validates the five distinct member keys/endpoints, generates a new random history
identifier and records the exact initial policy digest. The output contains an
absolute path to the owner's key file, not its private contents. Keep this context
and the subsequently printed genesis digest independently backed up with the
owner keys. Generating another configuration is not a recovery operation.

`owner-prepare` requires a new empty destination. It creates the encrypted live
baseline, pristine writer and retained archive, and exports the owner-signed
encrypted genesis plus public context. It makes **no network requests** and prints
`readiness: "unverified"`. Distribute `enrollment.json` to the chosen volunteers
and verify its context/genesis fingerprints through a trusted channel. The file
contains opaque owner ciphertext; volunteers cannot validate its hidden policy
or spend semantics without the owner's decryption key.

Existing output files are never overwritten. If an output write is interrupted,
retain the partial file and export to another path:

```sh
node --import tsx scripts/admission-history.ts owner-export \
  owner-config.json policy.json owner-storage.hex owner-data enrollment-copy.json
```

If setup was interrupted **after the authoritative spend baseline was published**
but before its pristine writer/archive was created, explicitly use
`owner-resume-setup` with the same five arguments. It only recreates components
whose original baseline is still pending and for which no committed writer
history exists. Missing live spend state or missing already committed writer data
is refused. It does not reset a lost history or replay accepted application work.
If no authoritative baseline was ever published, keep the interrupted directory
and review a separate new destination. Restored successor state cannot be exported
as a replacement genesis.

## 3. Review and enroll each volunteer

On each volunteer, keep the enrollment input and private key files **outside** its
dedicated replica data directory:

```sh
node --import tsx scripts/admission-history.ts replica-plan \
  enrollment.json member-private.json member-storage.hex replica-data

node --import tsx scripts/admission-history.ts replica-enroll --approve <review-digest> \
  enrollment.json member-private.json member-storage.hex replica-data
```

Review the owner, authority, member, destination, context and genesis fingerprints,
and copy the returned `approvalDigest` only after verifying them. The digest binds
that exact destination, member, context/root, local storage key and configured
limits. A changed file/key/destination requires another review. This approval
records an explicit operator decision; it does not establish trust by itself.

Enrollment only initializes a new empty directory and only for one of the pinned
members. It retains the genesis and initial empty successor slot, then closes.
Repeated enrollment cannot clear existing state. Do not use fresh enrollment to
replace a volunteer's lost accepted history; that requires recovery preserving
its commitments and the quorum's retained-state assumptions.

## 4. Serve the retained chain

```sh
node --import tsx scripts/admission-history.ts replica-serve \
  enrollment.json member-private.json member-storage.hex replica-data 9160
```

Startup reopens existing state and prints its loopback checkpoint/agreement
endpoints. Port `0` is supported for local test allocation; deployed configurations
need a stable, independently configured endpoint. The listener is loopback-only,
bounded and compression-disabled. For remote volunteers, a configured TLS proxy
must preserve `/history-checkpoint`, `/history-agreement`,
`/history-agreement-data` and `/history-provision` and their existing frame limits.
No proxy or certificate is installed automatically. All protocol requests remain
owner-authenticated and target-bound. SIGINT/SIGTERM close the listener and stores.

`openHistoryVolunteerService` reconstructs the complete local chain from the
independently pinned genesis. Each parent's durable activation and registered
provision journal bind its child. It routes checkpoint reads/writes, agreement,
selected-history transfer and provision requests to that exact generation.
After certified child publication, the child becomes routable and receives an
empty slot for its own future successor. Existing generations remain readable;
their freeze barriers still prevent new writes.

A missing successor journal after parent activation is lost history, not empty
setup. Missing/corrupt published child data, a damaged journal or unregistered
files refuse reopening and remain intact for inspection. The only resumable empty
slot is one whose durable parent has **never activated a child**. In that case the
service may finish initial creation under the existing process lock, recognizing
only the expected encrypted temporary and lock files. An interrupted lock-recovery
guard or unknown contents still refuse automatic repair. This does not detect a
coherent rollback of all honest-volunteer disk state; the protocol's retained-state
assumption and owner readiness checks remain necessary.

Limits are 65 generations, 10,001 blocks and 64 MiB per generation, with the
existing 256 MiB ancestry accounting. Store accounting includes reserved manifest
copies; provisioning journals, filesystem metadata, sockets and process memory
are additional costs. These numbers are not a total device-space or memory cap.
Capacity refusal preserves all accepted generations; nothing deletes ancestors.

## 5. Start protected admission

After volunteers are enrolled and reachable, follow the
[protected startup guide](v0.4-protected-admission-operations.md). Its first policy
installation uses `RELAY_ADMISSION_POLICY_INITIALIZE=true` while opening the
already prepared spend history. Remove that flag on later starts. The relay waits
for four fresh exact-head acknowledgements before its application listener opens.
History replication does not replace any witness authorization required by policy.

## 6. Inspect retained generations without changing them

```sh
node --import tsx scripts/admission-history.ts owner-inspect owner-config.json enrollment.json
```

This command needs the backed-up owner signing key, configuration and enrollment
file; it does not open or recreate the owner's lost working directory. Every hop
asks a pinned volunteer for its activated child using a fresh owner-signed
`continuation` request. A returned boundary must contain the four-signature
confirmation certificate for that exact parent and match its frozen head. A
claimed generation number alone cannot advance the traversal. Requests retain
their existing 30-second validity; the complete traversal has one 30-second
deadline, at most five simultaneous requests, 65 generations and 40 KiB replies.

One valid certified boundary can identify the next root. Four fresh responses
without an activated child end inspection at an **observed** leaf. This is not
proof that no newer prepared or confirmed decision exists: a confirmed child may
not have been activated yet, or a concurrent provision may race the observations.
The command reports `readiness: unverified` and never freezes history, chooses an
agreement value, provisions a child or enables writes. A subsequent recovery must
still use actual agreement selection and fresh readiness. Silent or invalid
responses cannot keep the operation open indefinitely; cancellation closes its
outstanding connections. Remote endpoint accounting uses the configured transport.

## Evidence and remaining integration

The command integration runs five separate volunteer processes, creates its owner
configuration from a signed policy, prepares/exports the genesis, reviews/enrolls
each member, refuses readiness with only three live processes, then accepts a
real blind token after a fourth returns. Exact replay remains bound to its original
operation. Negative cases cover changed approvals/member/local keys/destinations,
untrusted policy authorities, duplicate members, output preservation and refusal
to recreate committed missing writer data. The service tests run complete network
freeze/agreement/provision/write/read across three generations, restart every
service, inject missing/corrupt state and kill a process before/after empty-slot
publication.

Inspection tests traverse two certified boundaries over real sockets, preserve
every store, reject forged/replayed replies, bound silent peers and cancellation,
and distinguish a confirmed but unactivated decision from an observed leaf. The
CLI inspects with the owner's working directory deleted and refuses three replies.

These are local tests. The commands currently dial pinned endpoints; history
exchange is not yet carried over the desktop relay's authenticated reverse links
for outbound-only volunteers behind NAT. That routing, desktop service lifecycle,
operator restore/maintenance, complete policy/witness recovery, safe compaction,
policy freshness, resource measurements and independent volunteer validation remain
part of the completion work. No always-on managed relay is introduced.
