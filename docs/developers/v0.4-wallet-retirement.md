# Permanent retirement of an old access-token wallet

Status: **implemented for the opt-in v0.4 pilot, 2026-10-01**. This extends [issuer-ledger retirement](v0.4-issuer-retirement.md) to the desktop's encrypted token wallets.

## Decision: remove tokens, retain retry denials

An old wallet contains bearer tokens and reservations binding each used token to one relay, action and request. Simply deleting the wallet or its reservations is unsafe: the managed provider searches previous reservations before allocating a token. Forgetting a reservation would let a retry of an old request silently spend a token from the current wallet.

Retirement therefore permanently closes the old wallet and replaces its entries with:

- Its original scope and actual issuer public-key fingerprint.
- The pinned authority fingerprint, policy revision/digest, final retry cutoff and retirement time.
- Historical counts of removed tokens and reservations.
- One sorted, unique SHA-256 denial digest per distinct normalized reservation. The digest covers a domain separator, canonical relay URL, action and exact request binding. Equivalent legacy URL spellings share a denial.

The entire snapshot remains encrypted with the wallet's identity-derived key. No bearer token, raw request binding or reservation URL remains in the retired wallet snapshot. Public setup details remain in the separate managed profile snapshot. Digests are retained evidence, not a claim that all activity traces have disappeared.

Every managed capability lookup checks **all** retired denials before returning a retained capability or allocating a new token. A matching old request fails locally with no replacement token, including after restart or clock rollback. A different request can still use the current wallet. Direct SDK imports and fresh reservations on the closed wallet are permanently refused.

## Eligibility and review

Cleanup is explicit, never automatic. It requires:

1. An installed, authenticated and currently valid signed community policy, pinned through the existing independent-authority setup. Manual profiles alone cannot authorize deletion.
2. A saved wallet that is not the active key in that policy.
3. The key's **`retryUntil` reached**. Earlier issuance/spend cutoffs and policy expiry alone do not authorize cleanup.
4. No pending token request or in-progress wallet update/import.
5. Approval of the current review digest. This binds the resolved wallet path, actual issuer key, complete target wallet state, signed-policy digest and full managed profile/policy configuration. A policy/setup or target-history change requires review again. Changes to the separate current wallet balance do not invalidate an otherwise unchanged old-wallet review.

The current policy and final cutoff are checked again immediately before writing. Review exposes counts and public setup metadata, never token strings, reservation bindings, denial digests or encryption keys. It does not rewrite the wallet.

## Desktop workflow

In **Dashboard → Access-token wallet → Previous wallet setups**:

1. Finish or cancel any pending issuance request and install a current signed successor policy.
2. Once eligible, select **Review cleanup** on the old wallet.
3. Check the issuer, token period, key, retry deadline and counts. The review explains that unused tokens are removed too, closure cannot be reversed, old requests remain blocked, and no setup slot is freed.
4. Choose **Permanently close old wallet**, or **Cancel cleanup** to leave it intact.

After closure, the old row displays historical removal counts. Current available/reserved balances and the automatic-mailbox preference remain unchanged. Neither review nor cleanup sends relay traffic. An error or stale approval requires another review; failed I/O requires closing and reopening the local session to inspect recovered state.

Authenticated local HTTP endpoints:

```text
POST /api/admission-wallet/retirement-plan
{ "keyFingerprint": "sha256:..." }

POST /api/admission-wallet/retire
{ "keyFingerprint": "sha256:...", "approvalDigest": "sha256:..." }
```

Both require the unlocked session's bearer authorization. Malformed fields return 400, unauthorized calls return 401, and ineligible/stale operations return 409. The application never accepts a replacement policy or authority as part of a cleanup request. SDK integrations should use `openManagedAdmissionWallet`; the lower-level wallet maintenance methods require the caller to authenticate and pin their supplied policy.

## Persistence and failure behavior

Live wallets keep the original encrypted version 1 state. Retirement replaces that same file with version 2, empty `entries`, retirement metadata and denial digests. Older binaries reject version 2. The key fence, denials and removal are one atomic, flushed snapshot; no managed-profile rewrite is needed during cleanup.

Single-writer locks cover the wallet and managed profile files. An uncertain write failure poisons the open wallet handle. Reopening recovers either the complete original evidence or the complete retired state. Tests inject failures before and after the replacement and kill a separate process after durable cleanup. Saved wallet files are opened in explicit existing-file mode; missing, empty, malformed or key-mismatched history refuses unlock rather than recreating capacity.

Reopening verifies the saved signed policy and consistency with each retained retirement marker: authority, minimum revision, policy digest for the same revision and non-extended cutoff. Retired wallets cannot become active through manual setup, recovered orphan files, or a newer signed policy. Reading status remains possible after policy expiry; spending still follows current-policy checks. The marker is authenticated local state, not a separately signed network revocation certificate.

## Bounds and remaining work

- Cleanup releases token strings and reservation details, **not spendable allowance**. Closed wallets report zero available/reserved tokens and zero usable capacity; removed counts describe history. Nothing is refunded or transferred.
- Up to 4,096 denial digests can remain per retired wallet. Both live and retired files retain the 8 MiB limit. Large histories shrink; metadata can make an empty or tiny wallet larger. Physical secure erasure, backups and exported copies are outside this operation.
- Cleanup itself preserves profiles, files and markers and frees no community configuration slot. [Signed policy v2 archives](v0.4-policy-archives.md) now allow a ninth issuer by separating eight current configurations from up to 64 permanent archives while retaining local rejection evidence. Managed v2-policy wallets can retain up to 72 historical profiles; manual/v1-policy wallets retain their eight-profile limit.
- This is local retirement, not global token revocation. Other devices follow their installed policy, deadlines and evidence. It does not compact issuer ledgers, witness records or relay spends on other devices.
- Deliberate file deletion/reinitialization, restoring stale filesystem backups, cloned identities and bypassing the managed provider remain outside the honest-device assumption. Retired denial evidence must stay with the authoritative local state.
- Unattributed and empty legacy relay spend logs still need a conservative recovery design. Admission remains opt-in; this does not resolve membership, volunteer availability or traffic-analysis limits.

## Verification

Ten new wallet tests cover real tokens, v1 preservation on review, cutoff/current-policy/active-key checks, stale approval after reservation and policy changes, pending issuance/imports, normalized and duplicate legacy reservations, cross-wallet denial precedence, permanent reactivation refusal, unchanged active balances, corrupt/missing history, clock changes, failed file/directory flushes and SIGKILL recovery.

Desktop HTTP coverage adds authenticated review/apply, strict request validation, stale approval refusal, pending issuance, real signed response import, no relay traffic and retained denials after lock/unlock. Two UI tests check review gating, consequences, disabled controls and closed-wallet reporting.

A local browser check exercised review, cancellation, confirmation and reload using real temporary signed policies and token wallets: four old tokens (one reserved) were removed, the old reservation stayed blocked, and the current wallet retained two available tokens. Embedding initialization was stubbed in this wallet-only preview; no embedding or network-delivery claim is made from it. The separate HTTP suite exercises real local relays with fixed test embeddings.

TypeScript and frontend compilation passed. The final complete local suite passed **110 files / 572 tests** with one worker in 299.63 seconds. Remote CI runs separately after push. No installer or release is part of this checkpoint.
