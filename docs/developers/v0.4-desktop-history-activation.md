# Reviewed desktop owner activation

An unlocked desktop can review and activate an already prepared or recovered
protected owner history. This closes the gap between restoration into a new
folder and an ordinary service start: restoration supplies the spend/writer
history, while activation prepares the independent policy store and saves the
reviewed service paths. It does not initialize witness or coordinator state.

## Operator workflow

1. Enter **Protected history maintenance** and stop the relay. Every subsequent
   operation independently checks stopped state and retains the runtime/control
   claims; a previous successful check is insufficient.
2. In **Activate prepared owner history**, enter full local paths for the owner
   configuration, independent enrollment backup, pinned authority, current signed
   policy, history encryption key and prepared/recovered history folder.
3. For reverse or bridged connections, also provide the runtime routing file and
   the operator recovery connection file. Without the latter, activation uses
   the pinned direct endpoints. It never silently changes transport on failure.
4. Select **Review activation**. This opens retained local state but performs no
   network exchange or policy creation. The review shows the history identity,
   destination, generation, policy action and retained spend/denial counts.
5. Select **Approve and configure owner**. Four current durable copies of the
   exact retained head must answer before policy preparation. Successful apply
   saves the selection and leaves maintenance active and the relay disabled.
6. Leave maintenance, then explicitly start the relay. Startup validates the
   saved state and obtains fresh readiness again.

Keys remain in their local files; the form contains paths, not key contents.
The browser does not persist the selection. The authenticated local server saves
it with the existing relay settings. Approved history paths take precedence over
stale desktop launch variables when enabling the service again. Other configured
roles keep their existing precedence rules.

## Approval and retained-state rules

The review binds canonical runtime/history directories, independent genesis,
current head/generation, policy revision, prior installed policy/context, storage
key identity and desktop service intent. The desktop also binds selected file
bytes and normalized routing configuration, and checks them again before saving
service settings. Changes require another review. Input files remain operator
owned; normal startup still validates them rather than treating saved paths as
immutable file snapshots.

The supplied policy must already match the protected image. Pending history must
be finished explicitly first. Initialization, implicit policy advance, promotion
and restoration are separate workflows, never activation side effects. An
unbound runtime containing an old spend ledger cannot select a separate history
and abandon that evidence; it must first protect and bind its current history.

Apply checks the approval before network exchange, requires four fresh exact-head
copies and then creates/resumes/updates only the authenticated owner policy store.
The permanent context binding prevents later local-only fallback and cannot be
replaced by another history. A coherent stale backup or only three live copies
cannot authorize activation. Witness and coordinator initialization remains off.

Existing policy/history locks and a dedicated activation claim remain held
through preparation. The desktop retains its stopped-runtime/control claims
through the final atomic settings replacement. A settings failure can leave a
valid prepared policy while retaining the previous settings. Another explicit
review detects that state and permits resumption; it does not erase or roll back
accepted evidence. The six before/after policy rename crash boundaries retain
the spend file unchanged.

## Authentication and cancellation

The local API requires the unlocked session and its bearer token:

| Endpoint | Effect |
| --- | --- |
| GET `/api/relay/history/activation` | Read the saved file selection |
| POST `/api/relay/history/activation/review` | Review exact `{input}` offline |
| POST `/api/relay/history/activation/apply` | Apply exact `{input, approvalDigest}` |
| POST `/api/relay/history/cancel` | Cancel this GUI process's active history operation |

Cancel, session lock and client disconnect close in-flight history exchanges.
Exclusion stays held until the operation settles. Cancellation preserves the
maintenance marker, prior history and any preparation already made durable.
Another GUI cannot cancel this process through its own in-memory controller; the
shared control claim still prevents competing writes. Forced death leaves the
saved pause and durable state for explicit review after restart.

## Evidence and remaining work

Package compilation and **35 tests across eight files** passed in **61.79 seconds**.
These include authenticated desktop API refusal, offline/wrong/changed approval,
settings replacement failure, three cancellation paths, real Node startup using
the saved environment, stale-head/three-copy refusal and six SIGKILL boundaries.
The five-process operator scenario now activates three successive restored
generations through this same primitive, retaining all accepted tokens and a
permanent denial while refusing conflicting reuse. UI review wording has an SSR
test; the form/review layout was inspected in a static local browser preview.
Native OS installation is mocked; the preview does not test interactive behavior.
