# Protected history in the desktop relay service

Status: opt-in operator configuration, 2026-10-17. The desktop can retain prepared
owner, enrolled volunteer and explicit bridge roles in its supervised relay
process. These roles survive GUI restarts. Preparation, enrollment and recovery
remain the separate reviewed operator workflows; enabling the service cannot
initialize missing policy, spend or witness history.

## Configure before enabling the relay

Launch the desktop with the relevant variables below, then enable **Act as Relay**.
Each file path is resolved to an absolute path and retained in local relay
settings. A later launch without the variable keeps the retained value. An
explicit replacement takes effect on enable/update; an explicit empty value
removes that setting from the next service definition. This changes participation
without deleting retained history or transferring its obligations.

| Desktop variable | Existing configuration/input |
| --- | --- |
| `RESONANCE_RELAY_HISTORY_VOLUNTEER_FILE` | [Enrolled volunteer](v0.4-history-volunteer-runtime.md) |
| `RESONANCE_RELAY_HISTORY_BRIDGE_FILE` | [Explicit bridge routes](v0.4-history-volunteer-bridge.md) |
| `RESONANCE_RELAY_ADMISSION_HISTORY_FILE` | [Prepared owner context and members](v0.4-protected-admission-operations.md) |
| `RESONANCE_RELAY_ADMISSION_HISTORY_DIRECTORY` | Optional separately prepared protected spend/writer directory; requires a retained policy/history binding |
| `RESONANCE_RELAY_ADMISSION_HISTORY_LINKS_FILE` | [Owner relay routing](v0.4-history-owner-runtime.md), version 1 direct or version 2 bridged |
| `RESONANCE_RELAY_ADMISSION_AUTHORITY_FILE` | Independently pinned policy authority public key |
| `RESONANCE_RELAY_ADMISSION_POLICY_FILE` | Current signed community policy |
| `RESONANCE_RELAY_ADMISSION_POLICY_KEY_FILE` | Existing local policy/spend encryption-key file |
| `RESONANCE_RELAY_IDENTITY_PASSPHRASE_FILE` | Existing infrastructure keystore passphrase file |
| `RESONANCE_RELAY_PUBLIC_ENDPOINTS` | Up to eight distinct comma-separated public relay endpoints |

All three policy files are required together. Protected history requires those
three files, and relay routing requires the history file. Invalid combinations,
control characters in paths and missing/nonregular input files fail before
replacing a registered service. The relay still performs full signature, context,
membership and retained-history validation when it starts. Changing file contents
at the same path requires an explicit service restart; it does not live-reload
membership or policy.

By default the owner is prepared in the desktop data directory's `relay-data`
subdirectory. An explicit `RESONANCE_RELAY_ADMISSION_HISTORY_DIRECTORY` selects
only the already prepared protected spend ledger and retained writer/archive.
The relay identity, publication/mailbox journals, policy store and witness/
coordinator records remain in `relay-data`. The generated service uses
`RELAY_ADMISSION_HISTORY_DIRECTORY`; an absent or explicitly empty value selects
the default location. The override requires the protected-history file and all
three policy files. Missing target state never falls back to the default ledger.

The installed policy store must already bind the exact history context before a
separate location can start. Protected default-location startup records that
binding durably after fresh readiness and before returning admission. The local
encrypted policy format then refuses context replacement or local-only fallback,
including when an old valid local ledger is still present. Signed policy updates
preserve the binding. Older policy-store readers reject the newer local format;
the signed community policy itself is unchanged. Removing the bound policy store
cannot initialize a replacement during normal desktop startup.

This directory option is an integration primitive, not the complete reviewed
desktop activation workflow. Preparing/binding a new policy store from restored
history still needs explicit review. It must not reconstruct missing witness or
coordinator votes. Set `RESONANCE_DATA_DIR` only when intentionally selecting an
entire separately prepared desktop data directory. Volunteer history stays in its
enrollment configuration's path. Do not move only the spend ledger or create a
replacement policy file to make a failed startup succeed.

The service remains bound to loopback. A bridge's advertised public WSS endpoints
therefore require a separately configured reachable TLS proxy to that local
listener. Advertising an endpoint does not create the proxy or prove reachability.
An outbound-only owner/volunteer can leave this list empty. Peer descriptors must
bind the endpoint actually contacted. Local tests may use loopback WS.

## Secret handling and restart

Service definitions contain paths, not raw history signing/storage keys or the
infrastructure passphrase. A WSS-advertised desktop service requires the passphrase
file. The Node entry point also supports `RELAY_IDENTITY_PASSPHRASE_FILE`; supplying
both a nonempty inline passphrase and a file is refused.

The file must be regular, at most 4096 bytes and valid UTF-8, containing one line
of at least 16 characters. A single final LF/CRLF is removed; meaningful spaces
are preserved. Read buffers are cleared, but JavaScript strings cannot be
guaranteed erased. Protect the file with local owner-only permissions and retain
it for restart. An encrypted keystore and a passphrase file readable by the same
compromised account do not protect against that account. This option does not
complete the OS key-storage audit.

The existing identity store migrates a plaintext relay identity atomically when
the passphrase is configured, preserving its DID. Losing the passphrase cannot
silently replace that identity. The desktop service explicitly disables policy
and witness initialization and clears absent role variables in its generated
environment.

## Status semantics

- **Relay Starting:** the service is configured but has not answered its local
  authenticated stats request.
- **Relay Preparing:** the process responds, but protected admission is not ready.
  User requests remain unavailable; infrastructure links can establish history
  readiness meanwhile.
- **Relay Active:** admission initialization completed. This is not a current
  quorum/replica count; each subsequent protected write still needs four fresh
  durable acknowledgements.
- **Relay Running:** the process responds but does not report a recognized
  readiness boolean. The panel explicitly says readiness is unknown.

The desktop refreshes local readiness and aggregate history stats every five
seconds while unlocked and relay mode is enabled. Its stats
request has a one-second whole-response deadline and a 100,000-byte limit;
malformed, interrupted, oversized or continuously trickling responses cannot
become successful status evidence.

Successful service installation is recorded before waiting for a response. If it
does not answer, the enabled setting and role paths remain available so the user
can inspect or stop it. A GUI restart does not silently forget that installation.
The authenticated status response omits the private role paths and keys.

## Validation and remaining work

Tests generate macOS LaunchAgent, Linux user-service and Windows scheduled-task
definitions with the retained file paths. Real Node owner/bridge processes use
the same generated environment: admission waits for four members, a missing first
member does not block the other four, bridge/owner restarts preserve accepted
tokens, and the bridge identity remains encrypted. Desktop session tests use real
loopback stats and saved settings, replacing only native OS install/uninstall.
They cover delayed readiness, reconnecting the GUI, explicit path replacement,
unresponsive installation, stop, malformed status and response deadlines.

The separate-location scenario retains an old valid local ledger while accepted
protected tokens and publication journals survive owner/bridge restart. Missing
target history, missing policy, unreviewed binding and removal of protection all
refuse startup without resetting accepted state. Policy-store tests retain the
context through signed archive updates and restart, and reject context replacement
and older local-format readers. Read-only service path validation distinguishes
the prepared directory from regular role files before any native action.
Compilation passes. Final protected/runtime checks passed **28 tests / two files
in 44.38 seconds**, and service/control checks passed **14 tests / three files
in 3.10 seconds**. These are focused local results.

This does not certify native service installation on all three operating systems.
[Aggregate history health](v0.4-history-health.md) is now available. Full desktop
enrollment/recovery review and combined history storage controls,
independent Internet/TLS/volunteer-overlap and energy validation remain required.
