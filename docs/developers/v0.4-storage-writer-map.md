# Storage writer map for the combined-budget work

This is a source audit with bounded control writers and optional shared snapshot
reservations. It is not an enabled production combined quota. Bounds below concern encoded regular-file bytes;
they do not measure filesystem allocation, physical free space or device energy.
Use [the inventory and registry guide](v0.4-combined-storage-budget.md) for the
implemented behavior and its validation.

## Shared snapshot writer

`packages/core/src/local-encrypted-state.ts` owns encrypted snapshot creation,
replacement, temporary cleanup and per-file process locks. It encodes and checks
`maxBytes` before opening a temporary file, writes every byte, flushes the file,
renames it and flushes the directory on POSIX. Old and replacement images coexist.
Capacity refusal preserves the old snapshot; an uncertain write poisons the open
handle. With an explicitly supplied managed authority it now reserves twice its
encoded cap plus 8 KiB of lock/recovery headroom before opening, captures immutable
path/cap values and retains a lease for later writes. Reopening authenticates state and refuses missing protected components.

A combined authority must cover **initial open as well as later `write()`**.
Opening a component can create its directory, lock, initial state, or a provably
pristine subordinate slot. An HTTP apply callback alone does not cover these
writes. Metadata/lock recovery and authenticated cleanup also need an explicit
allocation. Never release a history allocation merely because a file disappeared.

| Consumer | Encoded image maximum | Location / scope |
| --- | --- | --- |
| `core/admission-policy.ts` | 1 MiB | Runtime policy image, including retained policy archive |
| `relay/admission-spend-history.ts` | 8 MiB | Local-only spend image at `admission-spends-v2.jsonl` |
| `relay/protected-admission-history.ts` | 32 MiB | Protected image at the same filename; format fences distinguish it |
| `relay/admission-witness.ts` | 16 MiB votes; 32 MiB certificates | Independently retained witness/coordinator journals |
| `relay/history-checkpoint-quorum.ts` | 40 MiB | Owner writer journal |
| `relay/history-writer-archive.ts` | 2 MiB | Owner ciphertext manifest; ciphertext has a separate bound |
| `relay/history-checkpoint-store.ts` | 2 MiB per generation | Volunteer manifest, including agreement promises/staging |
| `relay/history-generation-provisioner.ts` | 64 KiB per successor slot | Child publication journal; slots are prepared on reopening too |
| `relay/history-ancestry-download.ts` | 2 MiB per download | Authenticated downloaded-block manifest |
| `relay/admission-history-recovery.ts` | 4 MiB | Recovery workflow coordinator |
| `relay/history-checkpoint-recovery.ts` | 96 MiB | Frozen-history recovery preparation |
| `relay/history-checkpoint-successor.ts` | 96 MiB | Successor selection and retained preparation |
| `relay/history-agreement-coordinator.ts` | 2 MiB | Agreement owner journal |
| `relay/history-provision-coordinator.ts` | 512 KiB | Owner provisioning journal |

Each maximum needs old-plus-new replacement headroom. These are **per image**:
multiple roles, recovery workspaces and retained generations multiply the relevant
allocations. Do not add only the currently selected generation. Do not confuse
the ciphertext archive limit with the much larger set of owner files.

## Other live relay writers

| Writer | Existing enforcement / durability | Combined-budget integration requirement |
| --- | --- | --- |
| `operation-log.ts` | Fsynced append and atomic compaction. `server.ts` assigns half of `maxJournalStorageBytes` to the file; the default total is 1 GiB. Existing commitment floors retain withdrawal/repair evidence. | Reserve append growth and simultaneous compaction output; preserve the journal's existing commitment floor. Publications, matches, mailbox envelopes/acks, receipts, placement and reconciliation share this authority. |
| `private-replay-log.ts` | A file cap of 2 MiB, with atomic compaction of unexpired evidence. | Up to old plus replacement; track interrupted temporaries and truncate/cleanup explicitly. Do not remove live replay protection to admit another write. |
| `blind-admission-verifier.ts` manual single-key ledger | At most `maxSpends` rows, each at most 512 bytes; durable append. | Charge existing legacy rows and new accepted rows. Migration cannot silently reclaim unproven spends. |
| `history-writer-archive.ts` ciphertext | At most 64 MiB ciphertext, bounded block count; exclusive temporary block, flush and rename before manifest update. | Charge ciphertext separately from both manifest copies, including an unindexed interrupted block or temporary until authenticated reopening resolves it. |
| `history-checkpoint-store.ts` ciphertext | Per-generation byte/block caps include two manifest allowances; ancestry also has a 256 MiB ceiling. | Preserve staged and retained blocks. Verify the ancestry composition rather than multiplying a generation cap or charging only the newest generation. Provisioning journals remain separate. |
| `history-ancestry-download.ts` ciphertext | A 256 MiB ceiling per download, including two manifest allowances. | Charge every live download/workspace and any separate restored copy. A completed download is not permission to drop the original history. |
| `history-generation-provisioner.ts` directory publication | Staged child directory is renamed to its published slot after durable journal steps. | Move the existing reservation with the exact slot; do not count a rename as freed storage or allocate a second independent writer. |
| `relay-identity-store.ts` | Temporary identity output, exclusive publication or replacement, file/directory flushing. | Cover initial identity creation and plaintext-to-encrypted migration, without permitting identity replacement to reclaim protected history. |
| `owner-resource-policy.ts` and `relay-resource-meter.ts` | Each current file and `.next` replacement is capped at 4 KiB by `resource-checkpoint.ts`; the two components require at most 16 KiB of encoded file headroom. Bounded reads, exact schemas, ordinary single-link files, full writes and flush/rename preserve committed counters. Failed writes poison the open writer; new work remains refused until reopening. | Reserve the 16 KiB peak in the shared authority. The runtime claim still supplies writer exclusion; this is not an independent global lease, anti-rollback proof or byte reservation. |
| `relay-maintenance.ts` and local-state locks | Persistent maintenance marker and process-ownership files. | Reserve bounded control metadata independently of new-work capacity, so a full budget cannot prevent pausing or safe recovery. |

The private replay cap, journal cap and history caps are separate today. Adding
these numbers to the stats endpoint would not enforce their combined peak.

## Desktop, operator and supervisor outputs

- `admission-operator-files.ts` writes bounded, exclusive outputs with file and
  directory flushing. Configuration, enrollment exports and reviewed limit files
  can be outside the history roots. Desktop-approved outputs now retain their
  individual paths before writing and participate in aggregate inventory; the
  CLI supports repeated `--file` selections without scanning parent folders. A
  total managed-output budget must reserve these exact files before creation.
  CLI-created files and input keys are not automatically added by desktop bookkeeping.
- `session.ts` atomically replaces bounded desktop settings. The durable
  `history-storage-registry.ts` retains approved history locations independently
  of that settings replacement. The inventory now includes its own manifest and bounded interrupted temporary
  files. The one MiB manifest, up to 128 retained one MiB temporary files and sibling
  lock still need a shared control allocation; observed usage is not a reservation.
- `relay-supervisor.ts` writes service definitions and, on Windows, a PowerShell
  launcher. Native service installation is still mocked in integration tests.
- The discovered unbounded macOS `relay-service.log` path is addressed for new
  service definitions by [bounded structured diagnostics](v0.4-relay-diagnostics.md):
  two 1 MiB files, with native stdout/stderr capture disabled. Startup and runtime
  errors remain available through the structured sink, and authenticated stats
  report failures/drops. Existing installed definitions and legacy log files are
  unchanged until explicitly updated. Diagnostic control metadata and the separate
  directory still require accounting in a future total managed-output budget.


## Export APIs and out-of-scope application data

`publication-store.ts`, `mailbox-store.ts`, `matching-engine.ts`, `hamming-index.ts`
and `hnsw.ts` expose persistence/export methods. HNSW includes a native
`writeIndexSync` call, so searching JavaScript file-write imports alone misses it.
The current `server.ts` rebuilds live relay state from the operation journal and
does not call these export methods. Any future production caller must add its
native/output allocation before using them under a combined quota.

The app database, one-use wallet, models, previews and unrelated user files are
not included in the current history/runtime inventory. A future UI must name the
scope of its budget. A relay-data quota must not be advertised as a whole-app or
whole-device quota.

## Next implementation boundary

1. Wire the implemented durable authority into shared CLI, managed-runtime and
   maintenance selection. Register/adopt existing files conservatively before
   enabling a total managed-data control.
2. Extend the implemented lifetime-peak model beyond shared encrypted snapshots.
   Ciphertext and metadata writers above must consult the same authority before
   accepting work. A path registry or optional snapshot hook alone is insufficient.
3. Preserve old-plus-new peaks, pending work, permanent denials, ancestry and
   repair/control headroom. Reserve new recovery workspaces before creating them.
4. Cover reopen/initialization, direct block writes, append, rename, cleanup and
   native export paths. Unknown or missing obligations cannot become free bytes.
5. Only expose a reviewed total limit when the production call paths are covered.
   Test concurrent roles, full capacity, stale paths, partial writes, flush errors
   and process death with real retained state. This audit is an input to that work,
   not a reason to mark combined storage enforcement complete.
