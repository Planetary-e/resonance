# Desktop maintenance before history recovery

The dashboard can persist a maintenance pause, stop the managed relay and check
that it has stopped. The pause survives closing the GUI or killing a process.
Leaving maintenance permits a later start; it does not restart the service,
complete recovery, clear history or discard pending work.

This is a prerequisite for guided desktop recovery. The recovery/enrollment forms,
reviewed activation of a restored owner and combined storage controls remain open.

## Exclusion and retained state

`main.ts` claims `relay-runtime.lock` in its data directory before opening relay
state. It holds the claim through startup and shutdown until process exit. A
second process using that directory cannot start. The existing local encrypted
state lock provides exclusive creation, PID ownership and guarded stale-owner
recovery. Only a confirmed dead PID permits reclaim; interrupted recovery and
uncertain ownership fail closed. This is single-host coordination, not a lease
across computers or permission to reuse an identity elsewhere.

Desktop start, stop and maintenance operations hold a separate
`relay-desktop-control.lock` across their complete asynchronous operation. Multiple
GUI instances cannot race service installation, removal or history mutation.
Competing operations receive an error rather than entering a background queue.

Starting maintenance writes and flushes `relay-data/relay-maintenance.json`
**before** asking the supervisor to stop. Any marker, including a corrupt or
dangling entry, blocks runtime startup. A corrupt marker is retained for inspection.
If stopping fails, the pause stays active. An automatic supervisor restart cannot
reopen history while maintenance is active.

Before a history operation, the desktop must acquire the runtime claim and observe
connection refusal on the configured loopback port. Missing authenticated stats
are insufficient: an unresponsive process can still own files, and older processes
may not hold the runtime claim. A busy port or an uncertain connection result
blocks the operation. Waiting for stop is bounded to ten seconds and can be
cancelled. Every operation reacquires and retains both claims until completion;
a past UI check does not authorize later writes.

Saved service settings are bounded, validated and atomically replaced. Missing
settings alongside existing relay data, malformed or dangling settings cannot
silently select the default port, stop a different
configuration or overwrite the evidence. The local probe cannot detect unrelated
unmanaged processes using a different directory/port, remote copies of the same
identity or a bridge that has not yet observed disconnection. Existing per-history
file locks and infrastructure identity pins remain required.

## Desktop API and UI

The authenticated local `/api/relay/maintenance` endpoint supports GET (read the
saved pause), POST (persist pause, request stop and verify) and DELETE (verify stop
and remove the pause). All require an unlocked session and its bearer token. The
status reports only `active` and `createdAt`; it opens no history or network session.
Conflicting operations or invalid local state return an error without clearing
the pause.

The dashboard distinguishes a saved pause from the last successful stop check and
explains what leaving maintenance does. The existing start action refuses while
the marker exists. Failed or cancelled history operations release their process
claims while preserving the marker and pending durable work.

## Shared command implementation

`packages/relay/src/admission-history-command.ts` contains the reviewed operator
implementation. The CLI is a thin adapter for arguments, JSON output and process
signals. A desktop caller can invoke the same implementation without spawning an
unbundled source script or modifying environment variables. Each call owns its
key copies, handles and transport session. It returns one result, plus an explicit
stop function only for the long-lived standalone volunteer listener.

Explicit approval digests, fresh quorum requirements and retained-state rules are
unchanged. An abort signal closes direct checkpoint/agreement/data/provision
exchanges as well as pinned relay-link transports. Cancellation does not undo work
that may already have reached a volunteer. The desktop operation wrapper holds
exclusion across the whole call; the standalone CLI still requires the operator
to coordinate service shutdown.

## Validation

Focused tests exercise real relay child processes, forced death and stale claim
recovery; persistent/corrupt markers; competing operations; closed-port/live-owner
and busy-port cases; cancellation; damaged settings; locked/unauthenticated API
refusal; UI wording; concurrent shared commands and direct transport cancellation.
Existing multi-generation CLI and bridged recovery tests remain regression gates.
Native launchd/systemd/Windows service installation is mocked in desktop tests;
these tests do not certify all three operating systems or independent volunteers.

Package compilation and strict standalone script typechecking passed. The shared
command/recovery/maintenance regression passed **39 tests across nine files** in
**82.71 seconds**. After adding missing-settings refusal, the final maintenance,
service configuration, protected-owner startup, TLS and UI group passed **28 tests
across nine files** in **20.32 seconds**. The groups overlap; neither is the complete
repository suite. Complete CI on this checkpoint must be reported separately.
