# v0.4 connection-path audit

This audit covers production socket constructors in `packages/core`, `packages/node`, `packages/relay`, and `packages/app`. It is a code-path inventory, not proof that a volunteer's router, DNS, TLS proxy, or certificate renewal works on the public Internet.

| Path | Caller / listener | Current protection | Remaining verification |
| --- | --- | --- | --- |
| Personal client operation | `node/relay-client.ts`, `node/private-relay-client.ts` | Rejects public `ws://`; WSS uses Node WebSocket TLS certificate verification; private mode requires a separate entry and destination, and uses one short socket per operation | Real external CA certificate and household-to-household test; destination/key discovery still relies on local DNS resolution |
| Personal and relay discovery | `node/relay-discovery-client.ts`, `relay/relay-discovery-client.ts` | Rejects public `ws://`, caps frame size and handshake time; verifies responder and signed descriptors | Online contact reachability and resolver behavior; signed descriptors do not prove operator independence |
| Long-lived volunteer relay link | `relay/relay-link-client.ts` | Rejects public `ws://`; receiver issues a per-socket challenge before signed opening; signed accept is checked | Test a real WSS reverse link through NAT and reconnect churn |
| Admission witness vote | `relay/admission-witness-transport.ts` → `relay/server.ts` | Secure endpoint check, normal WSS validation, no redirects/compression, 3-second handshake and 4 KiB replies; quorum caller owns the overall cancellation deadline; witness/coordinator authenticate and persist votes | Independently verify public TLS and owner resource accounting |
| Experimental checkpoint append/read/freeze/repair/seal | `relay/history-checkpoint-exchange.ts` | Owner/member signatures bind fresh requests and pinned histories; normal WSS validation, no redirects/compression, bounded frames and 30-second transport ceiling; dedicated listener is loopback only with raw-connection/header/lifetime bounds | Public TLS proxy deployment, total transfer accounting and owner power/schedule integration; these APIs do not yet protect live admission |
| Experimental history agreement, data transfer and child provisioning | `relay/history-agreement-exchange.ts` | One pinned origin with separate bounded routes; owner/member authentication, normal WSS validation, no redirects/compression; shared loopback-only raw-connection limit and per-connection deadline | Public TLS proxy deployment and resource accounting; retained downloads and live repair may create multiple sequential connections within one bounded attempt |
| Entry to destination private forward | `relay/server.ts` | Asserts secure endpoint, fetches signed destination key, checks observed IP/domain, sends signed forward, caps frame and timeout | A TLS terminator must bind only to a loopback backend; DNS rebinding, redirects, and cross-network behavior need adversarial Internet tests |
| Relay inbound HTTP and WebSocket | `relay/server.ts` | Direct HTTPS/WSS using configured cert/key; checks certificate date and advertised names at start; cleartext listener rejects public-source IPs; proxy mode requires loopback backend | Public certificate issuance/renewal and firewall behavior; local renewal/restart and proxy rotation are tested below |
| Local desktop UI API/events | `app/server/server.ts`, `app/api.client.ts` | Loopback-only; exact host/origin checks, per-response CORS, session-bound bounded event sockets and strict bounded JSON | Covered by `v0.4-desktop-http-security.md`; native renderer/packaging remains separate from this local HTTP boundary |

The relay's infrastructure identity key can be encrypted with the configured passphrase; the TLS private-key PEM is a separate operator-managed file. This audit does not establish that every relay advertised in discovery is reachable or independent. Two-hop privacy still assumes non-colluding operators, and global network observers can correlate timing and volume.

## Follow-up from the 2026-10-16 constructor inventory

The history endpoints above were added after the original six-path inventory.
They must remain part of the TLS, authenticated-input and resource audits even
while opt-in. The shared agreement listener now also routes checkpoint traffic;
its checkpoint route has the larger encrypted-block bound, not the ordinary
operation frame limit.

Static inspection found that witness transport, the relay-link client and both
discovery clients invoked `onTransportSocket` directly from the WebSocket
`upgrade` event without a local catch. A throwing accounting callback could escape
the event emitter instead of failing the request. These four paths now fail the
request/handshake, close its socket and fence the subsequent `open` handler.
Completed discovery/witness/checkpoint exchanges also ignore late frames and
accounting callbacks. Discovery, relay-link and witness clients explicitly disable
compression and redirects. Accepted long-lived links still process their frames.

Eight new real-socket cases cover accounting exceptions in both discovery clients,
relay links, witnesses, checkpoint and agreement transports, plus cancellation
inside the node-discovery and witness callbacks. They observe socket closure,
zero application messages and no compression negotiation. TypeScript and the
focused discovery/link/witness regression group passed **25 tests in five files**
in **28.82 seconds**. This closes the callback-failure finding, not the whole TLS,
resource or authenticated-input audit.

## Forwarding and socket options follow-up, 2026-10-17

Private forwarding now contains a throwing socket-accounting callback and fences
later `open`/`message` events. It sends no encrypted operation after accounting
refusal or cancellation. The inbound listener destroys sockets whose accounting
registration fails. Direct client operations, indirect private discovery,
encrypted client operations and entry forwarding explicitly disable WebSocket
compression and redirects. The relay listener explicitly disables compression.

Real-socket validation: forwarding/accounting passes 12 tests in two files;
actual direct and complete two-hop handshakes plus a 302 trap pass two further
tests. The trap's target receives zero connections. Private deadline/mailbox
regressions pass two tests. TypeScript passes. A new fixture initially used an
invalid zero batch window and omitted destination enrollment; correcting the
fixture preserves the production scheduler and discovery checks.

The continuing audit also found missing pre-authentication connection bounds.
The implementation below addresses those. The subsequent desktop origin, static
file, session-event and strict JSON-body audit is recorded in
`v0.4-desktop-http-security.md`. Application schemas, complete signature/deadline
coverage and public TLS paths remain open.

## Main listener admission and shutdown bounds

The main relay now caps all accepted TCP sockets at 256 by default, including
HTTP/TLS openings and authenticated links. `maxInboundConnections` accepts 1–4096;
it is an overall ceiling, separate from the authenticated-link ceiling. HTTP
headers are limited to 8 KiB. HTTP header/body and TLS-handshake deadlines default
to ten seconds; `inboundHandshakeTimeoutMs` accepts 250–10,000 ms for embedding
configuration and tests. HTTP idle sockets also time out. A drip of partial
headers cannot extend the header deadline. WebSocket upgrades clear the HTTP
idle timer; a separate first-frame deadline terminates non-cooperating peers,
and authenticated links retain their existing heartbeat rules.

Binary frames are refused before parsing any application request. Shutdown
stops new client work, performs the existing optional handoff, terminates remaining
WebSockets/raw sockets, and waits for already-started admission/persistence
handlers before returning. It does not cancel or erase a committed token spend.
Repeated/concurrent stop calls share the same result instead of writing a second
resource checkpoint after a replacement owner has taken over. Restart clears
that completed stop only after it has succeeded.

Sixteen initial listener/TLS/deferred-admission tests pass. A broader seven-file
run passes 48 tests and exposes one new reopen-test failure: repeated stop wrote
the old resource snapshot after the new instance had checkpointed. The idempotent
stop fix passes the final ten listener/restart tests, including durable replay of
a publication whose admission finished during shutdown. The broader passing
files cover reverse links, link cancellation, private forwarding, protected
admission and the v0.3 delivery scenario. TypeScript passes.

These bounds prevent unbounded sockets and opening waits; they do not promise
availability against a sustained connection flood. Durability work already in
progress is awaited, rather than abandoned under a fabricated shutdown deadline.
Public firewall/NAT/TLS-proxy and independent-network tests remain separate gates.

## Personal-client reply and cancellation audit

All six direct v2 request forms now use one bounded exchange implementation.
It validates the signature before reading an application payload, refuses binary
frames, catches serialization/capability/send errors, terminates the one-use
socket after completion and cancels connecting as well as open sockets on
disconnect. A monotonic ten-second budget covers all fallback attempts for an
operation; a late response cannot revive it. Each client accepts at most 16
configured endpoints and 64 concurrent direct exchanges. Parallel mailbox reads
retain valid replies when another copy times out, while explicit disconnect
cancels the complete pending result.

Direct and private paths share exact acknowledgement and mailbox schemas.
Acknowledgements have a bounded reference, a known status and an optional bounded
string message. Mailbox responses carry only the requested mailbox/request IDs
and at most the existing server limit of 100 structurally valid, individually
mailbox-bound, nonduplicate encrypted envelopes. The private path additionally
checks binary frames at indirect discovery and encrypted response boundaries,
and terminates completed/failed one-use sockets without waiting for a peer close.
Its existing authenticated destination binding and operation deadline remain.

The obsolete direct root-DID session implementation is removed. Its compatibility
methods reject locally, as the relay has already disabled legacy authentication;
they never send an account identifier or start an automatic reconnect loop.
The direct development transport still relies on WSS endpoint authentication on
the Internet; a self-consistent signed reply alone is not proof of an independently
pinned operator. Private routing retains its explicit signed destination pins.

Validation: 42 tests in seven integration files pass, including node publication,
search/mailbox, real four-of-five witness admission/restart and private transport.
Two additional real private-route cases send valid signed/encrypted responses as
binary frames and observe refusal. The final 21-case direct boundary group passes,
including malformed signed payloads, oversized frames, an incomplete HTTP upgrade,
64 competing requests, cancellation, and the actual ten-second shared deadline.
TypeScript passes. The stalled HTTP fixture explicitly consumes TCP EOF; it does
not require an uncooperative remote half-open socket to close itself.

CI `39070025594` (`da1ffe6`) passed 2,121 tests but failed its witness integration
test with `EADDRINUSE`. That fixture no longer selects a random fixed port range.
Kernel-assigned TCP frontends remain bound across kernel-assigned relay backend
restarts, preserving the original signed endpoints. Offline backends refuse
connections. The focused integration above verifies partition, restart and
cross-destination double-spend refusal through these transparent local frontends.

## Local TLS matrix, renewal and IPv6 validation

Eleven production transport paths now pass 110 real TLS boundary cases: direct
personal requests, both discovery clients, relay-link opening, witness votes,
checkpoint exchange, agreement, agreement data, provisioning, compaction and
frontier requests. Each runs over IPv4 and IPv6 with a valid certificate, an
untrusted issuer, a wrong host, an expired certificate and a future certificate.
Valid TLS reaches one application frame; every negative case reaches neither
WebSocket upgrade nor application data. These probes intentionally close after
that first frame: they test TLS enforcement, not complete protocol exchanges.

A separate complete two-hop WSS scenario publishes and searches, creates and
decrypts a match notice, restarts the destination with a new certificate/key,
reads the exact retained notice, acknowledges it and confirms the mailbox is
empty. The infrastructure identity and publication survive. Another actual TLS
proxy forwards to a loopback-only backend and rotates credentials between
signed destination discovery and forwarding: valid renewal succeeds; a changed
wrong-host certificate prevents the operation reaching the backend.

This exposed a Node 24.19 IPv6 availability regression: IDNA conversion turns an
IPv6 literal into an empty name before the built-in hostname check. The upstream
report is [nodejs/node#64144](https://github.com/nodejs/node/issues/64144). All ten
production outbound WebSocket constructors now share a narrow checker: only IPv6
literals use OpenSSL-backed `X509Certificate.checkIP` against the authenticated
DER certificate's exact IP SAN. DNS/IDNA and IPv4 retain Node's normal check.
Native TLS still validates trust, dates and signatures before this callback; no
verification or trust-store bypass is used. See Node's
[IP matching contract](https://nodejs.org/docs/latest-v24.x/api/crypto.html#x509checkipip)
and [TLS callback contract](https://nodejs.org/api/tls.html#tlscheckserveridentityhostname-cert).
The installed runtime is unchanged.

Ten direct checker cases reject wrong/mapped addresses, misleading DNS names,
forged legacy SAN strings and missing/malformed DER. The 14-test checker/matrix/
complete-route/proxy group passes in 3.06 seconds; the prior 61-case transport
regression group and TypeScript also pass. CI now runs the TLS group on Linux,
macOS and Windows without native installer builds. Its cross-platform result is
pending. Test certificates and their public test keys are isolated fixtures;
only child processes receive the test CA through `NODE_EXTRA_CA_CERTS`.

This completes the local certificate-boundary matrix and local renewal/proxy
scenarios. It does not certify public CA issuance, real DNS/router/firewall
configuration, independent relay operators or Internet reachability. Those remain
explicit pilot gates. The broader signature/schema/deadline and key-store audit
also remains open.
