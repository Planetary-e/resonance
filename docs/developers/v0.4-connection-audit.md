# v0.4 connection-path audit

This audit covers production socket constructors in `packages/core`, `packages/node`, `packages/relay`, and `packages/app`. It is a code-path inventory, not proof that a volunteer's router, DNS, TLS proxy, or certificate renewal works on the public Internet.

| Path | Caller / listener | Current protection | Remaining verification |
| --- | --- | --- | --- |
| Personal client operation | `node/relay-client.ts`, `node/private-relay-client.ts` | Rejects public `ws://`; WSS uses Node WebSocket TLS certificate verification; private mode requires a separate entry and destination, and uses one short socket per operation | Real external CA certificate and household-to-household test; destination/key discovery still relies on local DNS resolution |
| Personal and relay discovery | `node/relay-discovery-client.ts`, `relay/relay-discovery-client.ts` | Rejects public `ws://`, caps frame size and handshake time; verifies responder and signed descriptors | Online contact reachability and resolver behavior; signed descriptors do not prove operator independence |
| Long-lived volunteer relay link | `relay/relay-link-client.ts` | Rejects public `ws://`; receiver issues a per-socket challenge before signed opening; signed accept is checked | Test a real WSS reverse link through NAT and reconnect churn |
| Admission witness vote | `relay/admission-witness-transport.ts` → `relay/server.ts` | Secure endpoint check, normal WSS validation, no redirects, 3-second handshake and 4 KiB replies; quorum caller owns the overall cancellation deadline; witness/coordinator authenticate and persist votes | Test callback failures and late transport events; independently verify public TLS and owner resource accounting |
| Experimental checkpoint append/read/freeze/repair/seal | `relay/history-checkpoint-exchange.ts` | Owner/member signatures bind fresh requests and pinned histories; normal WSS validation, no redirects/compression, bounded frames and 30-second transport ceiling; dedicated listener is loopback only with raw-connection/header/lifetime bounds | Public TLS proxy deployment, total transfer accounting and owner power/schedule integration; these APIs do not yet protect live admission |
| Experimental history agreement, data transfer and child provisioning | `relay/history-agreement-exchange.ts` | One pinned origin with separate bounded routes; owner/member authentication, normal WSS validation, no redirects/compression; shared loopback-only raw-connection limit and per-connection deadline | Public TLS proxy deployment and resource accounting; retained downloads and live repair may create multiple sequential connections within one bounded attempt |
| Entry to destination private forward | `relay/server.ts` | Asserts secure endpoint, fetches signed destination key, checks observed IP/domain, sends signed forward, caps frame and timeout | A TLS terminator must bind only to a loopback backend; DNS rebinding, redirects, and cross-network behavior need adversarial Internet tests |
| Relay inbound HTTP and WebSocket | `relay/server.ts` | Direct HTTPS/WSS using configured cert/key; checks certificate date and advertised names at start; cleartext listener rejects public-source IPs; proxy mode requires loopback backend | Public certificate issuance/renewal, firewall behavior, and cert-rotation tests |
| Local desktop UI API/events | `app/server/server.ts`, `app/api.client.ts` | Binds HTTP/WebSocket only to `127.0.0.1`; authenticated session token for events | Local origin/CSRF and token handling require separate application-security audit; this is not an Internet relay path |

The relay's infrastructure identity key can be encrypted with the configured passphrase; the TLS private-key PEM is a separate operator-managed file. This audit does not establish that every relay advertised in discovery is reachable or independent. Two-hop privacy still assumes non-colluding operators, and global network observers can correlate timing and volume.

## Follow-up from the 2026-10-16 constructor inventory

The history endpoints above were added after the original six-path inventory.
They must remain part of the TLS, authenticated-input and resource audits even
while opt-in. The shared agreement listener now also routes checkpoint traffic;
its checkpoint route has the larger encrypted-block bound, not the ordinary
operation frame limit.

Static inspection also found that witness transport, the relay-link client and both discovery clients
invoke `onTransportSocket` directly from the WebSocket `upgrade` event without a
local catch. A throwing accounting callback could escape the event emitter
instead of failing the request. Checkpoint/agreement transports already contain
that callback failure. Add negative tests and contain these remaining callbacks;
verify late events cannot send after close/cancellation. This is an identified
implementation follow-up, not a completed boundary audit.
