# Protected history compaction

## Scope and safety decision

The first implementation step publishes a complete, unchanged encrypted image of
one protected local-spend role on four pinned volunteers. It does **not** delete
ciphertext, shorten ancestry, reset sequence numbers, reduce storage reservations
or authorize recovery from that image alone. Witness votes/coordinator state and
policy membership/freshness retain their separate requirements.

A usable compacted history needs both recoverable application state and retained
protocol evidence. PBFT separates stable checkpoint certificates, retained state
and transfer to lagging replicas before discarding protocol messages
([Castro and Liskov, section 4.4 and 6.2](https://cseweb.ucsd.edu/classes/wi09/cse223a/castro.pdf)).
We use that separation as a design constraint, not PBFT's fault model or a proof
of this protocol. Resonance's existing assumption remains a correct owner and at
most one faulty member among five independently pinned volunteers, with four-copy
writes. Volunteers authenticate ciphertext and cannot evaluate its plaintext.

A signed snapshot also does not prove freshness. Recovery must retain generation
barriers, later accepted records and permanent denials. etcd documents how restoring
an old snapshot can roll revisions back and requires explicit handling for cached
clients ([recovery guide](https://etcd.io/docs/v3.5/op-guide/recovery/)). A revision
bump does not reconstruct missing spend evidence and is not a recovery mechanism
for Resonance.

## Implemented full-state publication

`admission-state-checkpoint` is accepted only in an encrypted checkpoint envelope,
within the existing 8 MiB payload bound. Semantic replay independently verifies
the signed policy and complete spend-state schema. It requires exactly the same
policy digest, spent identifiers, actions, request bindings, issuer attribution,
unproven legacy rows and permanent issuer-denial set as the preceding image.
An otherwise valid newer policy still requires the separate policy operation.
The record's owner-asserted time must lie inside that policy's validity period;
it does not establish network freshness.

`planCheckpoint()` reads current complete state offline, exposes aggregate counts
and binds approval to the participant, context, generation root, applied head and
application image. It refuses unfinished history. It neither generates new
ciphertext nor contacts volunteers. `checkpoint(digest)` runs under the existing
exclusive protected operation guard, requires readiness and rechecks approval.
It creates one successor envelope, checks local archive headroom before writing
intent, persists exact ciphertext before transmission and applies the image only
after the existing four-member durable-write certificate is retained. It keeps
all predecessor blocks and all existing reservations.

Lost replies or process death preserve the exact pending ciphertext. Explicit
`owner-ready` resumes it, using the existing writer/repair protocol. A stale review
cannot publish another snapshot after completion. A failed capacity preflight
leaves no checkpoint intent and does not block already accepted work.

### Operator commands

With the relay stopped, use the same independently retained configuration and
current policy as the protected owner:

```sh
node --import tsx scripts/admission-history.ts owner-checkpoint-plan \
  owner-config.json policy.json owner-storage.hex owner-directory
node --import tsx scripts/admission-history.ts owner-checkpoint --approve <digest> \
  owner-config.json policy.json owner-storage.hex owner-directory
```

The plan is offline. Apply obtains fresh quorum readiness, then checks its digest
again. Both commands refuse an implicit policy update. Selected relay storage and
pinned outbound operator transport use the existing CLI environment selection.
Results explicitly report zero files removed and zero bytes reclaimed. No periodic
snapshot traffic or automatic pruning is enabled.

## Certified ancestry and reconstruction

### Implemented ancestry endorsements

The owner can sign a short-lived proposal naming the independently enrolled
genesis, pinned context/membership, current generation root and exact non-genesis
checkpoint. A volunteer endorses it only when its current unfrozen generation
retains that checkpoint and its complete activated ancestry. Later accepted
records remain untouched. Four distinct member signatures form a bounded
historical certificate; neither expiration nor an old certificate can reopen a
frozen generation. Volunteers attest to authenticated ciphertext and retained
ancestry, not plaintext semantics.

Collection verifies each response against its expected member and original
proposal, returns after four valid votes and cancels remaining work. It refuses
foreign genesis/context, swapped or duplicate members, forged/cross-proposal
signatures, wrong checkpoints, cancellation and late replies. Request size is
8 KiB, reply size 1 KiB; existing connection, operation, buffer and full-exchange
deadlines apply. Direct loopback/TLS transport, pinned outbound relay links and
explicit single-hop bridges carry the same signed request. The operator adapter
stays lazy and has no fallback when configured routing fails.

Endorsement and collection create no files, mutate no manifests and remove no
blocks. Separately reviewed local retention below persists the proof. Neither
operation is a pruning command or a source of current writer authority.

### Implemented compacted semantic replay

The explicit `compaction` option to semantic replay/restore review accepts the
original independently pinned genesis, the certified complete state checkpoint,
then every later selected record and continuation. Without that option, replay
still requires the complete original chain. The certificate is bounded and copied
before asynchronous verification. The checkpoint must contain the full state
record, a valid policy from the pinned authority, a policy successor to genesis
and valid spend/denial state. The suffix uses the existing semantic reducer.

At the next frozen boundary, every frozen head at or above the checkpoint must
match its exact retained suffix position; the selected highest head cannot be
omitted. An older head below the checkpoint relies on the four-member ancestry
certificate. With the existing correct-owner and at-most-one-fault assumptions,
four endorsements and four freeze responses intersect in at least two honest
members. The verifier also checks all retained ciphertext links. It does not
re-evaluate omitted plaintext mutations: preserving their complete state is the
correct owner's obligation, enforced by the protected checkpoint publisher.

After that boundary, subsequent generations again require complete local chains
and their normal agreement proofs. Reconstruction is historical evidence only;
review still binds the exact destination and recovered image, and a restored owner
still requires four fresh current write receipts before serving. This API does not
add a compacted network downloader, change default CLI recovery, delete blocks or
release storage reservations.

### Implemented durable anchor retention

A separately reviewed local operation can retain the certificate in the encrypted
authoritative manifest. Review binds the current store, or every generation and
provisioning promise when using the volunteer service. The original genesis pin
propagates through retained activated parents; it is never taken from the incoming
certificate. Reopen verifies signatures, metadata and the actual checkpoint
ciphertext before exposing the store or cleaning unreferenced files.

Anchor sequence numbers only increase. Exact-checkpoint retries return the first
retained proof without another write, even after a later freeze; a frozen or
committed generation cannot advance its anchor. A successful update retains every
ciphertext block and later accepted record, all agreement/activation evidence and
all storage reservations. The existing manifest reserve funds the small proof
and replacement peak. This local operation is not exposed as an unauthenticated
network write.

An optional independent compaction progress pin detects restoration of an older
manifest that loses the proof. Without independently retained progress, a coherent
rollback of all local files remains undetectable. That limitation is unchanged.

TypeScript and **75 tests / five files in 36.25 seconds** pass for this layer:
monotonicity, stale review, corruption, missing checkpoint data, old-manifest
rollback, before/after-rename and flush uncertainty, five real SIGKILL boundaries,
later writes, freezes and service reopen across activated generations. Failure
leaves either the old or new authoritative proof and requires reopen after
uncertain I/O. No prefix blocks are removed.

### Implemented authenticated certificate control

Certificate retention and read now have separate owner-signed requests, bound to
the original genesis, generation root, pinned target member, challenge and a
maximum 30-second validity window. Retention additionally authorizes the exact
submitted certificate identity. A volunteer signs its current local head and
retained proof only after durable storage and another expiration check. Expiration
during persistence suppresses the reply without rolling back the committed proof;
a fresh authorized read recovers it.

If the exact checkpoint already has a different valid four-vote certificate, an
idempotent retention request returns the first proof. The signed response must bind
the requested checkpoint and current retained head; it cannot substitute another
checkpoint, generation, member or request. Reads may report authenticated absence.
All proof validation still uses independently pinned genesis and membership.

Control frames/replies are bounded to 16 KiB. The existing endorsement request
remains bounded to 8 KiB and its client reply to 1 KiB. The same authorization runs
over loopback/TLS endpoints, pinned outbound links and explicit single-hop bridges.
The verified client rechecks signature, request expiration, cancellation and the
whole-operation deadline, even for an injected transport that ignores aborts.
The operator adapter remains lazy and does not silently change routing.

TypeScript and **90 tests / seven files in 65.87 seconds** pass, including signed
field tampering, wrong-target responses, absence, alternative valid proofs for one
checkpoint, canceled/silent transports, expiration during durable writes, actual
direct/outbound/bridged retention and read, and subsequent generation reopen.
One response is historical local evidence, not a four-copy compaction commit or
admission readiness. No remote request in this protocol removes ciphertext.

### Implemented resumable compacted download

An explicit downloader option accepts the independently retained original genesis
and exact certificate. It authenticates the selected head and every later link
while descending through continuation barriers, stops at the certified checkpoint,
then retains the original genesis locally. Frozen heads at or above that checkpoint
must match; earlier evidence relies on its four-member ancestry proof. The output
is the original genesis, certified checkpoint and complete selected suffix, ready
for the explicit compacted semantic review API.

The proof is retained in the encrypted download manifest. Reopen requires the same
external pins and performs no network operation; missing proof never silently
enables or disables prefix skipping. Capacity includes the copied genesis, all
suffix bytes and existing manifest/replacement reserves. A failed or interrupted
step retains every already accepted block. One authentic source can supply
historical ciphertext; this is separate from the fresh four-copy readiness gate.

TypeScript and **31 tests / three files in 44.81 seconds** pass for the downloader
layer, including the existing download regressions and ten additional SIGKILL

### Implemented compacted freeze preparation

An explicit original-genesis pin and certificate allow preparation to freeze the
current generation and read from its certified checkpoint through each reported
head. The selected history preserves later accepted and partially replicated
records. Heads below the checkpoint rely on the ancestry certificate; each head
at or above it must have a complete authenticated suffix. Four fresh same-attempt
freeze replies are still required. Historical endorsements cannot replace them.

The exact proof is copied before work and retained with the encrypted intent and
preparation. Reopen is offline and refuses missing or changed pins. A later
attempt cannot regress an already retained selection. Core preparation parsing
and successor creation require the independently supplied genesis for compacted
input, and selection uses the actual head sequence rather than the suffix length.
The successor wire format and agreement rules remain unchanged. Legacy
full-prefix successor reservation refuses compacted preparations.

TypeScript and **37 tests / four files in 25.15 seconds** pass, including full
recovery/successor regressions, unavailable omitted prefixes, one later partial
tail, a lagging frozen replica, current-quorum loss, retained-tail regression,
changed external pins and tampered suffixes. This does not yet enable prefix
deletion. Compacted lagging-replica installation is described below.

### Implemented lagging-replica installation

A staged checkpoint can carry a separately bounded four-member certificate. The
fresh owner signature binds the exact proof, selected agreement, target and
ciphertext. Parsing requires the independently enrolled genesis. A replica first
stages the selected tail backwards; the certified checkpoint can then bridge an
unavailable interval below it. The atomic manifest update retains the proof,
complete suffix, existing accepted local blocks and current agreement/barrier.
No prepared vote is available until that installation is durable. A newer view,
activation, newer accepted head or conflicting known frozen head prevents it.

The bounded sequence index uses null only for that unavailable interval. Such an
interval requires the certificate, frozen generation and provisional agreement;
reopen authenticates the original root, retained earlier blocks, checkpoint and
suffix. Existing local blocks are not discarded. Lost replies are idempotent and
orphan cleanup still removes only unreferenced, unaccepted staging files. Fixed
sequence/ancestry limits remain; this is not indefinite storage compaction.

The agreement owner binds the exact external proof in its encrypted journal. It
can use a completed local download or authenticate a suffix from remote sources.
It sends the proof only with the checkpoint and never requests an omitted block.
Original full-history transfer remains available without explicit proof.

Transfer validation passes **38 tests / four files in 33.84 seconds**. Store,

### Implemented composed recovery and CLI

Freeze review now binds the exact optional certificate and checks that its root
belongs to the observed activated ancestry. Every reopened phase requires the
same proof. Current-generation anchors flow into freeze, agreement and download;
ancestor anchors shorten the download while current-generation selection retains
its normal full-chain checks. Provisioning, semantic restore review and retained
readiness inspection use the same authenticated result. Reopen/status/review do
not send requests. Current readiness still requires four fresh durable receipts.

All `owner-recovery-*` commands accept `--checkpoint-proof certificate.json` after
`--approve <digest>` when present, and before positional file arguments. Example:

```sh
node --import tsx scripts/admission-history.ts owner-recovery-plan \
  --checkpoint-proof certificate.json owner-config.json enrollment.json \
  owner-storage.hex recovery-directory 1
node --import tsx scripts/admission-history.ts owner-recovery-start \
  --approve <digest> --checkpoint-proof certificate.json owner-config.json \
  enrollment.json owner-storage.hex recovery-directory 1
node --import tsx scripts/admission-history.ts owner-recovery-step \
  --checkpoint-proof certificate.json owner-config.json enrollment.json \
  owner-storage.hex recovery-directory
```

Supply that same independently retained certificate on status, review, restore
and readiness commands too. Removing or substituting it fails closed. No proof
is inferred from the recovery directory, and neither review nor proof grants
permission to erase a prefix.

### Operational certification and retention

A protected owner can review its latest applied full-state checkpoint offline.
Certification refuses a genesis, delta, policy-only checkpoint, unfinished write
or image that differs from current accepted state. It takes the same exclusive
operation guard as publication. After readiness, four pinned volunteers must
endorse the exact ciphertext. A later accepted mutation invalidates review;
closing the owner immediately cancels the collection. A restored owner continues
to use its original independently retained genesis.

The CLI binds export approval to the current checkpoint and canonical destination.
It reserves managed output capacity before readiness/collection, then writes and
flushes one new bounded certificate file. It never overwrites an existing or
partially written file; after interruption, retain that file and select another
output. Certification exports historical proof; it does not automatically retain
that proof remotely.

Certification review also explicitly authorizes retaining that proof in the
owner's encrypted archive to enable the live repair path below. An export failure
does not undo this local durable proof; a retry preserves the first proof for the
same checkpoint and writes only to a new output file.

```sh
node --import tsx scripts/admission-history.ts owner-checkpoint-certification-plan \
  owner-config.json policy.json owner-storage.hex owner-directory certificate.json
node --import tsx scripts/admission-history.ts owner-checkpoint-certify \
  --approve <export-digest> owner-config.json policy.json owner-storage.hex \
  owner-directory certificate.json
node --import tsx scripts/admission-history.ts owner-checkpoint-retention-plan \
  owner-config.json enrollment.json certificate.json
node --import tsx scripts/admission-history.ts owner-checkpoint-retain \
  --approve <retention-digest> owner-config.json enrollment.json certificate.json
```

Retention starts from the independently pinned enrollment and already saved proof.
Its offline review binds the checkpoint, exact certificate and member/endpoints.
Apply sends five fresh owner-authorized requests, verifies four distinct replies,
and cancels remaining work. Three retained proofs are not success. A timeout or
lost reply may leave a committed subset; retry reuses the same certificate and
does not undo those writes. Silent or invalid transports remain bounded by the
whole-operation deadline. Returned counts describe historical proof retention,
not current admission readiness or permission to delete history.

TypeScript and **53 tests / three files in 63.07 seconds** pass. Coverage includes

### Live writer repair

The writer archive retains an authenticated checkpoint proof monotonically, bound
to its committed ciphertext and independently supplied original genesis. Pending
work prevents proof advancement. Reopen authenticates the proof and actual
checkpoint before exposing the repair index; opening remains offline. An uncertain
proof flush requires reopening. Missing, changed or insufficient evidence fails
closed without resetting history.

A returning member below the anchor receives a fresh owner-signed `install`
request with the exact canonical certificate identity and checkpoint digest. The
member validates its independently enrolled ancestry and four endorsements,
persists payload then manifest, and replies `installed`. Installation refuses
freeze/agreement/activation/sealing, any newer accepted head, a known conflicting
adjacent predecessor, owner storage pause, stale authorization and capacity
exhaustion. Expiration during persistence suppresses success while retaining the
durable result. An exact unfrozen retry does not rewrite the manifest.

Every previously accepted block stays indexed. Unavailable intervals are allowed
only below the latest certified full-state checkpoint; each retained segment
after a gap begins with an owner-signed checkpoint. All known adjacent links and
the complete suffix remain verified. A subsequent certificate covers earlier
unavailable intervals under the stated correct-owner/four-endorsement assumption;
this does not add Byzantine-owner fork resolution. Root and generation barriers
remain present. No accepted payload is deleted by this repair protocol.

Installation is historical repair, never a write receipt. The writer separately
copies the tail and collects four fresh appends for its current target, even when
the target is the installed checkpoint itself. Lost installation replies leave
exact pending intent; retry inspects the resulting head. A proof, head response
or installed prefix cannot substitute for the fourth current target receipt.

## Required next layers before deleting history

1. Extend the retained certificate into an explicit prefix boundary atomically
   with the manifest. Preserve later and partially accepted suffixes, writer intent,
   successor promises, view state, generation barriers and permanent denials.
2. Extend the live-owner archive's full digest index to an explicit retained-prefix
   boundary, preserving the checkpoint repair path above. A returning old owner
   or replica must not resurrect a removed prefix or lower a barrier.
3. Delete only blocks rendered unnecessary by the committed boundary, with
   bounded replacement/repair headroom and resumable cleanup. Interrupted cleanup
   must retain a readable authoritative manifest. Do not release lifetime storage
   promises merely because files were removed.
4. Exercise repeated checkpoints, partitions, lost replies, concurrent freeze,
   hidden accepted tails, corrupt/missing proofs, stale backups and SIGKILL across
   every manifest/cleanup boundary, including actual owner restoration.
5. Replace finite absolute sequence and ancestor indices with bounded rolling
   evidence before claiming indefinite compaction. Filling unavailable sequence
   slots or reclaiming payload bytes alone does not remove those limits.

Until those layers are implemented, this publication is a safe prerequisite and
consumes additional space. It does not close the long-term compaction roadmap row.
