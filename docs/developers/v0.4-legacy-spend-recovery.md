# Recovering legacy spend capacity from token evidence

Status: **implemented for the opt-in v0.4 pilot, 2026-10-03**. This is offline maintenance for complete historical spend records whose issuer was not recorded. It does not reconstruct lost history or repeat a user's original operation.

## Decision

The old JSONL format retained a token hash, action and exact request binding, but no issuer key. A hash alone cannot recover that key or the bearer token. Guessing that every row belongs to the current issuer, or that every unknown row has expired, would permit unsafe deletion. A witness certificate is also insufficient on its own: witnesses sign an authorized coordinator's claim without verifying the bearer token themselves.

An existing token presentation provides stronger evidence. Recovery verifies the actual Blind RSA signature, signed-policy scope and issuer key, derives the token's spend hash, and requires its action and request binding to match an existing unattributed row exactly. The issuer must be inactive and past its final retry cutoff under the current installed policy. Both current and archived policy entries can supply the verification pins.

After an explicit review, one atomic encrypted snapshot:

1. Retains a permanent denial fence for every proven issuer key.
2. Removes the proven unattributed rows and any rows already attributed to those same keys.
3. Preserves every other row, including unknown rows that might belong to those keys.

The fence and removal cannot commit independently. This recovers only demonstrated capacity and permanently refuses the affected keys, including exact retries. It changes no issuer allowance, wallet balance, witness vote, coordinator certificate or publication/mailbox record. It sends no network requests and authorizes no token redemption. A subsequent batch can prove more rows under an already fenced key.

## Evidence and limits

The input is a JSON array of **1–32 proofs**, at most **64 KiB**. Each proof has this exact shape:

```json
[
  {
    "version": 1,
    "kind": "admission-legacy-spend-proof",
    "issuerKey": "sha256:<issuer-public-key-fingerprint>",
    "action": "search",
    "requestBinding": "admreq_<original-request-digest>",
    "capability": {
      "version": 2,
      "kind": "admission-capability",
      "scheme": "privacy-pass-blind-rsa-v1",
      "issuer": "<original-issuer-name>",
      "token": "<original-base64url-token>",
      "requestProof": "<original-presentation-proof>"
    }
  }
]
```

The placeholders are not valid evidence. A requester or operator must already possess the real historical presentation, or the original token and exact request binding from which the existing `presentBlindAdmissionTokenV2` helper can construct it. This checkpoint does not add desktop wallet export or solicit tokens from users automatically. A token removed by wallet cleanup cannot be reconstructed from its denial digest.

Proofs contain bearer tokens and exact-operation digests. Keep the proof file in an owner-only local file and use an independently trusted offline exchange if evidence must move between devices. A shortened cutoff is only effective on updated devices; an old policy may still accept a token elsewhere. The recovery output and stored ledger contain no bearer tokens. JavaScript strings and operator backups are not physically erased by this command.

Duplicate proofs, an unrelated valid token, a changed action/binding, a forged signature, an unknown key, and a proof for a missing/already attributed row reject the whole batch. No prefix of a failed batch is applied. The existing 10,000-record / 8 MiB ledger limits are unchanged; this operation adds no separate unbounded archive.

## Operator workflow

Stop the relay and retain its data directory and storage key. Its latest signed community policy must already be installed. The command reads and authenticates that installed policy under a separately supplied authority, holds both existing process locks and refuses missing history. It does not import a policy or initialize a relay.

Review:

```sh
node --import tsx scripts/recover-admission-spends.ts plan \
  relay-data authority.pub local-policy-key.hex proofs.json
```

The report contains the resolved directory, authority fingerprint, policy revision/digest, selected issuer keys and their retry cutoffs, existing fences, proven/previously attributed removal counts, remaining unknown rows and an `approvalDigest`. It omits bearer tokens, spend hashes and raw request bindings. Review leaves the history file unchanged, apart from the storage layer's ordinary locks and stale temporary-file cleanup.

Apply exactly that review:

```sh
node --import tsx scripts/recover-admission-spends.ts recover \
  --approve 'sha256:<review-digest>' \
  relay-data authority.pub local-policy-key.hex proofs.json
```

Application verifies all cryptography again and checks the digest against the complete current ledger, exact signed policy, directory and proven row selection. A different selection, history, policy or location requires a fresh review. Proof order and JSON formatting do not change the selected evidence. Policy expiry and key deadlines are checked again before commit. Concurrent ledger writes/retirement are refused while verification is pending; closing the ledger prevents a late review or commit.

The same encrypted version 2 snapshot and ciphertext domain are used. File/directory flush failure poisons the handle: close and reopen before retrying. Reopening yields intact old evidence or the complete new state including all fences. If the evidence was already removed, another recovery request is refused; do not reset the file. Windows still lacks the underlying POSIX directory flush, and process-crash checks do not certify every power-loss scenario.

## Missing, empty, malformed or unprovable history

These cases have no safe automatic reset:

| Available evidence | Behavior |
| --- | --- |
| Complete unknown row plus matching token presentation | Review and recover after the inactive key's final cutoff |
| Complete unknown row without a matching token | Retain the row and its capacity charge |
| Empty old JSONL file | Refuse; indistinguishable from a truncated newer encrypted snapshot |
| Missing, malformed or truncated existing file | Refuse; a recovered prefix cannot prove the missing suffix contained no accepted spends or fences |
| Older intact backup only | Its integrity does not prove freshness; restoring it can lose later accepted spends or permanent fences |

Continuing an existing role requires its latest intact, authoritative evidence. If that is unavailable, the affected role stays stopped. The [checkpoint decision and executable model](v0.4-history-checkpoint-decision.md) specify freshness and writer-fencing requirements; operational recovery remains unimplemented. This command does not infer an unused allowance, reset identities or initialize over damage. Those limitations remain explicit in the roadmap.

## Validation

Real-token tests cover exact legacy attribution, successful capacity recovery with fresh-token acceptance, current and archived policy pins, preservation of unrelated rows, repeated batches under a permanent fence, a 32-proof/two-issuer batch, signature/key/binding attacks, count/byte bounds, stale approval, policy/deadline changes, concurrent mutation and close during verification. File/directory flush faults cover both sides of atomic replacement; a child process is killed after durable recovery and reopens through stale-lock recovery with its fence intact.

The actual CLI tests verify installed-authority pinning, unchanged review bytes, required approval, no secrets in reports/errors, bounded input, and missing/empty/corrupt-file refusal. This remains local recovery evidence, not a volunteer deployment, rollback-proof storage or an independent protocol audit.
