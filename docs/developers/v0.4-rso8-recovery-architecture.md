# DEC-016 / RSO8 sharded recovery architecture

**Status: CONFIRMED REJECTION.** Independent review confirmed multiple decisive physical falsifiers and an additional original-semantics routing defect. Do not advance `RSO8-Range32` to implementation or treat it as a viable production architecture. This evaluates the single authorized RSO8 candidate, not every conceivable sharded architecture, and claims no implementation, production, R1/R2, or K/R acceptance.

DEC-016 authorized one read-only design pass and one independent review. The review is recorded in `../evals/v04-dec016-rso8-rejection-review-2026-11-20.md`. No implementation, product test, campaign, installer, deployment or release action occurred.

## Decisive falsifiers for rejection review

1. **Fixed-five storage:** four copies of current+pending minimum-size rows have a perfectly balanced five-volunteer average of 4,416,000 B per node against `D=524,288 B`; even one generation averages 2,208,000 B. The absolute current+pending lower bound is 43 storage volunteers before all overhead, not a claim that 43 suffices.
2. **Hot-key `D`:** a legal 10,000-entry state can concentrate all 32-byte vote/certificate proof references on one spend. Current+pending references alone require 640,000 B, exceeding `D` by 115,712 B before rows, indexes, pages, or manifests.
3. **Recovery work:** the optimistic balanced-shard forecasts are 5,321,454 B for cold reserve, 5,206,766 B for NEW_VIEW import, and 5,174,231 B for local-`C` recovery against `W=4,718,592 B`.
4. **Aggregate entries:** under the report's explicitly additive retained-baseline model, only the 160 data-member scopes produce 604 entries against 512, before the control plane. This is a conditional additive-model falsifier, not a claim about an unauthorized re-baseline.
5. **All-shard cumulative terminal cuts:** one forecast 32-shard terminal-cut barrier costs 224,251,360 B; two cost 448,502,720 B against cumulative 268,435,456 B, before observer/policy work, retries, failures, private transfer, or recovery. Per-shard meter resets are prohibited.

All numeric physical and work results below are **forecasts or lower-bound counterexamples**, not observed implementation performance or acceptance evidence.

## The single candidate evaluated: `RSO8-Range32`

The most favorable coherent shape found by the design pass is:

- **32 fixed spend-range data shards**, not dynamically unlimited shards.
- **One bounded global control plane** containing the range directory, current/pending policy and configuration heads, at most 72 issuer-denial identities, and cross-shard transaction descriptors. It contains no per-row global index.
- Ordinary vote/certificate/accept/retry commands are **single-shard**.
- Retirement, legacy multi-spend attribution, range migration, and same-key replacement use an **Atomix-derived certificate-based lock/unlock transaction**, strengthened to require Resonance's four-signer stable certificates and four durable copies.
- Each shard has five pinned agreement/storage volunteers, quorum four, at most one Byzantine member, and four independently durable copies.
- The original business witness set and its `setId` signatures remain distinct from shard agreement membership. Otherwise disjoint shard cohorts could not verify the same original `AdmissionWitnessRequest`, whose `setId` is fixed by policy.

This shape fails physically and in recovery work even before its unspecified global metadata is fully costed.

## 1. Exact ownership and routing

Let `raw(spend)` be the 32-byte value obtained by decoding the existing base64url spend identifier. An authenticated control directory at configuration `c` contains 31 canonical boundaries

```text
b0 < b1 < ... < b30
```

and 32 shard configuration identities. The assignment is:

```text
shard_c(spend) = j
where boundary[j-1] <= raw(spend) < boundary[j]
```

with `-∞` and `+∞` as the outer boundaries. Range boundaries are selected by certified row counts, not by assuming hash uniformity. The directory is `O(number of shards)`, not an `O(number of rows)` global index.

| Command or outcome | Authoritative routing and state |
| --- | --- |
| Witness vote | `shard_c(vote.spend)`; preserve original `setId`, issuer, spend, action, binding, witness, and signature. |
| Certificate | `shard_c(certificate.votes[0].spend)`; all four original votes remain intact. |
| Acceptance | `shard_c(request.spend)`; the shard sees every issuer's use of that spend and evaluates the original reducer against the current global denial/control head. |
| `fresh` / `bound` | Determined from the complete local evidence for that spend and the authenticated control epoch. |
| `denied` | Either the spend-local binding differs or the issuer appears in the authenticated global denial set. |
| `conflict` | All certificates for the same spend, including different issuers and historical sets, reach the same shard. |
| `split` | All votes and accepted bindings for that spend reach the same shard. |
| Exact retry | Same request/spend shard and request identity; return the existing certified result without another notification. |
| Changed-byte same-identity retry | Same shard; permanent conflict, never replacement by arrival order. |
| Uncertain outcome | Resolve the durable pending record, prepared lock, commit certificate, stable head, or cross-shard lock before another command. No new business outcome is invented. |
| Legacy unattributed row | Still routed by its authoritative `spend`; null issuer does not require a global scan. |
| Legacy attribution batch | Its explicit spend list identifies the participant shards directly; use the multi-shard protocol below. |
| Permanent issuer retirement | Control shard plus every data shard containing that issuer's rows. Each data shard has a local issuer secondary index; no global issuer-to-row index exists. |
| Same-key replacement | Control proposal keyed by `issuerKey`, followed by terminal cuts and private transfer on every affected data shard. |
| Range migration | Old directory remains authoritative until source locks, destination four-copy installation, and the control directory transaction all commit. |
| Policy update | Control chain authenticates it. A data shard must prove the required control head/cutoff before its next authorization; emergency expiry cannot be bypassed by stale cache. |

### Cross-shard commit rule

For transaction `x`, each input shard's lock certificate binds:

```text
txDigest, configurationEpoch, shardId, businessKey,
inputDigest, postLockStateRoot, pendingGenerationRoot,
stableSequence, stableView, transactionCoordinatorDescriptor
```

A commit requires an acceptance certificate from **every** input and the control participant. A single valid rejection certificate permits abort, never commit. Commit/abort installation is idempotent and authenticated at every participant. Outputs or external completion are invisible until the full commit certificate exists.

A lost quorum can leave a lock unresolved and stop progress; it cannot convert uncertainty into acceptance. Any party may resume using the durable descriptor, avoiding Atomix's dependence on one client remaining online.

## 2. Membership, trust, copies, and why five total volunteers fail

Two four-member quorums among five members intersect in at least three members. With at most one Byzantine member, their intersection contains at least two honest members. Conflicting valid four-signer certificates therefore cannot be accepted under the stated model. Four matching durable acknowledgments remain a separate obligation; a quorum certificate is not itself four storage copies.

A node belonging to a data shard stores:

- only that shard's semantic rows and local issuer index;
- current and pending immutable page generations and manifests;
- the bounded suffix, stable heads, prepared locks, complete NEW_VIEW evidence, and old-cohort fence;
- pending cross-shard lock/outcome records naming that shard;
- the bounded authenticated control cache;
- opaque evidence/delegation ciphertext required for its role.

A control member stores global control metadata, not every semantic row.

### Fixed-five-volunteer impossibility

If the same five volunteers constitute every shard, each node stores every shard's state. Even allowing optimal placement of only the mandatory **four** copies:

```text
one plaintext generation       = 10,000 * 276 = 2,760,000 B
current + pending              = 2 * 2,760,000 = 5,520,000 B
four copies of two generations = 4 * 5,520,000 = 22,080,000 B
perfectly balanced per node    = 22,080,000 / 5 = 4,416,000 B
D per node                                         524,288 B
minimum excess                                   3,891,712 B
```

Even one generation has a perfectly balanced four-copy average of `2,208,000 B`, exceeding `D` by `1,683,712 B`.

At least 43 storage volunteers are necessary just for four copies of two plaintext generations under perfect divisibility:

```text
ceil(22,080,000 / 524,288) = 43
```

That is an absolute lower bound before pages, indexes, manifests, consensus, configuration, or failed extents; it is not a claim that 43 suffices.

Multiple communities cannot share one five-volunteer cohort without adding every community's bytes to the same per-node `D`. They require separately funded cohorts and aggregate entry/metadata accounting.

## 3. Established protocol comparison

### OmniLedger / Atomix

The [OmniLedger primary paper](https://eprint.iacr.org/2017/406.pdf), especially Sections III–IV-C and V-C, provides:

- disjoint validator subsets processing shard state;
- client-driven **initialize → lock → unlock-to-commit/abort**;
- proof-of-acceptance from every input for commit;
- proof-of-rejection from any input for abort;
- another party may drive a stalled unlock;
- shard state blocks for bootstrapping.

Only the Atomix transaction shape is relevant. OmniLedger's permissionless random shard sampling, global identity chain, epoch synchrony, ByzCoinX membership assumptions, UTXO semantics, and pruning of historical payloads do not match Resonance. In particular, Resonance cannot prune original evidence or accept a leader's unsupported lock statement. The adapted certificate therefore needs four shard signatures, four-copy storage proof, original business signatures, and a durable resumable coordinator descriptor.

### RapidChain

The [RapidChain primary paper](https://eprint.iacr.org/2018/460.pdf), Sections 1.2, 3, and 4, assumes:

- large sampled committees, honest majority within a committee, and global corruption below one-third;
- synchronous intra-committee consensus and slowly adaptive corruptions;
- permissionless identities/Proof-of-Work and a reference committee;
- output-committee-driven cross-shard verification and Kademlia-inspired routing;
- every committee member storing that committee's shard.

Those are not Resonance's five-member/quorum-four/one-Byzantine or authenticated volunteer-configuration assumptions. RapidChain's consensus, bootstrapping, routing, and reconfiguration should not be imported. Its storage model also illustrates why adding logical shards helps only when committee membership is actually disjoint.

### Simpler pattern retained

Ordinary Resonance operations need no cross-shard transaction under `Range32`: spend uniqueness and all conflict/split evidence are colocated, while the bounded denial set is authenticated globally. The existing RSO7-style prepare/commit/stable chain is sufficient inside one shard, provided NEW_VIEW carries **every** surviving lock and has a fully specified four-signer QC. Crash-only two-phase commit without shard certificates would be unsafe.

## 4. Cuts, recovery, fencing, and configuration continuity

Each data shard maintains an independent `(genesis, shardEpoch, sequence, view)` chain:

1. Preflight the complete command, original evidence, pending state, current+pending pages, indexes, manifests, certificates, and failed extent.
2. Persist original ciphertext and pending `T/M`; obtain four exact durable acknowledgments.
3. Form prepare QC, persist every prepared lock, and again obtain four copies.
4. Form commit QC and append the certified suffix.
5. Execute the certified mutation without rerunning a different reducer.
6. At a cut, write all pending pages and indexes, then manifests, then the stable head. Four complete copies precede the stable vote and client acknowledgment.
7. Atomically promote either the complete old generation plus suffix or the complete pending generation, never a mixture.

At most four suffix entries are admitted before a cut. Superseded pages retire only after the successor stable head and all named objects have four copies. Originals, denials, conflicts, alternate certificates, and unresolved locks never become suffix garbage.

Recovery modes are:

- **Cold:** authenticate original genesis, control chain, exact range assignment, stable QC, continuous shard suffix, state/index roots, evidence, delegations, and four-copy floors before serving.
- **Returning:** compare authenticated roots and transfer only missing objects, while still proving four-copy availability and never regressing a local floor or lock.
- **NEW_VIEW:** four view-change records carry the complete committed suffix and **complete lock set**. Highest prepared values survive; a local higher floor or omitted lock refuses installation.
- **Local private-state loss:** use exact remote ciphertext/delegations only when the remote four-copy floor is intact; otherwise escalate to cold/quorum recovery or refuse.
- **Cross-shard recovery:** recover each participant's lock/outcome before resolving the transaction. A new view cannot silently discard an Atomix input lock.

Same-key replacement requires a control terminal record binding every affected shard's terminal head, successor funding, four successor copies, observer drain, and policy activation. After activation, every old-cohort proposal, vote, cut, delegation, and write is rejected. Historical verification retains the old configuration and terminal evidence.

Configuration ancestry is a digest-linked control chain from original genesis. Certified archive pages/frontiers may avoid linear traversal but cannot discard required policy/activation evidence or reuse the existing 65-generation configuration limit. A same-sequence different digest, mixed cohort QC, stale policy, missing activation, or incompatible terminal vector refuses service.

## 5. Private evidence and delegation

The existing RSO5/RSO7 privacy boundary remains:

- original plaintext is opened only by the authorized role owner;
- each original has immutable encrypted content and an authenticated recipient capsule/delegation;
- shard and history replicas receive ciphertext and bounded signed metadata only;
- recipient private keys, DEKs, original evidence plaintext, and delegation plaintext never become replica state;
- successor recipients receive only the evidence/delegations required for their authorized shard and historical scopes;
- old key versions remain available where retained proofs require them;
- a stable state root or QC never substitutes for original-signature and recipient-enrollment verification.

The finite 72-proof `C` forecast remains `258,595 B`, with only `3,549 B` headroom. Sharding does not make additional originals, capsules, or delegation identities free.

## 6. Exact 10,000-row physical model and counterexamples

The following is an **optimistic forecast-only subtotal** for the most balanced legal accepted-row distribution across 32 shards. It uses the existing RSO7 page/manifest/index encodings:

```text
Page(n=4096)   = 4,380 B
Manifest(n)    = 318 + 40*n B
index entry    = 197 B
suffix + heads + finite policy/activation + NEW_VIEW
               = 107,548 B
```

For the largest shard:

```text
rows per shard       n = ceil(10,000 / 32) = 313
row plaintext        J = 313 * 276 = 86,388 B
row pages                ceil(86,388 / 4,096) = 22

index plaintext      I = 256 + 313*197 = 61,917 B
index pages              ceil(61,917 / 4,096) = 16
```

Per data member:

| Component | Calculation | Bytes |
| --- | ---: | ---: |
| Current+pending row pages | `2*22*4,380` | 192,720 |
| Current+pending index pages | `2*16*4,380` | 140,160 |
| Current+pending row manifests | `2*1,198` | 2,396 |
| Current+pending index manifests | `2*958` | 1,916 |
| Suffix, heads, finite policy/activation, NEW_VIEW | inherited subtotal | 107,548 |
| **Optimistic per-node D subtotal** | | **444,740** |
| Nominal remaining before global control and cross-shard state | `524,288-444,740` | **79,548** |

Maximum page-plus-manifest failed extent:

```text
Fextent = 4,380 + max(1,198,958) = 5,578 B
F headroom = 32,768 - 5,578 = 27,190 B
```

Five-member prospective aggregate reservation across 32 disjoint data cohorts:

```text
160 * 444,740 = 71,158,400 B
```

This excludes the control cohort, every node's control cache, cross-shard certificates, migration duplicates, >64-configuration growth, and all non-finite original workloads. Consequently the subtotal is not complete physical closure even where it is below `D`.

Using the retained aggregate baseline `2,042,919,814 B / 444 entries`, adding only the 160 data-member scopes gives:

```text
bytes = 2,042,919,814 + 71,158,400 = 2,114,078,214 B
entries = 444 + 160 = 604 > 512
```

Thus the additive model already exceeds the entry cap by **92 entries before the control plane**. Re-baselining existing obligations to evade that result would require proof and owner review; it is not assumed here.

### Independent hot-key counterexample

Range balancing accepted rows does not balance proof references. The original parser has no per-spend distribution limit. A legal 10,000-entry state can place all vote/certificate references on one spend and therefore one shard:

```text
one generation of 32-byte proof references = 10,000*32 = 320,000 B
current + pending                                        = 640,000 B
D limit                                                   524,288 B
excess before rows, indexes, pages, or manifests           115,712 B
```

Moving complete originals into `C` does not remove the semantic references needed by the reducer. This independently falsifies the claim that `Range32` bounds every legal 10,000-entry semantic state.

Using RSO7's forecast primitives, for one maximally populated balanced shard:

```text
     = 780,616 B

Sc_s = S_s + 11*(22*284 + 2*1,198)
     = 875,700 B
```

Related forecasts also fail:

```text

                = 5,206,766 B
excess          =   488,174 B

local-C recovery = NEW_VIEW import - (79,737 - 47,202)
                 = 5,174,231 B
```

These are optimistic because `J` counts only minimum row payloads, not the remaining state/header overhead.

For cumulative work, retain:

```text
R       = 42,315 B
U       = 865,685 B
Cut_s   = U + Sc_s = 1,741,385 B

one non-cut shard command aggregate = R + 4U
                                    = 3,505,055 B

one all-shard terminal cut aggregate = 32*(R + 4Cut_s)
                                     = 224,251,360 B
```

Two such barriers cost `448,502,720 B`, exceeding cumulative `268,435,456 B` before observer/policy work, retries, failures, private transfer, or recovery. No per-shard meter reset is permissible.

For a transaction with `k` input/lock shards and `l` output shards:

```text
Wcommit >= Σinput Wlock + Σoutput Wcommit + Wcontrol + Wrecovery
Wabort  >= Σlocked Wlock + Σlocked Wabort + Wcontrol
```

Every failed attempt, lost reply, observer/policy operation, durable copy, and retry remains in the same cumulative ledger.

An exact network or 3 s/30 s forecast is not available: actual TLS framing, connection establishment, retransmission, impaired-network loss, observer scheduling, queueing, and disk flush behavior are not implemented or measured for this design. That is a precise evidence blocker, not a latency pass. The physical and work counterexamples already support the rejection recommendation without waiting for those measurements.

## 8. Required executable controls if a future design is authorized

No design controls were run under the read-only DEC-016 pass. Mechanical arithmetic checks for this document do not implement or qualify the architecture. A future implementation candidate must freeze at least these controls, under a separate owner decision:

### Positive controls

- Route identical spends across issuers and historical `setId`s to one authoritative shard; compare every result byte-for-byte with the full original reducer.
- Exercise fresh, bound, denied, conflict, split, exact retry, changed-byte retry, and uncertain outcomes.
- Crash at evidence, pending, prepare, commit, execute, stable, page, manifest, promotion, NEW_VIEW, migration, retirement, and activation barriers.
- Prove four-copy recovery with predecessors offline; three copies never acknowledge.
- Commit a cross-shard transaction only with every input certificate; abort and unlock with one genuine rejection.
- Preserve every prepared and cross-shard lock through competing views and stale installations.
- Cross configuration 64/65 and complete 100 transitions without resetting global sequence, policy ancestry, or work meters.
- Recover role-private evidence locally while replica captures contain no plaintext or recipient private keys.
- Prove no node holds every semantic row and enumerate every node's actual `D` reservation.

### Negative controls

- Reject the five-volunteer/four-copy average-`D` counterexample and the 10,000-reference hot-key case as candidate failures, not as workload exclusions.
- Reject leader-only locks, missing input certificates, mixed-configuration QCs, early output visibility, partial retirement, stale policy, post-fence writes, and conflicting retries.
- Reject snapshots missing denials, originals, indexes, manifests, locks, terminal heads, or configuration ancestry.
- Inject 0/1/3/4 durable copies, corrupt ciphertext, stale restores, competing writers, torn extents, and exhausted `C/L/P/D/F/W`.
- Charge all failures, retries, observer/policy work, migration copies, and recovery to one cumulative ledger.
- Detect any hidden global row index, unnamed storage partition, replica plaintext capability, or per-shard cumulative reset.

## Remaining unknowns and review disposition

Unknowns include actual full command/configuration maxima, complete global metadata encoding, true network/deadline behavior, and whether a future owner might authorize disjoint cohorts or a different aggregate inventory. None is evidence of feasibility. The fixed-five storage counterexample, legal hot-key overflow, and cold/NEW_VIEW/local-loss work overflows already support rejection; aggregate entries and cumulative all-shard cuts supply additional falsifiers under the stated forecast models.

**Disposition: preserve `RSO8-Range32` at `REJECTION REVIEW PENDING`. No implementation is authorized or accepted.** The pending independent review is to confirm or challenge these falsifiers, not to treat the candidate as ready for detailed production design, implementation, R1/R2, or K/R acceptance.
