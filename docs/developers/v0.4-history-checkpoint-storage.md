# Signed encrypted history storage

Status: **experimental storage primitives, 2026-10-04**. These implement the first
storage step of the [checkpoint decision](v0.4-history-checkpoint-decision.md).
They are not connected to admission, a network endpoint or a recovery command.
The app continues to refuse missing or damaged admission histories.

## Implemented boundary

`@resonance/core/history-checkpoint` seals, authenticates and opens opaque blocks.
`packages/relay/src/history-checkpoint-store.ts` stores one enrolled history on
one pinned volunteer. A successful append means local durability only; it does
not authorize accepting a spend or establish a four-volunteer quorum.

The independently supplied context binds the history identifier, the
`relay-admission-spends` role, owner signing key, authority key, exact policy
digest, five distinct sorted member keys and the four-member threshold. The
store additionally pins its own member identity, starting generation and root
checkpoint digest. The constructor does not authenticate a policy document or
discover those pins. Future enrolment must validate and retain them independently.

Each envelope contains:

- A context digest, writer generation, sequence and predecessor digest.
- A kind: full `checkpoint` or incremental `delta`. Sequence zero must be a
  checkpoint with no predecessor; later blocks must extend the exact chain.
- An AES-256-GCM ciphertext, random 96-bit nonce and authentication tag. HKDF-SHA256
  derives the payload key from the owner's 32-byte key with domain and context
  separation. The header is authenticated as associated data.
- An Ed25519 owner signature over the complete header and encryption fields.
  Parsing rejects extra fields, noncanonical encodings and oversized payloads.

Volunteers can authenticate and store blocks without the payload key. They see
context, generation, sequence, kind, timing and size, so this is not metadata
anonymity. Plaintext snapshot/delta semantics are deliberately outside this
primitive: a valid signature alone cannot prove that the owner included every
spend or permanent denial. The recovery integration must validate that content.

Retries must reuse the exact envelope. Encrypting the same plaintext again
creates a different digest and is a conflicting record at an existing sequence.
The API makes defensive copies; modifying a returned object cannot alter the
stored chain. No signing key or owner payload key is retained by the store.

## Persistence ordering

The dedicated directory contains immutable ciphertext `.block` files and a small
encrypted manifest listing their ordered digests and any generation barrier.
The manifest uses the existing single-writer PID lock and atomic snapshot helper,
with a separate local key. Appending does the following synchronously:

1. Validate the signature, pins, sequence, predecessor and capacity.
2. Exclusively create an owner-only temporary block, complete short writes, flush
   the file, rename it to its content-addressed name and flush the directory.
3. Write the new encrypted manifest to a temporary file, flush, rename and flush
   its directory. Only then return success.

Existing payload blocks are never rewritten by an append. The bounded manifest
is rewritten, so this is incremental payload I/O, not constant-size metadata I/O.
An I/O failure makes the handle unusable until close/reopen. A capacity refusal
happens before writing and leaves the previous history usable.

On restart, authenticate the manifest and every referenced block, verify the
entire chain and any external progress anchor, then remove unreferenced block
files and abandoned block temporaries. Missing, empty, altered or truncated
referenced data stops reopening; it is never truncated away to resume service.
A process killed before manifest installation can leave an unaccepted orphan.
After installation it can leave a retained block whose acknowledgement was lost;
exact retry is idempotent. A damaged or incomplete enrolment directory cannot be
reinterpreted as a fresh history.

This uses file and directory `fsync` on macOS/Linux. Node's Windows directory
handles do not provide the same directory flush path; files are still flushed.
The tests exercise filesystem calls and process death, not power-loss behavior
of every filesystem, controller or operating system. Physical media loss remains
a replication concern.

## Generation barriers and freshness

An owner-signed freeze names the context, old generation, a strictly higher
generation and a challenge. The store atomically persists the barrier with the
retained block list. It then rejects all appends, including exact retries, and
keeps refusing them after restart. Repeated freezes cannot reduce the barrier;
a higher authenticated barrier can supersede it without deleting payloads.

There is intentionally no successor activation or thaw operation. Allocating
generations across concurrent recoveries, collecting challenge-bound signed
replica responses, selecting a complete compatible chain, writing it back to
four members, and atomically restoring the live role remain future protocol work.
The stored freeze command is not a fresh replica response. An equal-generation
retry keeps the original durable command; a future response layer must bind its
answer to the current request challenge separately.

Local authenticated storage cannot detect replacing the entire directory with
an older authentic copy if every external progress anchor is also lost. Optional
`minimum` pins reject a chain missing a previously known sequence/digest or
generation barrier. They do not establish global freshness. Recovery still needs
the independent quorum protocol and intact enrolment pins/decryption key.

## Bounds and retention

Defaults: 64 MiB logical serialized storage budget, up to 10,001 blocks, maximum
8 MiB plaintext per checkpoint and 64 KiB per delta. The store reserves 4 MiB for
two maximum-size manifest copies; retained block bytes consume the remainder.
Budgets can be configured within hard bounds. Filesystem allocation units,
directory entries, other histories and application files are outside this byte
counter; the block-count limit bounds the number of retained payload files.

Later full checkpoints are appended without dropping earlier evidence. Safe
compaction needs a quorum-confirmed checkpoint and reviewed preservation of
denial semantics. Until that exists, capacity exhaustion refuses new appends.
Reserved manifest space still allows freezing a full history. No acknowledgement
permits deleting an accepted block in this implementation.

## Verification

```sh
npx vitest run --maxWorkers=1 history-checkpoint
npm run build
```

Coverage uses real signatures and encryption: field tampering, wrong owners,
keys and pins, exact retry, chain gaps/forks, generation mismatch, bounded input,
capacity, writer exclusion, defensive copies, missing/corrupt data and externally
anchored rollback. Injected short writes, failed writes, rename failures and
file/directory flush failures exercise uncertain outcomes. Child-process tests
use SIGKILL after acknowledged append/freeze and on either side of manifest
installation, then reopen using the original pins and keys.

These checks establish the bounded local storage behavior. They do not certify
distributed recovery, semantic completeness of a spend checkpoint, membership
replacement, policy freshness or arbitrary concurrent recovery schedules.

Local validation on 2026-10-04: TypeScript compilation and 59 focused tests pass
(41 new storage/crypto/crash cases, seven model cases and eleven relay-link cases).
The final full suite passes **117 files / 639 tests** in 315.72 seconds with one
worker. Remote CI is recorded separately in the draft PR.
