# DEC-020/DEC-021 client-held discovery implementation-prototype specification

**Status: ACCEPT FOR BOUNDED PROTOTYPE EVALUATION.** The DEC-020 findings and DEC-021 two-generation quota correction passed independent follow-up review. This is a plausible bounded prototype specification, not product implementation, implementation authorization, model-selection acceptance, production/K/R acceptance, or release. Every numeric prototype limit is evaluation-only and requires owner approval before use. See `../evals/v04-dec021-implementation-feasibility-review-2026-11-22.md`.

DEC-020 explores a content-plane/storage change. It does not replace FEAT-001 authority, policy, witness, issuer, wallet, or configuration recovery. Existing K5/K6 failures and all R/K gates remain open.

## 1. Bounded prototype proposal

Original content remains in encrypted client storage. A local generative stage may eventually propose summary/intent JSON, but deterministic local policy and user review remain responsible for item type, authorization, consent, identifiers, lease times, and publication. Existing Nomic embedding and random-hyperplane LSH produce the matching fingerprint. The network stores only signed leased indexes and bounded encrypted offline **requests**, never original content or generated private caches.

The original-holding client supplies original bytes only through an authorized online private delivery path. A mailbox holds a request while its recipient is offline; it cannot fulfill the original while the holding client is offline. The requester must also return online to receive the response.

The following remain distinct:

- **Index availability:** replicas retain or can repair a signed index.
- **Owner liveness:** a client recently answered a private challenge.
- **Original possession/retrievability:** an authorized response supplied bytes verifying against the commitment.

A valid lease, replica receipt, owner challenge, queued request, or recipient storage ACK proves neither original truth, consent, possession, nor future delivery. There is no hidden always-on service or permanent network content archive.

The first protocol spike uses fixed precomputed derivation/embedding fixtures and does not require a generative model, model download, llama.cpp, MLX, or a new queue dependency. A future model runtime is isolated behind the adapter in section 11.

## 2. Data boundaries and local durability

### Relay-visible data

Only signed leased indexes, fingerprints/commitments, public mailbox encryption information, availability/replica evidence, encrypted mailbox envelopes, and signed maintenance records are network-visible. No public record may contain raw original content, generated summary/intent text under the default private derivation, true embedding, private contact address, commitment key, or unsalted original-content hash.

Generated text is another potentially sensitive representation, not an anonymizer. Existing LSH warns that public projections are not encryption (`packages/core/src/lsh.ts:8`); the existing real-text screen measured 86–97% reconstruction and 100% known-text identification (`docs/evals/scoped-fingerprint-real-2026-10-18.md:19`). No privacy claim follows from summaries, embeddings, commitments, fixed-size encryption, or signatures.

### Client-private transaction

Before network submission, one bounded, flushed, encrypted local transaction retains:

- exact original bytes for each semantic revision;
- generated summary/intent, true embedding, and public fingerprint;
- original commitment key;
- publication signing and mailbox private keys;
- exact serialized signed operation/frame;
- `nextLeaseSequence`, current `semanticRevision`, acknowledged operation, pending intent, withdrawal state, and match/notice/dedup state.

`packages/core/src/local-encrypted-state.ts:87` supplies bounded encrypted atomic replacement and flush-failure handling; `packages/node/src/store.ts:755` separately encrypts raw text and embeddings. The canonical original is the exact user-entered bytes. Unicode normalization, trimming, generation, and embedding preprocessing are versioned derivatives and never alter committed bytes.

The client backup responsibility explicitly covers originals, private keys, exact signed indexes, mailbox generations, content grants, outbox/inbox/dedup state, and pending operations. Relay replicas do not repair permanent client/key/original loss.

## 3. Leased index and original commitment

### 3.1 Signed schema and generation identity

Reuse publication-scoped Ed25519 keys, opaque IDs, canonical signed bodies, and strict unknown-field rejection from `packages/core/src/protocol-v2.ts:77`. Add a new versioned operation:

```text
LeasedIndexV1 {
  version: 1
  kind: "leased-discovery-index"
  publicationId
  clientLeaseId
  leaseSequence
  semanticRevision
  publicationKey
  groupId
  itemType

  derivationId
  fingerprint {
    algorithm: "random-hyperplane-lsh"
    bits: 512
    epoch
    value
  }

  original {
    commitmentAlgorithm: "hmac-sha256"
    commitment
  }

  mailbox { id, encryptionKey }
  createdAt
  expiresAt
  signature
}
```

`generationId` is the digest of the complete canonical signed index, including both `leaseSequence` and `semanticRevision`. Every mailbox deposit, replacement link, replica receipt, and ACK binds `generationId`.

`derivationId` pins the summary/intent schema and prompt, generator model/revision/artifacts/decoding configuration, preprocessing, embedding model/revision, quantization, and LSH configuration. It contains neither private input nor generated private output. Deterministic local policy, not the generator, assigns `itemType`.

The prototype chooses a stable `clientLeaseId` so quotas and recipient dedup work across refreshes. This deliberately links generations and, together with stable commitments/publication IDs/fingerprints, expands the correlation surface. It does not satisfy K5/K6. Unlinkable generations would require a separately reviewed quota credential and are not the prototype arm. Generated text remains private by default.

### 3.2 HMAC commitment

For each original revision, generate an independent random 32-byte key \(K\), retained only in encrypted client storage:

```text
C = HMAC-SHA-256(
      K,
      "resonance:leased-content:v1\0" ||
      unsigned_64_bit_big_endian(length(originalBytes)) ||
      originalBytes
    )
```

Only `C` enters the signed index. `K` is disclosed inside an authorized encrypted content response so the recipient can verify exact original bytes. This uses [RFC 2104 §§1–3](https://www.rfc-editor.org/rfc/rfc2104.html). Anyone receiving `K` can subsequently test guesses for that revision, so its disclosure is part of the grant. No public unsalted content hash is used.

## 4. Lease sequence versus semantic revision

### 4.1 Prototype parameters

- Original/generated embedding input: at most **8,192 bytes** (`packages/core/src/embedding.ts:33`).
- Canonical signed index: at most **4,096 bytes**.
- Maximum lease: **7 days** (`packages/node/src/commands/publish.ts:93`).
- Refresh when half the lease remains, at most once per **24 hours**.
- Optional owner challenges expire within **3 seconds**.
- Five desired replicas, three healthy minimum, and 64-operation inventory/handoff batches.
- Receiver polling on unlock/startup and, as a prototype-only schedule, at most once per **60 seconds** while unlocked and running.

No work continues after the client closes. Refresh/retry/polling schedules are bounded maintenance and stop at immutable expiry. They are not a hidden service.

### 4.2 Transition rules

| Transition | `leaseSequence` | `semanticRevision` | Matching/notification behavior |
| --- | --- | --- | --- |
| Exact replay | unchanged | unchanged | Return durable prior outcome; no allocation, admission spend, match, or notice. |
| Lease-only refresh | +1 | unchanged | Extend expiry by owner signature; retain derivation/fingerprint/commitment. Do not clear dedup, rebuild matching, or re-match. |
| Semantic/model/content revision | +1 | +1 | Use the controlled semantic path; change the appropriate fields and re-evaluate matches without resetting dedup. |
| Withdrawal | +1 | unchanged | Terminal tombstone dominates every live generation; stop discovery/delivery. |
| Stale backup | no write | no write | Reconcile first; never overwrite newer relay-observed state. |

A stable `matchId` derives from the relationship/pair identity and stable `publicationId`, not `leaseSequence`, `generationId`, content bytes, or replica identity. `notificationId` derives from `matchId` and the recipient notification scope. Both persist in the relay journal and client snapshots across restart, replica repair, and semantic revisions. A semantic revision may legitimately change match outcomes, but it cannot manufacture a second notification for the same already-notified logical match.

The existing `replaceAndMatch()` path clears withdrawal/dedup state and re-runs notifications (`packages/relay/src/matching-engine.ts:108`); it cannot handle lease-only refresh. The prototype requires a separate lease-update path and a controlled semantic-revision path.

### 4.3 One active writer, conflicts, and rollback

One publication has one active writer. Before writing, the client must:

1. Open the exact encrypted local snapshot and prove its writer identity.
2. Collect current signed state from the selected replica set, including tombstones and conflict evidence.
3. Reconcile `leaseSequence`, `semanticRevision`, all generation IDs, and local outbox state.
4. Acquire the local writer lease and compute the next operation only after reconciliation.

A restored/stale backup remains read-only until this completes. Multi-device concurrent writing is outside the prototype.

Exact duplicate detection compares the **complete signed operation and ciphertext bytes**, not only an ID. Lower lease sequences return `stale`. Equal lease sequence with different bytes retains both operations, returns `conflict`, and quarantines automatic fan-out/matching. The current publication-store conflict return does not retain the incoming operation and must change. One bounded conflict slot per logical operation is reserved; further conflicting attempts return existing authenticated conflict evidence without growing storage. Accepted conflicting evidence is never discarded.

Expiry is local policy independent of signature validity (`protocol-v2.ts:293`). At `now >= expiresAt`, indexes leave search, matching, refresh, and delivery. Relays do not fabricate owner-signed expiry tombstones. Withdrawal does not delete the local original. Terminal evidence remains until related matches, requests, grants, and conflicts expire and no stale deposit remains admissible. Tombstones do not prove physical erasure.

### 4.4 Availability evidence

1. **Replica custody:** signed `stored`/`already-stored` receipts and receipt-authorized inventory responses establish observation of an exact signed revision (`relay-replication.ts:222`).
2. **Owner liveness:** an optional private rate-limited response binds `{challenge, verifier, publicationId, generationId, issuedAt, expiresAt}`.
3. **Original possession/retrievability:** established only by authorized content bytes verifying against the commitment.

One missing replica index is repaired from another replica or returning owner using exact signed bytes. If every replica loses it while the owner is offline, discovery waits for a return. Permanent owner/original loss means permanent content loss and eventual expiry.

## 5. Authorized online original delivery

Reuse consent, fresh relationship keys, channel secrets, sequenced operations, private forwarding, durable pending outbound state, and inbound dedup from `relationship-v2.ts:98`, `channel-v2.ts:115`, and `pairwise-channel-v2.ts:222`.

1. Requester sends signed `ContentRequest {requestId, channelId, publicationId, generationId, contentCommitment, createdAt, expiresAt}` inside the active relationship.
2. Owner verifies channel/counterparty, current consent, exact generation, local withdrawal, and original presence. Match/relationship consent alone is insufficient; require an explicit owner grant or previously chosen scoped disclosure policy.
3. The single-use grant binds requester, request ID, channel, generation, commitment, and expiry no later than lease expiry.
4. While online, the owner sends original bytes and `K` in a signed, sequenced, channel-encrypted response over the live private route. Relays forward ciphertext but never journal original responses as an offline archive.
5. Recipient verifies request/grant/channel bindings and recomputes the commitment before display.

If the generation changed while a request was pending, either deliver the explicitly retained old revision under a valid grant or return `superseded`; never substitute new bytes silently. Withdrawal before transmission denies delivery. Already received content cannot be recalled.

## 6. Generation-aware offline-request mailbox

### 6.1 Logical, storage, and transport identities

1. **Logical `requestId`:** `oreq_` plus base64url of 32 bytes truncated from SHA-512 over a domain-separated canonical stable body containing request kind/payload, a 128-bit random request nonce, original `createdAt/expiresAt`, sender request public key, recipient `clientLeaseId`, and reply capability. It excludes `leaseSequence`, `semanticRevision`, `generationId`, and mailbox ID. Refresh/redeposit cannot change the logical ID or original expiry. The random nonce prevents a predictable-text dictionary ID.
2. **Generation-scoped storage key:**

   ```text
   envelopeId = env_ + base64url(
     SHA512(domain || clientLeaseId || mailboxId || generationId || requestId)
   )
   replicaKey = (clientLeaseId, mailboxId, generationId, envelopeId)
   ```

   `generationId` is mandatory even when refresh retains the mailbox. This makes refreshed redeposit a new storage generation rather than a same-ID ciphertext conflict.
3. **Per-attempt transport ID:** fresh for each transport exchange and never used for mailbox dedup, admission replay, or notification identity.

Fetch/ACK RPC IDs are separate maintenance IDs. A redeposit carries `previousGenerationId` and `previousEnvelopeId` when replacing an earlier generation, proving the old/new linkage. It never overwrites the old record implicitly.

### 6.2 Signed plaintext and encryption

The encrypted signed inner body contains:

- protocol version and `offline-discovery-request` kind;
- `requestId`, request nonce, original creation/expiry;
- `clientLeaseId`, publication ID, `leaseSequence`, `semanticRevision`, and exact `generationId`;
- recipient mailbox ID and encryption-key identity;
- sender's one-logical-request Ed25519 public key;
- bounded request payload and fresh reply mailbox/direct-contact capability;
- `previousGenerationId/previousEnvelopeId` when applicable.

It contains no original content/ciphertext, permanent content reference, or public private contact address. The recipient verifies the signature, recomputes `requestId`, and requires all duplicated outer/inner bindings to match because the existing NaCl `box` API has no associated-data parameter.

Reuse `mailbox-v2.ts:188` and `:240`:

- fresh ephemeral X25519 key and random 24-byte nonce per logical envelope generation;
- XSalsa20-Poly1305 encryption to the exact mailbox public key in that generation;
- persisted ciphertext for exact retries, never re-encryption during an ordinary retry;
- fixed **8 KiB** padded plaintext, at most **4 KiB** meaningful plaintext, and **16 KiB** maximum serialized stored envelope.

Padding does not hide request count, timing, mailbox identity, or index activity. A fresh sender request key per logical request limits sender linkage but proves neither real-world identity nor claim truth.

### 6.3 Exact replay, replacement, and conflicts

For one `replicaKey`:

- Complete byte equality returns the durable prior result without growth or another admission spend.
- Different signed/ciphertext bytes retain the existing and incoming bounded records, return `conflicting_request`, and quarantine delivery of that generation.
- A valid refreshed generation has a different `replicaKey`; it links the previous generation and shares the lease-wide count/byte quota and logical recipient dedup.
- At most one active and one draining generation binding per logical request are admitted. Further redeposit returns `drain_required` until the older generation is ACKed or expires. This bounds old-generation obligations rather than permitting unlimited refresh churn.

Admission binds the exact immutable deposit generation. Exact replay is free; refreshed redeposit is a new admitted deposit generation but the same logical request for recipient notification purposes. Entitlement-level issuance limits distinct logical requests, preventing free permanent regeneration.

### 6.4 Admission and replica evidence

A new deposit requires:

1. Referenced generation is current and active at that relay.
2. Digest, `clientLeaseId`, mailbox ID, and encryption key match the deposit.
3. `now < index.expiresAt`, no supersession/withdrawal, and request is unexpired.
4. Outer signature, schema, size, freshness window, and absolute expiry are valid.
5. Inclusive per-lease/global capacity and journal/ACK/conflict reserves exist **before admission is spent**.
6. One admission capability binds the exact immutable deposit.

Replicas receive signed deposit and admission evidence, preventing sync from bypassing admission. Replicated presentation resolves as the same spend/replay in shared admission history, not a second charge. If verification is unavailable, replication can stall without endangering existing obligations or ACK maintenance.

Relays cannot inspect semantic spam inside ciphertext. Admission, rate limits, quotas, and recipient-local blocking are the controls. Recipient ACKs for accepted, declined, invalid, and duplicate requests have identical wire form.

### 6.5 Stored, queued, and replica loss

- **`stored`:** one relay fsynced the exact deposit.
- **`queued`:** three selected replicas returned signed receipts binding relay ID, `replicaKey`, ciphertext digest, generation, and request expiry.
- **`outcome-unknown`:** an attempt may have committed but required evidence is missing.
- **`expired`:** immutable request expiry passed.

The existing one-relay ACK (`server.ts:1261`) is only `stored`. Neither `stored` nor `queued` means recipient receipt, consent, response, or content delivery.

Under the prototype's three-receipt `queued` contract, losing any two of those selected replicas leaves at least one evidenced durable copy. It does not promise three surviving copies, recipient delivery, or safety against false/Byzantine receipts. Repair must restore three selected copies. Loss of the sole `stored` replica loses that copy; exact sender outbox retention permits retransmission while unexpired.

The sender retains its exact outbox entry until sufficient `queued` evidence, recipient ACK, or immutable expiry. `outcome-unknown` never clears merely because a timeout occurred.

### 6.6 Drain, withdrawal, and anti-entropy

Request and index expiries are separate absolute timestamps. Request lifetime is at most **7 days from original creation**; refresh/retry never extends it. Reject processing at `now >= request.expiresAt`. A stale search result returns `stale_index`; redeposit uses the same logical `requestId` and unchanged expiry.

| Index event | New deposits to old generation | Accepted old-generation requests |
| --- | --- | --- |
| Ordinary refresh/semantic supersession | Reject; use current generation | Drain until generation-scoped ACK or request expiry |
| Natural lease expiry | Reject | Drain until ACK or request expiry |
| Explicit withdrawal/key-compromise revocation | Reject | Purge every generation without further delivery |
| Request expiry | Reject | Purge envelopes only after ACK/dedup/withdrawal retention rules permit |

Drain retains the historical signed generation, mailbox authentication, old mailbox private keys, and replica routes until ACK/expiry. Old-generation placements remain eligible for anti-entropy.

Every sync event carries `clientLeaseId`, `generationId`, `replicaKey`, event kind (`deposit`, `ACK`, `withdrawal`), and original request expiry. An ACK applies only to its exact generation; an old-generation ACK cannot remove a refreshed deposit. ACK-before-deposit leaves a tombstone that suppresses later arrival. Withdrawal applies to every generation and suppresses later stale deposits. ACK/withdrawal tombstones remain until no stale deposit is admissible, including the longest live request/conflict window.

Recipient dedup remains `(clientLeaseId, requestId)` across generations. Redelivery/redeposit produces no second visible request. Compaction preserves deposit/ACK/withdrawal causal barriers and all live dedup/conflict expiries; latest-ACK-only compaction is unsafe (`mailbox-journal-compaction.ts:48`).

### 6.7 Recipient inbox-before-ACK

1. Merge reachable replica responses by generation-scoped storage key; an empty stale replica cannot hide another's envelope.
2. Validate expiry, relay response, encryption, inner signature, generation binding, and logical ID.
3. Atomically persist encrypted local inbox/dedup keyed by `(clientLeaseId, requestId)`.
4. Expose one durable inbox item without a second retry notification.
5. Only after local commit, send owner-signed ACKs for all known generation copies.
6. Replicate each observed-remove ACK with the original request expiry.
7. Drop tombstones only after no legitimate/stale deposit is admissible.

Unknown-ID ACKs are refused and create neither tombstones nor admission-free storage. Signed ACK proofs may repair a missing envelope only within prepaid reserves. Storage ACK is maintenance, not consent, acceptance, read receipt, or original delivery.

### 6.8 Crash and retry boundaries

| Actor/failure | Required behavior |
| --- | --- |
| Sender before transmission | Persist encrypted outbox, immutable deposit, admission capability, generation binding, and original expiry. |
| Sender crash while sending | Reopen `outcome-unknown`; retry identical deposit/admission with fresh transport ID. |
| Deposit reply lost | Exact full-byte retry returns duplicate/stored or sufficient receipts; no second request/spend. |
| Admission spent before append | Exact admission replay can commit after restart. |
| Relay crash after append before reply | Journal replay restores envelope; retry is duplicate with no growth. |
| Relay crash after ACK append before reply | Retry reports zero newly acknowledged envelopes and appends no row. |
| Recipient crash after inbox commit before ACK | Redelivery resolves local dedup, creates no second item, then retries generation-scoped ACK. |
| Recipient crash after ACK before reply | Redelivery remains deduplicated; synchronized tombstone prevents eventual redelivery. |
| Conflicting retry | Retain bounded conflict evidence and quarantine; never replace by arrival order. |
| Uncertain journal append/rename | Stop the poisoned writer and reopen rather than guessing durability (`local-encrypted-state.ts:87`, `operation-log.ts:276`). |
| Compaction crash | Retain old and replacement journals until the complete causal barrier and new file are durable. |
| Recipient keys/client lost | Requests expire undecryptable/undelivered; no hidden service reconstructs the client/originals. |

Sender retry uses bounded exponential backoff with jitter while running/online and stops at immutable expiry. Receiver polling uses the bounded maintenance schedule. The generic saved-request outbox creates a fresh signed request on retry (`private-request-outbox.test.ts:60`); that behavior must not be copied.

## 7. Inclusive prototype quota ledger

### 7.1 Scope

The quota is **fully inclusive per selected replica per `clientLeaseId`**, across all generations. It includes envelopes, future ACKs, journals, admission/replay evidence, dedup, old-generation authentication, conflicts, replica receipts, and temporary metadata. It is not an envelope-only quota. Client-local outbox/inbox/originals and relay-global storage are separately bounded.

The following maxima are prototype costing rules, not measurements or approved limits. They deliberately reserve one conflict and two generation bindings per logical request, including the complete envelope/ACK and journal obligations of both active and draining generations, so those cases cannot consume unbudgeted storage or metadata.

### 7.2 Maximum charge per logical request

| Component | Derivation | Maximum bytes |
| --- | ---: | ---: |
| Active + draining envelopes + prepaid ACKs | `2*(16,384+4,096)` | 40,960 |
| Both deposit/ACK journal sets, current+replacement | `2 generations*2*((16,384+4,096)+(4,096+4,096))` | 114,688 |
| Admission evidence + replay record | 8,192 + 4,096 | 12,288 |
| Recipient/storage dedup metadata | fixed allowance | 1,024 |
| Active + one draining generation | `2*(4,096 signed index + 2,048 route/auth)` | 12,288 |
| One conflicting operation + quarantine metadata | 16,384 + 4,096 | 20,480 |
| Five signed replica receipts | `5*1,024` | 5,120 |
| Temporary/atomic metadata allowance | fixed allowance | 16,384 |
| **Total per logical request** | | **223,232** |

| Component | Bytes |
| --- | ---: |

### 7.3 Explicit caps and headroom

The prototype chooses **16 logical requests** and **4 MiB inclusive bytes per selected replica per lease**:

\[
16\times223,232+53,248
=\boxed{3,624,960\ \text{B modeled peak}}
\]

\[
4,194,304-3,624,960
=\boxed{569,344\ \text{B headroom}}
\]

The count cap rejects the 17th distinct logical request even if bytes remain. Actual serialized-byte enforcement remains independent of count: the byte cap rejects any actual encoding/ledger overflow even below 16. Both apply across every generation. Exact duplicates and already-prepaid ACK/withdrawal maintenance remain possible at full quota because they add no commitments. New work is refused without destroying accepted work.

At five desired replicas, reserving the full allowance is `5*4 MiB = 20 MiB` per lease; the three-receipt queued tier reserves 12 MiB across those selected replicas. These are prototype envelope arithmetic, not proof of relay-global fit. The existing 128 MiB relay mailbox default (`runtime.ts:104`) is a comparison only; journal storage remains separate and the number of leases must be explicitly bounded by the prototype deployment.

The sender's local outbox remains bounded by the existing **64 operations / 16 MiB** evaluation envelope. A local per-request record reserves exact deposit/ciphertext, admission evidence, five receipts, outbox metadata, and snapshot replacement. Recipient inbox/dedup and historical mailbox keys are separately charged in encrypted local snapshots. No client-local byte fit is inferred from the relay quota.

## 8. Resource and availability evaluation boundary

For 10,000 maximum-size indexes:

\[
10,000\times4,096\times5
=\boxed{204,800,000\ \text{B raw current index payloads}}
\]

This excludes revisions, journals, matches, mailboxes, tombstones, conflicts, allocation metadata, repair, and replacement peaks. It is not a fit claim.

The full resource ledger must add the section 7 mailbox charges, index journals, old generations, stable match/notification records, client snapshots, temporary files, and every retry/failure. Network/work includes discovery, admission, TLS, padding, all physical replica edges, polling, ACK/withdrawal propagation, compaction, expiry cleanup, failed attempts, signature verification, and full-mailbox scans. Original transfer is a subsequent operation included in lifecycle traffic. Cold model artifacts/initialization and idle lease maintenance count against K7.

### Frozen evaluation denominators

- **Discovery:** all valid submitted discovery attempts against the selected relay/service conditions; success requires the correct unexpired signed discovery result within the deadline.
- **Offline-request queueing:** all valid deposit attempts; success requires the declared `stored` or `queued` evidence level, reported separately, within the deadline.
- **Original fulfillment:** all valid authorized content requests after grant. Offline owner/requester outcomes count as failure or undelivered, never disappear from the denominator.
- **Online-eligible fulfillment:** a separately reported secondary subset where both clients are online at attempt start. It cannot replace the all-request fulfillment denominator.

K1/K8 owner review must approve these definitions before using them as product KPIs. Index availability is never substituted for original fulfillment.

These are not download sizes, RSS, or runtime lower bounds. Scales, unquantized tensors, tokenizer, KV cache, runtime, application, and temporary files are additional/different. Official sources: [3B](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct), [1.5B](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct), and [0.5B](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct).

[Qwen's benchmark](https://qwen.readthedocs.io/en/latest/benchmark/speed_benchmark.html) reports GPTQ-Int4 one-token-input A100 memory of 2.06 GB for 3B, 1.18 GB for 1.5B, and 0.48 GB for 0.5B. These are not MLX/llama.cpp predictions, but they falsify treating parameter arithmetic as total memory.

Begin with 1.5B as default hypothesis and 3B as challenger. Admit 0.5B only after larger candidates fail resource gates and only if it independently passes every quality/privacy/safety gate. No model is selected.

The 3B model uses the **Qwen Research License**, including non-commercial terms and a requirement to request commercial licensing; 1.5B/0.5B use Apache 2.0. The [3B license](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/raw/main/LICENSE) requires separate intended-use/distribution review independent of quality.

### 10.3 Runtime and cache identities

Primary comparison uses official Qwen GGUF **Q4_K_M** artifacts for all three sizes, pinned llama.cpp, greedy decoding, identical prompts/schema/token bounds: [3B GGUF](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF), [1.5B GGUF](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF), and [0.5B GGUF](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF).

Apple Silicon measures llama.cpp Metal and CPU-only four-thread arms. If the best quality-viable model misses latency/energy goals, an optional [MLX-LM](https://github.com/ml-explore/mlx-lm) 4-bit conversion of that same model must pin converter, bits/group size, source revision, and artifact hashes. Windows/Linux x64 uses llama.cpp CPU-only four threads/memory mapping, separately from macOS. No initial Transformers.js generation arm is added.

Freeze **2,048 input tokens, 256 output tokens, greedy/temperature 0, fixed seed, one inference, and no persistent cross-user prompt/KV cache**. Reject over-limit input. No rotating KV compression in the primary arm. “4-bit” alone is never cache identity.

The three stages remain independent:

1. Generative proposal: original local text → validated canonical summary/intent JSON; no authority over item type, consent, eligibility, IDs, lease, signature, or publication.
2. Embedding: approved deterministic rendering → existing Nomic FP32 vector, with Nomic/rewrite/prefix/pooling/dimensions/thresholds fixed for the first comparison.
3. Deterministic transformation: vector + projection/group/epoch → 512-bit LSH. Neither digests nor LSH prove truth/confidentiality.

Use a no-generation control and the same frozen Nomic/LSH/matching path for every generator. Report English and Spanish separately; cross-language pairs are secondary diagnostics.

Structured output contains only `schema_version`, `language` (`en`, `es`, `mixed`, `unknown`), bounded nonempty `summary` and `intent`, and at most six normalized unique bounded `topics`. Require no additional properties, duplicate-key rejection, NFC, UTF-8 limits, control/bidi rejection, topic dedup, and hard byte/token ceilings. Reject Markdown fences, trailing prose, non-JSON values, and missing EOS. No autonomous semantic repair. [llama.cpp grammars](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md) are only a first barrier; unsupported features and `uniqueItems` require independent validation.

Use separate encrypted generation, embedding, and final-index cache records. Generation identity includes original input, item type, prompt/schema/preprocessing, model/tokenizer/chat-template/artifact hashes, runtime/build/backend, quantization, decoding, and token bounds. Embedding identity includes canonical rendered text and complete Nomic/runtime/rewrite/prefix/pooling identity. Fingerprint identity includes vector and projection/group/epoch. Cache the exact signed index.

Cache hits must be byte-identical with zero generator invocations across warm/cold/restart/concurrent calls. Final-index replay must work with models unavailable and networking disabled. Any identity change, corrupt/truncated/tampered/interrupted entry, or validation failure cannot reuse/publish an incompatible result. Regenerated mismatch is a new semantic revision, never a retry or silent replacement.

### 10.4 Model evaluation and selection gates

Freeze candidate, corpus, seeds, commands, thresholds, and destinations before execution. Use at least three counterbalanced runs per model/runtime/device without concurrent host workloads; report counts, p50/p95/p99, variation, and 95% confidence intervals.

Measure:

- cold acquisition hosts/redirects, artifact/on-wire bytes/retries, elapsed time, temporary/final disk, BOM/hash reconciliation, and energy, including interruption/corruption/offline restart;
- startup initialization/model/tokenizer load, first token, and validated JSON across empty-cache cold, populated-cache cold process, and warm model;
- generation latency by language/input size, prefill/decode, timeout/cancellation, and joules per valid output;
- generation alone, Nomic alone, serialized generation→Nomic, and co-resident diagnostics with process-tree RSS and Apple Silicon memory-pressure/GPU evidence;
- fixed-cardinality and maintenance idle for at least 30 minutes with matched physical incremental power;
- zero post-acquisition inference network requests and no original/private prompt/true embedding/generated private cache in logs or telemetry.

Use independent English/Spanish holdouts with **≥1,000 queries and ≥10,000 publications**, labels independent of the tested models, frozen splits, and frozen notification thresholds. Measure Recall@5, candidate-filter quality, notified precision, and FPR against no-generation. Human-audited subsets score intent correctness, unsupported facts, omitted constraints, negation/number/entity errors, language preservation, and need/offer inversion; no LLM judge.

Run separate reconstruction and known-text attacks among **100 candidates**. Audit any proposed public summary directly. Adversarial inputs cover prompt injection, secret/contact exfiltration, canaries, fabricated identities/numbers/negations, HTML/URLs/scripts, Unicode controls/homoglyphs, oversized/repeated input, malformed JSON, extra keys, duplicate topics, and authorization/item-type manipulation.

Predeclared gates remain:

- each language: Recall@5 ≥90%, notified precision ≥80%, FPR ≤5%; threshold-straddling intervals are inconclusive;
- reconstruction and known-text identification each ≤5%; direct original/private-contact disclosure or unexpected inference networking blocks;
- full application meets K7 memory/idle CPU/idle power and K1 deadlines, with cold costs visible;
- 100% independent structured validation and byte-identical/invocation-free cache hits; any invalid/malicious published output fails;
- proposed ≤1% unsupported-critical-fact rate per language and zero critical authorization/contact fabrication, subject to owner confirmation;
- select 3B over 1.5B only with proposed ≥3-point Recall@5 gain in the weaker language, no >2-point regression in the other, all gates passing, and license clearance;
- select 0.5B only after larger resource failures and only with every gate passing;
- if no model satisfies the joint gates, stop the local-generative candidate and retain deterministic control.

Model quality does not resolve K5/K6, and no model arm is required for the first protocol spike.

## 12. Executable prototype test matrix and stop criteria

No tests were run for this revision. The following are future frozen tests after owner authorization.

### 12.1 Lease/index/delivery controls

| Control | Positive assertion | Negative/falsifying assertion |
| --- | --- | --- |
| Exact replay | Restart/lost reply returns identical full bytes/signature/counters and one notice/spend. | Generator/model rerun, changed bytes, second allocation/spend/notice fails. |
| Lease refresh | Lease sequence/expiry advance; semantic revision and match/notice IDs remain stable; no re-match. | Any dedup clear, rebuild-generated duplicate notice, or semantic-field change fails. |
| Semantic revision | Controlled path changes semantic fields and match evaluation while preserving dedup/audit. | Retry treated as revision, stale repair changing identity, or repeated logical notice fails. |
| Schema/commitment | Valid signed operation and authorized original verification succeed. | Unknown fields, wrong signature/key/length/commitment, public private data, or cross-publication binding fails before mutation. |
| Writer/stale backup | Reconciled writer resumes at correct counters; restored backup remains read-only until reconciliation. | Stale overwrite or multi-writer automatic fan-out fails. |
| Conflict/rollback | Higher valid sequence converges; bounded conflicting operations remain retained/quarantined. | ID-only duplicate acceptance, discarded incoming conflict, or arrival-order replacement fails. |
| Expiry/withdrawal | Expiry boundary and terminal tombstones converge across arrival orders/restarts. | Expired/withdrawn search/match/delivery or immediate global-withdrawal claim under partition fails. |
| Replica repair/availability | Missing index is restored from exact signed bytes while owner is offline; evidence classes remain distinct. | Fabricated inventory, owner-liveness-as-possession, or all-replica-loss recovery claim fails. |
| Authorized content | Explicit grant delivers channel-encrypted exact original and verifies commitment. | No consent, wrong requester/channel/generation, expired/withdrawn grant, plaintext journal, or offline original delivery fails. |
| Current policy/admission | Exact replay preserves admission; reconnect authenticates current policy. | Revoked-policy acceptance, changed request on same proof, or double charge fails. |

### 12.2 Mailbox and quota matrix

1. Exercise ordinary refresh and semantic supersession with the same mailbox: redeposit gets a new `replicaKey`, stable logical `requestId`, unchanged expiry, one recipient inbox item, and no old-ACK deletion of the new generation.
2. Exercise same-generation exact duplicate and changed ciphertext: full-byte comparison returns prior result or retains/quarantines conflict; no ID-only acceptance.
3. Force ACK-before-deposit, withdrawal-before-deposit, stale replica replay, restart, and compaction: no ACKed/withdrawn request resurrects.
4. Drain one old generation and redeposit once; a further redeposit returns `drain_required` until ACK/expiry. All generations share the same lease count/byte ledger.
5. Lose one/two of three `queued` replicas and verify one evidenced copy remains and repair restores three. Loss of the sole `stored` copy is not described as queued durability.
6. Crash before/after deposit append, reply, inbox commit, ACK append/reply, withdrawal, journal rename, and compaction. No lost acknowledgement, duplicate notice, second admission spend, or uncertain-as-success is permitted.
7. Fill exactly 16 fully charged logical requests, each with active+draining generations, conflict evidence, and prepaid ACK/withdrawal state, at 3,624,960 B modeled peak; reject the 17th. Force actual serialized-byte overflow below 16 and reject independently of the count. Exact duplicates and prepaid ACK/withdrawal maintenance still work at full quota without growth.
8. Prove conflict, second-generation, receipt, admission, dedup, journal-replacement, and temporary metadata charges consume the declared slots; no zero-metadata accounting or old-generation escape.
9. Lower configured quota below accepted obligations: startup refuses rather than discarding them. Unknown-ID ACK creates no state.
10. Concurrent deposits/ACKs/expiry cannot starve or skip anti-entropy cursors. Closed clients perform no refresh/polling/retry work.
11. Verify UI never equates stored/queued/storage ACK with consent/content delivery and that all offline fulfillment outcomes remain in the primary denominator.
12. At maximum cardinality/retry/poll load, measure process-tree RSS, CPU, disk/fsync and replacement peaks, full-edge network, work, and physical power against K7; any breach stops the candidate.

### 12.3 Model/cache controls

- Independently validate every accepted output; reject malformed JSON, extra/duplicate fields, missing EOS, Unicode/control abuse, excessive topics, and policy/identity manipulation.
- Prove byte-identical invocation-free cache hits and offline/model-unavailable final-index replay.
- Change every model/prompt/schema/tokenizer/artifact/runtime/quantization/scope/embedding/projection/source identity; incompatible reuse fails.
- Inject interrupted/corrupt/tampered model/cache artifacts; none publishes or becomes a successful cache entry.
- Retain no-generation control and per-language reporting; Spanish failure cannot be averaged away.
- Interrupt cold acquisition and restart offline; charge all bytes, temporary disk, startup, and energy.
- Any direct original/private-contact disclosure, unexpected inference networking, malicious publication, or critical authorization/contact fabrication blocks selection.

### 12.4 Stop criteria

Stop the prototype or current arm on any safety/privacy failure, duplicate logical effect, stale resurrection, missing generation/admission evidence, quota escape, uncharged temporary/retry work, lost accepted acknowledgment, unsupported durability claim, resource-limit breach, unapproved product/AI scope change, unresolved model license, or failure of the predeclared model gates. Do not relax limits after observation or convert refusal of a legal prototype workload into acceptance.
