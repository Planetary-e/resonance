# DEC-020 client-held content and leased discovery architecture

**Status: REVISE — independent review found protocol corrections required before any implementation decision.** This is a consolidated architecture and future evaluation specification, not an implementation, model-selection acceptance, production/K/R acceptance, or release. Every proposed numeric limit is an **evaluation-only parameter**, not an approved product threshold. No model, dependency, campaign, or product-test execution is authorized by this document. See `../evals/v04-dec020-client-held-discovery-review-2026-11-22.md`.

DEC-020 explores a product/storage change; it does not replace the rejected FEAT-001 recovery architectures or approve an implementation. Existing K5/K6 failures and all R/K gates remain open.

## 1. Proposal, invariants, and non-goals

Original content remains in the client's encrypted local storage. A local generative stage may propose a summary/intent object, but deterministic local policy and user review remain responsible for item type, authorization, consent, identifiers, lease times, and publication. The existing Nomic embedding and random-hyperplane LSH pipeline converts the approved derivative into the matching fingerprint. The network stores only signed, leased discovery indexes and bounded encrypted offline **requests**, not original content or generated private caches.

The owner supplies original bytes only through an authorized online private delivery path. A mailbox can hold a request while its recipient is offline; it cannot fulfill the original while the holding client is offline. The requester must also return online to receive a response.

The following claims are explicitly distinct:

- **Index availability:** a signed index is retained or repairable on replicas.
- **Owner liveness:** a client recently answered a private challenge.
- **Original possession/retrievability:** an authorized response supplied bytes that verify against the original commitment.

A valid lease, replica receipt, owner challenge, queued request, or recipient storage ACK does not prove original truth, consent, possession, or future delivery. There is no hidden always-on service or permanent network content archive.

This architecture does **not** replace authority, policy, witness, issuer, wallet, configuration, or other control-plane recovery. Index replication is not K2/K3 recovery evidence.

Owner decisions still required include whether generated summary/intent text can ever be network-visible (the safe default is **no**), whether K1/K8 measure original fulfillment separately from discovery, lease/mailbox values, client backup responsibility, stable lease pseudonymity, and local generative-model approval. Multi-device simultaneous writers are out of scope: one publication has one active writer, and restored/stale writers must reconcile before writing.

## 2. Data boundaries and exact local transaction

### Public or relay-visible data

Only the signed leased index, its fingerprint and commitment, public mailbox encryption information, availability/replica evidence, encrypted mailbox envelopes, and signed maintenance records are network-visible. No public record may contain:

- raw original content;
- generated summary/intent text under the default private derivation;
- the true embedding;
- a private contact address;
- a commitment key;
- an unsalted original-content hash or other confirmation oracle.

Generated text is another potentially sensitive representation, not an anonymizer. Existing LSH source explicitly warns that public projections are not encryption (`packages/core/src/lsh.ts:8`). The existing real-text screen measured 86–97% reconstruction and 100% known-text identification (`docs/evals/scoped-fingerprint-real-2026-10-18.md:19`). Summaries, embeddings, HMAC commitments, and signatures create no confidentiality claim.

### Client-private data

Before any network submission, one bounded, flushed, encrypted local transaction must retain:

- exact original bytes for each revision;
- generated summary/intent, true embedding, and public fingerprint;
- the original commitment key;
- publication signing and mailbox private keys;
- exact serialized signed operation/frame, not merely a reproducible model request;
- `nextSequence`, current acknowledged operation, pending intent, withdrawal state, and dedupe/notice state.

`local-encrypted-state.ts:87` already supplies bounded encrypted atomic replacement and flush-failure handling; `packages/node/src/store.ts:755` separately encrypts raw text and embeddings. The canonical original is the exact user-entered byte sequence. Unicode normalization, trimming, summary generation, and embedding preprocessing are versioned derivatives and never alter the committed bytes.

## 3. Leased index and original commitment

### 3.1 Signed schema

Reuse publication-scoped Ed25519 keys, opaque IDs, canonical signed bodies, sequence numbers, and strict unknown-field rejection from `packages/core/src/protocol-v2.ts:77`. Add a new versioned operation rather than overloading v2 with unsigned semantics:

```text
LeasedIndexV1 {
  version: 1
  kind: "leased-discovery-index"
  publicationId
  clientLeaseId
  sequence
  publicationKey
  groupId
  itemType

  derivationId       // digest of the complete frozen derivation manifest
  fingerprint {
    algorithm: "random-hyperplane-lsh"
    bits: 512
    epoch
    value
  }

  original {
    commitmentAlgorithm: "hmac-sha256"
    commitment
  }

  mailbox { id, encryptionKey }
  createdAt
  expiresAt
  signature
}
```

`clientLeaseId` is the shared quota/dedup pseudonym required by the mailbox design. It deliberately links refreshed generations; making generations unlinkable instead requires a separate quota credential and changes the privacy/resource contract. This field integration and its owner/privacy approval remain review items.

`derivationId` pins the summary/intent schema and prompt, generator model/revision/artifacts/decoding configuration, text preprocessing, embedding model/revision, quantization, and LSH configuration. It contains neither private input nor generated private output. Deterministic local policy, not the generator, assigns `itemType`.

### 3.2 HMAC commitment

For each original revision, generate an independent random 32-byte commitment key \(K\), retained only in the encrypted client store:

```text
C = HMAC-SHA-256(
      K,
      "resonance:leased-content:v1\0" ||
      unsigned_64_bit_big_endian(length(originalBytes)) ||
      originalBytes
    )
```

Only `C` enters the signed index. `K` is disclosed inside an authorized encrypted content response so the recipient can verify the exact original bytes. This uses HMAC's shared-secret verification property in [RFC 2104 §§1–3](https://www.rfc-editor.org/rfc/rfc2104.html). Anyone receiving `K` can subsequently test guesses for that revision, so its disclosure scope is part of the grant. A public unsalted content hash is never used.

## 4. Lease state, replay, migration, and availability

### 4.1 Evaluation parameters

- Original/generated embedding input: at most **8,192 bytes**, matching `packages/core/src/embedding.ts:33`.
- Canonical signed index: at most **4,096 bytes**.
- Maximum lease: **7 days**, matching `packages/node/src/commands/publish.ts:93`.
- Refresh when half the lease remains, at most once per **24 hours**. Replaying unchanged bytes is not a refresh.
- No continuous owner heartbeat; optional availability challenges expire within **3 seconds**.
- Existing placement evaluation uses five desired replicas and three healthy minimum, with 64-operation inventory/handoff batches.

A refresh increments `sequence`, retains the same content commitment/derivation/fingerprint, and extends `expiresAt` only through a new owner signature. A semantic/model/content change also increments `sequence`, changing the appropriate fields. Refresh must preserve existing match/notification dedup identity; the current update path clears pair notification dedup before re-matching (`packages/relay/src/matching-engine.ts:108`) and cannot be reused unchanged.

Expiry is local policy independent of signature validity (`packages/core/src/protocol-v2.ts:293`). At `now >= expiresAt`, the index leaves matching, search, refresh, and delivery. Relays do not fabricate owner-signed expiry tombstones.

A signed withdrawal/supersession tombstone is terminal and dominates live revisions regardless of arrival order (`packages/relay/src/publication-store.ts:53`). Withdrawal stops network discovery/delivery but does not delete the local original. Retain terminal evidence until all related matches, mailbox envelopes, grants, and conflicts expire, and at least through the maximum preceding live-index lifetime plus declared clock skew. Tombstones are not proof of physical erasure.

### 4.2 Exact replay versus a new revision

- **Transport retry, crash recovery, missing-replica repair:** replay the stored signed bytes with unchanged sequence/signature. Never rerun generation.
- **Deliberate regeneration, model migration, content edit:** create sequence `n+1`; this is a new revision, not a retry.
- **Original available but signed index lost:** generation cannot promise byte identity. Recover a user-held exact backup or publish a new publication/revision and let the old lease expire.
- **Original lost:** no possession proof, refresh, or delivery is permitted even if keys/index survive.
- **Owner key lost:** refresh, withdrawal, and authorization as that publication become impossible; the old lease expires.

Relays need only signed operations. The current server rebuilds its derived matching cache from the journal (`packages/relay/src/server.ts:4300`), so no relay needs original bytes or true embeddings.

### 4.3 Conflict, rollback, and partitions

| Case | Required behavior |
| --- | --- |
| Exact duplicate | Return the durable prior result; no second allocation, admission spend, match, or notice. Existing admission replay remains bound to the exact request (`server.ts:4247`). |
| Lost acknowledgement/crash after send | Preserve `outcome-unknown`; retry exact bytes using the existing outbox model (`publication-outbox.ts:48`). |
| Lower sequence | Return `stale` and authenticated current-state evidence during reconciliation. |
| Same sequence, different signed operation | Return `conflict`; retain both and quarantine automatic fan-out/matching. |
| Tombstone versus live revision | Terminal tombstone wins on every replica receiving it. |
| Stale client backup | Reconcile before writing; never overwrite a newer relay-observed revision automatically. |
| Isolated replica | It may serve an older unexpired signed record. Acknowledge withdrawal only after the declared replica set durably confirms it; document the residual partition window. |

The existing five-desired/three-healthy placement and bounded repair (`packages/relay/src/replica-placement.ts:27`) are reusable for indexes, but do not establish owner/content availability.

### 4.4 Availability evidence classes

1. **Replica custody:** signed `stored`/`already-stored` receipts and receipt-authorized inventory responses establish acknowledgement/observation of an exact signed revision (`packages/core/src/relay-replication.ts:222`).
2. **Owner liveness:** an optional private rate-limited response binds `{challenge, verifier, publicationId, sequence, indexDigest, issuedAt, expiresAt}`.
3. **Original possession/retrievability:** established only by an authorized content response whose bytes verify against the commitment.

Search UX may distinguish `lease-valid`, `owner-attested-at`, and `owner-offline/unknown`, but none means guaranteed content availability. Replication can continue while the owner is offline. One missing replica index is repaired from another replica or returning owner using exact signed bytes. If every replica loses it while the owner is offline, discovery waits for a return. Permanent owner/original loss means permanent content loss and eventual expiry.

## 5. Authorized online original delivery

Reuse consent, fresh relationship keys, channel secrets, sequenced operations, encrypted private forwarding, durable pending outbound state, and inbound dedup from `packages/core/src/relationship-v2.ts:98`, `packages/core/src/channel-v2.ts:115`, and `packages/node/src/pairwise-channel-v2.ts:222`.

Use a content-specific exchange:

1. Requester sends signed `ContentRequest {requestId, channelId, publicationId, sequence, indexDigest, contentCommitment, createdAt, expiresAt}` inside the active relationship.
2. Owner verifies channel/counterparty, current consent, exact index revision, local withdrawal state, and original presence. Match or relationship consent alone does not authorize original delivery; require an explicit owner grant or previously chosen scoped disclosure policy.
3. The single-use grant binds requester, request ID, channel, exact index digest, commitment, and expiry no later than lease expiry.
4. While online, the owner sends original bytes and `K` in a signed, sequenced, channel-encrypted response over the live private route. Relays may forward ciphertext but must not journal original responses as an offline archive.
5. Recipient verifies request/grant/channel bindings and recomputes the commitment before display.

If the index changed while a request was pending, either deliver the explicitly retained old revision under a valid grant or return `superseded`; never substitute new bytes silently. Withdrawal before transmission denies delivery. Already received content cannot be recalled.

## 6. Bounded encrypted offline-request mailbox

### 6.1 Three identifier classes

1. **Logical `requestId`:** `oreq_` plus base64url of 32 bytes truncated from SHA-512 over a domain-separated canonical stable body containing request kind/payload, a 128-bit random request nonce, original `createdAt/expiresAt`, sender request public key, recipient `clientLeaseId`, and reply capability. Exclude index sequence, index digest, and mailbox ID so the logical request survives refresh without an expiry extension. The random nonce prevents a predictable-text dictionary ID.
2. **Storage `envelopeId`:** `env_` plus base64url of 32 bytes from `SHA-512(domain || mailboxId || requestId)`. Replica dedup key is `(mailboxId, envelopeId)`. Exact retries carry identical signed deposit and ciphertext; different bytes for an existing key return `conflicting_request` without mutation.
3. **Per-attempt transport ID:** fresh for each private-transport exchange, never used for mailbox dedup, admission replay, or user notification identity.

Fetch/ACK RPC IDs are separate maintenance IDs.

### 6.2 Signed plaintext and encryption

The encrypted signed inner body contains:

- protocol version and `offline-discovery-request` kind;
- `requestId`, request nonce, original creation/expiry;
- `clientLeaseId`, recipient index ID/sequence/exact signed-index digest;
- recipient mailbox ID and encryption-key identity;
- sender's one-logical-request Ed25519 public key;
- bounded request payload and fresh reply mailbox/direct-contact capability.

It contains no original content/ciphertext, permanent content reference, or public private contact address. The recipient verifies the signature, recomputes `requestId`, and requires every duplicated outer/inner binding to match because the existing NaCl `box` API has no associated-data parameter.

Reuse the existing mailbox cryptography (`packages/core/src/mailbox-v2.ts:188` and `:240`):

- fresh ephemeral X25519 key and random 24-byte nonce per logical envelope;
- XSalsa20-Poly1305 encryption to the exact mailbox public key in that signed index generation;
- persisted ciphertext for exact retries, never re-encryption during an ordinary retry;
- fixed **8 KiB** padded plaintext buckets, with at most **4 KiB** meaningful plaintext and **16 KiB** maximum serialized stored envelope.

Padding reduces exact-length leakage only. It does not hide request count, timing, mailbox identity, or index activity. A fresh sender request key per logical request limits sender linkage but proves neither real-world identity nor claim truth.

### 6.3 Admission and replica evidence

A new deposit requires:

1. The referenced signed generation is current and active at that relay.
2. Digest, `clientLeaseId`, mailbox ID, and mailbox encryption key match the deposit.
3. `now < index.expiresAt`, no supersession/withdrawal, and the request is unexpired.
4. Outer signature, schema, size, freshness window, and absolute expiry are valid.
5. Per-lease/global capacity and journal/ACK reserves exist **before admission is spent**.
6. One admission capability binds the exact immutable deposit; exact replay returns the prior replay result without another entitlement spend.

Replicas receive the signed deposit and admission evidence, so replica sync cannot bypass sender admission. A replicated presentation resolves as the same spend/replay in shared admission history, not a second charge. If admission verification is unavailable, replication can stall without endangering existing obligations or ACK maintenance.

Relays cannot inspect semantic spam inside ciphertext. Admission, rate limits, per-recipient quotas, and recipient-local blocking are the available controls. Recipient ACKs for accepted, declined, invalid, and duplicate requests have identical wire form so maintenance does not reveal the decision.

### 6.4 Index drain, withdrawal, and request expiry

Request and index expiries are separate absolute timestamps. Proposed request lifetime is at most **7 days from original creation**; refresh/retry never extends it. Reject processing at `now >= request.expiresAt`. A stale search result returns `stale_index`; rediscovery may redeposit the same logical `requestId` against a fresh generation with unchanged original expiry.

| Index event | New deposits to old generation | Already accepted old-generation requests |
| --- | --- | --- |
| Ordinary refresh/supersession | Reject; use current generation | Drain until ACK or request expiry |
| Natural lease expiry | Reject | Drain until ACK or request expiry |
| Explicit withdrawal/key-compromise revocation | Reject | Purge without further delivery |
| Request expiry | Reject | Purge envelopes and dedup tombstones |

Drain requires retained historical signed generation/mailbox authentication, old mailbox private keys, and old replica routes until ACK/expiry. Those obligations consume the same lease quota. Receiver dedup by `(clientLeaseId, requestId)` prevents a second visible request after refreshed-generation redeposit. A genuinely new request uses a fresh nonce/ID.

### 6.5 Replica states and recipient ACK

Use the configured placement policy; current defaults of five desired/three healthy are not universal constants. Distinguish:

- **`stored`:** one relay fsynced the deposit.
- **`queued`:** the configured minimum selected replicas returned signed receipts binding relay ID, index digest, `envelopeId`, ciphertext digest, and request expiry.
- **`outcome-unknown`:** an attempt may have committed but required evidence is missing.
- **`expired`:** the immutable request deadline passed.

The existing one-relay deposit ACK (`server.ts:1261`) is only `stored`; it must not be presented as `queued`. Neither state means recipient receipt, consent, response, or content delivery.

Recipient processing order:

1. Merge reachable selected-replica responses by storage key; an empty stale replica cannot hide another's envelope.
2. Validate expiry, relay response, encryption, inner signature, index binding, and logical ID.
3. Atomically persist encrypted local inbox/dedup keyed by `(clientLeaseId, requestId)`.
4. Expose one durable inbox item without a second retry notification.
5. Only after local commit, send the owner-signed storage ACK.
6. Replicate an observed-remove ACK tombstone expiring at the original request expiry. It wins over earlier/later deposits and prevents stale-replica resurrection.
7. Drop the tombstone only after legitimate deposits are no longer admissible.

Unknown-ID client ACKs create neither tombstones nor admission-free storage. Signed ACK proofs may repair a missing envelope subject to the prepaid-byte rule. Compaction preserves causal deposit/ACK barriers and longest live dedup expiry; latest-ACK-only compaction is unsafe (`mailbox-journal-compaction.ts:48`).

### 6.6 Quotas and stable-pseudonym tradeoff

| Scope | Proposed evaluation rule |
| --- | --- |
| Request | 4 KiB meaningful plaintext; 8 KiB padded plaintext; 16 KiB stored envelope; seven-day maximum |
| Client lease | At most **32** live/ACK-retained requests and **512 KiB** retained mailbox state across all index generations |
| Relay global | Existing configurable **128 MiB** mailbox-state default is a comparison only; journal storage has a separate quota (`runtime.ts:104`) |
| Sender | One admission unit per distinct deposit generation; exact replay free; entitlement issuance bounds distinct logical requests |
| Transport | Bounded address/connection rates for CPU/network protection, not Sybil-resistant admission |
| Client local | Bound outbox, inbox, dedup markers, old mailbox keys, and snapshot replacement peaks |

The count and byte caps are independent: admission is the stricter of both. Thirty-two maximum 16-KiB envelopes alone equal 524,288 B, leaving no byte headroom for metadata; therefore 32 is not a claim that 32 maximum-size requests plus metadata fit. Independent review must resolve whether 512 KiB includes all authentication/dedup/replica metadata or define a smaller effective count.

A stable `clientLeaseId` makes a genuine per-client quota enforceable across refreshes but links those generations. Intentionally unlinkable generations instead provide only a per-mailbox limit unless a separate quota credential is approved. Rotating mailbox IDs must not bypass the claimed quota.

### 6.7 Crash, retry, polling, and loss

| Actor/failure | Required behavior |
| --- | --- |
| Sender before transmission | Persist encrypted outbox, immutable deposit, admission capability, index binding, and original expiry before network activity. |
| Sender crash while sending | Reopen `outcome-unknown`; retry identical deposit/admission with fresh transport attempt ID. |
| Deposit reply lost | Exact retry returns duplicate/stored or sufficient receipts; no second request or admission charge. |
| Admission spent before relay append | Exact admission replay can commit after restart. |
| Relay crash after append before reply | Journal replay restores the envelope; retry is duplicate with no growth. |
| Relay crash after ACK append before reply | Retry reports zero newly acknowledged envelopes and appends no row. |
| Recipient crash after inbox commit before ACK | Redelivery resolves local dedup, creates no second item, then retries ACK. |
| Recipient crash after ACK before reply | Redelivery remains deduplicated; synchronized remote tombstone prevents eventual redelivery. |
| Uncertain journal append/rename | Stop the poisoned writer and reopen rather than guessing durability (`local-encrypted-state.ts:87`, `operation-log.ts:276`). |
| Recipient keys/client lost | Requests expire undecryptable/undelivered; no service reconstructs the client or originals. |

Sender retry uses bounded exponential backoff with jitter while online and stops at immutable expiry. Receiver polling occurs on unlock/startup and thereafter on an explicitly budgeted schedule. Poll frequency is a privacy/power/network tradeoff. The current generic saved-request outbox creates a fresh signed search request on retry (`private-request-outbox.test.ts:60`); that behavior must not be copied for mailbox deposits.

The mailbox stores only requests/reply capabilities. After the recipient returns and authorizes disclosure, the original-holding client must still be online to send it, and the requester must return to receive it.

### 6.8 Established-pattern comparison without a queue dependency

[MQTT 5.0](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html) is a comparison only:

- QoS 1 is at-least-once; PUBACK/DUP does not prove application dedup. This supports stable identity plus recipient dedup, not exactly-once claims.
- Message Expiry deletes undelivered expired copies; this design instead carries immutable absolute expiry so forwarding cannot extend it.
- Session expiry permits queued state loss when a client never reconnects, consistent with explicit expiry rather than permanent storage.

MQTT account/session/packet IDs and QoS 2 do not provide Resonance's cross-refresh logical IDs, encrypted per-request mailboxes, owner-signed deletion proofs, multi-replica anti-entropy, or notification dedup. No MQTT or new queue dependency is proposed.

## 7. Source reuse and mandatory corrections

Reuse the strict parsers, local encrypted snapshots, signed journal operations, admission replay, matching cache rebuild, replica placement/repair, encrypted mailbox cryptography, anti-entropy, observed-remove ACKs, and private relationship/channel delivery identified above.

Necessary corrections before any implementation candidate:

- Preserve match/notification dedup across lease-only refresh; do not use the current dedup-clearing update path unchanged.
- Compare ciphertext for duplicate storage IDs; current duplicate checks do not reject same-ID conflicting ciphertext (`mailbox-store.ts:95`).
- Expose single-relay acknowledgement as `stored`, never multi-replica `queued`.
- Keep immutable end-to-end request IDs and exact ciphertext/admission across retries; do not reuse fresh-request retry behavior.
- Send admission evidence with replica sync and resolve the same shared spend/replay.
- Preserve old-generation mailbox authentication/keys/routes during drain and old placements during anti-entropy.
- Bound every journal, ACK, tombstone, conflict, old-generation, temporary-file, and retry obligation before acknowledgement. Existing 512-byte tombstone headroom (`replica-storage-ledger.ts:13`) is not assumed sufficient for a larger leased schema.
- Preserve exact current-policy checks on publish/refresh/search/delivery and admission replay across reconnects.

## 8. Resource model and no-fit boundary

Preserve existing K7 and storage/work limits unless a separate owner decision changes them. No generative model runs on relays. Generator and embedding inference are local, separately pinned, cancellation/deadline bounded, and serialized rather than concurrently hiding peak memory. Current outbox evaluation retains at most **64** held outgoing operations and **16 MiB** local outbox bytes.

For 10,000 maximum-size indexes:

\[
10,000\times4,096\times5
=\boxed{204,800,000\ \text{B raw current index payloads}}
\]

This is arithmetic only. It excludes referenced/old revisions, conflicts, journals, matches, mailboxes, tombstones, allocation metadata, replica repair, and replacement peaks. It is not a fit claim.

Each accepted mailbox request charges:

- current retained `max(serializedEnvelopeBytes, serializedAckTombstoneBytes)`;
- complete deposit journal row, wrapper, and newline;
- prepaid full future signed ACK row;
- historical index authentication and replica-placement metadata;
- old and replacement journals during compaction, using the existing two-times-current-journal-plus-reserves metric (`server.ts:2379`);
- client encrypted-snapshot temporary peaks;
- old mailbox keys/routes and local dedup/inbox/outbox state.

Exact duplicates and ACK maintenance remain possible at full quota without increasing commitments. Lowering a configured quota below accepted obligations must refuse unsafe startup, not discard them.

Network/work accounting includes discovery, admission, TLS, padding, retries, every physical replica edge, polling, ACK propagation, expiry cleanup, failed attempts, signature verification, and full-mailbox scans. Original transfer is a subsequent operation and remains in full-lifecycle traffic. Cold model artifacts/initialization and idle lease maintenance count against K7. A complete maximum-cardinality/retry/poll ledger is required before any feasibility claim.

## 9. Local generation and index-generation evaluation

### 9.1 Current source facts and limitations

- The current path is embedding-only: Transformers.js loads `nomic-ai/nomic-embed-text-v1` as FP32, mean-pools/normalizes a 768-dimensional vector, limits input to 8 KiB/512 tokens, serializes inference, and applies a 10-second deadline (`packages/core/src/embedding.ts:105`, `packages/core/src/types.ts:48`). The lockfile pins Transformers.js 4.3.0.
- Need rewriting is deterministic and English-oriented; offers are unchanged and need prefixes have no Spanish equivalents (`embedding.ts:51`). The [Nomic model card](https://huggingface.co/nomic-ai/nomic-embed-text-v1) documents 8192-token capability and English retrieval benchmarks, not this application's Spanish qualification; the application separately imposes 512 tokens.
- The downstream 512-bit random-hyperplane LSH is not encryption or a cryptographic content hash (`packages/core/src/lsh.ts:1`). Existing small English-only evidence recorded 78–98% negative-pair false positives, 86–97% reconstruction, and 100% known-text identification (`scoped-fingerprint-real-2026-10-18.md:3`).
- Measured FP32 artifacts total **548,267,042 B**, dominated by a **547,552,426 B** ONNX file; cold-exercise peak RSS was **1,169,620,992 B** (`docs/evals/model-cache-download-2026-10-18.json:12`). The CLI's “~90MB” first-download message is stale (`packages/node/src/commands/init.ts:45`).
- Corrected bounded-cache isolated median peak was about **988.2 MiB**, versus **1,481.7 MiB** before correction. Two-thread/no-arena alternatives were rejected because they slowed inference without meaningful memory improvement (`v0.4-model-memory.md:32`, `embedding-resources-2026-10-18.md:44`). These are one-host English measurements, not energy or steady-state guarantees.
- Reference hardware is four CPU cores/8 GiB RAM/SSD. K7 retains complete-process-tree RSS ≤1.5 GiB sustained/≤2 GiB startup, idle CPU ≤1% of one core, and incremental idle client power ≤1 W (`v0.4-acceptance-kpis.md:48` and `:92`).

Official GGUF repositories: [3B](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF), [1.5B](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF), and [0.5B](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF).
2. **Apple Silicon:** llama.cpp Metal and CPU-only four-thread arms. If the best quality-viable model misses latency/energy goals, optionally evaluate an **MLX-LM 4-bit** conversion of that same model, pinning converter version, bits/group size, source revision, and artifact hashes. [MLX-LM](https://github.com/ml-explore/mlx-lm) supports Apple Silicon/local conversion and configurable KV cache.
3. **Lower-resource Windows/Linux x64:** llama.cpp CPU-only four threads with memory mapping and no GPU assumption, qualified separately from macOS.
4. No initial Transformers.js generation arm; existing evidence supports its Nomic feature-extraction path only.

Freeze **2,048 input tokens, 256 output tokens, greedy/temperature 0, fixed seed, one inference, and no persistent cross-user prompt/KV cache**. Reject over-limit input rather than truncating silently. Do not use MLX rotating KV compression in the primary arm because smaller caches can worsen quality. “4-bit” alone is never cache/version identity.

### 9.4 Three independent pipeline stages

1. **Generative proposal:** local original text → validated canonical summary/intent JSON. It cannot determine item type, authorization, consent, eligibility, identifiers, lease times, signatures, or publication.
2. **Embedding:** versioned deterministic rendering of approved JSON → existing Nomic FP32 vector. Keep Nomic, rewrite, prefixes, pooling, dimensions, and thresholds fixed for the first comparison. Never substitute Qwen hidden states for Nomic.
3. **Deterministic transformation:** vector + versioned projection/group/epoch → 512-bit LSH. Separate cryptographic digests may identify local cache entries; neither digests nor LSH prove truth/confidentiality.

Run a no-generation control using the existing raw-text path, then compare every generator through the same frozen Nomic/LSH/matching path. Report English and Spanish separately, with cross-language pairs as secondary diagnostics; do not average away a Spanish failure.

### 9.5 Strict structured output

Use one JSON object containing:

- `schema_version`: fixed integer;
- `language`: `en`, `es`, `mixed`, or `unknown`;
- `summary`: bounded nonempty string;
- `intent`: bounded nonempty string;
- `topics`: at most six bounded, deterministically normalized unique strings.

Require `additionalProperties: false`, duplicate-key rejection, NFC normalization, UTF-8 byte/string limits, control/bidi-character rejection, topic dedup, and hard output byte/token ceilings. Reject Markdown fences, trailing prose, extra fields, non-JSON values, and missing EOS. No autonomous semantic repair.

llama.cpp JSON Schema/GBNF is only a first barrier: its [grammar guide](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md) says unsupported schema features may be skipped and `uniqueItems` is unsupported. Independent validation is mandatory for llama.cpp and MLX.

### 9.6 Exact cache and replay

Use separate encrypted local records:

- **Generation key:** domain-separated digest of canonical original input plus item type, prompt/schema/preprocessing versions, model/tokenizer/chat-template/artifact hashes, runtime/build/backend, quantization, decoding parameters, and token bounds. Value: canonical JSON and digest.
- **Embedding key:** digest of canonical rendered text plus complete Nomic/runtime/rewrite/prefix/pooling identity. Value: exact vector bytes.
- **Fingerprint/index:** vector bytes plus projection/group/epoch identity; deterministic LSH needs no model invocation. Cache the final canonical signed index for exact republication.

Warm call, cold restart, concurrent duplicate, and exact retry must return byte-identical output with **zero generator invocations on a cache hit**. A populated final-index cache must replay with model files unavailable and networking disabled. Changed model/prompt/schema/tokenizer/quantization/runtime/embedding/scope/source bytes cannot reuse an incompatible entry. Corrupt/truncated/tampered/interrupted/invalid entries never publish or become successful cache entries. Greedy decoding is not assumed byte-stable across runtimes/hardware; a mismatch is a new candidate/version, never silent replacement.

## 10. Executable evaluation and selection criteria

Freeze candidate, corpus, seeds, commands, thresholds, and result destinations before execution. Use at least three counterbalanced runs per model/runtime/device with no concurrent host workload. Report counts, p50/p95/p99, run variation, and 95% confidence intervals.

### 10.1 Physical/resource measurements

- **Cold acquisition:** requested hosts/redirects, artifact/on-wire bytes including retries, elapsed time, temporary/final disk peak, hash/BOM reconciliation, and energy. Inject interruption near start/middle/end, corrupt/oversized artifacts, offline restart, and partial-cache reuse.
- **Startup:** module/process initialization, tokenizer/model load, time to first token, and time to validated JSON. Separate empty-cache cold startup, populated-cache cold process, and warm model.
- **Generation:** end-to-end latency by language and short/maximum input, prefill/decode tokens/s, timeout/cancellation settlement, and joules per valid output.
- **Complete application:** generation alone, Nomic alone, serialized generation→Nomic, and co-resident diagnostic. Record full-process-tree RSS and Apple Silicon unified/GPU/memory-pressure evidence that RSS may miss.
- **Sustained/idle:** fixed-cardinality operation and ordinary-maintenance idle for at least 30 minutes; physical incremental power against matched OS/brightness/power baselines. CPU seconds are not energy.
- **Network/privacy:** zero requests after approved artifact acquisition and no original text, private prompt, true embedding, or generated private cache content in logs/telemetry.

Serialization is the preferred resource hypothesis: existing Nomic already approaches 1 GiB, while idealized 1.5B/3B weights add roughly 0.72/1.44 GiB before runtime overhead. Co-residency is not assumed.

### 10.2 Quality, privacy, and malicious-input evaluation

Use independent held-out English/Spanish data with **≥1,000 queries and ≥10,000 publications**, labels independent of the model/embedding under test, frozen topic/paraphrase splits, and frozen notification thresholds. Measure per-language Recall@5, candidate-filter quality, notified precision, and FPR against the no-generation control.

On a frozen human-audited subset, score intent correctness, unsupported facts, omitted constraints, negation/number/entity errors, language preservation, and need/offer inversion. Do not use an LLM judge.

Run separate cross-scope reconstruction and known-text attacks among **100 candidates**. Audit any proposed public summary itself for direct disclosure; fingerprint-attack failure is unnecessary for a summary to leak content.

Adversarial inputs cover English/Spanish prompt injection, prompt/secret/contact exfiltration requests, private canaries, fabricated identities/numbers/negations, HTML/URLs/scripts, Unicode controls/homoglyphs, oversized/repeated input, malformed JSON, extra keys, duplicate topics, and attempts to change authorization/item type. No generated value autonomously reaches publication without deterministic policy and required user approval.

### 10.3 Predeclared selection and failure criteria

These are proposed experiment gates, not achieved results:

- **Quality:** each language independently must reach Recall@5 ≥90%, notified precision ≥80%, and FPR ≤5%. Threshold-straddling confidence intervals are inconclusive, not passes.
- **Privacy:** reconstruction and known-text identification each ≤5%, independently. Any reproducible original-plaintext/private-contact publication or unexpected inference network route blocks the candidate.
- **Resources:** the complete application must meet K7 memory/idle CPU/idle power limits with cold costs visible; warm end-to-end behavior must also fit K1 deadlines rather than reporting tokens/s alone.
- **Structural validity/replay:** 100% of accepted outputs pass independent validation; exact-replay checks are byte-identical and invocation-free on hits. Any invalid/malicious output reaching an index is a safety failure.
- **Summary faithfulness screen:** proposed ≤1% unsupported-critical-fact rate in each language and zero critical authorization/contact fabrication in the frozen adversarial suite. This new threshold needs owner confirmation.
- **3B over 1.5B:** require a proposed ≥3-percentage-point Recall@5 gain in the weaker language, no >2-point regression in the other, every gate passing, and license clearance. Otherwise prefer 1.5B.
- **0.5B:** only after larger candidates fail resource gates and only if it independently passes all quality/privacy/safety gates.
- **Overall:** if no model satisfies the joint gates, stop the local-generative candidate and retain the deterministic control. Do not relax thresholds or relabel summaries/embeddings/signatures as confidential or truthful.

A successful generator comparison alone cannot resolve the inherited fingerprint/privacy failures.

## 13. Consolidated executable controls

These are frozen future Vitest/integration/physical procedures using real parsers, encrypted snapshots, relay journals, and actual transport paths. None has been run or passed under DEC-020.

### 13.1 Leased index and online-delivery controls

| Control | Positive procedure and assertion | Negative/falsifying procedure |
| --- | --- | --- |
| Exact replay | Derive once, persist, restart, submit after lost reply; every attempt has identical bytes/signature/sequence and one logical notice. | Force different generated text on retry. Regenerated operation or second spend/notice falsifies replay. |
| Schema/signature | Verify canonically reordered valid fields and replicate the signed operation. | Mutate fingerprint, derivation, commitment, lease, mailbox, or sequence; add unknown fields or exceed size. Fail before mutation. |
| Commitment | Authorized recipient verifies exact original bytes with disclosed key. | Wrong key, changed byte/length, cross-publication key, or superseded commitment fails. Public records contain no key/original/generated text/embedding/private address. |
| Refresh | Same-content refresh advances sequence/expiry, converges, and produces no duplicate notice. | Old refresh is stale; over-long/backdated leases and post-withdrawal refresh fail. |
| Expiry/tombstone | Assert active-before/inactive-at expiry; first-seen tombstone converges with later live record. | Any expired or acknowledged-withdrawn in-scope search/match/delivery fails. |
| Conflict | Higher valid sequence replaces current state and retains match-audit references. | Same-sequence fork preserves both and stops fan-out; stale backup cannot overwrite newer state. |
| Crash/retry | Kill after journal flush before acknowledgement; exact retry returns prior result and repairs matching/mailbox once. | Lost durable record after ACK, duplicate allocation/spend/notice, or uncertain-as-success is unsafe. |
| Replica repair | Delete one replica index; inventory reports missing and repair restores exact signed operation while owner is offline. | Fabricated inventory without prior receipt, wrong signature, or relay original-byte requirement fails. |
| Owner liveness | Fresh challenge binds current index and expires in its declared window. | Replayed challenge, wrong verifier/sequence/index, stale signature, or owner-offline-as-content-available fails. |
| Authorized delivery | Active consent plus explicit grant delivers channel-encrypted original; recipient verifies commitment/request binding. | No consent, closed channel, wrong requester, expired grant, withdrawn/superseded index, replayed request with new content, or plaintext response journal denies/fails. |
| Offline/loss | Offline owner leaves discovery intact while requests expire/dedup; returning owner resumes. | All replicas lost plus owner offline cannot claim recovery. Missing original blocks refresh/delivery; missing keys block owner-authorized refresh/withdrawal. |
| Admission/current policy | Publish/refresh/search/delivery use exact request-bound admission/current policy; exact retries spend nothing new. | Revoked-policy authorization after cutoff, changed request using the same proof, or reconnect without current-policy refresh fails. |
| Privacy/quality | On independent Spanish/English holdout data, measure original→summary/intent→embedding→LSH against the frozen direct-original control. | Fail if recall@5 <90%, notified precision <80%, FPR >5%, rotation loss >5 points, or either known-text/reconstruction attack identifies >5%. Test private-index and any public-summary variant separately. |
| Resource closure | At maximum schemas, account current/referenced indexes, five replicas, journals, mailboxes, tombstones, conflicts, temporary files, refresh churn, and failures. | Acknowledgement before funding, unbounded tombstone/conflict growth, relay model requirement, K7 breach, or closed-client background work falsifies feasibility. |

### 13.2 Mailbox fault and resource falsifiers

Reject or revise on any of the following:

1. **Reply loss/restart:** exact retry creates a second request, spends admission twice, or produces a second inbox item/notification.
2. **Commit boundary:** `stored`/`queued` precedes durable evidence, or a queued request is lost after fewer than declared replica failures.
3. **Replica reorder:** ACK-before-deposit, stale replay, restart, or compaction resurrects an ACKed/withdrawn request.
4. **ID conflict:** equal `(mailboxId, envelopeId)` with different ciphertext is accepted as an exact duplicate.
5. **Lease boundary:** expired/superseded indexes accept deposits; natural expiry cannot drain accepted requests; refreshed redeposit duplicates notification; withdrawal still delivers.
6. **Admission/capacity atomicity:** capacity refusal burns a token, admission replay expires before legitimate retry ends, or replica sync bypasses admission.
7. **Quota escape:** the 33rd distinct request or byte overflow succeeds, old generations escape the lease total, full-quota ACK/duplicates grow state, or mailbox rotation defeats the limit.
8. **Recovery funding:** restart/compaction exceeds retained/journal/temporary reserves, or a lower quota silently discards accepted obligations rather than refusing unsafe startup.
9. **Pagination/churn:** concurrent deposits/ACKs/expiry starve or permanently skip an anti-entropy event.
10. **Offline behavior:** UI equates stored/queued/storage ACK with consent or content delivery, or original content appears without the holding client online.
11. **Resource envelope:** maximum cardinality/retry/poll load exceeds applicable K7 RSS, CPU, power, disk-peak, or all-edge network limits (`v0.4-acceptance-kpis.md:92` and `:137`).
12. **Privacy:** fixed-size encryption is treated as observer protection while timing/count/source linking remains detectable, or predictable request text can be confirmed despite the random nonce.

### 13.3 Model and cache controls

- Validate every accepted structured output independently; reject malformed JSON, extra/duplicate fields, missing EOS, Unicode/control abuse, excessive topics, and autonomous policy/identity changes.
- Prove warm/cold/concurrent/restart cache hits are byte-identical with zero generator invocations; prove final-index replay with models unavailable and network disabled.
- Change each model, prompt, schema, tokenizer, artifact, runtime, quantization, scope, embedding, projection, and source-byte identity independently; incompatible cache reuse must fail.
- Inject interrupted/corrupt/tampered cache and model artifacts; no invalid entry may publish or become a successful cache entry.
- Keep the no-generation control and report each language separately. A Spanish or weaker-language failure cannot be hidden by an aggregate average.
- Interrupt acquisition near start/middle/end and restart offline; reconcile every artifact/hash/BOM and charge temporary disk, retries, startup, and energy.
- Measure serialized generation→Nomic and co-resident diagnostics without concurrent host workloads; CPU seconds, work bytes, and RSS are not substitutes for watts or elapsed time.
- Any direct original/private-contact disclosure, unexpected inference route, malicious publication, or critical authorization/contact fabrication blocks selection regardless of average benchmark quality.

## 14. Architectural falsifiers and disposition

Reject or revise the architecture if it requires offline original delivery after permanent client loss; treats signed leases as proof of truth/possession; claims instantaneous withdrawal convergence across arbitrary partitions without a stronger freshness/witness protocol; requires an unnamed queue/service; or claims that summaries, embeddings, HMAC commitments, fixed-size encryption, or LSH fingerprints provide confidentiality without independently passing K5/K6 attacks.
