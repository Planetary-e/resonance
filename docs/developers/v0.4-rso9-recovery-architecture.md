# DEC-017 / RSO9 stateless recovery architecture

**Status: CONFIRMED REJECTION.** Independent review confirmed decisive original-evidence storage and legal issuer-wide-transition failures. Do not advance `RSO9-SMT16` to implementation or campaign. This evaluates the single authorized RSO9 candidate, not every conceivable authenticated-data-structure architecture, and claims no implementation, production, R1/R2, K/R, economic, or release acceptance.

DEC-017 authorized one read-only design pass and one independent review. The confirmed verdict and remaining non-inclusion specification defect are recorded in `../evals/v04-dec017-rso9-rejection-review-2026-11-20.md`. No implementation, product test, campaign, installer, deployment or release action occurred.

All physical, work, network, and timing numbers below are **design forecasts, optimistic subtotals, or lower-bound counterexamples**, not measured RSO9 performance. Source-derived repository facts are identified separately.

## Decisive falsifiers for rejection review

1. **Original evidence `C`:** one legal 10,000-accepted-row history requires at least **10,240,000 B of original signed material per copy before encoding**, against `C=262,144 B`. The candidate's encoded forecast is 15,455,739 B per copy.
2. **Witness-producing indexes `D`:** two minimal 32-byte accepted-row indexes require **640,000 B**, against `D=524,288 B`, before tree nodes, evidence indexes, roots, pending state, or ancestry. Including the finite control subtotal gives 739,628 B.
3. **Linear legacy attribution and issuer retirement:** a legal command can remove 10,000 rows. Its pending update list is at least **980,252 B**, materialization alone forecasts **14,703,780 B > W**, and its network witness exceeds 1 MiB before Merkle paths.
4. **Recovery work:** cold reserve, returning recovery, NEW_VIEW import, and local-`C` recovery exceed `W` under the retained per-object four-copy availability accounting.
5. **Metadata, configuration, and timing:** 10,000 evidence metadata entries leave only 38,576 B of the independent 1 MiB allowance for every other metadata object; `>64` continuity and 3 s/30 s timing remain unqualified. These limitations are not needed for rejection.

Evidence retention and witness generation therefore defeat the verifier-local root savings even where ordinary root proofs are compact.

## 2. The single candidate: RSO9-SMT16

### 2.1 Authenticated structures

Use sixteen fixed-depth, binary sparse Merkle trees. All hashing is existing SHA-256; all signatures remain existing Ed25519. There is no VRF, accumulator, Bloom filter, new dependency, or probabilistic conflict rule.

For map `m` and canonical binary key `k`:

\[
k_m=SHA256(\text{"resonance:rso9:key:v1"}\parallel m\parallel k)
\]

The tree has depth 256 and one position for each possible 256-bit digest.

\[
\begin{aligned}
Leaf(m,k,v)&=H(0x00\parallel m\parallel k_m\parallel v)\\
Node(l,r)&=H(0x01\parallel l\parallel r)\\
E_{256}&=H(0x02\parallel \text{"resonance:rso9:empty:v1"})\\
E_d&=Node(E_{d+1},E_{d+1})
\end{aligned}
\]

An empty tree root is `E0`. Integers are big-endian, values use a canonical binary schema, and duplicate keys or trailing bytes are invalid.

The sixteen maps are:

| Map | Logical key → value |
| --- | --- |
| `A` | `spend` → complete accepted row |
| `AI` | `issuerKey,spend` → accepted-row reference |
| `C` | `issuerKey,spend` → constraint summary |
| `B` | `issuerKey,spend,bindingDigest` → full binding and vote/accepted/certificate counts |
| `V` | `setId,issuerKey,spend,witness` → original vote proof reference |
| `VI` | `issuerKey,proofId` → vote reference |
| `X` | `setId,issuerKey,spend,owner` → original certificate reference |
| `XI` | `issuerKey,proofId` → certificate reference |
| `E` | `proofId` → kind, scope, frame digest, encoded length, semantic reference |
| `NL` | local-spend `issuerKey` → permanent denial |
| `NW` | `witness,issuerKey` → permanent denial |
| `NC` | `coordinator,issuerKey` → permanent denial |
| `S` | `setId` → exact `AdmissionWitnessSet` digest |
| `H` | `issuerKey,epoch` → handoff activation digest |
| `G` | `configurationId/revision` → signed policy/advance/terminal ancestry digest |
| `O` | `requestBinding` → original command digest and certified outcome |

The accepted-row secondary index and `VI`/`XI` are necessary for exact issuer-wide deletion. Omitting them merely turns retirement into a full-state scan.

### 2.2 Exact inclusion and non-inclusion proofs

A proof contains:

```text
mapId[1]
queryKey[32]
terminalType[1]        // 0=empty, 1=present leaf
terminalKey[32]
valueLength[4]
value[valueLength]
siblings[256][32]      // leaf-to-root order
```

Directions are derived from the query-key bits, so no direction bytes are needed.

\[
|\pi|=1+32+1+32+4+|v|+256\cdot32
     = \boxed{8,262+|v|\text{ B}}
\]

Verification:

- **Inclusion:** `terminalType=1`, `terminalKey=queryKey`; hash the supplied value and all 256 siblings.
- **Non-inclusion by empty position:** terminal is the canonical empty leaf.
- **Non-inclusion by another leaf:** `terminalKey != queryKey`; the supplied terminal leaf and siblings reconstruct the same root. Because every digest has exactly one leaf position, this excludes the queried key.
- Any wrong map, terminal key, sibling order, non-canonical value, or root mismatch refuses the command.

A plain append-only Merkle log is insufficient because it does not provide this absence semantics. [RFC 6962 §§2.1–2.1.2](https://www.rfc-editor.org/rfc/rfc6962.html) supplies the established inclusion/consistency background; [Dahlberg, Pulls, and Peeters, *Efficient Sparse Merkle Trees*](https://eprint.iacr.org/2016/683) defines sparse Merkle membership and non-membership audit paths and their storage/cache trade-offs. [CONIKS](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/melara) is another primary reference for Merkle-prefix inclusion/absence and signed roots. None of these sources proves Resonance's reducer equivalence, root certification, availability, physical fit, or acceptance.

### 2.3 Compact root state

The root bundle is:

```text
magic[8] + version[4]
+ genesis[32] + context[32] + configuration[32]
+ sequence[8] + view[4]
+ 16 map roots[16*32]
+ delegationRoot[32] + terminalFence[32] + layoutRoot[32]
```

\[
\boxed{|RB|=728\text{ B}}
\]

Current and pending bundles consume 1,456 B. Verifiers retain these bundles, stable heads, bounded suffix metadata, prepared locks, current configuration, and local fencing state—not accepted rows, vote/certificate arrays, or full evidence.

The **prover still needs the maps and original evidence**. In this candidate every potential leader has a private prover index in its named `D` reservation; replicas hold encrypted evidence in `C`. There is no unnamed external proof service.

## 3. Exact reducer decomposition and witnesses

Let:

- \(i\) be `issuerKey`, \(s\) be `spend`;
- \(\beta(v)=(v.action,v.requestBinding)\);
- \(Comp(i,s)\) be distinct bindings of all certificates for `(i,s)`;
- \(Claims(i,s)\) be distinct bindings of votes and accepted rows for `(i,s)`.

`C` commits the exact distinct counts and the unique binding where count equals one. `B` commits per-binding reference counts. On insertion, counts and unique bindings are updated directly. On deletion from two distinct bindings to one, the witness supplies the other `B` leaf. This inductively reproduces:

\[
witnessConstraint=
\begin{cases}
denied & i\in NL\cup NW\cup NC\\
conflict & |Comp|>1\\
bound & |Comp|=1\land Comp=\{\beta(claim)\}\\
denied & |Comp|=1\land Comp\ne\{\beta(claim)\}\\
split & Comp=\emptyset\land |Claims|>1\\
bound & Comp=\emptyset\land Claims=\{\beta(claim)\}\\
denied & Comp=\emptyset\land |Claims|=1\land Claims\ne\{\beta(claim)\}\\
fresh & Comp=Claims=\emptyset
\end{cases}
\]

Thus ordinary decisions do **not** need all 10,000 hot-key proofs.

### Ordinary and hot-key boundedness result

For non-deleting vote/certificate/accept/retry cases, the schema needs at most 16 map proofs. Bounding semantic leaf values to 512 B gives an optimistic ordinary witness bound:

\[
|\mathcal W_{ordinary}|
 \le 16(8,262+512)
 =\boxed{140,384\text{ B}}
\]

plus the original command, historical set object where needed, and availability receipts. A hot-key ordinary query is bounded by the authenticated `C/B` summaries; it does not enumerate all hot-key evidence.

**Overall per-command witness size is not bounded.** For issuer retirement or legacy attribution, if \(r\) rows are removed:

\[
|\mathcal W|\ge 32r
\]

just to identify the affected spend/proof keys, excluding all Merkle siblings and values. A legal legacy state can contain 9,999 rows for retired issuer `i` plus one matching unattributed row; one attribution then removes all 10,000. Hot-key retirement is likewise linear even though hot-key ordinary queries are compact.

## 4. Root certification, views, retries, and fencing

Reuse RSO7's canonical `T/V/Q/K/Z/Lock/VC/NV` certification pattern, with RSO9 roots and variable mutation size:

```text
Mutation M(n) =
  magic[8]+version[4]+sequence[8]+view[4]
  + command/preState/postState/evidence/delegation/ancestry/layout digests[7*32]
  + updateCount[4]
  + n*(mapId[1]+operation[1]+key[32]+oldLeaf[32]+newLeaf[32])
```

\[
\boxed{M(n)=252+98n},\qquad
\boxed{Y(n)=1,878+M(n)=2,130+98n}
\]

`T=540`, `Q=539`, `K=408`, `Z=1,203`, `Lock=616`, and `VC=3,078` remain as in RSO7. The NEW_VIEW size is:

\[
\boxed{NV=15,110+\sum_{j=1}^{4}Y(n_j)}
\]

For ordinary eight-update transitions, `M=1,036`, `Y=2,914`, and `NV=26,766`.

### Transition rules

1. Authenticate original command, policy cutoff, current stable root, old-cohort fence, writer lease, all physical/work/network reserves, and all witnesses.
2. Each voter independently evaluates the original reducer decomposition and computes byte-identical `T/M`, result, and all post-roots.
3. Persist original encrypted evidence and obtain four exact durable acknowledgments before PREPARE.
4. Persist command, `T/M`, witness digest, and pending root; form prepare QC and durable lock.
5. Form commit QC and append `Y`; execute only the certified update set.
6. Sign STABLE only after current/pending roots, evidence, delegation, configuration ancestry, and four-copy floors are durable.
7. Install stable `Z` at four replicas before client acknowledgment or notification.

No voter trusts a leader-supplied post-root without checking its witnesses.

### View change

Four signed `VC` records carry the stable head, continuous committed suffix, **every prepared lock**, current/pending roots, evidence/delegation roots, and local floors. The new leader:

- selects the highest continuous committed chain;
- refuses equal-sequence different digests;
- preserves highest prepared values in global sequence order;
- imports any higher local floor/lock before installation;
- fetches exact pending commands and witnesses by digest;
- refuses ambiguous ancestry rather than inventing an outcome.

For ordinary transitions:

\[
W_{VC,member}=15VC+11NV=340,596\text{ B}
\]

\[
W_{NV,leader}=15NV+6Z=408,708\text{ B}
\]

These control-only forecasts exclude the already-failing availability recovery.

### Retry and old-cohort fencing

- A stable exact retry resolves through `O` and never notifies twice.
- An identical pending command remains uncertain until its durable outcome is known.
- Same request identity with different bytes is conflict evidence.
- The terminal stable cut binds the old configuration, successor configuration, sequence, all semantic/evidence roots, delegation floor, and successor funding.
- After that cut, old-cohort proposals, votes, cuts, delegations, and writes are rejected at every view. Read-only resolution of an already certified retry is allowed; no new old-cohort effect is created.
- The successor begins at global sequence `s+1`; global history never resets.

Cold installation must verify the signed original genesis and every configuration/terminal link to the current root. A recent root or QC alone is not accepted. The existing 65-generation store and non-shared 64-depth traversal are not reused as an answer to the `>64` requirement: `packages/relay/src/history-volunteer-config.ts:27-42` and `packages/relay/src/history-checkpoint-store.ts:295-313`.

## 5. Evidence placement, delegation, and private recovery

### Named placement

- Each original plaintext object remains exact immutable original evidence.
- It is sealed in the existing `RSO5F001` format: 265 B frame overhead plus original content, authenticated by the original owner.
- Each stored frame has a 256 B archive header.
- Four mandatory ciphertext copies reside in four explicitly reserved evidence-replica `C` scopes.
- `E` commits object identity and frame metadata, not availability by itself.
- `D` holds prover indexes, roots, suffixes, availability-checkpoint heads, configuration ancestry, and pending/stable records.
- Existing `RSO5D001` delegations remain in `C`; recipient private keys never leave the recipient.

The current framing and delegation properties are in `packages/relay/src/sustainable-rso5-opaque.ts:58-76` and `:148-197`.

### Recovery behavior

- **Cold:** authenticate genesis-to-current ancestry and stable roots; restore delegations; prove four-copy evidence availability; fetch and privately decrypt only evidence selected by later commands. Root verification never substitutes for original-signature verification when an original is opened.
- **Returning:** compare stable/proof/delegation roots, transfer missing ciphertext only, and still prove every required four-copy floor.
- **Local `C` loss:** use intact remote ciphertext and recipient-private delegation; fetch selected evidence by digest. If the remote four-copy floor is not intact, escalate to cold/quorum recovery or refuse.
- **Disjoint successor:** all required evidence and delegations must obtain four successor copies before readiness/activation. Reference transfer is permissible only when the exact retained frames and their existing four-copy floor remain valid.

This avoids loading full semantic state, but the physical and availability costs below remain fatal to the candidate.

## 6. Physical model and falsifiers

### 6.1 Original evidence independently exceeds `C`

A certificate contains at least four votes. Ignoring JSON field names, action, kind, version, request object, and every other byte, each vote must represent:

```text
witness key       32
signature         64
setId             32
issuerKey         32
spend             32
requestBinding    64   // conservative decoded lower bound
                     ---
                     256 B
```

Therefore each distinct accepted-row original requires at least:

\[
4\cdot256=\boxed{1,024\text{ B}}
\]

of signed certificate material. Distinct spends force distinct signed claims, so these objects cannot be deduplicated as identical evidence.

For 10,000 accepted rows:

\[
E_{raw}\ge10,000\cdot1,024=\boxed{10,240,000\text{ B per copy}}
\]

\[
E_{raw}-C=10,240,000-262,144
=\boxed{9,977,856\text{ B excess}}
\]

This is before framing, archive headers, delegations, requests, JSON, encryption, or indexes. Four raw copies require at least **40,960,000 B** aggregate.

Using this candidate's existing framing:

\[
C_{9}\ge10,000(1,024+265+256)+5,739
=\boxed{15,455,739\text{ B per copy}}
\]

\[
\boxed{C_9-C=15,193,595\text{ B}}
\]

Four encoded copies require at least **61,822,956 B**, excluding all other state.

The historical 72-proof closure was already `258,595 B`, leaving only 3,549 B: `docs/developers/v0.4-rso5-recovery-architecture.md:241-268`.

**Evidence retention alone therefore defeats stateless verifier savings.** Moving evidence between `C`, `D`, or an unnamed store cannot cure this.

### 6.2 Prover state independently exceeds `D`

Even granting a highly optimistic index containing only one 32-byte reference per accepted row:

\[
D_{index}\ge10,000\cdot32\;(A)+10,000\cdot32\;(AI)
=\boxed{640,000\text{ B}}
\]

\[
\boxed{D_{index}-D=115,712\text{ B}}
\]

There are still no internal SMT nodes, `E/V/VI/X/XI/C/B` indexes, pending paths, stable roots, or ancestry. Removing `AI` avoids this particular overflow only by restoring an unbounded issuer scan.

An optimistic finite control reservation is:

| Current/pending stable heads | 2,406 |
| Ordinary durable NEW_VIEW | 26,766 |

### 6.4 Legal legacy transition exceeds pending/failed extents

For \(r=10,000\), counting only one update per deleted row and ignoring both indexes and summary repairs:

\[

\[

### 6.5 Aggregate and metadata

The complete aggregate equation is:

\[
\begin{aligned}
Agg_9={}&Agg_{unchanged}
+4(C_{evidence}+C_{delegation}+C_{orphans})\\
&+\sum_{nodes}(D_{index}+D_{control}+D_{ancestry})\\
&+P_{pending}+F_{failed}+Metadata
\end{aligned}
\]

The new evidence plus one minimum dual index is already at least **62,462,956 B**; with five potential-leader indexes it is **65,022,956 B**, before control state. Aggregate bytes alone need not exceed 2 GiB, but that cannot rescue per-node `C/D`.

No extra reservation scopes are required by the root design, so the entry count need not grow merely because there are 10,000 objects. However, 10,000 existing 101-byte evidence metadata entries alone serialize to **1,010,000 B**, leaving only **38,576 B** of the independent 1 MiB allowance for scope descriptors, roots, ancestry, and other metadata. No metadata headroom or closure is claimed.
