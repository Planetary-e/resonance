# Offline preparation and review of admission rotation

The v0.4 operator tool creates a successor policy for a **fresh RSA issuer key and four-of-five witness cohort**, using the existing community authority. It preserves every old key's original verification rules and history obligations. See the [rotation decision](v0.4-witness-replacement-decision.md) for the fault model, volunteer procedure and limitations.

The workflow is **prepare → check → sign**. Preparation and review need only public configuration. Signing requires the authority's private key and the digest printed for the reviewed plan. These commands use local files; they do not install a policy, contact volunteers, allocate permits, convert tokens or reset any role's history.

## Prepare the inputs

Work from the repository root with its dependencies installed. Retain:

- `authority.pub`: the independently verified community authority public key.
- `previous-policy.json`: the latest signed policy known to the community. The tool authenticates this file but cannot establish global freshness or discover a different device's installed revision.
- `new-issuer-profile.json`: the new issuer's trusted public profile (`version`, `scope`, `issuerPublicKey`, `relayUrls`). Use a fresh 2048-bit RSA key, the same logical issuer/community, and a new shared period (`scope.epoch`) not present in any retained entry. The RSA private key is never an input to this tool.
- `new-witness-set.json`: the public witness configuration described in [witness setup](v0.4-admission-decision.md#witness-setup): `version: 1`, `quorum: 4`, five distinct `members` with public keys and endpoints, and one to eight authorized `coordinators`. Verify ownership and availability with the volunteers separately.

Construct the request from those public files. The example allows issuance for one day, new spends for two, recorded retries for three, and a four-day policy lifetime. Agree actual windows and the separate new permit allowance with the community first.

```sh
node --input-type=module - <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const now = Date.now(), day = 86400000;
const request = {
  version: 1, kind: 'admission-rotation-request',
  issuedAt: now, expiresAt: now + 4 * day,
  newKey: {
    profile: JSON.parse(readFileSync('new-issuer-profile.json', 'utf8')),
    witnesses: JSON.parse(readFileSync('new-witness-set.json', 'utf8')),
    notBefore: now, issueUntil: now + day,
    spendUntil: now + 2 * day, retryUntil: now + 3 * day,
  },
  retire: [],
};
writeFileSync('rotation-request.json', JSON.stringify(request, null, 2), { flag: 'wx', mode: 0o600 });
JS

node --import tsx scripts/rotate-admission-policy.ts prepare \
  authority.pub previous-policy.json rotation-request.json plan.json
```

`retire: []` preserves all old cutoffs. To shorten an old entry, include its `issuerKey` fingerprint and all three integer Unix-millisecond values: `issueUntil`, `spendUntil`, `retryUntil`. They must remain ordered after its original `notBefore`, and each must be no later than its previous value. Duplicate or unknown keys are refused. A shorter cutoff affects updated devices only; older unexpired policies may still be used elsewhere.

Preparation copies every old entry, adds exactly one fresh active entry, increments the revision by one, and writes an **unsigned** plan. It refuses changing old profiles, witness membership/endpoints, coordinators or start dates. It also refuses deleting old keys or extending their cutoffs. A previously local-only key stays local-only; rotation does not give its old tokens witness protection.

To free a current slot after a key's final retry cutoff, use request `version: 2` and add `archive: ["sha256:<expired-key-fingerprint>"]`. Selected entries move unchanged into the permanent signed archive; they cannot also appear in `retire`. Existing archives remain intact. This produces policy v2, which permits eight current and up to 64 archived entries. See [signed archives](v0.4-policy-archives.md) before using this workflow.

## Review before signing

```sh
node --import tsx scripts/rotate-admission-policy.ts check \
  authority.pub previous-policy.json plan.json
```

Inspect the JSON report:

- Authority fingerprint, predecessor digest and old/new revisions.
- Retained and new cohorts, including their public scope, witness endpoints and authorized coordinators.
- Old/new deadlines, with both Unix milliseconds and UTC dates. Effective deadlines are limited by each policy's expiry.
- Current-key count and remaining slots out of eight; archived-key count and remaining slots out of 64; `retained[].archived` selections; and exact compact signed-file size against the 64 KiB v1 or 512 KiB v2 limit.
- `historyCapacity.inspected: false`: remaining vote, certificate, wallet and issuer capacity must be inspected locally. Rotation neither frees that storage nor proves remote history is intact.
- `approvalDigest`: identifies the normalized plan, authority and exact predecessor. Formatting alone can change without changing this digest; changed policy values require a new review.

An expired signed predecessor can still anchor the comparison. A new current policy can resume old-key windows that were only blocked by the predecessor's expiry; the report exposes this through the effective deadlines. It cannot extend or restore an expired key cutoff. Review overlapping allowances explicitly. The new cohort must have an issuance window remaining within the new policy; a future start date is permitted.

## Sign the reviewed plan

Replace `<approval-digest>` below with the report's full `sha256:…` value. Use the authority private file created by `scripts/admission-policy.ts authority-keygen` and keep it local.

```sh
node --import tsx scripts/rotate-admission-policy.ts sign \
  --approve '<approval-digest>' \
  authority.pub authority-private.json previous-policy.json plan.json policy.json
```

Signing checks the predecessor, rules, current dates and approval digest again, verifies the private key matches the pinned authority, and rechecks the issuance window after signing. A changed plan cannot be signed with its earlier approval. Policies without archives retain version 1; archival plans and successors of version 2 use version 2. Follow the [cutover procedure](v0.4-witness-replacement-decision.md#volunteer-governance-and-cutover-procedure) to install it and verify readiness before separately approving new permits.

The approval digest prevents accidental substitution within this workflow. It does not prove a human read the report, prevent authority equivocation, or replace devices' installed-revision checks. The lower-level general policy signer still exists; it does not enforce this rotation workflow.

## File and capacity behavior

Inputs must be regular files within bounded sizes. Plans may use up to 1 MiB, requests 64 KiB, and signed policy files 512 KiB; semantic validation still limits signed v1 policies to 64 KiB. Outputs are exclusively created, flushed, and owner-only on POSIX. Existing files and output symlinks are refused. Directory flushing is unavailable through this tool on Windows. A failed write can leave a reserved partial output; retain it for diagnosis and use a new filename after correcting the cause. This command does not atomically install a policy.

Eight current keys and 64 permanent archives are hard pilot limits, potentially reached earlier by file size. A full current list requires an eligible archive selection before adding a key; a full archive cannot accept another retired configuration. Do not delete histories, prior entries or installed revision state to bypass a limit. Authenticated checkpoints and membership governance remain separate roadmap work.

## Validation

The eight focused tests exercise real RSA/Ed25519 key material, signed predecessor verification, unchanged old pins, rejected retirement extensions, fresh-key/period rules, stale approval, cutoff expiry during signing, expired predecessors and key capacity. They also invoke the actual CLI through prepare/check/sign, verify the resulting signature and successor rules, and check file permissions, refusal to overwrite files/symlinks, bounded input and private-input error redaction. These are offline local checks; they do not certify volunteer readiness or Internet behavior.
