# Protected owner over relay links

Status: opt-in Node relay runtime, 2026-10-17. The owner can open its authenticated
relay transport before its protected admission history is ready. Publication,
search and mailbox admission remain closed until four fresh durable history
acknowledgements succeed. A transport handshake or cached certificate cannot open
that gate.

## Explicit configuration

Keep the prepared history and signed-policy configuration described in
[protected startup](v0.4-protected-admission-operations.md). Additionally set
`RELAY_ADMISSION_HISTORY_LINKS_FILE` to a regular JSON file, at most 64 KiB, with
exactly `version: 1` and `members`. The latter contains five records:

```json
{
  "version": 1,
  "members": [
    { "publicKey": "first-enrolled-history-key", "relayId": "first-infrastructure-DID" },
    { "publicKey": "second-enrolled-history-key", "relayId": "second-infrastructure-DID" },
    { "publicKey": "third-enrolled-history-key", "relayId": "third-infrastructure-DID" },
    { "publicKey": "fourth-enrolled-history-key", "relayId": "fourth-infrastructure-DID" },
    { "publicKey": "fifth-enrolled-history-key", "relayId": "fifth-infrastructure-DID" }
  ]
}
```

Replace every placeholder with an actual enrolled key and its independently
selected relay identity. Every key must already occur in the history context;
both keys and infrastructure identities must be distinct. Unknown fields, new
members, endpoint hints and initialization instructions are refused. This file
neither enrolls volunteers nor changes their history signing keys.

The owner must expose a reachable relay endpoint in `RELAY_PUBLIC_ENDPOINTS` for
volunteers to connect to it, or use configured outbound relay contacts to reachable
volunteers. The endpoint advertised in the signed descriptor must match the
contacted endpoint. Remote connections use the existing secure-transport policy.
Each enrolled volunteer authorizes the owner's infrastructure identity in its
[controller configuration](v0.4-history-volunteer-runtime.md).

This routing file replaces direct history transport with explicitly pinned relay
links. The original history configuration's member endpoint validation remains;
those endpoints are **not** a fallback route. The owner can also host an enrolled
volunteer role: both directions share one router and its buffer/operation limits,
with separate explicit authorizations for incoming role requests and outgoing
member requests.

## Readiness and failure

- `started` means the listener exists. It does not certify admission readiness.
- While opening history, `/health` returns HTTP 503 with `admission_starting` and
  authenticated `/stats` reports `admission_ready: false`.
- Fresh valid user operations across all six frame families reject with
  `admission_unavailable` before spending
  a credential, marking a search as seen or writing mailbox/publication state.
  Forwarded search returns `unavailable`; configured witness votes also stay closed.
  Authenticated infrastructure links can establish history readiness meanwhile.
- After configured admission finishes, the relay emits `admission_ready`, health
  becomes HTTP 200 and stats reports true. These indicate initialized admission;
  they are not a continuously measured count of online replicas. Every later
  protected mutation still requires its own four durable receipts.
- History failure exits with code 1. Missing/corrupt history cannot initialize a
  replacement ledger. Removing protection cannot open protected data locally.
- SIGTERM/SIGINT close the admission gate and history router before awaiting
  shutdown. Waiting requests release their slots; an opening verifier that finishes
  late is closed and cannot activate a stopped process. Retained pending intent
  remains available for the existing exact-retry/restart protocol.

Without the links file, direct history keeps its original eager contract: readiness
must complete before the listener starts. Ordinary unprotected startup is unchanged.

## Bounded connection waiting

Only this explicit runtime routing enables `waitForConnection`. Each request can
wait for its pinned authenticated socket within the same maximum 30-second RPC
budget. Waiting consumes one of the router's eight operation slots and releases it
before the actual stream reserves its slot. Connection, serialization, transfer
and response processing cannot renew that deadline. Caller cancellation or router
shutdown rejects the wait without dispatching a late request. A lost active socket
is not transparently resent on its replacement.

The [stream limits](v0.4-history-reverse-links.md) and original signed protocol
expiry/abort checks still apply. Readiness can involve several bounded protocol
stages; the per-RPC ceiling is not a promise that the whole startup always takes
less than 30 seconds.

## Evidence and remaining work

Real-process tests start the owner before its volunteers, observe HTTP 503 with
three connections, then accept the same real blind credential after a fourth
volunteer connects. Exact publication retry and double-spend rejection survive an
owner restart. Another scenario stops an unready owner, reopens the retained
history and refuses a missing history. All direct history endpoints in these tests
are deliberately unreachable.

Additional socket tests cover all six user frame families, publication withdrawal,
mailbox acknowledgement and authenticated forwarded search. Router tests cover
unpinned connections, eight waiting slots, cancellation/close/expiry, no late
transmission and a serialization cutoff after connection waiting.

A reachable volunteer is still required at the other end of each connection.
Both-outbound bridging, complete desktop owner configuration/recovery/health,
quorum-safe compaction, policy/witness recovery and independent Internet/resource
validation remain required. Local processes do not establish independent operator
availability or device energy costs.
