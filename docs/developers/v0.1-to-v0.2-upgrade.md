# Upgrading Local Data from v0.1 to v0.2

This procedure preserves a user's private v0.1 items while moving every active item to the unlinkable protocol v2 identity model. It is a local-data migration. There is no deployed v1 relay network to drain, and the procedure does not publish compatibility records or v1 tombstones.

## What the Upgrade Preserves

- The encrypted root identity, used locally for database encryption and future device recovery
- Each item's local UUID, type, raw text, true embedding, perturbed embedding, and privacy setting
- Withdrawn status for items the user already withdrew
- Legacy match and channel rows as local history

The local item UUID never appears in a v2 relay request. Legacy match and channel rows are not converted into v2 relationships because doing so would falsely claim fresh pairwise consent and could link the two protocols.

## What the Upgrade Replaces

Every active item without v2 credentials receives:

- A random Ed25519 publication key and identifier
- A random X25519 publication-mailbox key and identifier
- A new signed v2 publication record derived from the stored true embedding
- Encrypted local storage for both new secret keys

The new record contains no root DID or signature from the root identity. Different items receive unrelated publication and mailbox keys.

## Before Running It

1. Stop the Resonance desktop app and any CLI process using the same data directory.
2. Confirm that `identity.json` and `resonance.db` exist in `~/.resonance/`, or in `RESONANCE_DATA_DIR` when that environment variable is set.
3. Keep enough free disk space for another copy of both files.

The command creates a backup before opening the database. Opening the database performs the structural schema migration from version 1 through version 5; the semantic item upgrade runs afterward.

## Run the Upgrade

To create the v2 records and publish them to a relay:

```bash
resonance upgrade-v2 --password <password> --relay ws://localhost:9090
```

Use a different matching group when needed:

```bash
resonance upgrade-v2 --password <password> --group <group-id> --relay <relay-url>
```

For a two-step rollout, first prepare records without contacting a relay:

```bash
resonance upgrade-v2 --password <password> --local-only
```

Inspect the command summary, then rerun without `--local-only`. The second run submits the exact records created by the first run; it does not rotate their keys.

Every invocation makes a fresh backup at:

```text
~/.resonance/backups/pre-v2-<UTC timestamp>/
```

When `RESONANCE_DATA_DIR` is set, the `backups` directory is created underneath it instead.

## State and Retry Rules

For each local item, the command applies these rules:

| Existing state | Result |
|---|---|
| Withdrawn v0.1 item | Remains withdrawn; no v2 keys or record are created |
| Active v0.1 item | Gets fresh v2 publication and mailbox keys; status becomes `local` |
| v2 record awaiting relay acknowledgement | The stored signed record is retried unchanged |
| v2 record already acknowledged | It is left unchanged and is not submitted again |
| Tombstoned v2 record | It is left unchanged and is not republished |

The publication secret insert and the transition to `local` occur in one database transaction. A crash before that transaction commits leaves the item eligible for a clean retry. A relay failure leaves the signed record and encrypted keys locally available for the next run. The item changes to `published` only after an `ok` relay acknowledgement.

The command continues past item-specific failures, lists every affected local item ID, and exits unsuccessfully when any item still needs attention. Rerunning it is safe.

## Verify the Result

The summary reports:

- Legacy items discovered
- Fresh v2 identities created
- Items that already had v2 identities
- Publications acknowledged during this run
- Publications still pending
- Withdrawn items skipped

A completed online upgrade has zero pending publications and no item errors. A completed local-only preparation is expected to report pending publications until the online run succeeds.

## Roll Back

1. Stop the desktop app and every Resonance CLI process.
2. Choose one `pre-v2-...` backup directory.
3. Copy both `identity.json` and `resonance.db` from that same directory over the current files.
4. Start the application again.

Never mix the identity from one backup with the database from another. The database encryption key is derived from the identity secret, so a mismatched pair may be unreadable. Rollback only restores local state; any v2 publication already accepted by a relay must still be withdrawn with its v2 publication key before discarding the upgraded database.

## Security Invariants

- The root identity remains encrypted locally and never signs the replacement publication.
- Publication and mailbox key material is generated independently for every item.
- New secret keys are encrypted before persistence and cleared from the temporary upgrade buffer afterward.
- Raw text, embeddings, and local item UUIDs never leave the local store during upgrade.
- Legacy matches and channels remain local history and cannot silently become v2 consent or channel state.
