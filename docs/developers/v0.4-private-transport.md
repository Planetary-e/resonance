# v0.4 private transport: implementation sequence

The v0.3 protocol protects some payloads, but a relay that receives a request can still associate its network source with the operation. v0.4 must separate those observations for publish, search, and mailbox traffic. The [roadmap](../../roadmap.md) defines the full completion test; a TLS connection alone does not satisfy it.

## Threat model and route

For each operation the client selects two **distinct, verified** volunteer relays: an entry and a destination. The client encrypts the operation for the destination and wraps it in an independently encrypted instruction for the entry. The entry sees the client's address and the next hop, but cannot read the operation. The destination sees the operation and the entry's address, but should not receive the client's address or stable client identifier. Replies follow a short-lived return route. Selection must account for distinct relay identities and observed failure domains; bootstrap hints alone are not trust evidence.

This construction assumes the two relays do not collude. Colluding relays or a global observer can correlate timing and volume; padding, batching, jitter, route rotation, and measurements are later parts of v0.4. A volunteer-only network cannot promise an available two-hop route at every moment. A client should queue or retry a private operation when it cannot find two suitable relays, rather than silently fall back to a direct request.

Use a reviewed hybrid public-key encryption design such as [HPKE (RFC 9180)](https://www.rfc-editor.org/rfc/rfc9180) for hop payloads, with authenticated relay public keys in signed descriptors. Before implementation, specify key rotation, context separation, expiry, replay rejection, bounded frame sizes, return-route lifetime, and what each hop signs. Do not reuse the v0.3 DID or an admission credential in an observable outer frame.

## Delivery slices

1. **Transport boundary (started):** Reject Internet-facing `ws://` URLs before client, discovery, and relay-link dials, and before relay advertisement. Permit cleartext loopback and private-LAN endpoints for local testing. This does not yet provide TLS service or remove local-network observers.
2. **Reachable TLS (started):** The standalone relay can load a certificate and private key with `RELAY_TLS_CERT_FILE` and `RELAY_TLS_KEY_FILE` to serve HTTPS/WSS directly. Set `RELAY_PUBLIC_ENDPOINTS=wss://your-host:port/` with a certificate whose name matches that host. Both files must be supplied, and a TLS listener cannot advertise `ws://`. Alternatively, terminate TLS in a trusted local reverse proxy and bind the relay's cleartext backend to `RELAY_HOST=127.0.0.1`; the server rejects a non-loopback backend when advertising `wss://` without its own TLS configuration. Keep the backend port inaccessible from outside the machine. Certificate issuance, renewal, and cross-household validation remain operator/deployment work. Audit inbound paths, reverse proxies, and bootstrap/configuration surfaces.

   A direct TLS relay can be started with:

   ```sh
   RELAY_HOST=0.0.0.0 RELAY_PORT=9090 \
   RELAY_TLS_CERT_FILE=/secure/path/fullchain.pem \
   RELAY_TLS_KEY_FILE=/secure/path/privkey.pem \
   RELAY_PUBLIC_ENDPOINTS=wss://relay.example.org:9090/ \
   npm run start --workspace=@resonance/relay
   ```

   The relay binds to `127.0.0.1` by default. Use `RELAY_HOST=0.0.0.0` only when you intend to accept external connections through a TLS listener, or when explicitly opting into private-LAN discovery. Protect the private-key file with operating-system permissions. Use a certificate trusted by the clients; the test's bundled self-signed key is solely a local fixture.
3. **Two-hop protocol:** Define bounded request and response frames, independent relay choice, encrypted hop layers, authenticated acknowledgements, and retry behavior. Test entry/destination views in separate processes.
4. **Anonymous admission:** Introduce one-use blind capabilities with community issuance, replicated spends, and partition behavior. Remove linkable per-DID controls only once equivalent abuse controls work.
5. **Traffic and fingerprint privacy:** Add route rotation, short sessions, padding, batching and jitter; rotate group fingerprint epochs; measure privacy, availability, and match quality under churn and adversaries.

No v0.4 privacy claim is complete until the roadmap's end-to-end observation test passes.
