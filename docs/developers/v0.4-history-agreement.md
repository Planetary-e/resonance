# Signed successor agreement on durable volunteer stores

Status: **experimental replica implementation, 2026-10-15**. This implements the
signed messages and durable transitions selected by the
[view-change evaluation](v0.4-successor-view-change-decision.md). It does not yet
provide a network coordinator, automatic payload repair or writer activation.

## What changes

The earlier [one-shot reservation](v0.4-history-checkpoint-successor.md) can split
two honest volunteers for A and two for B. A dishonest fifth signing both leaves
each proposal with three votes. Those irrevocable reservations still cannot be
reset. The new protocol separates a tentative preparation from confirmation,
allowing a later round to resolve tentative choices using verifiable evidence.

The membership remains five pinned volunteers and the quorum remains four. A
view is a recovery round for the same context, root and predecessor/successor
generation pair. It does not change membership or create a new writer generation.
Safety assumes at most one Byzantine volunteer, retained honest state and no
duplicated honest signing identities. Progress additionally needs a stable
proposer and four available volunteers holding the admissible complete history.

## Authenticated evidence

`@resonance/core/history-agreement` defines separately versioned/domain-separated
v2 requests, reports, preparation votes and confirmation votes. Every request is
owner-signed and binds the target volunteer, slot, view, challenge, validity
window, exact proposal identity and exact proof digest. Every reply is signed by
the pinned target. Requests last at most 30 seconds; historical evidence remains
valid after that window. Expiry cannot revoke an issued vote.

- **Promise:** durably enter a view and report the highest preparation certificate
  retained before an earlier confirmation. Four distinct same-attempt reports
  form a view certificate. Same-view retries retain the original entry snapshot.
- **Prepare:** verify four view reports. Preserve the proposal from their highest
  valid prepared proof, or select a valid proposal if none exists. Conflicting
  highest proofs refuse work. Verify every selected local ciphertext block and
  persist one proposal choice in the current view before returning a vote.
- **Confirm:** require the matching four-member preparation certificate and the
  volunteer's own preparation in the still-current view. Persist that complete
  proof before returning confirmation. Four matching confirmations decide the
  proposal even when the replies never reach the owner.
- **Advance:** a higher promise clears only the current tentative preparation;
  it preserves the proof behind the highest previous confirmation. Older
  preparation and confirmation requests are refused thereafter.

The candidate value reuses the immutable owner-signed successor proposal. Its
identity remains unchanged across views. Legacy `sealed` receipts cannot serve
as either new phase. Vote/report collections require four distinct members from
one exact attempt, and parsers canonicalize member order before hashing proofs.
Public hash/selection helpers expect already parsed evidence.

## Persistence and compatibility

`createHistoryAgreementReplica` is an explicit local entry point over the existing
checkpoint store. The store saves the agreement in its encrypted manifest, using
the same lock and atomic file/fsync/rename/directory-flush sequence as the payload
index and freeze barrier. Signed responses remain local until persistence
completes. A final expiry check can suppress a response without undoing the
persisted transition. Uncertain I/O failures poison the handle until reopen.

Reopen authenticates retained requests, reports, votes and certificates, checks
their phases, proposal relationships, context/member/root/generation pins and
complete selected ancestry, then loads the indexed ciphertext blocks. Retained
state includes the entry report, the current tentative vote and the highest
confirmed prepared proof; it does not grow an unbounded chain of earlier views.

Opt-in is deliberately narrow:

1. A valid first promise may opt in an already frozen store with **no legacy
   successor reservation**. The opt-in and view barrier are one manifest write.
2. A store with any legacy reservation refuses opt-in, preserving that exact
   reservation. Four old vote reports do not justify resetting it.
3. After opt-in, legacy sealing and repair are refused, as are changes to the
   successor generation. Ordinary writes remain frozen. Same-barrier freeze
   requests and reads remain available.
4. Unmodified older manifests remain readable. Older binaries reject the added
   manifest field, preventing silent downgrade of an opted-in store.

This fences the two protocols at each honest signer. It does not make an existing
split set of legacy reservations recoverable. Four legacy seals and four new
confirmations cannot coexist under these honest-state rules: their signer sets
intersect in honest volunteers that refuse participation in both protocols.

Frames are bounded to 256 KiB, view certificates to 192 KiB, individual reports
to 64 KiB and vote certificates to 16 KiB. Existing proposal, manifest and storage
bounds still apply. Views range from 1 to 1,000,000 and never wrap. An optional
independent `minimum.agreementView` anchor detects rollback to an earlier view.
It does not detect erased votes within the same view; deliberate deletion,
copied signing identities and complete rollback without an adequate external
anchor remain outside the guarantee. SIGKILL is not a physical power-loss test;
Windows retains the existing limitation of file flushes without directory fsync.

## Validation

```sh
npm run build
npx vitest run --maxWorkers=1 history-agreement
```

The 19 new tests use real signatures, encrypted manifests and ciphertext blocks.
They cover four-volunteer completion with a silent fifth, a two/two tentative
split with an equivocating fifth, a hidden final certificate, higher-view proof
selection, old-message refusal, restart, failed fsync and expiry during
persistence. They also reject forged/duplicate/mixed-attempt/wrong-phase evidence,
wrong slots, oversized frames, missing or newer local payloads, incompatible
legacy reservations, damaged retained relationships and anchored view rollback.
Nine subprocess cases use SIGKILL before rename, after rename and after durable
completion of each phase, with no delivered signed reply.

TypeScript compilation passes. With production and test sources unchanged during
the run, the complete local suite passes **125 files / 734 tests** using one
worker in 437.13 seconds. These are local single-host checks, not Internet or
physical power-loss certification.

The preceding [CI run](https://github.com/Planetary-e/resonance/actions/runs/38741875420)
failed two existing tests: a four-round real-crypto test exceeded Vitest's default
five-second budget, and the relay-link test read an expired descriptor while its
connection was refreshing. This change gives that crypto test a 15-second test
budget and waits for both authenticated link ends plus a current descriptor.
Production deadlines and descriptor lifetimes are unchanged. All 22 tests in
those two files pass locally. Remote CI must confirm these fixes on Linux.

## Next boundary

Add bounded network exchange and a durable owner coordinator that can recover
its exact pending phase and collect fresh same-attempt replies. Compose the
agreement with complete-history selection and suffix transfer before opting in
volunteers that lack blocks. The current implementation requires the selected
chain to be present already and refuses both missing and newer local tails; a
signature never authorizes truncation. Prove progress for this combined protocol,
then implement certificate-controlled activation and cross-generation ancestry.
No live admission restore or installer is enabled by this milestone.
