# Fresh policy observations in bounded batches

## Problem and decision

The calibrated 25 ms application experiment completes serial operations but
only three of six paired searches. A protected admission decision has three
seconds including queue waiting. Each complete transaction takes about
1.86–2.00 seconds, so the second transaction cannot finish in the remaining time.
The coordinator also asks five witnesses to consult the same five observers.
Those consultations repeat read-only history checks through bounded sockets.

Moving the coordinator's first policy query outside its writer queue saves only
about 0.27 seconds and does not resolve this measurement. It can also consume
the freshness slot needed when the coordinator is itself a witness. Witness
authorization is not a read-only preflight: it persists votes and a certificate.
It must not be moved outside the existing serialization without a separate
durability design.

The selected change instead lets a protected observer check at most two
already-queued, read-only requests against one newly collected history quorum.
Each caller retains its own challenge, signed vote and deadline. No policy or
history wire format changes. Admission decisions, certificates and spend
writes keep their existing serialization.

## Freshness argument

Both requests are copied and validated before the shared history collection
starts. That collection obtains four current, authenticated head replies. Each
caller then receives a separately signed vote bound to its original request.
The common read occurs after both requests arrive and before either response.
Updates and recovery fencing cannot run during that read.

This replaces the requirement for a distinct internal history challenge per
caller with a fresh challenge per bounded batch. It does **not** replace the
distinct caller challenges. A request arriving after collection starts needs a
new collection, even if the previous result has not yet been returned. A
completed result is never cached as authority for a later request.

The queue can group only adjacent reads. An earlier policy advance is an
exclusive barrier: requests behind it cannot join a batch in front of it.
Missing history, a stale restored owner, a freeze, a pending write or retained
terminal conflict still prevents a usable observation.

## Bounds and cancellation

The existing eight-request exchange bound counts callers, including queued
requests and active batches. A batch contains at most two callers and only one
batch runs through this exchange at a time. A local implementation must
explicitly support batching; other observers retain their existing path.
No socket, history-operation, byte or deadline cap is increased.

Scheduling waits only until the next event-loop check phase to gather requests
already waiting. There is no additional timed collection window. Queue time
still counts toward each original monotonic and signed deadline. A shorter or
expired request cannot receive a late vote or extend another request's budget.
Local validity checks run before signing and again before returning each reply.
Work that has not actually settled remains charged.

## Validation status

The composed TypeScript build and strict standalone application-evaluator
typecheck pass. All 63 distinct focused cases pass across bounded runs: 46
existing observer/configuration cases, 16 new batch cases, and a final retained
pending-update regression. The initial stale-backup test incorrectly copied an
open writer's ownership marker; closing before the snapshot reproduced the
intended coherent stale backup, which is refused after the current owner advances.

The dedicated suite establishes one fresh collection for two pre-start callers,
separate authenticated votes, new collections for later callers, immutable
request snapshots, original monotonic expiry, FIFO updates, eight-caller
accounting, and refusal on close, freeze, lost quorum, expiry, fencing, retained
conflict, stale backup or unconfirmed durable updates. An adapter that ignores
abort remains charged until it actually settles. Independent read-only review
checked both the production change and these assertions.

The subsequent [complete application measurement](../evals/v04-policy-batches-2026-10-18.md)
still fails three of six paired searches. Batching reduces TCP bytes by 15.4%
across those rounds, but the second protected decision still exhausts its
original queue-inclusive deadline. This change does not establish the concurrent
latency target, public Internet operation or completion of v0.4.
