# Completing readiness after a published restoration

A restore can publish the protected owner image and then lose its fourth
volunteer before obtaining readiness. A process can also die between publishing
that image and creating its empty writer/archive. Neither case permits restoring
over the folder, resetting it or starting admission from cached receipts.

## Reviewed resumption

Resume the completed recovery workspace in the desktop, then select **Review
retained restoration** for an occupied destination. The command-line equivalent
is:

```sh
node --import tsx scripts/admission-history.ts owner-recovery-readiness-plan owner-config.json enrollment.json owner-storage.hex recovery-work policy.json retained-owner
node --import tsx scripts/admission-history.ts owner-recovery-ready --approve <digest> owner-config.json enrollment.json owner-storage.hex recovery-work policy.json retained-owner
```

Both use the same pinned direct or optional outbound operator transport as the
other recovery commands. The desktop retains its stopped-runtime/control claims.
Standalone command users must coordinate stopping the old process themselves.

Review is offline. It replays the completed workspace's authenticated selected
ancestry and checks that the destination's encrypted image has the same genesis,
certified successor and replayed baseline. It holds the spend-store lock while
reading the validated state. It does not open/create the writer/archive, finish a
pending update, contact volunteers or install a policy/service configuration.

The displayed counts describe locally applied spends and denials; a separately
reported pending update may still need completion. Approval binds the exact local
state, requested signed policy, root/generation, storage-key identity and any
unfinished pristine setup. The desktop additionally binds its selected files,
routing and output locations. Another review is required if those inputs change.

Apply releases inspection and opens the ordinary protected history with the
expected-state digest checked **before** any writer setup. Existing writer/archive
consistency checks remain required. It completes only the exact retained work,
applies the explicitly reviewed successor policy if needed and requires four
fresh exact-head copies. It leaves the relay paused. Activation and a subsequent
ordinary service start remain separate and recheck readiness.

## Pristine setup versus lost committed history

A missing writer or archive alongside locally applied history is refused. The
existing writer/archive validation also refuses reconstructing a committed writer
from an empty index. No capability initializes a missing spend image. Unknown
files, damaged journals, mismatched baselines and uncertain process ownership
remain evidence to preserve.

An explicitly approved retry may finish first archive publication when the parent
writer has neither a committed nor pending entry. Only its recognized manifest
lock and encrypted manifest temporary filenames may be present, and each must be
a regular file. The normal encrypted-state lock must establish exclusive
ownership before cleaning those unpublished snapshots. Live locks, interrupted
lock-recovery guards, symlinks and other files refuse resumption. This exception
is not enabled by ordinary startup or a generic archive initialization request.

If an attempt fails after making setup durable, retain the folder and review
again. Its new state may produce a different approval. Cancellation cannot undo
already durable state; success requires a fresh readiness check, not a previous
review or an old root receipt.

## Validation scope

The regression covers lost-fourth-copy restoration and reviewed completion through
the authenticated desktop API, wrong approval without network transmission,
offline missing-writer inspection, changed-state refusal before setup, committed
writer/archive loss, and process death before/after writer creation, archive index
publication and local apply. Archive tests exercise unknown files, pending writer
evidence, live ownership, recovery guards and symlinks. Package compilation and
**96 tests / eight files in 179.71 seconds** passed. After final guard and lifetime
assertions, the affected recovery/protected/API group passed **53 tests / three
files in 132.94 seconds** and compilation passed again. These groups overlap.
Native service installation,
independent volunteers and physical power-loss behavior remain external gates.
