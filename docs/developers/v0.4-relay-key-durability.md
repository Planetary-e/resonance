# Relay infrastructure key durability

The relay's Ed25519 identity is separate from personal account keys and from the
operator's TLS certificate/key. Its encrypted format remains scrypt (N=32768,
r=8, p=1, 32-byte output), AES-256-GCM, a random 16-byte salt, 12-byte nonce,
16-byte tag and a fixed format-specific associated-data string. Reachable WSS
configuration still requires the encrypted infrastructure key. Plaintext remains
available only for existing development configurations; supplying a passphrase
migrates the same identity rather than generating another.

## Findings and correction

The previous initial publication avoided overwriting a competing creator, but
plaintext-to-encrypted migrations did not share process ownership. Two processes
could both read the plaintext key and replace its encryption with different
passwords. Random temporary names also had no defined interruption recovery.

Creation, load and migration now share the canonical directory's existing
PID/nonce ownership mechanism. One deterministic candidate is written with mode
0600, bounded to 4 KiB, completely written, fsynced, directory-flushed and renamed
atomically under that ownership. The published name is directory-flushed before
success. The primary is never deleted to start over. If a complete candidate
survives interruption, restart authenticates it, compares its key with the
retained original when present, refuses an encryption downgrade, flushes it and
finishes the exact publication. No new salt/key/ciphertext is generated during
that recovery. A partial or conflicting candidate remains for inspection and
blocks the writer. Older random temporary keys also remain and require explicit
inspection; startup never chooses among unknown artifacts.

Bounded, fatal-UTF-8 reads reject symlinks, external hard links, file substitutions
and changes during reading. Key schema, canonical encoding, DID and full keypair
verification remain mandatory. Failed validation and interrupted writes clear
owned secret buffers; authenticated-decryption buffers are cleared even when GCM
or JSON parsing fails. JavaScript strings and runtime-internal copies cannot be
promised securely erased. The read-only operator loader neither changes modes
nor recovers candidates, and continues to require an already encrypted identity.

Managed storage reserves 16 KiB for primary, candidate and ownership metadata.
Existing smaller reservations must grow before mutation; a full authority may
refuse that growth while preserving existing files. The directory inventory is
bounded to 4096 entries. Ownership assumes cooperating processes on one local
filesystem, with a trusted operating-system account. It does not claim distributed
filesystem locking, protection from a hostile local account, secure physical-disk
erasure or a password-reset recovery mechanism. Windows flushes files but does
not support the directory-flush operation used on Unix. SIGKILL tests establish
process-interruption behavior, not physical power-loss guarantees.

## Evidence

The focused key/configuration/storage/TLS group passes **52 tests in six files**
in 13.70 seconds; the separate operator-transport group passes 15 tests in 2.09
seconds and TypeScript passes. It includes 19 process-interruption and
concurrency cases: SIGKILL during initial creation and encryption migration,
reported write/flush/publication failures, and three competing processes using
different passwords. Completed candidates recover byte-for-byte; incomplete
ones remain and never cause key rotation. Negative cases retain originals after
conflicting keys, downgrade attempts, oversized/malformed candidates, orphaned
legacy temporaries and unsafe links. The read-only path preserves bytes/modes.
The Linux/macOS/Windows lightweight CI matrix includes the key and interruption
tests; all three jobs pass at `1ae3806` / run `39073398153`. The complete
Linux suite for that commit remains pending.

The full transport/schema/signature audit and external operator secret-handling
and backup practices remain separate completion gates.
