# Native Ed25519 verification

## Finding and change

Cold replay of a nearly full protected witness/coordinator image spent most of
its time repeatedly validating signatures with TweetNaCl. Comparing verification
backends also exposed a security defect: the old verifier accepted five invalid
signatures from the pinned C2SP/Wycheproof Ed25519 vectors (63, 64, 65, 66 and 85).
Their scalar S is outside the canonical range required by
[RFC 8032 §5.1.7](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.7).
This permits alternative encodings of a signature; this finding does not show
that arbitrary messages can be forged or that a deployed system was exploited.

The shared `core/crypto.ts` verifier now uses Node's native Ed25519
[`crypto.verify`](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoverifyalgorithm-data-key-signature-callback)
with the required null algorithm. It checks 32-byte public keys and 64-byte
signatures, constructs standard Ed25519 SPKI key objects, and returns false on
malformed input. Signing, generated keys, signed payloads and wire formats are
unchanged. Existing valid records need no conversion. Noncanonical records are
refused; history readers do not delete them or initialize empty replacement state.

At most 512 public key objects are retained, indexed by copied key bytes and
admitted only after a successful verification. No private keys or signature
results are cached here. The separate retained-vote and history verification
caches keep their existing exact-content bounds and authorization checks.
This core runtime already targets Node; the desktop frontend has no runtime
imports of this module. Native verification is exercised on all three supported
operating systems in the lightweight CI job, without building installers.

## Evidence

The pinned upstream vectors and Apache-2.0 license are in
`packages/core/src/__tests__/fixtures/wycheproof/`. The 151 vectors comprise
88 valid and 63 invalid cases. Before the change, five invalid cases were
accepted and twelve malformed lengths threw instead of returning false. After
the change all vectors pass. Additional checks cover existing generated
signatures, messages through 64 KiB, mutated messages/signatures/keys and key
views within larger buffers. These finite vectors are not a full cryptographic
audit or an equivalence proof for every possible input.

Local Node v24.19.0 validation on 2026-10-17:

- TypeScript build passes.
- Core vectors, crypto, history-signature cache and policy archives: 180 tests /
  four files / 0.98 s.
- Admission, rotation, encrypted envelopes/forwarding, mailbox signatures,
  retained roles, real private-client/witness sockets and role SIGKILL recovery:
  73 tests / twelve files / 41.17 s.
- Full CI and the cross-platform native-verification matrix are separate gates.

and [previous report](../evals/protected-role-process-costs-defaults-2026-10-17.json)
use 2,691 retained rows per role, 7,548,300 plaintext image bytes, five separate

and role code.

All new measured operations succeed. A concurrent two-request witness burst
still accepts one and refuses the competing writer; this is bounded exclusion,
not a throughput claim. Capture offers and delivers 50,351,200 application bytes
across five copies. Subsequent new witness/coordinator writes offer 12,260 /
23,660 bytes respectively; exact retries offer no new history traffic.

The experiment uses one Mac, generated fixtures, loopback and a fixed clock for
signed-policy validity. Fixture seeding is excluded from admission-throughput
claims. Process peaks include runtime and prior allocations; they are not a RAM
budget guarantee. Application bytes exclude witness transport and TCP/TLS
framing. Internet delay, independent volunteer availability, total traffic and
device energy still require their separate roadmap validation.

## Native signing in the composed application (October 18)

The protected real-application workflow initially exceeded the ten-second
mailbox delivery budget. A parent-process CPU profile of that failed run recorded
54.5 seconds elapsed, including 23.9 seconds idle and 8.9 seconds in `fsync`.
Two TweetNaCl arithmetic functions alone accounted for 10.1 seconds; call stacks
led through repeated infrastructure-key self-checks and signed history exchanges.
This is one diagnostic run, not a throughput benchmark.

`sign()` now uses Node/OpenSSL Ed25519. It imports the existing 32-byte seed in
the [RFC 8410 private-key encoding](https://www.rfc-editor.org/rfc/rfc8410#section-7),
derives and checks the existing NaCl key's public half, then signs the unchanged
message. It does not cache private keys and clears its temporary seed encoding.
Malformed/truncated/mutated keys refuse. The wire format, keys, signatures and
all durability flushes remain unchanged.

The native output matches TweetNaCl byte for byte for messages from zero to
65,536 bytes, and matches the first three
[RFC 8032 signing vectors](https://www.rfc-editor.org/rfc/rfc8032#section-7.1).
The 151 pinned adversarial verification vectors still pass. The five-file
crypto/protected-role/observer group passes 216 cases; the final vector file
passes 157 cases after adding the three RFC examples. These counts overlap.

The full protected application subsequently completes, including mailbox
delivery, restart and quorum-loss checks. Its maximum observed mailbox API time
is 9,111 ms, still close to the unchanged ten-second deadline. See
`../evals/v04-real-app-2026-10-18.md`; independent Internet latency remains a gate.
