# Protected issuer history

This development component protects a new issuer's allowance and exact issuance
responses on five explicitly enrolled volunteer devices. A mutation needs four
durable acknowledgements before the issuer releases its result. It advances the
K2 recovery and K4 admission work; neither gate is complete.

## What is protected

The encrypted history retains the signed allocation and claim assignments,
consumed allowance, permit secrets, exact batch reservations, prepared and
completed responses, installed policy, policy-observation floors and conflicts,
and sealed retirement. Volunteers receive signed encrypted checkpoints. They do
not receive the RSA issuer private key or the checkpoint decryption key.

Protection is explicit and supports **new ledgers using allocation v2 and signed
claim assignments**, plus reviewed restoration of their protected history.
Initialization requires an independently pinned
community authority, a matching signed current policy, the history owner key and
five history-member pins. Policy observers are also explicitly pinned at creation;
grant and issuance commands collect a new observation for each attempt. Five keys
and endpoints do not establish five independent operators or failure domains.

The protected file has its own outer schema. The ordinary local issuer command
cannot reopen it as an unprotected ledger. There is no implicit conversion of an
existing issuer, no fallback to a local-only write, and no replacement of a missing
owner file, writer or archive with empty state.

## Commit and retry behavior

Each mutation first retains the exact encrypted checkpoint locally, then obtains
four durable acknowledgements, then applies the state locally. Relevant policy
authorization is checked again before returning a permit or signed response.

- A grant protects the assignment, secret and quota debit before returning the
  permit. Recovering that same assignment returns its retained permit, without
  another debit.
- Issuance protects the exact permit-to-batch binding before blind signing.
  Another request cannot take over that reservation.
- Generated signatures are retained as a prepared response before promotion to a
  completed response. Expiry does not refund the allowance or authorize a different
  batch. Completion must itself be protected before the response is released.
- Capacity for both response checkpoints is checked before signing. If the process
  dies after reserving the batch but before durably saving its signatures, restart
  cannot tell whether signing happened. That unresolved reservation refuses
  automatic re-signing; it is not a recoverable completed response. Its quota stays
  consumed. This conservative failure boundary can strand a permit.
- Restart finishes the same pending checkpoint. A certificate written before an
  interrupted local apply does not cause a new mutation. Serving again requires
  fresh acknowledgements for the exact retained head.
- With only three available members, new protected mutations cannot finish.
  Pending work remains retained and prevents a different operation from replacing
  it. Failure to export a result does not undo a committed grant or issuance.

Opening and local status inspection do not establish network readiness. Explicit
readiness and mutation commands contact the pinned volunteers. Closing during a
request prevents a later result from escaping the closed handle.

## Operator commands

Use the existing [signed allocation and assignment workflow](v0.4-claim-assignments.md)
to prepare `allocation.json` and a private `assignment.json`. Supply the RSA issuer
profile/key, independently verified `authority.pub`, current signed `policy.json`
and [policy observer pins](v0.4-policy-freshness-decision.md). Protected mode requires
observer enrollment at creation; it cannot be removed on reopening.

`owner-private.json` contains the separate Ed25519 history owner's base64url
`publicKey` and `secretKey`. `members.json` is an array of five
`{ "publicKey": "…", "endpoint": "…" }` records supplied by the volunteers.
Public deployment endpoints must use the existing TLS/pinning configuration;
unencrypted loopback listeners are for local tests.

```sh
node --import tsx scripts/protected-admission-issuer.ts config --approve owner-private.json authority.pub policy.json members.json issuer-config.json
node --import tsx scripts/protected-admission-issuer.ts init --approve issuer-config.json issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub allocation.json policy.json observers.json issuer-enrollment.json
```

Initialization writes local state and exports the signed encrypted root. It does
not claim readiness or contact volunteers. The writer/archive lives alongside the
ledger at `issuer-ledger.json.history`; retain both. Existing local ledgers cannot
be passed to `init` to convert or reset them.

Give the enrollment artifact to each pinned volunteer through the agreed trusted
channel. Each volunteer reviews and enrolls its own history using its distinct
member signing key and local storage key:

```sh
node --import tsx scripts/admission-history.ts replica-plan issuer-enrollment.json member-private.json storage-key.hex volunteer-history
node --import tsx scripts/admission-history.ts replica-enroll --approve '<approvalDigest>' issuer-enrollment.json member-private.json storage-key.hex volunteer-history
node --import tsx scripts/admission-history.ts replica-serve issuer-enrollment.json member-private.json storage-key.hex volunteer-history 8443
```

The digest comes from that volunteer's exact `replica-plan` output. The dedicated
listener is loopback-only; use the existing secure proxy or pinned relay transport
for other computers. Only these enrollment/serve commands accept the new issuer
role. Spend-specific restore, limits and retention commands do not operate on it.

Once four enrolled volunteers are reachable:

```sh
node --import tsx scripts/protected-admission-issuer.ts ready issuer-config.json issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub
node --import tsx scripts/protected-admission-issuer.ts grant --approve issuer-config.json issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub assignment.json permit.json
node --import tsx scripts/protected-admission-issuer.ts issue --approve issuer-config.json issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub permit.json request.json response.json
node --import tsx scripts/protected-admission-issuer.ts status issuer-config.json issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub
```

`request.json` is the client's existing blinded batch request. Give the permit and
response privately to that client. Every grant/issue invocation establishes fresh
history readiness and collects fresh policy evidence. Exports create new files;
after a failed output, use another filename for the exact assignment/batch retry.
The command refreshes an expired signing observation at most once, without
re-signing a durably prepared response. An unresolved reservation remains refused.

`policy --approve <common> next-policy.json signed-advance.json` installs a signed
immediate update. `plan-retirement <common>` returns a digest for
`retire --approve <digest> <common>`, after the existing retry cutoff. `<common>`
means the five config/profile/private-key/ledger/authority arguments shown above.
`enrollment <common> new-enrollment.json` re-exports the existing root. Status and
enrollment export remain offline. `RESONANCE_HISTORY_OPERATOR_TRANSPORT_FILE`
selects the existing explicitly pinned outbound transport when direct history
endpoints are not available; a bad supplied configuration never selects a fallback.

## Recover lost owner state: development API

Authenticated history replay and reviewed restoration are available through Node
APIs and an explicit resumable operator workflow. Desktop recovery controls are
not implemented. The existing generic protocol components supply the evidence;
the spend-specific restore command is not an issuer restore command.

Retain the RSA issuer key, Ed25519 history owner key, original genesis identifier,
context/member pins, issuer profile and authority independently of the lost device.
Volunteers retain ciphertext and cannot reconstruct either private key. Restoring
an old local backup and continuing to issue is not this recovery protocol.

1. Freeze the old generation with `createHistoryCheckpointRecovery`. Obtain a
   **confirmed agreement certificate** through `createHistoryAgreementCoordinator`
   and create its continuation root. A successor reservation alone is insufficient.
2. Download the complete selected ancestry with `createHistoryAncestryDownload`,
   including earlier generations back to the independently pinned genesis. Provision
   the certified successor through `createHistoryProvisionCoordinator`.
3. Call `prepareProtectedIssuerRestore` with that continuation, downloaded blocks,
   retained pins and encryption key, and a new owner path plus empty writer directory.
   Review its exact destination, generation, retained totals, policy floor, conflict
   and retirement status, then supply its approval digest to the protected API.
4. Open with the returned in-process capability; then call `ready()` to obtain fresh
   four-member evidence in the successor generation. Opening is offline. Agreement
   certificates, provisioning receipts and restored data alone do not authorize serving.

```ts
const preparation = await prepareProtectedIssuerRestore({
  destination: { path, writerDirectory }, context, genesisId, profile, authority,
  encryptionKey, continuation, blocks, minimumEvidence,
});
// Inspect preparation.review before approving its exact digest.
const issuer = await openProtectedAdmissionIssuerLedger({
  path, expectedProfile: profile, privateKey, expectedAllocationAuthority: authority,
  restore: { preparation, approvedDigest: preparation.review.approvalDigest },
  protection: { context, signingKey, members, writerDirectory,
    initializeWriter: true, initializeArchive: true },
});
await issuer.ready();
```

Replay authenticates every full checkpoint and transition. It rejects gaps,
truncation, changed assignments or responses, quota resets, backwards policy floors,
cleared conflicts and post-retirement issuance. Optional `minimumEvidence` contains
independently retained exact applied/pending images; every supplied image must occur
in the selected history. Replay cannot discover facts lost before any durable copy.
The review object is an in-process capability: a JSON copy or fabricated object
cannot authorize restoration. Its digest binds both destinations and all recovery pins.

Restoration preserves the exact baseline, including expired policy, unresolved
reservations, prepared responses and permanent retirement. It does not refresh a
policy or release allowance. Install an authenticated policy successor through the
normal path when required. A prepared response can complete without signing again;
a bound batch without a retained response remains unresolved and refuses signing.
Historical images do not retain every observation certificate or blinded request:
replay validates authenticated state and its preservation, not every past live check.

### Resumable operator commands

Keep the **original generation-zero enrollment** exported during initialization.
A later enrollment export from a restored issuer contains its continuation and
cannot replace that original pin. The existing issuer config, profile, keys and
authority remain applicable. `<common>` below means the same five
`config.json profile.json private.pem source-ledger.json authority.pub` arguments
as the ordinary issuer commands. The source writer is `source-ledger.json.history`.

```sh
node --import tsx scripts/protected-admission-issuer.ts recovery-plan <common> original-enrollment.json recovery-workspace available 1
node --import tsx scripts/protected-admission-issuer.ts recovery-start --approve '<freeze-review-digest>' <common> original-enrollment.json recovery-workspace available 1
node --import tsx scripts/protected-admission-issuer.ts recovery-status <common> original-enrollment.json recovery-workspace
node --import tsx scripts/protected-admission-issuer.ts recovery-step <common> original-enrollment.json recovery-workspace
```

Planning is read-only discovery; starting applies the exact reviewed approval.
With `available`, the source must open successfully and the review captures its
applied and pending evidence. Start completes the same pending checkpoint without
new blind signing, then durably fences the source before freezing its remote
generation. The fence survives restart and prevents subsequent issuance, readiness,
policy mutation or retirement from that source. Failed pending completion preserves
the source and refuses recovery; it never silently drops the pending image.

Use `unavailable` instead of `available` only when explicitly declaring loss of the
source. A missing/corrupt file or occupied lock never makes that choice automatically.
`1` is the initial agreement view. An existing workspace cannot be reset with a new
plan. Retain all interrupted files for inspection; a missing registered component
is an error. A workspace not yet published but containing interrupted temporary
files is preserved; select a separate empty workspace and obtain a new review.

Repeat `recovery-step` while inspecting the returned phase. The approved workspace
journals freeze, selection, download/semantic validation, confirmation and provisioning.
Each attempt has finite bounds and resumes existing component identities. Semantic
validation and preservation of known source evidence precede agreement confirmation.
`recovery-status` is offline. A completed workspace is ready for destination review,
not for issuance.

```sh
node --import tsx scripts/protected-admission-issuer.ts recovery-review <common> original-enrollment.json recovery-workspace restored-issuer.json
node --import tsx scripts/protected-admission-issuer.ts recovery-restore --approve '<restore-review-digest>' <common> original-enrollment.json recovery-workspace restored-issuer.json
```

Restore writes a new owner file and `restored-issuer.json.history`. If publication
is interrupted after the owner exists, review the exact retained artifacts:

```sh
node --import tsx scripts/protected-admission-issuer.ts recovery-resume-plan <common> original-enrollment.json recovery-workspace restored-issuer.json
node --import tsx scripts/protected-admission-issuer.ts recovery-resume --approve '<resumption-review-digest>' <common> original-enrollment.json recovery-workspace restored-issuer.json
```

Resumption replays the selected history and authenticates the retained restored
baseline. It recreates only demonstrably pristine missing writer/archive components,
after four fresh exact unfrozen root heads rule out a later accepted suffix. Missing
archive data alongside committed history is refused. Changed files or destinations
invalidate approval. Both restore and resumption leave readiness unverified; run
the ordinary `ready` command with the restored ledger path before use. Retain the
recovery workspace and original enrollment; this workflow does not compact them.

## Bounds and remaining limits

The logical checkpoint payload is limited to 8 MiB; the encrypted outer owner file
is limited to 32 MiB. The outer file can contain the applied state, root and pending
ciphertext; a restored owner also retains its immutable baseline and continuation,
so its bound can refuse work before the logical maximum. Writer and
archive files have separate limits. Full checkpoints consume archive space on
every mutation; this is not an efficient long-term compaction format.

Issuer histories cannot use the shared ciphertext-only compaction certificate.
Archive exhaustion refuses new work rather than deleting accepted obligations.
Semantic compaction and bounded migration remain separate work.
The two-response headroom check follows durable batch reservation. If that check
fails, even an unsigned batch can remain reserved and refused on retry; no allowance
is refunded. Initial setup interrupted before all local files exist also requires
inspection; there is no automatic setup repair in this component.

Replay is bounded to 10,001 blocks, 256 MiB in total, 64 MiB per generation and 65
generations. It requires the full selected ancestry; issuer compaction is forbidden.
The default replay deadline is 30 seconds and cancellation is explicit.
Restoration after losing owner state is implemented through both the API and the
resumable operator workflow, with process-interruption tests.
Lost private keys, ambiguous signing, sustainable retention and initial setup repair
remain outside this component's recovery guarantee.

An operator able to copy signing keys, roll back all owner state, operate modified
software or create unrelated authorities remains outside this component's honest
operator guarantee. Assignment protection also does not prove that a claim belongs
to a unique person. Automated eligibility, governance and fair distribution remain
required for K4. Local processes cannot establish independent volunteer availability
or certify the complete v0.4 service.

## Validation

TypeScript and the composed regression pass: **195 tests across 20 files**. The real
CLI test uses separate Node invocations with native addons disabled, five issuer
replicas and five protected observers backed by 25 histories. It checks offline
initialization/status, refusal with three copies, four-copy issuance and unblinding,
exact permit/response retry, repair through a different returning fourth volunteer,
and newer-policy refusal followed by a signed update. Adapter/API tests cover
pending intent and local-apply failures, coherent stale backups, missing files,
capacity, close, freshness expiry, prepared/completed response retention and
permanent retirement. Existing issuer crash tests remain in the regression group.
The restoration tests additionally run five volunteer services over real local
sockets, freeze and confirm successors, download complete ancestry and provision
new generations. Two successive recoveries preserve exact permits/responses and
the unresolved reservation without resetting the exhausted quota; the second starts
after deleting the owner file, writer and archive. They also verify fresh quorum,
old-writer refusal, newer policy floors, offline reopening and permanent retirement
after policy expiry. Policy-observer votes in this recovery fixture are controlled
signed inputs; the separate CLI fixture exercises live observers. Semantic tests
include validly signed regressions, missing known evidence and fabricated review
capabilities. The workflow adds 27 separate-process SIGKILL scenarios at source
fence, journal, every component intent/registration, selection/confirmation,
provisioning and restored owner/writer/archive publication. Real CLI commands run
two generations, including explicit owner loss; status stays offline and readiness
remains separate. Approval tests cover canonical destination/source/workspace pins,
symlink retargeting and retained storage authority. These suites join the macOS,
Windows and Linux ownership CI matrix. See the
[predeclared experiment and results](../evals/v04-issuer-recovery-2026-10-18.md).
All processes run on one computer; these results do not measure Internet availability.
