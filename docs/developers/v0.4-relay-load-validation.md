# Relay recovery under local CPU load

Status: development regression coverage; not a multi-device pilot or a release certificate.

## Why this was investigated

[CI run 37153728421](https://github.com/Planetary-e/resonance/actions/runs/37153728421)
at `ffbc21a` passed 590 of 591 tests. The seven-relay completion scenario failed
while waiting for mailbox acknowledgements to reach every replica after restart.
Its logs also contained repeated five-second handshake timeouts. The same test
passed locally without added load in 13.12 seconds.

Adding 20 milliseconds of synchronous work to **each real Ed25519 verification**
reproduced repeated handshake timeouts locally. That run failed earlier, at the
post-restart connection/receipt gate, in 85.75 seconds. This reproduces the
reconnection failure under load, not the exact CI acknowledgement assertion.

## Changes

- A rejected outbound handshake now ignores later messages. A regression test
  withholds a genuine signed acceptance, lets the dial expire, then delivers
  the buffered message. Previously this installed heartbeat and descriptor
  timers even though the connection promise had already rejected. The test
  checks that neither timer is created. This is independently demonstrated;
  the CI log alone does not establish that this race caused its failure.
- The seven-relay fixture polls every 500 ms, repairs every second, and checks
  inventory every 30 seconds. Previously its 75 ms polling and two-second
  signed inventories competed with all seven relays on one event loop.
- The fixture uses a 15-second handshake budget (the client default), a
  15-second heartbeat timeout, and slower reconnect retries. Production
  intervals are unchanged. The 40-second convergence and 180-second total
  test budgets are unchanged.
- Both ends must report connected before the scenario advances after startup
  or restart. A controller's inbound registration alone occurs before the
  volunteer has validated the acceptance.
- A failed acknowledgement wait reports per-relay envelope counts and link
  status instead of only a generic timeout.

## Reproduce

```sh
npm test -- --maxWorkers=1 packages/relay/src/__tests__/relay-link-client.test.ts
npm run test:relay-load
```

The opt-in load command runs the same seven-relay completion assertions, with
real cryptography and sockets plus 20 ms of extra synchronous work for each
signature verification. It covers five verified replicas, search and encrypted
notice retrieval with the controller and two volunteers down, restart, one
notice per mailbox, acknowledgement propagation, and withdrawal propagation.
Ordinary CI runs the scenario without the artificial delay. The load command
does not build desktop installers.

The added delay models a constrained shared event loop. It does not model
Internet delay, independent CPUs, TLS, energy consumption, arbitrary sustained
overload, or volunteer availability. A passing run is evidence for this bounded
scenario only. Product-wide overload control remains a separate concern.

Local validation on 2026-10-03 (UTC): the corrected load scenario passed in 76.26
seconds, including all recovery and mailbox assertions. The relay-link file
passed all 12 tests, and the TypeScript project build passed. The final full
suite passed **113 files / 592 tests** in 311.89 seconds with one worker.
Remote CI results are recorded with the draft PR; a local pass alone does not
establish that the Linux CI failure is resolved.

Follow-up: [Linux run 37157129754](https://github.com/Planetary-e/resonance/actions/runs/37157129754)
passed the seven-relay completion scenario in 25.673 seconds and the late-acceptance
regression. A different placement/withdrawal test hit its default five-second
whole-test timeout, then a separate restart test expected the missing tombstone
from that incomplete fixture. Placement, withdrawal and restart now form one
scenario with a 30-second total budget; its existing per-request/per-condition
deadlines and production behavior are unchanged. The relay-link file now has
11 tests because these two dependent tests were combined.

Further diagnosis: [Linux run 37173761134](https://github.com/Planetary-e/resonance/actions/runs/37173761134)
passed 597/598 tests. The remaining assertion waited for `already-stored` after
a duplicate submission coincided with descriptor renewal. The repair loop
removed the explicit refresh before attempting the disconnected target, losing
that retry even though the old receipt remained valid. Pending refreshes now
retain each unanswered target and remove only answered targets; one offline
volunteer does not cause continuous retries to peers that already answered.
Refreshes are scoped to the operation signature and cleaned on expiry, intent
removal, target replacement or reconciliation. They remain process-local hints;
durable placement intent and receipt recovery are unchanged.

The placement scenario now explicitly stops the hub without graceful handoff,
submits the duplicate while disconnected, observes the attempted repair and
restarts the hub before checking the signed duplicate receipt. This preserves
the assertion and exposes the race independently of machine speed.
The forced-outage scenario fails against the previous implementation at its
duplicate-receipt assertion and passes with the fix. Final local validation:
TypeScript build and **117 files / 639 tests** pass in 315.72 seconds. This result
includes the independent checkpoint-storage changes; it is not a new load run.
