# Recovering lost admission history: checkpoint decision

Status: **executable design evaluation, 2026-10-04; operational recovery is not implemented**.
The follow-up [storage implementation](v0.4-history-checkpoint-storage.md) adds
real signed encrypted blocks and a local generation barrier, still outside the
live admission path.
The existing relay still refuses missing, empty or corrupt histories. The legacy
proof command still requires intact rows. Nothing here permits an empty reset,
refund, policy rollback, or importing an older backup as the latest state.

## Decision

Develop an opt-in recovery protocol backed entirely by **five pinned volunteer
devices**, initially requiring **four durable acknowledgements** for protected
updates and recovery phases. There is no continuously operated service in this
design. When insufficient volunteers answer, the protected role must wait.

Start with the relay's local spend history. Require recoverable encrypted data,
fresh signed replies, and a durable generation barrier before resuming writes.
A generation identifies the authorized incarnation of the writer. Freezing the
old generation must stop its writes even if the old process is still running.
Preserve spent-token bindings and permanent issuer denials together.

Use an encrypted incremental journal with periodic full checkpoints for the
eventual transport. Full-snapshot replication is the model's semantic baseline,
not an acceptable per-token bandwidth policy. Neither encoding nor the network
protocol is implemented by this evaluation. The later storage work implements
the envelope encoding and local persistence; authenticated exchange remains pending.

Four/four is a conservative uniform starting point, **not a mathematical minimum
for every signed-data design**: this model also preserves completed four-member
writes with three fresh readers. Mixed quorums, concurrent recovery and membership
changes need a separate protocol argument before reducing any phase's quorum.

## Why a signed backup is insufficient

An authentic snapshot can predate a successful spend or a permanent denial. Its
signature authenticates bytes, not the absence of later work. An old set of four
signed responses has the same problem unless each response is tied to a new
unpredictable request challenge, history identity, membership and generation.
A signed digest cannot reconstruct missing encrypted bytes.

This follows the distinction between self-verifying values and propagation of
newer values in [Malkhi and Reiter's Byzantine quorum work, section 5.1](https://malkhi.com/files/byzquorums-STOC1997.pdf).
Their signed-data model still needs a correct intersection between write and
read quorums. Our checkpoint requirements are a design inference from that work,
not an implementation of its complete protocol.

Recovery can observe a valid partial update whose original completion reply was
lost. Retaining its denials is conservative. Before returning recovered state,
write it back durably to a quorum so a subsequent recovery cannot return less.
[Attiya, Bar-Noy and Dolev describe this read/write-back requirement](https://groups.csail.mit.edu/tds/papers/Attiya/JACM95.pdf)
for atomic registers. Their crash-failure proof is not a Byzantine recovery proof
for Resonance; our finite checks below use an explicit one-Byzantine assumption.

[etcd's recovery documentation](https://etcd.io/docs/v3.7/op-guide/recovery/)
likewise separates snapshot integrity from revision rollback and describes
changing cluster/member identities on restore. Bumping a revision does not
reconstruct missing accepted operations. Its trusted-cluster recovery procedure
is not a substitute for a volunteer protocol.

## Required ordering for a future implementation

1. **Protect before acknowledging.** A protected spend may become externally
   accepted only after its encrypted recoverable evidence is fsynced by four
   distinct pinned replicas. A digest-only receipt or local write is insufficient.
   The old incarnation must obey this rule too; fencing cannot control a legacy
   process that accepts work locally without consulting the checkpoint protocol.
2. **Freeze before selecting.** A recovery requests a new, authenticated writer
   generation. Each honest replica atomically persists rejection of old-generation
   writes and returns its retained complete state, bound to the recovery challenge.
   Collect four such replies. Freezing never deletes the previous payload.
3. **Select complete authenticated evidence.** Check history/role identity,
   owner and replica signatures, policy binding, generation, sequence and ancestry.
   Recover the newest compatible state, including valid partial updates. Conflicts
   or unavailable payloads require refusal or another protocol round, not guessing.
4. **Confirm the selected state.** Persist the selected snapshot and required
   journal suffix under the authorized generation on four replicas before returning
   recovery success. Exact generation/digest acknowledgement binding matters.
5. **Install locally before serving.** Atomically restore the matching policy,
   denials and spend evidence; enforce the active generation on every future write.
   A crash between phases must resume conservatively from durable evidence.

Fresh reads alone do not exclude a still-running writer: it can commit after the
read and before a stale recovery overwrites the state under a higher generation.
The barrier must therefore be enforced at replicas and at every protected output.
Generation allocation, repeated/concurrent recovery, interrupted freezes and
atomic installation still need implementation and broader verification.

## Executable evidence

Run `npm run eval:history-checkpoints`. The retained
[JSON report](../evals/history-checkpoints-2026-10-04.json) records source hashes,
the base commit, assumptions, counts and counterexamples. The evaluator reads no
real histories and sends no network requests.

Local validation: TypeScript compilation and the seven focused model tests pass.
The final complete suite passes **114 files / 598 tests** with one worker in
311.78 seconds. The retained report's hashes match both evaluator source files.

| Bounded check | Result |
| --- | --- |
| Three write acknowledgements / three readers | 30 of 600 quorum/fault combinations can miss a completed write |
| Four write acknowledgements / four readers | All 150 combinations retain at least two honest members in the intersection |
| Recovery with any partial newer snapshot | 14,400 selections preserve the completed write |
| Two recoveries without write-back | 41,500 of 1,080,000 enumerated comparisons go backwards |
| Same comparisons with four-member write-back | Zero backwards results |
| Old write racing a generation freeze | All 230 completed writes survive; 1,210 orderings block completion instead |
| New old-generation write after four freezes | At most two possible acknowledgements, below four |

These counts enumerate model choices, including equivalent choices when an
adversarial response or repair target is irrelevant. They are **not independent
network trials, probabilities, performance measurements or a full protocol proof**.

The three modeled revisions represent cumulative *denials*, not arbitrary
snapshots. They abstract logical preservation of spent bindings and permanent
key fences; compaction must preserve those semantics even when deleting rows.
The owner is correct and never signs incompatible histories. Replica signatures,
full payload validity and atomic durable storage are assumptions represented by
flags. Tests reject wrong challenges, foreign histories, missing payloads,
unauthenticated replies, invented versions and repeated identities; they do not
exercise real recovery cryptography.

The read/write-back submodel has a quiescent owner. The freeze submodel separately
enumerates every per-member ordering of one old write and one freeze over all
four-member quorums and zero/one faulty-member placements. It does not compose an
arbitrary sequence of recoveries or simulate all message schedules. Other
reported backup, digest-only and higher-generation-overwrite traces illustrate
failure modes; they are not additional exhaustive protocol searches.

## Resource and privacy budget

Payload-only lower bounds for the relay's existing 8 MiB local-spend snapshot cap:

| Snapshot | Upload to four replicas per protected update | Four reads plus four write-backs per recovery |
| --- | --- | --- |
| 64 KiB | 256 KiB | 512 KiB |
| 1 MiB | 4 MiB | 8 MiB |
| 8 MiB | 32 MiB | 64 MiB |

Sending the 8 MiB payload to all five consumes 40 MiB of upload and 40 MiB of
replica storage before temporary files, metadata, signatures, TLS or retries.
Other admission roles have different file limits; these numbers cover only the
local-spend payload, not an atomic multi-file policy/role bundle.

An incremental design must authenticate every record's predecessor and retain
the complete suffix since a quorum-confirmed checkpoint. It must not acknowledge
an update whose data exists only in an unreplicated local suffix. Compaction and
storage exhaustion must retain the same safety rule. Batching may reduce overhead
but cannot return success before the protected batch is durable.

Replicas should store opaque encrypted role data, not bearer tokens or clear
spend identifiers. Encryption still exposes the infrastructure history identifier,
update timing and ciphertext size. Fixed membership does not prove independent
operators, and five devices behind one failure domain are not five independent
failure risks. No Internet availability, bandwidth, latency or energy claim is
established here.

## Boundaries and implementation order

- A checkpoint system installed later cannot reconstruct previously lost work.
  Enrolment requires the intact latest history and separately trusted owner,
  policy and replica pins. Complete loss of those pins or of the decryption key
  cannot be repaired by trusting newly discovered peers.
- Honest checkpoint replicas must retain their durable state and generation
  fences across restart. A replica with damaged history must stop; resetting it
  would violate the model's fault bound. Keep checkpoint bootstrapping independent
  of the damaged admission role to avoid circular recovery dependencies.
- Missing quorum means unavailable recovery. Do not replace pinned members,
  lower the threshold, refund tokens, or infer empty history to regain availability.
  Simultaneous compromise of multiple replicas and owner equivocation are outside
  the model. No automatic same-key witness replacement is authorized.
- Checkpoint freshness does not resolve conflicting authority policies, latest
  policy distribution, or the bounded 64-entry signed-policy archive. Those remain
  separate migration/governance requirements; no archive entries may be dropped.
- Next implementation: bounded signed checkpoint/journal envelopes and durable
  generation/payload storage, followed by authenticated volunteer exchange,
  mandatory pre-acknowledgement integration, and reviewed atomic restore. Test
  forged/stale evidence, pending writes, competing recoveries, capacity, failed
  fsync/rename, SIGKILL, corrupt replicas and generation rollback before enabling
  the restore command. The model alone does not unlock recovery in the app.
