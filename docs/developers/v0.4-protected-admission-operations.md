# Protected admission startup

The relay entry point can reopen an explicitly prepared protected admission
history. It waits for four fresh exact-head acknowledgements before opening its
application listener. Failed readiness exits startup; it never falls back to an
ordinary local spend ledger.

This is an opt-in startup boundary. The enrollment, restoration and protected
maintenance commands are still being integrated. Preparing a history currently
uses the exported APIs in [protected admission](v0.4-protected-admission.md) and
[reviewed restoration](v0.4-admission-history-restore.md).

## Operator configuration

Set `RELAY_ADMISSION_HISTORY_FILE` to a JSON file containing exactly these fields:

- `version`: `1`.
- `context`: the exact independently pinned `HistoryCheckpointContext` used to
  prepare this history, including its authority, owner and five sorted member
  public keys. Do not derive replacement pins from a peer's reply.
- `members`: five `{ "publicKey": "...", "endpoint": "..." }` records matching
  those context members. Keys and normalized endpoints must be distinct. Remote
  endpoints require `wss:`; `ws:` is allowed only by the existing local/private
  transport policy. The history listener uses `/history-checkpoint`.
- `ownerKeyFile`: the owner signing-key JSON file, containing only `publicKey`
  and `secretKey`, encoded as canonical base64url. A relative path resolves from
  the configuration file's directory, not the relay's working directory. This
  must match `context.owner`; it is not the relay infrastructure identity.

The loader accepts regular files only, bounds configuration to 64 KiB and owner
key JSON to 4 KiB, and limits reads even if a file grows during loading. Malformed
private JSON produces a generic parse error without echoing its contents. The
loader's caller clears its copied signing secret once the protected ledger has
copied it. This does not claim that JavaScript strings or all runtime memory can
be securely erased. Protect the key files with the existing operator key-storage
procedures; OS-managed key storage remains part of the key audit.

No initializer, restore approval, promotion flag, filesystem destination or
capacity-reset instruction is accepted in this configuration. Unknown fields are
rejected. The relay's existing `RELAY_DATA_DIR` selects its already prepared
policy/spend/writer state.

## Start a prepared relay

Supply the existing three signed-policy files along with the new configuration:

```sh
RELAY_DATA_DIR=/path/to/prepared-relay \
RELAY_ADMISSION_AUTHORITY_FILE=/path/to/authority.pub \
RELAY_ADMISSION_POLICY_FILE=/path/to/policy.json \
RELAY_ADMISSION_POLICY_KEY_FILE=/path/to/local-policy-key.hex \
RELAY_ADMISSION_HISTORY_FILE=/path/to/history.json \
npm run start --workspace=@resonance/relay
```

The `.hex` file holds the same 32-byte local/history encryption key used during
preparation, in lowercase hex. The authority and current signed policy must match
the prepared context and authenticated policy history. Required witness roles
still use the existing witness/coordinator settings; history replication does not
replace their authorization.

If only the separate installed-policy file has not yet been created, explicitly
set `RELAY_ADMISSION_POLICY_INITIALIZE=true` for that first startup. With protected
history configured, this flag **never creates the spend history**. Missing spend
or committed writer/archive data refuses startup. Remove the policy initialization
flag for later starts; it is not a recovery flag.

The loader copies operator-selected member endpoints; it does not discover or
substitute volunteers. Readiness and repair use the normal authenticated exchange,
TLS policy, deadlines and bounded retained writer. Those outbound sockets are
connected to the relay's existing traffic meter. Live mutation keeps the same
four-copy admission boundary after startup. If only three copies respond, the
exact durable pending operation remains available for a later explicit restart.

Removing `RELAY_ADMISSION_HISTORY_FILE` while opening protected state fails at the
format fence. Configuring history without all three signed-policy files also
fails. Ordinary relays without a protected history retain their existing startup
behavior.

## Validation and remaining integration

Tests launch the real `packages/relay/src/main.ts` process against five local
WebSocket replicas. Three reachable endpoints refuse startup, restoring the
original endpoints starts the service with the same recovered image, and graceful
shutdown/reopen preserves its applied root. Removing protection or selecting a
missing history fails before listening, including with policy initialization
enabled. Additional cases reject duplicate/unpinned members, insecure remote
transport, injected initialization fields, oversized/non-regular files and an
unrelated owner key.

TypeScript and the configuration/protected-history group pass 25 tests in
25.43 seconds; the existing startup and transport-accounting files pass another
7 tests in 0.66 seconds. The preceding full 950-test checkpoint is `c54f7dd` and
predates this startup integration.

This does not deploy volunteers, provision TLS certificates, recover witness
state or expose the full operator workflow yet. Enrollment/restore/maintenance
commands, safe compaction, policy freshness and independent volunteer/resource
validation remain required before default enablement.
