# Authenticated volunteer checkpoint exchange

Status: **experimental exchange and durable write certificates, 2026-10-15**.
This extends [checkpoint storage](v0.4-history-checkpoint-storage.md). It is not
wired into live admission or a recovery command. The app still refuses missing
or damaged admission history. The follow-up [recovery preparation](v0.4-history-checkpoint-recovery.md)
adds frozen quorum collection; generation activation, operational recovery and
automatic history reset remain unavailable.

## What is implemented

| API | Responsibility |
| --- | --- |
| `createHistoryCheckpointReplica` | Bind a member signing key to its already enrolled store; authenticate owner requests; sign replies only after storage succeeds |
| `listenHistoryCheckpointReplica` | Dedicated bounded WebSocket listener on loopback, separate from ordinary relay frames |
| `createHistoryCheckpointWriter` | Persist one exact pending block, obtain four distinct current-attempt receipts and persist their certificate before returning success |
| `readHistoryCheckpoint` | Authenticate one replica's head or one full encrypted block; never decide global freshness |

The constructors are exported from `@resonance/relay`; signed wire types and
validation are available through `@resonance/core/history-exchange`. A listener
does not create or initialize a store. Enrolment still requires independently
trusted context, member identity, generation, root digest and intact root data.
All five endpoints and member keys must be supplied explicitly; discovery hints
cannot replace a pinned member. The owner retains its signing and payload keys;
replicas receive neither the payload key nor bearer tokens.

## Request and receipt binding

Every request is owner-signed and names the context digest, enrolment root,
generation, recipient member, random 32-byte challenge, action, sequence and
expiry. Append requests additionally bind the exact ciphertext envelope digest.
The payload has its own owner signature and predecessor link. Reads are also
owner-authorized: knowing an infrastructure history ID does not grant access.

A replica reply signs the complete authenticated request, status, current local
head/barrier and returned block digest. The reply must match the exact original
request. Replayed receipts from an earlier challenge, another target or another
block are rejected. Read payloads are independently verified against their owner
signature and the response binding. A signed missing result cannot simultaneously
claim a local head that already includes that sequence.

An append receipt certifies that this member durably retained the specified
block in its enrolled chain. It is historical evidence, not an eternal promise
of availability or proof that no later write or freeze exists. The read API
likewise authenticates a member's assertion; deciding the latest recoverable
state still requires a quorum protocol and complete compatible chain validation.

## Durability and retry ordering

The writer accepts one active attempt at a time. A new block must extend its
last committed block, or match the pinned root at initial sequence zero.

1. Persist the complete exact pending ciphertext before sending any request.
2. Send to the five pinned endpoints with one fresh challenge for this attempt.
3. Each honest member validates the owner, enrolment, chain, generation and
   capacity. It flushes the immutable block and manifest before signing a receipt.
4. Count four distinct authenticated replies for that exact attempt and block.
   Cancel the fifth connection without waiting for it.
5. Atomically persist the complete certificate and committed envelope, clearing
   the pending entry, before reporting success to the caller.

Insufficient replies leave the pending block available for explicit exact retry.
A different block cannot replace it. Restart does not send anything. An uncertain
write poisons the affected local storage handle until close/reopen. A retry can
recover a previously stored block whose reply was lost.

Even retrying the latest committed block requires **four fresh acknowledgements**.
The writer never uses its historical certificate to bypass a new attempt. In
particular, a quorum of frozen stores rejects further old-generation append
acknowledgements, including identical retries. Existing certificates remain
readable historical evidence; callers must not reinterpret them as fresh writer
authorization. Mandatory admission integration has not yet been implemented.

The writer file retains only the latest committed envelope/certificate and one
pending envelope. It is not the complete authoritative spend history. Volunteers
continue to retain their full root and suffix, and the owner must retain its
application history. There is no automatic repair of lagging replica suffixes,
replica re-enrolment, compaction, refund or replacement of missing history.

## Availability, resource and deployment limits

- Four of five distinct member identities are required, with the existing
  assumption of at most one Byzantine member. A three-versus-two partition
  cannot confirm a new write. Identity pins do not establish independent devices,
  operators, network paths or failure domains.
- One writer attempt opens at most five sockets. Its default total deadline is
  ten seconds, configurable from 50 ms to 30 seconds. Late replies and close
  cancel acceptance; completed synchronous work cannot be preempted. The writer
  checks the deadline again after signature validation and certificate storage.
- Requests have at most 30 seconds of wall-clock validity. Significant clock
  skew can refuse work. The writer also uses a monotonic elapsed-time deadline;
  changing the clock does not create an unlimited attempt.
- A listener allows four raw connections by default (configurable 1–8), one
  request per connection, a ten-second connection lifetime (50 ms–30 seconds),
  and no WebSocket compression. Header size, frame size and connection lifetime
  are bounded. Small acknowledgements/head replies are capped at 4 KiB on the
  client. A read may return one full bounded encrypted block, never the entire
  history. These bounds are not a Sybil-resistant rate limit or CPU/power budget.
- The dedicated listener accepts at most the existing maximum 8 MiB checkpoint
  ciphertext encoding plus bounded metadata. Ordinary relay frame limits are
  unchanged. Sending a maximum 8 MiB plaintext checkpoint to all five members
  takes roughly **53.3 MiB of base64 ciphertext alone**, plus framing/signatures.
  Cancellation of the fifth response does not guarantee saving its upload.
- The encrypted writer snapshot has a 40 MiB serialized cap and holds at most
  one committed and one pending envelope. Atomic replacement temporarily retains
  both files. Replica payload/count/manifest limits remain those documented for
  checkpoint storage. None is a whole-process memory or physical-disk allocation
  limit, and network accounting is not wired to desktop owner controls yet.
- Listeners bind only `127.0.0.1`. An Internet deployment requires a separately
  configured TLS proxy on the volunteer device; clients require `wss://` away
  from loopback, validate TLS normally and refuse redirects. No public listener,
  permanent service, NAT route or automatic deployment is created by this work.
  Listener shutdown closes connections; the caller separately closes the role
  and store that it owns.
- The replica owner may pause new payloads while allowing exact retries and
  authenticated reads. Durable generation barriers override retry acceptance.
  Full desktop bandwidth/power/schedule integration remains pending.

## Validation and next step

Run:

```sh
npx vitest run --maxWorkers=1 history-checkpoint history-exchange
npm run build
```

At the exchange milestone the focused suite passed **80 tests**, including 32 new protocol, coordinator and
socket tests. Tests cover tampered and expired requests, wrong/replayed replies,
duplicate member evidence, forged signatures, a silent fifth member, 3/2
partitions, lost replies, concurrent competing writes with one equivocating
replica, generation freezes, storage failures, deadlines and close. Five real
loopback services exercise new durable writes, restarts, authenticated reads,
the maximum 8 MiB full checkpoint, malformed/binary/oversized traffic and
SIGKILL of pending/committed writers. These are controlled single-host tests,
not an Internet pilot or proof for arbitrary recovery schedules.

That milestone's full local suite passed **120 files / 671 tests** in 329.24 seconds with one
worker. A follow-up timeout-test adjustment gives real request signing a
one-second budget on slower CPUs and explicitly checks all five transports were
started; all eleven coordinator tests pass again separately. Production code is
unchanged by that test adjustment. Remote CI is recorded in the draft PR.

Follow-up: authenticated freeze/read rounds and complete compatible chain
collection are implemented in [recovery preparation](v0.4-history-checkpoint-recovery.md).
[Successor reservation](v0.4-history-checkpoint-successor.md) adds selected-history
write-back and four-member reservations, including bounded `repair`/`seal`
exchange actions. Next: resolve competing partial reservations and implement
certificate-controlled activation with cross-generation ancestry. Then integrate replication before every protected admission
output and implement reviewed atomic restore and quorum-safe compaction. Until
those steps are verified, these certificates do not reopen lost live histories.
