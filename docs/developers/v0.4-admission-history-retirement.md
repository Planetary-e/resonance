# Permanent local retirement of admission histories

Status: **implemented for the opt-in v0.4 pilot, 2026-10-01**. This is local maintenance of an expired issuer key on one witness, coordinator or signed-policy relay spend ledger. It does not replace witnesses under a live key or provide network-wide garbage collection.

## Decision and safety boundary

An old vote cannot simply be deleted: if the same witness can sign again for that token, it may help form a conflicting certificate. Expiry of the current policy is also insufficient, because a successor may renew the policy while the key's own cutoffs remain unexpired.

The maintenance operation instead **permanently disables the entire RSA issuer key on that local role**, then removes its token-specific evidence in the **same encrypted, atomically replaced and flushed snapshot**. The retained key fingerprint is a retirement fence: the role refuses every future use of that key, including exact retries, before returning an old decision or signing a new one. New issuer keys remain independent. Local spend retirement applies the same rule before any token acceptance or exact retry, including after an asynchronous quorum response.

Retirement requires all of the following:

- The device's installed, authenticated policy is current.
- The issuer key belongs to that participant's signed witness/coordinator configuration, or to the installed policy for a local spend ledger.
- It is no longer the active issuer key. Install the intended successor first.
- Its own **`retryUntil` has passed**, including when the signed policy shortened that cutoff. Ending new spends or letting only the policy expire is insufficient.
- The operator approves a digest bound to the role, participant (local data-directory path for spends), authority, exact policy body, selected issuer key and complete current history.
- For a coordinator, there are no quorum attempts in progress. The offline command requires the relay to be stopped through the existing single-writer locks.

A retired honest witness does not contribute to any subsequent certificate for that key. An honest witness that still contributes retains its token decisions. This preserves the original four-of-five intersection argument under the existing one-equivocating-witness assumptions; it does not reclaim old tokens or let a replacement witness inherit an identity with empty history. A coordinator fence similarly prevents returning a removed certificate or gathering a new one. The local admission verifier still consults that gate even for previously recorded exact uses.

This is **not immediate revocation on other devices**. Other roles can retain older, unexpired policies and their histories. They keep enforcing their own configuration; the retired local role remains unavailable for that key regardless. Availability may decrease. No refund, allowance transfer or new issuance is authorized.

## Operator workflow

Stop the relay. Keep its existing data directory, policy storage key and participant key. First install the intended successor through the existing policy workflow, then stop the relay again for maintenance. This command reads `admission-community-policy.json` from that directory; it never imports an external policy or initializes missing state.

Review one role and one old issuer-key fingerprint:

```sh
node --import tsx scripts/retire-admission-history.ts plan \
  witness relay-data authority.pub local-policy-key.hex witness-private.json \
  'sha256:<old-issuer-key-fingerprint>'
```

The report shows the role, participant public key, authority fingerprint, policy revision/digest, issuer key, retry cutoff, before/removed/after record counts, entry capacity, fence count and `approvalDigest`. It contains no spend identifiers, request bindings, certificate contents or private keys. It is a local operator review, not a public activity report. Planning preserves the history snapshot; ordinary locking and stale temporary-file cleanup still apply.

Use the full digest from that reviewed report to apply it:

```sh
node --import tsx scripts/retire-admission-history.ts retire \
  --approve 'sha256:<review-digest>' \
  witness relay-data authority.pub local-policy-key.hex witness-private.json \
  'sha256:<old-issuer-key-fingerprint>'
```

For a coordinator, replace `witness` with `coordinator` and supply that role's private key. For the relay's separate local spend history, use `local-spends` and omit the participant private-key argument:

```sh
node --import tsx scripts/retire-admission-history.ts plan \
  local-spends relay-data authority.pub local-policy-key.hex \
  'sha256:<old-issuer-key-fingerprint>'

node --import tsx scripts/retire-admission-history.ts retire \
  --approve 'sha256:<review-digest>' \
  local-spends relay-data authority.pub local-policy-key.hex \
  'sha256:<old-issuer-key-fingerprint>'
```

The local-spends report also shows `unattributedRecordsRetained`. These records remain charged to capacity. The approval is bound to the resolved local directory; moving the directory requires a fresh review. This path is for operator review only and is not transmitted to peers.

If a device runs several roles, review and retire each separately. Each snapshot is independently safe; the role changes are not one transaction. A successful first change does not imply that the others happened.

Changed history or policy requires a fresh review. Missing/corrupt files, wrong authority or participant, a live writer, premature retirement and a missing/wrong approval digest are refused. Keep private key files local. The tool uses no network connection and exposes no remote maintenance endpoint.

## Persistence, migration and recovery

- Witness/coordinator version 2 snapshots retain `retiredIssuerKeys` alongside the remaining votes/certificates. There can be at most eight fences, and every fence must reference the policy's assigned issuer key. A fenced key cannot also have retained token records in that snapshot.
- Valid witness/coordinator version 1 snapshots remain readable with no fences and no automatic deletion. Reading/planning does not rewrite them. The next new vote/certificate or approved retirement writes version 2 using the existing encryption domain. Older binaries reject version 2 rather than silently ignoring its fences; do not downgrade by editing the format.
- Restart, policy renewal, attempts to reactivate a key, and clock rollback do not clear an existing fence. There is no unretire/reset command.
- The file write/flush/replacement must complete before in-memory evidence is removed. A failed write poisons the open role. Close and reopen before any further operation. Recovery sees either the old evidence or the permanent fence and remaining records. If the fence is already installed, planning reports that the key is permanently retired. Missing/corrupt snapshots refuse startup.
- The underlying storage uses process locks, file flushing and POSIX directory flushing. Windows lacks the directory-flush step. Process-crash tests are not a guarantee against every filesystem or power-loss failure.
- This does **not** protect against restoring an older filesystem backup, deleting/recreating state under the same signing key, or cloning a role. Such actions can discard the fence and remain outside the honest-role assumption. Keep the latest intact state and never restore stale signing history and resume service.

### Local spend migration

Signed-policy relays now store an encrypted version 2 snapshot at the **existing** `admission-spends-v2.jsonl` path. The historical suffix remains for safe in-place migration; the new contents are not JSONL. The state binds the community authority and stores the issuer-key fingerprint, spend digest, action and request binding for each attributed record, plus permanent key fences. The fingerprint is derived from the actual public key that verified the token, rather than supplied by the presentation.

Nonempty, complete, valid old JSONL logs are read under the new single-writer lock without rewriting them. Legacy rows have **no issuer attribution**. Reading or planning cannot infer it from the current key or policy. An authenticated exact retry, after any required witness check succeeds, may durably attribute that one row even during its retry-only interval. Conflicting requests and failed witness checks cannot do so. The next mutation encrypts the full retained history by atomically replacing the same path. Old/manual readers then refuse the new format; no second-file migration window leaves a writable obsolete log behind. Stop all older processes before upgrading: an old binary does not honor the new writer lock.

Retirement removes only rows explicitly attributed to that issuer key. Unknown legacy rows survive even if the key is fenced; they cannot authorize a token under the fenced key. An operator may install a fence with **zero records removed**, which provides a permanent refusal but frees no entries. Unknown rows can therefore still fill the ledger. There is no bulk guess, purge or reset.

An empty historical log cannot be distinguished from a truncated new snapshot. **Empty, missing and malformed existing spend files refuse startup and maintenance.** Restoring the latest intact history is required; this checkpoint does not provide a recovery command for genuinely empty legacy files. Never delete a file or use initialization to make this error disappear. Only a genuinely new signed-policy relay initializes a new encrypted empty snapshot, and initialization refuses an existing file. Manual single-key relay configuration keeps its old append-only log and has no retirement feature.

## What space this releases

The operation removes the selected key's provisional votes from one witness snapshot, its certificates from one coordinator snapshot, or its attributed spends from one local ledger, freeing those entries and their encoded bytes for other keys. Unexpired keys' records remain intact, including exact retry evidence and partial votes. Witness/certificate reads still verify signatures; local spend records retain their authenticated snapshot and exact bindings. This is not an opaque count reset.

Retiring only votes/certificates leaves the separate local spend capacity unchanged; review `local-spends` independently. Issuers have a separate [permanent ledger-retirement operation](v0.4-issuer-retirement.md): it removes per-permit evidence while sealing that issuer and preserving lifetime budget totals, without refunding allowance. These operations do **not** compact wallet token histories, community policies or publication/mailbox journals, and do not free any of the eight retained policy-key slots. Those stores and unresolved legacy records need separate retirement/recovery designs; admission stays opt-in.

The limits are 10,000 entries per role, with 16 MiB witness / 32 MiB certificate / 8 MiB encrypted local-spend snapshots. Atomic replacement needs room for old and new snapshots simultaneously. Near-capacity CPU, memory and disk costs have not been measured by this checkpoint.

## Validation

Eleven new tests cover both roles, retry-only retention, active-key and expired-policy refusals, approved deletion with fresh-key capacity recovery, state-bound stale approval, legacy preservation, malformed fences, clock/older-policy rollback, pending quorum attempts and reentrant owner maintenance. File- and directory-flush fault injection checks both sides of replacement. A real child process is killed after durable witness retirement and reopens through stale-lock recovery with its fence intact.

The actual CLI is tested for both roles against installed policies, including unchanged bytes during review, missing approval, wrong approval and missing-state refusal. A real Blind RSA token is first accepted and recorded; after certificate retirement, its exact retry is refused even with a rolled-back clock, while the separate local spend log remains byte-for-byte unchanged. These remain local checks, not a volunteer deployment or independent protocol audit.

Witness/certificate checkpoint: TypeScript compilation, **106 files / 537 local tests**, and its [remote CI](https://github.com/Planetary-e/resonance/actions/runs/36843684103) passed.

### Local spend checkpoint

Ten additional retirement tests use real Blind RSA tokens to fill a ledger, preserve exact retries, reject conflicting requests, reclaim only the retired key's entries, accept fresh-key work and refuse old tokens after restart or clock rollback. They cover conservative legacy migration and attribution, active-key/early/expired-policy refusals, stale approval after history/policy/directory changes, concurrent writer refusal, in-flight quorum-hook retirement, corrupt/truncated files, both sides of failed atomic replacement, the actual offline CLI, and SIGKILL with stale-lock recovery. Two storage tests verify explicit legacy decoding, schema/size enforcement, unchanged review bytes and encryption on mutation. Existing witness tests still require failed quorum authorization to leave local spend bytes unchanged.

These checks do not establish protection against filesystem snapshot rollback or near-capacity performance. New local spends rewrite a bounded encrypted snapshot; the cost at the 10,000-entry limit remains to be measured.

Local-spend checkpoint: TypeScript compilation and the final complete local suite passed, **107 files / 549 tests**, with one worker. Remote CI runs separately after push; no installer is built by this development push.
