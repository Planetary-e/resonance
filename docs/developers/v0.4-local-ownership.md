# Local writer ownership through process interruption

## Scope and problem

Encrypted local state must have one cooperating writer on one host. The previous
protocol exclusively created a lock file, then wrote its PID. Process death
between those actions left an empty authoritative file. Its owner could not be
identified safely. The same problem existed in the stale-owner recovery guard.

The replacement publishes a complete owner as directory names. It applies to
local filesystems used by cooperating processes on the same host. It is not a
distributed filesystem lock, protection against a privileged local attacker,
or a replacement for authenticated history/recovery evidence. PID reuse is
conservative: a live PID prevents automatic reclamation even if it belongs to
an unrelated newer process. Unknown ownership is never inferred dead by age.

## Representation and publication

For a resource `state.json`, the authoritative paths remain `state.json.lock`
and `state.json.recovery`. Each new claim is an ordinary directory containing
exactly one empty directory named `owner-<pid>-<random 128-bit nonce>`. No partial
file write can publish an incomplete owner. An empty authoritative directory
represents a release interrupted after removing the marker.

The writer prepares a uniquely named sibling candidate, creates its complete
owner marker, and flushes the candidate on platforms supporting directory fsync.
It renames the prepared nonempty directory to the authoritative name. The
publication cannot replace another nonempty claim. This uses documented
directory constraints in [Linux rename](https://man7.org/linux/man-pages/man2/rename.2.html),
[Apple rename](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/rename.2.html)
and [Windows MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexa).
Windows also refuses replacement of an existing empty directory; the bounded
retry path removes only an observed empty container before retrying.

The recovery claim is acquired first, then the primary claim, and released
before the resource is exposed. Publication success is followed by a parent
directory flush where supported. A failing flush does not grant ownership.
No network request, snapshot or protocol receipt can be sent on a guessed claim.

## Reclamation and competing processes

Only a PID reported absent by the local OS authorizes removal of a complete
previous owner. Permission errors and live PIDs refuse. A contender removes
the exact previously observed nonce marker, then uses `rmdir` on its container.
An intervening replacement has a different marker; it is nonempty and cannot
be removed by this operation. The final rename similarly cannot overwrite it.
Release uses the releasing writer's own marker, with the same protection.
These operations provide the exclusion argument under the stated local
filesystem/cooperating-writer assumptions; the concurrent-process tests cover
finite executions, not a proof of every possible filesystem implementation.

Unpublished candidates encode their PID and nonce in their own names. They
contain only zero-byte directory structures and never accepted state. Cleanup
checks the exact bounded structure and requires the candidate's PID to be dead.
Unexpected contents, aliases and excessive candidate counts are retained for
inspection. Scans have a 100,000-entry parent bound and a 128-candidate bound;
contention has eight publication attempts and can return a retryable refusal.

## Existing locks and storage controls

A complete old file claim is read through bounded ordinary-file/identity checks.
It can be replaced only after its PID is known dead, while the recovery directory
excludes the old file-based recovery protocol. Old code cannot exclusively create
or parse a file at a live new directory claim. Tests retain a frozen old protocol
implementation to verify both directions of this exclusion.

An incomplete old lock or recovery **file** still requires inspection. Nothing
in its empty contents proves who created it. The new protocol avoids producing
that ambiguity; it does not fabricate missing historical ownership evidence.

Existing reservation keys and byte amounts remain unchanged. A `local-state-lock`
allocation can name the strict zero-payload directory representation; this does
not authorize arbitrary child files or general directory output. Snapshot and
diagnostic allocations retain their existing control headroom. Storage adoption,
pristine history reopening and authorized ancestor retirement inspect the new
control layouts explicitly. Directory/inode overhead is filesystem-dependent:
logical byte reservations remain distinct from measured allocation and are not
a filesystem quota or free-space guarantee.

## Validation status

The isolated primitive passes 15 local tests, including ten real process-death
boundaries, live/obsolete legacy owners, malformed legacy evidence and three
processes performing 36 mutually exclusive updates. Integrated encrypted state,
managed storage, selected operator ownership and desktop scope tests pass
84 tests across six files. Existing history and desktop integration checks are
complete: history/service/provisioning/reverse-link regressions pass 89 tests
across four files (324.65s), and targeted desktop activation/adoption/ownership
checks pass 43 tests across three files (7.24s). Groups overlap. TypeScript passes.

CI run `39059692323` exposed an existing shutdown race: a prepaid runtime lock
could disappear between `lstat` and `realpath` while the desktop saved settings.
Three deterministic regression cases reproduced it for legacy locks, directory
locks and release during marker inspection. Resolution now walks from the parent
only after confirming that an `ENOENT` target is absent; an existing dangling
alias still refuses. Directory-control inspection retries only bounded `ENOENT`
races. No missing reservation, redirected scope or damaged claim becomes valid.
The final controls, actual child lifecycle, reservations and ownership group
passes 64 tests across four files (5.21s). Failed earlier injection mocks read the
obsolete PID-file layout; desktop checks now inspect the actual directory owner,
and cleanup damage tests still preserve unexpected contents and report failure.

CI run `39063197304` passes the focused Linux/macOS/Windows matrix for this
protocol, encrypted state and managed reservations. It installs test dependencies
without native install scripts and does not package any application. The full
regression job is separate. Process termination exercises process
failure, not physical power loss or filesystem rollback.

### October 18: recovery release race

CI at `711dc41` failed the Windows three-process contention case after its
15-second acquisition budget. The previous child fixture hid the caught error,
so that log alone cannot establish the exact failing interleaving.

A deterministic regression reproduced a related acquisition leak: process A
publishes its primary lock, removes its recovery marker, then finds a new
recovery owner B in the container. B sees A's live primary lock and removes its
own recovery claim before A inspects it. The resulting `ENOENT` escaped A's
cleanup and prevented A from receiving its release function, even though A
already owned the primary lock. Retrying with the same live PID could not
reclaim that lock.

After removing its own marker, release now tolerates only disappearance during
that final inspection. It preserves another live owner's claim and continues to
reject unexpected content, aliases and permission errors. No deadline or
reclamation authority changed. Tests cover disappearance of the whole container
or only its marker, a surviving successor, unexpected contents and `EPERM`.
Child failures now report bounded stage, reason and OS-code metadata without
paths, nonce values or payload contents. All 21 focused ownership tests pass
locally; the next Windows run must verify platform behavior.
