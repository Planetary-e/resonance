# Remote creation of certified history generations

Status: **experimental library APIs, 2026-10-16**. Builds on the certified
[continuation boundary](v0.4-history-agreement.md). This does not enable live
admission restore, change membership or deploy an Internet service.

## Behavior

The owner can now ask enrolled volunteers to activate the decided continuation
and create its child history remotely. A failed reply or process interruption
can leave useful progress on disk. An explicit retry resumes that same child;
it never replaces an operational child with an empty one.

`openHistoryGenerationProvisioner` owns one locally configured predecessor/child
slot. The operator supplies the retained parent handle, context, member key,
manifest key, directory and capacity. Enrolment is explicit and local. A remote
caller cannot choose a directory, key, member set or replacement predecessor.
Both child paths are derived locally from the certified continuation digest.

`createHistoryGenerationReplica` serves agreement for that predecessor, remote
provisioning, and checkpoint exchange for the predecessor and its ready child.
The child supplements the predecessor; old reads remain available with the old
pins and old writes remain frozen. Provisioning targets one slot. The subsequent
[ancestry milestone](v0.4-history-ancestry.md) adds routing of the complete locally
enrolled ancestor chain; configuring another provisioning slot still requires its
retained parent handle. This milestone's network creation test covers one boundary;
the ancestry scenario subsequently serves three generations on the same sockets.

## Authorization, limits and readiness

`@resonance/core/history-provision` uses separate signature domains for requests
and receipts. A request binds the owner/context, target member, fresh challenge,
validity window and deterministic child root. The complete continuation proof
must validate, including four confirmation signatures and its selected parent.
Equivalent genuine proofs of the same decision identify the same root. Requests
expire in at most 30 seconds; a post-fsync check suppresses an expired reply.

The new `/history-provision` route accepts at most 40 KiB and replies with at
most 1 KiB. `/history-checkpoint` provides existing bounded checkpoint exchange
on the same service. All routes share the existing raw-connection cap (default
four, maximum eight), connection lifetime (default ten seconds, maximum thirty),
4 KiB headers, no compression, and one application request per connection.
Listeners bind loopback. Remote deployment still requires an explicitly
configured TLS proxy; client transport refuses insecure non-loopback endpoints
and redirects. The parent/child stores retain their existing byte/block limits
and 64-link / 256 MiB aggregate ancestry bound. A replica's provisioning journal
is separately capped at 64 KiB; an owner's at 512 KiB. Temporary initialization
uses the same bounded manifest/block storage as ordinary stores.

A provisioning receipt certifies durable creation at the time of the request.
It is **not** a vote, root-write certificate or continuing availability claim.
The checkpoint writer still needs four fresh root-write receipts before its
first delta. The fixed membership is five volunteers, requiring four distinct
authenticated receipts. No continuously operated service has been introduced.

## Crash-safe creation

The encrypted, single-writer replica journal progresses from `empty` to
`creating` to `ready`:

1. Verify fresh owner authorization and the exact complete frozen parent chain.
   The local storage pause can refuse new creation here. Activate the parent
   durably without deleting any old block. A crash before the following journal
   write can only leave the same irreversible activation for the next retry.
2. Flush the certified child and `creating` intent before touching a child path.
3. Construct the root-only store in `.creating-<digest>`. Resume only the exact
   encrypted initialization manifest and authenticated root. A crash between
   root-file durability and its manifest entry is completed by indexing that
   verified root. Unknown files, corrupt manifests/blocks and operational history
   inside staging refuse progress and remain on disk.
4. Close the staged store, rename its complete directory to `generation-<digest>`
   and flush the enclosing directory. The API exposes no staged store to appends.
5. Reopen/validate the published child, flush `ready`, then expose checkpoint
   exchange and sign the receipt. An uncertain write poisons the provisioner
   until close/reopen. Reopening `creating` never performs network or creation
   work automatically; a fresh authorized request finishes it.

If `ready` exists, a missing directory, manifest or root is an error, never an
invitation to initialize. Retries of a ready child reopen/preserve all accepted
deltas. Ordinary `openHistoryCheckpointStore({ initialize })` retains its strict
empty-directory rule. Only the internal preparation helper can finish a registered
unpublished construction; it is not an operational reset API. Stale encrypted
temporary files may be cleaned under the existing store lock after validation.

Existing one-shot successor reservations, incompatible accepted tails and
incomplete predecessor transfers still refuse activation. Complete local state
rollback remains outside the protection of an unanchored local journal; this
milestone does not claim detection of coordinated rollback of all retained state.
Windows retains the existing limitation that directory handles cannot be fsynced.

## Explicit owner retries

`createHistoryProvisionCoordinator` persists the certified root and five signed
requests before sending. Every explicit `run()` uses a fresh challenge and collects
four replies for that attempt, including after an earlier success. It persists
the four receipts before returning. Timeouts, cancellation, lost replies and
close/reopen preserve the selected child; they do not select another generation.
Reopen/read never transmit. Missing or corrupt owner files are refused. An
attempt's deadline includes signing, local persistence, transport and reply
verification; an unresponsive custom transport cannot hold the call indefinitely.

## Validation

Tests exercise real signatures and encrypted manifests, nine SIGKILL boundaries
(creation intent, staging mkdir, initial manifest, root block, indexed root,
before/after directory publication, ready marker, and durable reply loss), plus
six failed-fsync positions. They check exact retry, preserved parent/child data,
missing/corrupt published stores, suspicious staging contents, owner storage
pause, missing/longer parent tails, expired authorization and fresh-attempt receipt
binding. Owner tests cover stale/duplicate receipts, cancellation, close, concurrent
attempt refusal and a transport that ignores cancellation.

The integration test runs five real loopback services. Two replies disappear
after durable creation, the owner restarts without traffic, and an explicit fresh
attempt succeeds. The writer then rejects a delta before four root writes, accepts
the root and delta through the same service, reads the old generation, and retries
creation after a service restart without losing the accepted delta.

TypeScript compilation passed. The history regression group passed **25 files /
241 tests** in **140.98 seconds**. The final complete suite passed **138 files /
822 tests** in **443.05 seconds**, with one worker. All **332 TypeScript source
hashes** remained unchanged throughout that complete run. These results validate
the local implementation; they are not a multi-device Internet pilot.
