# Atomic protected authorization and spend

## Decision

A protected coordinator previously replicated its four-witness certificate,
then replicated the matching spend as a second history mutation. Both records
belong to the same protected owner and the same decision. In the measured
25 ms application run, these separate serial rounds consumed part of the
original three-second admission deadline.

The protected configured path now writes one `authorized-spend` delta containing
the certificate and attributed spend row. It uses the existing encrypted,
owner-authenticated history envelope and the same four-copy confirmation.
The state becomes visible only when both parts have passed validation and the
single pending envelope has durably completed. No quorum, timeout, collection
limit, history capacity or private-delivery budget changes.

## Validation and recovery boundary

The reducer binds the certificate's issuer key, spend identifier, action and
request binding to the row. It applies the existing certificate and spend rules
to copied state. Invalid signatures, conflicting claims, either ledger's
capacity, retirement fences and historical cutoffs reject the entire mutation.
The unchanged delta, archive and next-checkpoint headroom checks run before
publishing intent.

One pending record retains the original full certificate and row. A retry
cannot replace it with a different valid subset of witness votes. Reopening and
`ready()` finish that original record and apply both parts. Historical separate
certificate and spend rows remain supported. Generic legacy `write()` cannot
silently complete a compound pending record; unavailable history still refuses
ordinary admissions until its existing recovery/readiness path completes.

The coordinator exposes an explicit trusted transaction callback. It holds its
existing serialization, cancellation and deadline through callback completion;
the established `authorize()` method still durably retains its certificate
before returning. A coordinator that is also a witness waits for its own durable
vote before starting the compound write. That witness vote remains separate.

The verifier retains its final freshness, policy, retirement, capacity and
accepted/replay checks around the write. Exact replay also invokes the protected
write path so a historical attributed spend can acquire a missing certificate.
When both already exist, validated replay appends nothing. Legacy configured
admission continues using its existing certificate-before-spend path.

This adds an encrypted history record kind. Existing records are unchanged;
older readers cannot consume the new kind and must fail closed. Live deployment
still requires compatible operators and remains opt-in.

## Evidence

- 67 tests across three history files pass, including 19 new atomic-record cases.
- A further pending close/reopen regression passes: the original envelope ID and
  signed proof survive, both halves apply, and no replacement delta appears.
- Ten new coordinator/verifier integration cases pass, including self-witness
  ordering, historical replay, cancellation and expiry before the final write.
- All 23 existing protected-role, blind-verifier and decision-queue cases pass.
- Composed TypeScript build and strict application-evaluator typecheck pass.

The new tests directly cover pending loss of replies, close/reopen and restored
history replay. They do not add a new OS process-kill harness for this record;
existing crash tests cover the unchanged shared intent/replication/apply machinery.
Independent cross-review of both history persistence and verifier integration
found no concrete safety issue; the identified pending-reopen gap was then
covered. The [whole-application measurement](../evals/v04-authorized-spend-2026-10-18.md)
passes eight functional/failure checkpoints but still only three of six paired
searches under calibrated 25 ms stream delay. The original queue-inclusive
deadline remains a failed gate; this atomic commit does not establish readiness.
