# Durable owner ciphertext and indexed live repair

Status: **experimental owner API, 2026-10-16**. This extends the
[checkpoint writer and live repair](v0.4-history-checkpoint-exchange.md). It does
not yet make admission acknowledgements depend on replication or authorize
restoration of a lost admission ledger.

## One retained current generation

`createRetainedHistoryCheckpointWriter` composes the sequential checkpoint writer
with a complete local archive under its `payloads` directory. The archive has an
encrypted `history-writer-payloads.json` index and immutable signed ciphertext
files. Its context, root and generation must match the separately locked writer.
The archive does not decrypt application data.

The returned writer retains `read()`, `replicate()` and `close()`, and exposes
`history()` for chronological ciphertext iteration and `historyStatus()` for
local block/byte counts. These APIs cover only the current generation. A
continuation root still depends on its retained predecessor history; it is not a
standalone replacement snapshot. Previous generation directories are not deleted.

The original low-level writer remains available for explicit callers with their
own retained source. Its journal alone is still limited to the last committed
and pending block. New operational admission integration must use complete
durable retention, not assume that this old journal contains a full recovery image.

## Ordering and interruption

Each explicit write follows this order:

1. Validate and durably record the exact pending ciphertext in the writer journal.
2. Flush and publish that immutable archive block.
3. Atomically replace and flush the encrypted archive index.
4. Check replica heads, repair compatible missing suffixes, and request the target
   write under one bounded attempt.
5. Persist four distinct matching target-write receipts before returning success.

No socket request precedes the archive index's durability. A capacity refusal or
failed archive write keeps the original pending ciphertext and prior committed
certificate. A retry must reuse that exact block. Unknown durability poisons the
archive handle until close/reopen; retrying the same open handle cannot bypass it.

Reopen authenticates the complete indexed chain, every payload's digest and
signature, and its root/generation/sequence links. The index must include the
writer's committed head and may contain exactly its one pending successor.
Indexed missing/corrupt files, unrelated orphan blocks, mismatched pins and a
writer-only rollback refuse opening. An intact pending block published before
its index entry is recognized only through the writer's independently persisted
exact intent. Explicit retry adopts it and advances the index before transmitting.
Reopen, status reads and iteration never send requests.

Initialization is explicit. If the process dies after creating a pristine writer
but before creating the archive, `initializeArchive: true` can finish archive
creation while that intact writer has **no committed block**. It refuses an
already committed writer, missing writer state or a nonempty archive directory.
There is no automatic empty migration for older writers whose complete payload
prefix was not retained. Existing accepted data must be recovered and verified,
not inferred from a last receipt.

A coherent old backup of both journals is still historical evidence, not proof
that no later write exists. Remote generation freezes, agreement and reviewed
application installation remain necessary for lost-state recovery.

## Indexed repair and resource bounds

The storage layer exposes an internal immutable index handle after authenticating
the chain. The repair layer accepts that registered local handle, checks its
context/root/generation, exact target/predecessor and budgets, and loads only
payloads actually missing from a responding member. Every loaded payload is
revalidated against its indexed digest and predecessor before sending.
An untrusted serialized object or a caller-supplied boolean cannot create that
handle. It is a local storage capability, not a transferable network certificate.

Healthy appends do not re-read the whole ciphertext prefix. Reopen does validate
every indexed block, and explicit history iteration reads each block again.
The encrypted digest manifest is still atomically rewritten on append; the
complete operation is not claimed to have constant CPU, allocation or I/O cost.
Near-capacity and physical resource measurements remain required.

Limits are 10,001 blocks and 64 MiB of encoded ciphertext in one generation,
with caller-configurable lower limits. Two maximum 2 MiB archive manifests allow
for atomic replacement overhead. The separate writer snapshot has its existing
40 MiB limit and its own replacement overhead. These are component bounds, not a
whole-process memory, physical-disk or whole-device budget. Increasing a locally
chosen lower bound on reopen is explicit and cannot exceed the protocol maxima.

## Validation

The first focused group passed 24 tests. After adding the crash/network scenarios,
TypeScript and **56 tests across six files** passed in **44.66 seconds**. Cases cover
payload-before-network ordering, durable owner reopen and a different fourth
volunteer, no full-prefix file reads during a healthy append, full validation on
reopen, four failed-flush boundaries, missing/corrupt/unknown data, writer-only
rollback, capacity refusal and interrupted initial archive creation.

Nine separate owner processes are killed before/after pending-intent publication,
payload publication, index publication, certificate publication, and after durable
completion. Five real loopback services retain the data. Reopen preserves the
committed head and exact pending state; fresh retry obtains four target receipts
without losing prior ciphertext. Keys reach child processes over IPC, not command
arguments. Another real-socket scenario reopens the owner's archive and catches
up a returning fourth volunteer. The subsequent two-generation integration test
also uses this retained writer. The final complete suite passed **146 files /
888 tests** in **492.26 seconds**, with one worker; all **347 TypeScript source
hashes** remained unchanged. Publication/CI status is recorded in the
[completion plan](v0.4-completion-plan.md).

These are process interruption and local filesystem/network tests. They do not
certify power-loss behavior, independent volunteers, Internet overlap or energy.
