# Signed archives for retired admission configurations

Status: **implemented for the opt-in v0.4 pilot, 2026-10-03**.

The ninth issuer rotation previously stopped because signed policies could retain only eight configurations. Deleting an old entry would lose the pins needed to validate returning devices' saved votes, certificates and wallet history. Increasing the number of usable keys alone would leave that lifecycle unresolved.

Policy **version 2** separates up to **eight current configurations** from up to **64 permanently archived configurations**. It retains the full public profile, cutoffs and witness set for each archived key. Archiving frees a current configuration slot; it permanently disables the old key, including exact retries. It neither deletes local history nor refunds tokens or permits.

## Signed policy rules

- Version 1 retains its original signature payload and 64 KiB signed-file bound.
- Version 2 adds the required `archivedKeys` array and signs a distinct `resonance:admission-policy:v2` payload. Its compact signed JSON file, including the final newline, is limited to 512 KiB.
- `keys` contains 1–8 current entries. `activeKey` must identify one of them. No issuer key may occur twice across the two arrays.
- An archive entry's `retryUntil` must be at or before the new policy's `issuedAt`.
- Moving an installed current entry to the archive requires its **original, unmodified final cutoff** to have passed. The entire normalized entry must remain identical. A proposal cannot shorten the cutoff and archive the key in the same update.
- Previously archived entries cannot be removed, edited or moved back into `keys`, even by a higher signed revision. Version 2 cannot downgrade to version 1.
- Current entries retain the existing non-extended-cutoff and immutable-pin rules. Revisions, authority pinning, policy expiry and rollback checks still apply.

These are local successor checks against the device's installed policy. A new device cannot establish global freshness from a signature alone. An offline device still follows its last installed policy until its original deadlines expire; this is not instantaneous network revocation.

## Preparing a ninth rotation

Use the existing [offline prepare → check → sign workflow](v0.4-admission-rotation-tool.md). Set the rotation request's `version` to `2` and add an explicit selection:

```json
{
  "archive": ["sha256:<fingerprint-of-an-expired-current-key>"]
}
```

This fragment is added to the full request, alongside `newKey`, `issuedAt`, `expiresAt` and `retire`. It is not a complete policy or request. Do not include a selected key in `retire` as well. The tool retains existing archives and copies selected entries unchanged, then adds exactly one fresh active issuer key. Its shared period must be new across current and archived profiles.

Review `retained[].archived`, original deadlines, the new cohort and both capacities. `policyCapacity` reports current entries/remaining slots, archived entries/remaining slots, and signed-file bytes/maximum bytes. The approval digest covers the complete normalized plan. Altering the proposal requires review again. Installation remains a separate operation on wallets, issuer ledgers and restarted relays; existing state directories must be preserved.

## Returning devices and local cleanup

| Component | Archive installation | Explicit local cleanup |
| --- | --- | --- |
| Wallet | Keeps existing wallet files and reservations; creates wallets only for newly seen current profiles; denies an old reservation before allocating a new token | Removes old bearer tokens and raw reservations while retaining the permanent key fence and encrypted retry-denial digests |
| Issuer | Retains permit accounting; refuses new grants, signing and cached response recovery for archived keys | Permanently seals the ledger, preserving lifetime totals |
| Witness | Validates saved votes using archived membership; refuses new or cached old-key votes | Replaces old votes with a permanent local fence |
| Coordinator | Validates saved certificates using archived membership; refuses old-key authorization even with a cached certificate | Replaces old certificates with a permanent local fence |
| Destination | Retains attributed spends and archived pins; only current entries become spend-verification policies | Removes attributed old-key spends with a permanent local fence; preserves unattributed legacy rows |

Archiving and local cleanup can occur in either order after the final cutoff, provided the active key has changed. Cleanup already performed under an earlier revision remains verifiable from archived pins. Missing historical wallet or role files still cause refusal; archiving does not authorize recreating them. Ordinary rollback to an older installed revision remains refused.

The managed-wallet profile snapshot uses version 4 with a v2 policy and can retain up to 72 historical profiles. A new device does not create empty wallets for archives it never used. Existing wallet filenames, token-storage formats and ciphertext domains remain unchanged. Profile metadata is bounded at 2 MiB; the relay's encrypted policy snapshot at 1 MiB. Older binaries reject the new policy/profile version; do not reset state to run an older binary.

## Validation and limits

New checks cover the unchanged v1 signature payload, signed archive tampering, duplicate/missing/active archive entries, original-cutoff enforcement, archive immutability, downgrade and rollback rejection, ninth-rotation approval and actual CLI signing. A valid policy larger than 64 KiB is verified and reopened from encrypted storage. Archive-count and byte limits fail closed.

The integration test issues real blind RSA tokens, records a spend through five witness roles, restarts all roles, installs the ninth issuer, and accepts its token. It confirms the old wallet, vote, certificate and spend files remain unchanged by archival installation; cached old work is refused. Separate cleanup and another restart retain those refusals and the fresh balance. The desktop's authenticated HTTP tests also install a v2 archive, invalidate a stale cleanup review and verify behavior after locking/unlocking.

The preceding Linux CI failed a mailbox cancellation assertion because it counted final server writes that need not happen before the shared deadline on a slower host. The fixture now checks closure of the actual client request sockets; reply withholding, partial-result checks and the production deadline remain unchanged.
