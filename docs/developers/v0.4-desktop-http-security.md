# Local desktop HTTP and session boundary

## Threat boundary

Binding to loopback does not by itself isolate a desktop API from browser pages.
An unrelated page can send cross-origin forms or attempt DNS rebinding. A browser
page with an obsolete session token must also lose event access after lock or
reauthentication. This work protects those boundaries; it does not isolate the
account from malicious software already running with the same OS user's rights.

The server now validates the exact local Host and listening port before serving
HTTP or upgrading WebSockets. It accepts the existing explicit Vite/Tauri origins
and its actual loopback origin; foreign and opaque origins are rejected before
handlers execute. Native loopback clients without Origin remain supported, while
cross-site browser requests without Origin are rejected. CORS headers belong to
each response, including overlapping async operations; responses no longer share
a mutable global origin.

## Session lifecycle

- Account identifiers, activity and counts in `/api/status` require a current
  bearer token. The public response supplies initialization/login state without
  exposing an already-open account.
- Locking an open account requires its token. An already-locked account can be
  locked idempotently. Requests without authentication cannot renew the activity
  timer. Authenticated API activity still renews it; this is not an OS user-idle
  measurement.
- Lock revokes tokens before closing local resources. Every token change closes
  event sockets, including password reauthentication of an already-open account.
  Broadcasts independently verify the current token and unlocked state.
- Initial creation and unlocking share one in-process exclusion guard. Lock
  invalidates pending model-load/unlock work; a late completion cannot reopen
  the account. Failure clears loaded private identity bytes. Initial creation
  refuses an existing identity and clears its temporary key after store setup.
- WebSocket authentication happens before upgrade. Event sockets accept no
  client messages, disable compression, cap incoming frames at 1 KiB, cap clients
  at sixteen, and disconnect a client whose outgoing event buffer exceeds 1 MiB.
  Tokens in event URLs remain local bearer credentials; do not log those URLs.

The HTTP listener caps raw sockets at 128, bounds headers at 8 KiB and HTTP
opening/body/idle waits at ten seconds, and destroys its sockets during stop.
Its JSON body limit is 1 MiB. The reader copies bytes into one bounded buffer,
decodes complete UTF-8 with fatal error handling and requires a non-null JSON
object. Malformed, non-object, interrupted and oversized input is refused before
the caller receives a body. Oversized requests close the socket. The buffer's
used bytes are cleared on success or failure. Passwords must be strings. A
multibyte password split across network chunks retains its original characters;
decoding individual chunks previously corrupted such input.

## Static files

Static assets are resolved against the real UI directory using path components,
then checked again after resolving links. Only regular files inside that directory
are served. Sibling prefixes, external symlinks, directories and invalid paths
cannot expose files or throw uncaught directory-read errors. Valid assets support
query strings and HEAD; unknown SPA routes retain the index fallback. Files are
streamed rather than loaded in full for each request. Tests use an explicit
temporary asset root; ordinary startup keeps its packaged UI location.

## Evidence and remaining scope

TypeScript passes. Twenty-seven tests in four files pass in 70.92 seconds:
seven new real HTTP/WebSocket/filesystem/session cases plus the existing desktop
wallet, private publication and history-setup integrations. Model initialization
is mocked to avoid a download; identity encryption, local stores, API sessions,
socket handshakes, lock/rotation and path checks are real. New cases include
overlapping origins, stale and foreign upgrades, unauthenticated lock/keepalive,
private status, symlink/sibling escape, simultaneous initialization and lock
during model loading.

The subsequent strict-body and existing history-activation group passes fifteen
tests in two files / 14.41 seconds, plus TypeScript. Actual HTTP tests cover
malformed and non-object JSON, invalid UTF-8, body overflow, continued server
availability and creation/unlock with an emoji split across chunks.

The remaining transport/input audit must include each application schema,
complete signature/deadline coverage and public TLS paths. Cross-process identity
creation and atomic account-file persistence also need explicit verification;
the guard above excludes simultaneous calls inside one desktop process only.
Native packaging and external cross-device validation are separate gates.
