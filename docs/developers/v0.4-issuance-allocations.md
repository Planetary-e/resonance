# Authority-approved issuance allocations

This component lets a community authority approve how many token batches each
issuer may allocate in one period. An allocation-required issuer derives its
limits from that signed plan instead of accepting locally selected limits.
It also requires operator-approved claim binding: one retained claim reference
recovers the same permit, without another allocation.

## Plan and trust boundary

A plan contains the supported `public` community, an epoch, an issuance window,
a total token budget and at most eight issuer allocations. Each allocation binds
a normalized issuer profile to a fixed batch size of 1–32 and a permit count of
1–256. Issuer keys cannot repeat, every profile must match the plan's community
and epoch, and the sum of allocated token capacity must not exceed the signed
total. The total is bounded at 65,536 tokens. These are capacity limits, not a
recommended allowance per person.

The existing community Ed25519 authority signs a separate, domain-separated
allocation format. Admission-policy versions 1/2 retain their existing meanings.
Operators must independently verify the authority pin; a public key supplied
alongside an untrusted plan does not establish trust.

The authority's encrypted local journal permits one immutable plan per
authority/community/epoch. Reviewing and signing the same normalized plan
recovers the same signed result. A different plan for that period is refused.
The journal records the signed plan before returning it or exporting a file.
Its bounds are 64 plans and 8 MiB; it refuses further allocation when full and
does not prune history or refund unused capacity.

**This is enforcement by honest local software.** Copying signing keys,
recreating a journal or restoring an old snapshot can bypass local accounting.
The plan's sum does not establish Byzantine-resistant network-wide issuance or
prevent an equivocating authority from signing plans outside this workflow.
Federation consensus, protected cross-issuer accounting, eligibility verification
and one-person-one-quota remain separate, unfinished K4 requirements.

## Issuer enforcement and retained rights

Allocation-required mode is explicit initialization of a new issuer ledger. It
pins the complete signed plan, its digest and authority; verifies that the
issuer's normalized profile has exactly one allocation; and derives its limits.
Caller-selected quota overrides and unbound grants are refused. Reopening the
ledger cannot remove this mode. Older ledger formats keep their previous
behavior; there is no implicit migration or allocation replacement.

Before granting or signing, the issuer must have a current signed community
policy from the allocation's authority containing its unchanged profile. Policy
freshness, active-key rules, conflicts, revocations and cutoffs still apply.
The allocation is an additional restriction, not permission to override policy.
The policy still has one active issuer key. Listing several issuers in an
allocation does not activate them together: each starts issuing only after a
valid signed policy selects its key. The two-issuer test exercises that succession.

New grants and first issuance, including promotion of prepared signatures,
require the allocation issuance window. A previously completed signed response
can be recovered exactly after that window closes while the existing policy's
recovery/spend window permits it. Recovering an already allocated permit neither
extends issuance rights nor consumes another slot. Retirement preserves lifetime
totals and seals the ledger permanently; no capacity transfers or refunds occur.

Claim references and allocation metadata are not added to the existing permit,
blinded request, issuance response or redeemed token formats. The issuer retains
the accounting evidence in encrypted local state. Authority and issuer devices
need not remain online for a wallet to redeem previously issued valid tokens.

## Offline operator workflow

Use the existing [authority and signed-policy setup](v0.4-admission-decision.md#offline-operator-setup).
Keep `authority-private.json` offline and private: it is an unencrypted secret
file. The authority journal is encrypted using a key derived from that secret.
Use one retained journal for that authority and one retained ledger per issuer
key. Never recreate missing history as a new empty journal to resume issuance.

Prepare `allocation-plan.json` from trusted issuer profiles. This one-issuer
example allocates 128 permits of eight tokens in the profile's existing epoch;
choose the allowance and current issuance window with the community. Timestamps
are Unix milliseconds, and the local clock is trusted.

```sh
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const profile = JSON.parse(readFileSync('issuer-profile.json', 'utf8'));
const now = Date.now();
const plan = {
  version: 1, kind: 'admission-issuance-allocation',
  community: 'public', epoch: profile.scope.epoch,
  notBefore: now, issueUntil: now + 86_400_000,
  totalTokenBudget: 1024,
  allocations: [{ profile, batchSize: 8, maxPermits: 128 }],
};
writeFileSync('allocation-plan.json', JSON.stringify(plan), { flag: 'wx', mode: 0o600 });
JS
node --import tsx scripts/admission-allocation.ts init authority.pub authority-private.json allocation-journal.json
node --import tsx scripts/admission-allocation.ts review authority.pub allocation-plan.json
```

Inspect the normalized plan, each profile, its limits and `allocatedTokens` in
the review output. Copy its exact `approvalDigest` into the next command; the
placeholder below is not a valid digest. Review requires no secret or journal.
Initialize the journal only once; subsequent periods reuse it.

```sh
node --import tsx scripts/admission-allocation.ts sign --approve '<approvalDigest>' authority.pub authority-private.json allocation-journal.json allocation-plan.json signed-allocation.json
```

Distribute only the signed allocation and independently verified authority pin
to issuers. On each issuer device, initialize a **new** ledger, install its
current community policy and then use the existing claim and batch workflow:

```sh
node --import tsx scripts/issue-admission-tokens.ts init-allocation --authority-file authority.pub --allocation-file signed-allocation.json issuer-profile.json issuer-private.pem issuer-ledger.json
node --import tsx scripts/issue-admission-tokens.ts policy --approve issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub policy.json
node --import tsx scripts/issue-admission-tokens.ts grant --approve --claim-file operator-claim.json issuer-profile.json issuer-private.pem issuer-ledger.json permit.json
node --import tsx scripts/issue-admission-tokens.ts issue --approve issuer-profile.json issuer-private.pem issuer-ledger.json permit.json request.json response.json
node --import tsx scripts/issue-admission-tokens.ts status issuer-profile.json issuer-private.pem issuer-ledger.json
```

`operator-claim.json` uses the [existing opaque claim format](v0.4-admission-decision.md#optional-operator-approved-claim-binding).
`request.json` is the wallet's original blinded request with exactly the signed
batch size. Keep that wallet state for importing `response.json`. Operators with
pinned live policy observers retain the [existing freshness enrollment and checks](v0.4-admission-decision.md#enroll-an-issuer-in-live-policy-checks);
the allocation does not enroll observers or prove that a policy is the latest.

All output files use exclusive creation. If an export fails, preserve the journal
and retry to a new output path. Repeating `sign` with the same reviewed plan
recovers its retained signature, including after the issuance window closes.
Alternatively, re-export by its exact epoch without signing again:

```sh
node --import tsx scripts/admission-allocation.ts reexport authority.pub authority-private.json allocation-journal.json '<epoch>' recovered-allocation.json
```

For a lost permit output, repeat `grant` with the same claim file and a new output
path. For a lost response output, repeat `issue` with the same permit and original
request. These operations reopen the retained ledger; do not initialize it again.
They remain subject to the policy and window rules above.

## Validation and completion boundary

The component tests cover real authority signing, two independently allocated
issuer ledgers, policy succession, claim grant, blind issuance and exact recovery.
Negative cases reject conflicting plans, wrong authorities, scope changes,
capacity inflation, quota overrides, stale policy observations and expired first
issuance. They also cover input mutation, concurrent signing refusal, journal
capacity/corruption, failed persistence/export and permanently retained retirement.

Local TypeScript compilation passes. The authority/core suites pass 14 tests;
the issuer allocation, ledger, freshness, retirement and crash suites pass 35.
Another 16 regression tests for blind issuance, signed policies and policy
archives pass, for 65 tests across ten files in this checkpoint. After review
corrected the CLI privacy assertion to use the actual exported allocation digest,
its seven-test issuer allocation file passed again.
The real CLI test signs an allocation, initializes an issuer, installs policy,
recovers failed permit/response exports, finalizes the blind token and verifies
its redemption. CI includes the new files on Linux, macOS and Windows; inclusion
is not a claim that a new cross-platform run has passed.

This component does not qualify K4, confidential-search privacy, deployment
availability or the full v0.4 release. See the [acceptance contract](v0.4-acceptance-kpis.md).
