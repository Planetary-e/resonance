# v0.4 anonymous admission decision

## Implemented boundary

The experimental admission module uses Privacy Pass public-verifiable Blind RSA tokens. In the intended flow, a community issuer applies its eligibility policy before signing a blinded request; that policy is not implemented yet. The client later presents the unblinded token to a relay, so the relay does not see the account or request that caused issuance. Tokens are scoped to an issuer, community, and epoch through the challenge digest. A presentation binds one token to one exact v2 request; the relay verifies the issuer signature and fsyncs the token's digest before applying the request. The verifier permits an exact retry at the same relay. This is a bearer token: anyone who obtains the token can present it, so private transport and local wallet protection still matter.

The core exposes blinding, issuing, presentation, and verification primitives. The standalone relay can opt in with `RELAY_ADMISSION_PUBLIC_KEY_FILE`, `RELAY_ADMISSION_ISSUER`, `RELAY_ADMISSION_COMMUNITY`, and `RELAY_ADMISSION_EPOCH`. All four settings are required together. A configured relay rejects v2 operations without a capability. The local verifier recognizes an exact retry; the operation's own replay rules still apply (a repeated search, for example, is refused). There is no end-user issuance interface; this is a protocol implementation slice, not a deployed admission service.

The node package exposes an experimental encrypted wallet for **manually issued** tokens. It checks the issuer signature and scope on import, holds at most 256 tokens for one issuer/community/epoch, and fsyncs an encrypted reservation before returning a capability to the network client. A reservation names the exact destination URL, action, and request digest. Restarting the client can reproduce that presentation for an exact retry, but cannot assign the token to a new request or destination. Two simultaneous imports are rejected rather than allowed to overwrite each other. Import is atomic: a mixed invalid batch adds nothing. Closing during asynchronous verification prevents the import from committing afterwards.

The wallet now shares the outboxes' encrypted atomic snapshot and process-lock implementation, retaining its original ciphertext domain and plaintext schema. PID locks permit recovery only when the previous owner is confirmed dead. A live/reused PID, malformed lock, or interrupted recovery fails closed. Prototype locks containing only a random owner string cannot prove that their owner died and still require manual inspection. The file and replacement snapshots use owner-only permissions. Writes flush the file and, on POSIX, its directory; Windows lacks the directory-flush step. Failed I/O poisons the open wallet until close/reopen. Snapshot capacity is 512 KiB; atomic replacement temporarily requires space for both old and new copies. This does not cap total process memory or disk usage. The wallet cannot make a compromised client device or copied bearer token safe.

## Desktop pilot: setup and use

1. Enable the existing private transport pilot with `RESONANCE_EXPERIMENTAL_PRIVATE_ROUTE_URLS=entry,destination[,fallback...]`, then unlock the desktop app. The wallet does not select or silently replace that route.
2. In **Dashboard → Access-token wallet**, enter an issuer name, token period, its 2048-bit RSA SPKI PEM public key, and 1–8 destination relay addresses obtained through a trusted community channel. The community is `public`, matching the app's current publication/search group. The token period is an explicit scope label; it is not silently derived from the calendar. No issuer public key or destination list is accepted from a token bundle or discovered relay. Setup pins these values and pauses automatic mailbox checks before saving trust configuration.
3. Compare the displayed SHA-256 public-key fingerprint with the community's trusted configuration. Local validation checks key format and imported token signatures; it cannot establish that the person who supplied the public key is trustworthy.
4. Paste manually issued tokens, one per line, and select **Import tokens**. Import validates the whole batch before writing it, ignores exact duplicates, and never contacts a relay, replenishes automatically, or resumes automatic checks. Tokens leave the form after the attempt and are not written to browser storage. The authenticated local API exposes counts, scope, destination list, and the key fingerprint, never token strings or request bindings.
5. Send or Run operations explicitly. The balance reports **available** and **reserved**, not "spent successfully": a reserved request may have reached its destination even without a reply. A fresh search or mailbox request needs a fresh token; an exact signed-publication retry to the same destination reuses its reservation. Background mailbox checks also consume tokens if explicitly re-enabled.

The desktop derives a separate wallet key from the encrypted local identity. `admission-profile.json` encrypts the pinned configuration (16 KiB maximum); `admission-wallet.json` encrypts tokens and reservations. Lock closes both and wipes the owned key buffers. Public keys stay public, but encrypting configuration prevents the disk file from exposing community membership and relay choices. The provider is wired to publication/search, mailbox fetch/ack/deposit, withdrawal, held publications, and saved request runs. It refuses destinations outside the pinned list and refuses token delivery through a direct client if private routing is removed. Existing held routes remain private and can still use the wallet. Exhaustion or storage failure is an error, never permission to omit admission, reuse another reservation, or downgrade transport.

This is a **single-profile pilot**: an issuer, key, token period, or relay-list change is refused rather than discarding existing bindings. All 256 token slots include reserved history, and there is no purge/reset control. Issuance UI/protocol, safe replenishment beyond that bound, issuer/epoch migration, revocation/retirement policy, and authenticated distribution of community configuration remain open. Calendar expiry is not implied by an epoch label; issuers and relays must agree on the accepted scope. Do not delete wallet files to replenish tokens or recycle reservations.

Local validation includes authenticated setup/import/status, encrypted storage, invalid-batch rejection, exhaustion, no reservation while held, disabled background mailbox checks, a lost destination reply with exact reserved-token retry, private-route removal without direct delivery, close during import/configuration, and SIGKILL recovery of both locks. Socket tests use a real admission-enforcing destination behind a separate entry relay, with a fixed embedding vector to avoid model downloads. They do not prove network-wide one-use admission or Internet anonymity.

The desktop-wallet checkpoint passed TypeScript/frontend compilation and 93 test files / 480 tests. A separate browser check used the real cached model and two local relays: setup, import, Save search, lock/unlock, and Run completed successfully. The balance stayed at one available token while held and changed to zero available / one reserved only after explicit release. This remains single-computer validation.

## Volunteer-only issuance

Community issuers can be volunteers who come online to approve batches of blinded requests. Their public verification keys and epoch policy must be distributed through an authenticated community configuration. A permanent issuer service is unnecessary for already issued tokens. An issuer's availability affects replenishing tokens, not redeeming tokens already in a wallet. The issuer must limit issue volume per eligible member without embedding that member's identity in the token or redemption channel. Splitting issuer authority across volunteers needs an audited threshold Blind RSA protocol; concatenating independent signatures or sharing one raw private key is not a threshold scheme.

## Partition-safe spending

The local spent-token log only prevents double spending at one relay. Eventually copying spent IDs does **not** prevent two relays on opposite sides of a partition from both accepting the same token. We will not treat gossip as an admission commit.

For global one-use admission, each token digest maps to one fixed, signed witness set for its epoch. The proposed pilot policy is five distinct volunteer witnesses with a four-signature acceptance certificate, tolerating one malicious witness. Each witness fsyncs a permanent vote for `(issuer, epoch, token digest, action, request binding)` before signing it and never votes for a conflicting binding during that epoch. Any two four-of-five certificates intersect in at least three witnesses, including at least two honest witnesses under that fault bound. The destination applies the request only after verifying the certificate and persisting its own spend. During a partition with fewer than four witnesses reachable, the request remains pending; it cannot be accepted optimistically. A witness that reserves a vote and later loses connectivity may leave a token unusable, because expiring a vote could allow two certificates. Recovery must use the same binding or a new token. This availability cost is deliberate.

Witness-set membership must be pinned before issuance; neither a client nor a destination may pick a convenient set at redemption. Signed descriptors and different observed IP ranges do not prove independent operators, so the one-malicious-witness assumption needs community governance and tests. The quorum protocol, signed votes, witness key rotation, and membership distribution are **not implemented**. Until they are, a relay using local admission must not advertise a network-wide one-use guarantee.

## Validation gates

Before enabling admission by default, test blind issuance without issuer-to-redemption identifiers; key persistence and rotation; quota enforcement; local crash recovery; concurrent conflicting spends; three-versus-two partitions; witness equivocation; and spend behavior when a witness disappears after voting. The adversarial suite must also measure timing and size correlation through two-hop transport. Passing unit tests for the blind signature or local log is not enough for a v0.4 privacy claim.
