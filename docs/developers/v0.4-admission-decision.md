# v0.4 anonymous admission decision

## Implemented boundary

The experimental admission module uses Privacy Pass public-verifiable Blind RSA tokens. The pilot requires a one-use community permit for a fixed-size blinded batch. A durable issuer ledger enforces permit use and a bounded total allowance; distributing permits fairly remains a community decision. The client later presents the unblinded token to a relay, so the relay does not see the account or request that caused issuance. Tokens are scoped to an issuer, community, and epoch through the challenge digest. A presentation binds one token to one exact v2 request; the relay verifies the issuer signature and fsyncs the token's digest before applying the request. The verifier permits an exact retry at the same relay. This is a bearer token: anyone who obtains the token can present it, so private transport and local wallet protection still matter.

The core exposes blinding, issuing, presentation, and verification primitives. The standalone relay supports the shared signed-policy mode described below, or manual pilot settings with `RELAY_ADMISSION_PUBLIC_KEY_FILE`, `RELAY_ADMISSION_ISSUER`, `RELAY_ADMISSION_COMMUNITY`, and `RELAY_ADMISSION_EPOCH`. All four settings are required together. A configured relay rejects v2 operations without a capability. The local verifier recognizes an exact retry; the operation's own replay rules still apply (a repeated search, for example, is refused). The desktop can prepare an offline blinded batch and import a volunteer-approved response. Invitation distribution remains manual; permit and total-budget enforcement are implemented. This is not a deployed admission service.

The node package exposes an experimental encrypted wallet for manually imported or locally unblinded tokens. It checks the issuer signature and scope on import, holds at most 256 available tokens and 4,096 total entries (including reservation history) per issuer key/scope, and fsyncs an encrypted reservation before returning a capability to the network client. A reservation names the exact destination URL, action, and request digest. Restarting the client can reproduce that presentation for an exact retry, but cannot assign the token to a new request or destination. Two simultaneous imports are rejected rather than allowed to overwrite each other. Import is atomic: a mixed invalid batch adds nothing. Closing during asynchronous verification prevents the import from committing afterwards.

The wallet now shares the outboxes' encrypted atomic snapshot and process-lock implementation, retaining its original ciphertext domain and plaintext schema. PID locks permit recovery only when the previous owner is confirmed dead. A live/reused PID, malformed lock, or interrupted recovery fails closed. Prototype locks containing only a random owner string cannot prove that their owner died and still require manual inspection. The file and replacement snapshots use owner-only permissions. Writes flush the file and, on POSIX, its directory; Windows lacks the directory-flush step. Failed I/O poisons the open wallet until close/reopen. Each token snapshot has an 8 MiB limit; atomic replacement temporarily requires space for both old and new copies. This does not cap total process memory or disk usage. The wallet cannot make a compromised client device or copied bearer token safe.

## Desktop pilot: setup and use

1. Enable the existing private transport pilot with `RESONANCE_EXPERIMENTAL_PRIVATE_ROUTE_URLS=entry,destination[,fallback...]`, then unlock the desktop app. The wallet does not select or silently replace that route.
2. In **Dashboard → Access-token wallet**, enter an issuer name, token period, its 2048-bit RSA SPKI PEM public key, and 1–8 destination relay addresses obtained through a trusted community channel. The community is `public`, matching the app's current publication/search group. The token period is an explicit scope label; it is not silently derived from the calendar. No issuer public key or destination list is accepted from a token bundle or discovered relay. Setup pins these values and pauses automatic mailbox checks before saving trust configuration.
3. Compare the displayed SHA-256 public-key fingerprint with the community's trusted configuration. Local validation checks key format and imported token signatures; it cannot establish that the person who supplied the public key is trustworthy.
4. Obtain a single-use issuance permit from your community and verify its issuer/key/period against your trusted setup. Its `count` gives the required batch size (1–32). Select that count and **Prepare blinded request**. Copy the displayed JSON to your volunteer issuer through your chosen channel, supplying the permit separately. Do not add the permit to the blinded request, response, or a relay operation. Paste their signed JSON response and select **Verify and add tokens**. Preparing and completing a batch are local; neither contacts a relay or resumes automatic mailbox checks. The app generates its own random tokens and verifies/unblinds the signatures, so the issuer does not learn the bearer tokens. Manual token import remains under **Import already-issued tokens**; manually supplied bearer tokens can be known to whoever supplied them.
5. Keep the app unlocked until issuance finishes. Blinding secrets are one-shot, in-memory state; lock, quit, or restart cancels an unfinished batch. A page refresh followed by unlocking preserves a pending batch only while the same backend session remains unlocked. **Cancel token request** explicitly discards it. An issuer may already have bound the permit to an abandoned batch. It cannot authorize a replacement batch; a new permit is required. Cancellation does not undo approval. Malformed/wrong-batch responses leave the pending exchange usable. A cryptographically invalid signature cancels the whole batch, adds no tokens, and requires a new request. A failed wallet write never exposes a capability; normal storage recovery still applies.
6. Send or Run operations explicitly. The balance reports **available** and **reserved**, not "spent successfully": a reserved request may have reached its destination even without a reply. A fresh search or mailbox request needs a fresh token; an exact signed-publication retry to the same destination reuses its reservation. Background mailbox checks also consume tokens if explicitly re-enabled.

The desktop derives a separate wallet key from the encrypted local identity. `admission-profile.json` encrypts up to eight pinned configurations (128 KiB maximum). The original `admission-wallet.json` remains the first profile’s token history; later profiles use files named by their public-key fingerprint. Each profile has its own 8 MiB snapshot limit (64 MiB across eight wallets, plus configuration and temporary copies). Lock closes all wallets and wipes the owned key buffers. Public keys stay public, but encrypting configuration prevents the disk file from exposing community membership and relay choices. The provider is wired to publication/search, mailbox fetch/ack/deposit, withdrawal, held publications, and saved request runs. It refuses destinations outside the pinned list and refuses token delivery through a direct client if private routing is removed. Existing held routes remain private and can still use the wallet. Exhaustion or storage failure is an error, never permission to omit admission, reuse another reservation, or downgrade transport.

### Replenishment and changing keys or periods

Replenishment adds new tokens to the active profile without deleting any old entry. Exact duplicates, including reserved tokens, add nothing. At 256 available tokens or 4,096 total entries, imports stop safely. These are bounded pilot limits, not indefinite retention or automatic expiry. There is no purge/reset control. Do not delete wallet files to replenish tokens or recycle reservations.

**Change issuer or token period** accepts community-verified setup details and explicitly activates the new profile. Every changed setup requires a different issuer public key; reusing one key across periods would let a blind signer issue a hidden challenge for another period. The issuer cannot inspect that hidden challenge, so this also requires operators to dedicate each signing key to one scope. The response bundle never changes trust configuration. Re-entering an identical previously pinned setup explicitly reactivates it; changing its period or destination allowlist under the same key is refused. Setup changes pause automatic mailbox checks and are refused while issuance is pending.

All prior wallets remain encrypted and locked alongside the active one. Before allocating a token, the provider searches every profile for an exact destination/action/request reservation. An old retry therefore keeps its original token after rotation, even if the active profile has new tokens. New requests use only the active profile; they cannot consume unused archived tokens automatically. If a relay has retired the old period, its rejection is surfaced; the client does not silently substitute a new token. The original single-profile configuration upgrades atomically when another profile is added; its token file is left intact. A missing archived wallet is an error on unlock, never a silently recreated empty history.

Calendar expiry is not implied by a token-period label. The signed-policy mode below adds explicit key deadlines enforced by the desktop, issuer, and relay. Manual setup remains available only until that wallet adopts a community authority; subsequent changes require its signature. At eight saved setups, another setup is refused. Automatic distribution, emergency revocation on disconnected devices, authority rotation, safe history compaction, and automated Sybil-resistant eligibility remain open.

Local validation includes authenticated setup/import/status, encrypted storage, invalid-batch rejection, exhaustion, no reservation while held, disabled background mailbox checks, a lost destination reply with exact reserved-token retry, private-route removal without direct delivery, close during import/configuration, and SIGKILL recovery of both locks. Socket tests use a real admission-enforcing destination behind a separate entry relay, with a fixed embedding vector to avoid model downloads. They do not prove network-wide one-use admission or Internet anonymity.

The preceding desktop-wallet checkpoint passed TypeScript/frontend compilation and 93 test files / 480 tests, plus a browser check with the real cached model. Issuance checks additionally exercise invalid and mismatched batches, concurrent updates, close during request creation/finalization, cancellation, original-profile migration, key rotation and exact retry across restart, missing-history refusal, replenishment past 256 historical reservations, and the 4,096-entry bound. Live desktop HTTP tests prepare/import a blinded batch without WebSocket activity, redeem through the private route, and refuse a signed response after locking cancels its pending request. The final checkpoint passed TypeScript/frontend compilation and 94 test files / 486 tests. A separate browser check with the real cached model prepared two blinded tokens, obtained approval through the actual PKCS8 issuer command, imported the response, and ran a successful private search: the balance moved from two available to one available / one reserved. Activating a fresh key/period retained the previous wallet, including across lock/unlock. The browser check caught and fixed an issuer-command key-import mismatch; the command is now exercised by a regression test. These remain single-computer checks, not a network-wide admission or privacy certification.

## Signed community configuration and retirement

The desktop, offline issuer ledger, and standalone relay can now adopt the same **Ed25519-signed policy**. Its authority is separate from the RSA token-issuance keys. Obtain and verify the authority public key through an independent community channel before installing a policy. Neither the policy file nor a discovered relay can authorize its own signing key. Once installed, that authority is pinned locally; manual wallet changes and updates signed by another authority are refused.

A policy contains a positive revision, issue/expiry timestamps, an active issuer-key fingerprint, and 1–8 cumulative issuer profiles. Each profile pins the key, issuer/community/period, and destination URLs. All times are integer Unix milliseconds. A policy is usable only from `issuedAt` through, but excluding, `expiresAt`; its validity cannot exceed 30 days. Each key has ordered cutoffs:

| Interval | Issuer | Wallet and relay |
| --- | --- | --- |
| Before `notBefore` | Refuse | Refuse |
| `notBefore` to `issueUntil` | New grants and batches only for the active key | Fresh uses allowed until `spendUntil`; wallet selects the active key |
| `issueUntil` to `spendUntil` | Return an already cached exact response; do not sign a new or incomplete batch | Previously issued tokens can still be used |
| `spendUntil` to `retryUntil` | Refuse | Relay permits only an exact use already recorded in its own spend log |
| At or after `retryUntil` | Refuse | Refuse, retaining all history |

Policy expiry overrides every interval. Retirement never deletes tokens, reservations, permits, spent IDs, or published content. The wallet retains exact reservations from prior keys, but a local reservation alone is not evidence of relay acceptance. During the retry-only interval, a request that never reached that relay is refused. Operation-specific replay rules still apply; admission permission does not make an expired/replayed search valid.

Updates must retain every prior key with identical profile pins and `notBefore`. They may shorten issue/spend/retry cutoffs, never extend them. Lower revisions, conflicting content at the same revision, and backwards `issuedAt` values are refused. A fresh key is necessary for a new period. Policy expiry may be renewed in a higher revision without extending old key cutoffs. There is no automatic active-key switch: the active fingerprint changes through an installed signed revision. Plan windows before distributing a policy. The eight-key bound includes retired history; ninth-key rotation and safe compaction remain unimplemented.

The desktop saves the signed policy, profile list, and active choice in one encrypted snapshot. Original wallet files and reservations remain intact. Pending blinded issuance must finish or be cancelled before changing policy. Installing a policy pauses automatic mailbox checks. Expired configuration remains readable after unlock, and local holds remain manageable; token issuance and delivery require a current policy. The issuer stores the policy alongside its existing permits without resetting allowance. The relay persists the pinned authority and highest accepted revision in a separate encrypted 128 KiB snapshot and uses the existing shared spend log for all accepted keys. The common encrypted-state/profile helpers now live in backend-only core subpaths; original ciphertext domains and file formats are preserved.

### Offline operator setup

Create a community authority once. Keep `authority-private.json` private and offline; it is an owner-only **unencrypted secret file**, not a hardware keystore. Share `authority.pub` and verify its displayed fingerprint through an independent channel. Use one authority/key policy for the cohort, not a unique authority per member.

```sh
node --import tsx scripts/admission-policy.ts authority-keygen authority-private.json authority.pub
```

Build the first policy from the operator's trusted `issuer-profile.json`. This example chooses one day for issuance, two days for new uses, three days for recorded retries, and a four-day policy lifetime. Choose actual windows with the community. On rotation, retain every prior entry, add the new profile, and increment the revision instead of regenerating this initial body.

```sh
node --import tsx --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
import { admissionKeyFingerprint } from '@resonance/core/admission-policy';
const profile = JSON.parse(readFileSync('issuer-profile.json', 'utf8'));
const now = Date.now(), day = 86_400_000;
const body = {
  version: 1, kind: 'admission-policy', revision: 1,
  issuedAt: now, expiresAt: now + 4 * day,
  activeKey: admissionKeyFingerprint(profile.issuerPublicKey),
  keys: [{ profile, notBefore: now, issueUntil: now + day,
    spendUntil: now + 2 * day, retryUntil: now + 3 * day }],
};
writeFileSync('policy-body.json', JSON.stringify(body), { flag: 'wx', mode: 0o600 });
JS
node --import tsx scripts/admission-policy.ts sign authority-private.json policy-body.json policy.json
```

Signing validates structure and key formats. It does not know recipients' installed revisions; they enforce successor rules. Outputs use exclusive creation and are never overwritten. Distribution is an explicit file exchange, with no polling, issuer connection, or always-on community server.

- **Desktop:** open **Dashboard → Access-token wallet → Community-signed setup**, enter the independently verified authority key and signed policy JSON, then select **Verify and apply policy**. If migrating a manually configured wallet, the signed policy must include all its prior profiles unchanged. Only the public key and signed policy belong here, never either private key.
- **Issuer:** initialize its permit ledger as described below, then install the same policy before granting permits. The command requires the already pinned issuer profile and matching private RSA key; it retains all prior grants/reservations. Repeat for each issuer ledger named in the policy.

```sh
node --import tsx scripts/issue-admission-tokens.ts policy --approve issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub policy.json
```

- **Standalone destination relay:** generate a separate local storage key on each relay device and retain it with its data directory. Share only the authority public key and policy, not this storage key. Supply all three file settings and omit the older four manual issuer settings. The initialization flag is for the first creation only.

```sh
node --import tsx scripts/admission-policy.ts storage-keygen local-policy-key.hex
RELAY_ADMISSION_AUTHORITY_FILE=authority.pub \
RELAY_ADMISSION_POLICY_FILE=policy.json \
RELAY_ADMISSION_POLICY_KEY_FILE=local-policy-key.hex \
RELAY_ADMISSION_POLICY_INITIALIZE=true \
RELAY_DATA_DIR=./relay-data \
node --import tsx packages/relay/src/main.ts
```

On subsequent starts, omit `RELAY_ADMISSION_POLICY_INITIALIZE`, retain the same authority, storage key and data directory, and supply the current signed policy file. A normal start refuses missing policy history; initialization refuses existing state. If first startup created policy state but later failed, recover that state and restart without the initialization flag. Applying an updated relay policy currently requires a restart. Dates are checked at each verification, including after asynchronous cryptography, so scheduled cutoffs take effect while running. Reachable relays still need the existing TLS, identity-keystore, and discovery configuration; this loopback example does not publish a relay on the Internet. The desktop's **Act as Relay** controls do not yet expose these signed-policy settings.

### Guarantees and limitations

This authenticates configuration and coordinates explicit retirement dates on devices that have installed it. It is **not network consensus or immediate revocation**. An offline device can continue using its last unexpired signed policy; shortening a date takes effect there only after an update. An expired policy stops admission until refreshed. Local clocks are trusted. Different devices can receive conflicting valid signatures; local same-revision rejection does not detect equivocation across devices. Authority replacement/recovery, policy transparency, automatic distribution, and protection against filesystem snapshot rollback remain open. Deleting or restoring old state, deliberately switching a relay back to manual verification, or using an issuer outside the ledger bypasses the honest-operator boundary.

Tests cover independent authority verification, tampering, changed pins, rollback and conflicting revisions, forbidden deadline extensions, restart persistence, policy expiry, retired-key exact retries, refusal of previously undelivered old tokens, and a cutoff crossed during asynchronous verification. An end-to-end test combines issuer allowances, wallet rotation, relay restart, and new-key redemption. Actual commands generate/sign policy, install it into an existing issuer ledger, preserve its earlier permit and refuse a retired grant. Desktop HTTP tests apply signed setup, lock/unlock, deliver through two relays, shorten cutoffs, and reject rollback. This checkpoint passed TypeScript/frontend compilation and **97 test files / 496 tests**. A separate browser check with the real cached model installed signed setup, imported a test token, searched successfully through two local relays, and retained revision 1 plus its one reservation across lock/unlock. Temporary keys, profiles, and relays were removed. These remain single-computer checks, not an Internet pilot or privacy certification.

## Volunteer-only issuance

Community issuers can be volunteers who come online to approve batches of blinded requests. Their public verification keys and epoch policy must be distributed through an authenticated community configuration. A permanent issuer service is unnecessary for already issued tokens. An issuer's availability affects replenishing tokens, not redeeming tokens already in a wallet. The issuer must limit issue volume per eligible member without embedding that member's identity in the token or redemption channel. Splitting issuer authority across volunteers needs an audited threshold Blind RSA protocol; concatenating independent signatures or sharing one raw private key is not a threshold scheme.

### Pilot eligibility decision: single-use permits

Eligibility in this pilot means possession of an unused **256-bit random bearer permit** allocated by the volunteer issuer. Each permit authorizes exactly one batch, with the same batch size for all permits under that issuer key. The operator chooses a fixed size of 1–32 and a cap of 1–256 permits when initializing the ledger. Both remain pinned. For example, 128 permits × 8 tokens gives a maximum of 1,024 signatures for distinct blinded requests through that ledger, including allowances lost to interrupted or abandoned exchanges. Exact retries reproduce signatures for the same inputs and do not grant additional tokens.

The permit carries the public issuer/key/period, required count, and random secret. It has no name, email, DID, device identity, or persistent member field. Only its domain-separated hash is stored in the encrypted issuer ledger. The permit is passed separately to the issuer; neither it nor its hash enters the blinded batch, signed response, or redeemed capability. Operators should give permits through the community's chosen private channel and use one shared key/period and batch size for the cohort. **Do not give each member their own issuer key.** A channel may identify a recipient to the operator; this mechanism does not make the invitation exchange anonymous to that operator.

This is an invitation-limited budget, **not proof of one human or one allowance per person**. Permits and tokens can be transferred, and several permits can go to one person. Automated eligibility, equitable invitation distribution, anonymous membership credentials, and Sybil-resistant enrollment remain open. There is no account registry, hardware attestation, proof-of-work task, or permanent issuer service in this pilot. Those are future policy choices, not claims made by the permit implementation.

The design follows the separation in [RFC 9576 §3.5.1](https://www.rfc-editor.org/rfc/rfc9576.html#section-3.5.1): deciding who qualifies is deployment-specific and separate from blind issuance. The RFC also warns that [issuer keys, metadata, and timing](https://www.rfc-editor.org/rfc/rfc9576.html#section-6) can divide users into distinguishable groups. Fixed-size permits and a shared cohort key are our pilot choices; they do not establish protection against those side channels. The existing Blind RSA token construction remains the [RFC 9578 publicly verifiable protocol](https://www.rfc-editor.org/rfc/rfc9578.html#section-5); the local JSON permit format is Resonance-specific.

### Volunteer operation

Use the issuer's own trusted profile JSON (the same `version`, `scope`, `issuerPublicKey`, and `relayUrls` shape as desktop setup) and its matching **2048-bit RSA PKCS8 PEM private key**. Never adopt a requester-supplied profile. Keep the signing key and ledger together on one issuer device. Use a fresh key for a new period. No network service is started by these commands.

Initialize once, choosing a cohort-wide batch size and total permit budget (example: eight tokens per permit, 128 permits):

```sh
node --import tsx scripts/issue-admission-tokens.ts init issuer-profile.json issuer-private.pem issuer-ledger.json 8 128
```

Explicitly approve an invitation and give only `permit.json` to the chosen recipient:

```sh
node --import tsx scripts/issue-admission-tokens.ts grant --approve issuer-profile.json issuer-private.pem issuer-ledger.json permit.json
```

The recipient prepares the required count in the desktop, keeps the app unlocked, and returns their permit with the blinded request. Approve that exact batch:

```sh
node --import tsx scripts/issue-admission-tokens.ts issue --approve issuer-profile.json issuer-private.pem issuer-ledger.json permit.json request.json response.json
node --import tsx scripts/issue-admission-tokens.ts status issuer-profile.json issuer-private.pem issuer-ledger.json
```

Return only `response.json` to the requester. The app verifies every signature before atomic import. The command bounds inputs to 32 KiB (64 KiB for a signed policy), verifies the private key against the pinned public key, checks permit and request scope/count, and refuses missing history. Output files use owner-only permissions and exclusive creation. Existing output is never overwritten. The earlier unrestricted `--approve profile key request response` invocation is no longer supported. The low-level `issueAdmissionBatch` remains a crypto primitive for tests/embedders; it does not enforce policy and must not be exposed as an operational signing endpoint.

`status` reports counts only, not permit hashes, batch IDs, member data, or token strings. The issuer ledger is an AES-GCM authenticated snapshot with a separate HKDF-derived encryption key from the issuer private key, an 8 MiB limit, flushed atomic replacement, and a single-writer process lock. The standard process-lock recovery rules apply. Initialization refuses existing state; ordinary commands require an existing ledger. Missing/corrupt state or altered profile pins fail closed. Windows flushes the replacement file but cannot flush its directory. Storage bounds exclude temporary replacement files and process memory.

### Crash and output recovery

- Grant allocation is durable before the secret is returned. If writing the permit file fails, its slot remains allocated; there is no refund/reset command. A lost permit file therefore consumes budget without a usable invitation.
- Approval pins the **entire batch digest before the first signature**. Unknown permits, mismatched scope/count, and malformed public request metadata are refused first. A cryptographically invalid blinded value discovered after reservation keeps the permit bound; no different batch may use it.
- The complete signed response is persisted before it can leave the ledger API. If the issuer closes or crashes during signing, the permit stays bound to the original batch. Re-submit the same permit and identical request to finish. A different batch is rejected, and no budget is refunded.
- If output is lost or partially written, retry to a **new response filename**. The cached exact response is returned without new signing or allowance consumption. If the client already lost its in-memory blinding state, that response is unusable and a new permit/request is necessary.
- One batch cannot be assigned to multiple permits. Live concurrent writers are refused; a confirmed-dead owner's lock can be recovered after a crash. Capacity exhaustion never removes history or starts a fresh ledger automatically.

This is local enforcement by an honest issuer. A copied/rolled-back ledger, another fresh ledger under the same signing key, or an operator who signs outside the permit command can bypass it. Keep one authoritative ledger per key; do not clone it across volunteers or restore an old snapshot and continue issuing. Lost history requires retiring that key with a signed policy update, subject to the offline-update limitations below. Multiple independent issuer keys have independent budgets; they are not a network-wide allowance. Quorum/threshold issuance and protection against malicious issuers remain open. The relay sees only the standard blind token and cannot audit that the issuer respected its local policy.

### Permit validation

Tests cover fixed and total limits, malformed/unknown/wrong-scope permits, count mismatch, concurrent approval, exact retry, duplicate batch allocation, missing/corrupt history, changed pinned policy/profile, encrypted storage, and absence of permit/batch identifiers in capabilities. Fault injection verifies that a failed reservation never signs and a failed response write never returns a result. A separate process is killed after its first signature in a two-token batch; restart resumes only the same batch without increasing its allowance. The actual PKCS8 command is exercised for initialization, grant, approval, output recovery, exhaustion, and missing explicit approval. Desktop HTTP tests unblind a permit-authorized response and redeem through a real admission-enforcing relay behind a separate entry. This checkpoint passed TypeScript/frontend compilation and the full local suite: 96 test files / 491 tests. Networking, cryptography, and persistence are real; desktop HTTP embeddings use a fixed test vector. The permit checkpoint changes issuer operation and wallet guidance, not the desktop response-import protocol. It does not establish Internet anonymity or network-wide quota enforcement.

## Partition-safe spending

The local spent-token log only prevents double spending at one relay. Eventually copying spent IDs does **not** prevent two relays on opposite sides of a partition from both accepting the same token. We will not treat gossip as an admission commit.

The optional witnessed mode now pins **one five-member witness set per issuer key** in the signed community policy. Every token under that key uses that same set; there is no dynamic sharding or choice at redemption. Four distinct valid Ed25519 votes form an acceptance certificate. With at most one equivocating witness, any two four-of-five certificates intersect in at least three witnesses, including at least two honest witnesses that will not vote twice. This is a fixed-membership safety rule, not leader election or a general consensus log.

The destination first verifies the actual Blind RSA token and its request proof locally. It then signs a vote request containing only the witness-set identifier, issuer-key fingerprint, token digest, action, and exact request binding. Witnesses accept requests only from infrastructure coordinator keys authorized in that signed set. They receive neither the bearer token, the request content, nor a client/account identifier. They cannot independently prove possession of the hidden token: a malicious authorized coordinator can consume witness capacity or reserve known digests. This is an explicit trust/resource boundary, not anonymous public access to the voting endpoint.

Each witness stores and flushes its signed vote **before returning it**. A repeated claim returns the same vote; a different binding for that issuer key/token digest is refused permanently. New votes respect the key's new-spend cutoff and the relay owner's new-work policy. Previously stored votes can be recovered until the key's retry cutoff while new work is paused. Policy expiry overrides both. Signatures bind membership, issuer key, digest, action and request binding. Duplicate witness signatures, foreign keys, mixed claims, and signatures for another set do not form a certificate.

The destination collects four signatures, verifies them and persists the complete certificate before writing its existing local spend log and applying the request. Three signatures never suffice. Certificates survive restart and permit an exact locally recorded retry without another witness round trip; operation-specific expiry/replay rules still apply. The claim intentionally does not bind a destination identity: the same signed operation may be checked at multiple relays, including forwarded search. This prevents a token authorizing **different request bindings**, not repeated execution of the identical operation at every relay. Those operations retain their own deduplication and replay checks.

Witness calls run in parallel with a three-second deadline, at most 32 in-flight quorum attempts per destination and five sockets per attempt. Four responses complete the quorum without waiting for a silent fifth. Timeout, close, malformed responses and missing quorum never fall back to local-only acceptance. Late votes cannot commit a timed-out attempt. The one-message WebSocket exchange refuses redirects, uses normal certificate verification for `wss://`, and permits cleartext only for existing local/private-LAN endpoint rules. Incoming vote requests and outbound reply payloads are limited to 4 KiB; the server additionally rate-limits requests per source address. Standalone coordinators attach established witness sockets to the existing bandwidth meter, and witness new-vote handling honors owner new-work limits. These bounds do not cap total CPU/memory, failed handshakes, TLS overhead or all inbound connection work.

The witness's encrypted atomic snapshot holds at most 10,000 votes / 16 MiB; a coordinator holds at most 10,000 certificates / 32 MiB. Byte limits can stop admission before entry limits. Both use process locks, fsynced replacement, separate ciphertext domains and the relay's local policy-storage key. Windows flushes replacement files but lacks POSIX directory flushing. There is no compaction, refund, automatic reset or vote expiry. Regular startup refuses missing history; corruption fails closed. An uncertain write poisons the open handle until recovery. Restoring old snapshots, recreating a witness's lost state under the same key, or cloning signing keys violates the honest-witness assumption.

### Witness setup

Before issuing tokens for a **fresh RSA issuer key**, create one dedicated signing key on each of five volunteer witnesses and each authorized destination coordinator. A device may hold both roles, but five distinct keys/URLs do not prove five independent operators. Each private file is owner-only and unencrypted; keep it local and protect it like the other offline keys.

```sh
node --import tsx scripts/admission-policy.ts participant-keygen witness-private.json witness.pub
# On a destination device, use separate filenames:
node --import tsx scripts/admission-policy.ts participant-keygen coordinator-private.json coordinator.pub
```

Add this `witnesses` field to that new key's entry in the unsigned policy body before signing it. Replace every placeholder with the actual public key or endpoint; collect five member entries and one to eight coordinator keys.

```json
{
  "version": 1,
  "quorum": 4,
  "members": [
    { "publicKey": "<witness-1-base64url-key>", "endpoint": "wss://witness-1.example/" },
    { "publicKey": "<witness-2-base64url-key>", "endpoint": "wss://witness-2.example/" },
    { "publicKey": "<witness-3-base64url-key>", "endpoint": "wss://witness-3.example/" },
    { "publicKey": "<witness-4-base64url-key>", "endpoint": "wss://witness-4.example/" },
    { "publicKey": "<witness-5-base64url-key>", "endpoint": "wss://witness-5.example/" }
  ],
  "coordinators": ["<destination-coordinator-base64url-key>"]
}
```

Sign and install the resulting policy in the desktop, issuer and participating relays using the preceding instructions. Membership, endpoints and coordinator authorization become immutable for that issuer key. Policy successor validation refuses adding, removing or replacing the set on an already pinned key, including changing it back to local verification. New membership requires a new issuer key and retained old history. No discovery result or request supplies replacement membership. Initial trust still depends on an honest authority distributing one consistent configuration; cross-device authority equivocation remains unresolved.

In addition to the three signed-policy file variables, a standalone relay enables its role with:

```sh
# A witness serves durable votes on its normal relay WebSocket listener:
export RELAY_ADMISSION_WITNESS_KEY_FILE=witness-private.json
# A destination gathers certificates before accepting witnessed tokens:
export RELAY_ADMISSION_COORDINATOR_KEY_FILE=coordinator-private.json
```

Set only the roles that device holds. The normal first-start `RELAY_ADMISSION_POLICY_INITIALIZE=true` also initializes those role histories. When adding a role to a relay that already has policy state, use `RELAY_ADMISSION_WITNESS_INITIALIZE=true` only for the explicit first creation of its enabled role histories, then remove it. Do not use initialization to recover lost histories; existing history refuses initialization. Retain the same data directory, encryption key and role keys on restart. A destination presented with a witnessed token but lacking an authorized coordinator refuses it. Keys without a `witnesses` field retain the explicitly local-only pilot boundary. The desktop contribution panel does not yet configure witness roles.

### Availability and validation

With fewer than four reachable witnesses, the operation returns unavailable without application. Some witnesses may already have stored permanent votes. Retrying the same binding can recover them after reconnection. If conflicting attempts divide the honest votes, neither may ever reach four; that token is stranded and cannot be refunded safely. A changed request needs another token. This policy deliberately favors rejecting conflicting uses over availability during partitions. Independently operated volunteers, honest destinations and an honest configuration authority are assumptions; identity keys and distinct URLs do not establish them.

Tests exercise simultaneous conflicting attempts with one equivocating witness, missing/duplicate/forged votes, three-versus-two partitions, minority votes that strand a token, immutable membership, owner pauses, key retirement, persistence failures, missing histories, bounded concurrency, timeout, close and late replies. A real process is killed after a durable vote and recovers only its original binding. A socket integration uses five witness relays, two destinations and a separate private entry: publish with a real blind token, refuse its reuse at another destination, refuse new publication with three witnesses, recover with four, restart the destination and retry an already certified publication with all witnesses offline. Witness frames omit the token and publication ID. TypeScript compilation and the full suite passed: **100 files / 507 tests**. A separate standalone-process smoke check exercised participant key generation, environment-based startup, signed socket voting, graceful restart, exact recovery and conflicting-request refusal; all temporary keys and state were removed. The final network check also verifies that witness sockets and bytes reach the bandwidth-meter callback.

These are local tests, not a volunteer availability benchmark. Witness traffic exposes action categories, digests, coordinator identities and timing to those infrastructure participants and adds connections/bytes. Internet TLS/proxy testing, bandwidth/energy/latency measurements, membership governance, safe witness replacement and history compaction remain open. No new GUI flow or installer was introduced. Local-only admission must still not advertise a cross-relay one-use guarantee.

## Validation gates

Before enabling admission by default, test blind issuance without issuer-to-redemption identifiers; key persistence and rotation; quota enforcement; local crash recovery; concurrent conflicting spends; three-versus-two partitions; witness equivocation; and spend behavior when a witness disappears after voting. The adversarial suite must also measure timing and size correlation through two-hop transport. Passing unit tests for the blind signature or local log is not enough for a v0.4 privacy claim.
