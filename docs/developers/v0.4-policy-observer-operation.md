# Preparing and operating protected policy observers

This experimental Node entry point prepares a new observer under an independently
pinned context, enrolls its five volunteer histories and operates existing state.
Preparation, local initialization and signing readiness are separate commands.
Desktop selection, protected compaction and private application integration remain
separate work. Five keys/processes do not prove five independent operators.

## Initial preparation and volunteer enrollment

Use new, dedicated participant keys and independent local storage keys. The
existing offline key commands are:

```sh
node --import tsx scripts/admission-policy.ts participant-keygen observer-private.json observer.pub
node --import tsx scripts/admission-policy.ts storage-keygen observer-storage.hex
```

Each volunteer keeps its own secrets; volunteers receive neither the observer's
private key nor its storage key. Independently verify the community authority,
initial signed policy, five observer identities/endpoints and five history
endpoints before preparing. The history context uses the same five identity pins
and a distinct deterministic `policy-observer` role for each owner.

Create a bounded JSON setup input from those actual pins:

```js
const setup = {
  version: 1,
  kind: 'policy-observer-setup',
  context,     // independently verified policy observer context
  members,     // five { publicKey, endpoint } history contacts
  directory: 'owner',
  signingKeyFile: 'observer-private.json',
  storageKeyFile: 'observer-storage.hex',
  policyFile: 'initial-policy.json',
  limits: { archiveBytes: 67108864, archiveBlocks: 10001 },
  listen: { port: 9101, maxConnections: 4, connectionTimeoutMs: 10000 }
};
```

Paths resolve relative to this input. Keep keys, preparation/configuration files
and public enrollment exports outside the dedicated owner-history directory.
Append these arguments to `npm run policy-observer --workspace @resonance/relay --`:

```text
setup-plan SETUP_JSON NEW_CONFIG
setup-create --approve DIGEST SETUP_JSON NEW_CONFIG
enrollment-export NEW_CONFIG PUBLIC_ENROLLMENT
```

Planning is offline and writes nothing. Its digest binds selected file contents,
keys, paths, context, member endpoints and resource limits. Creation checks the
policy again and exclusively saves the exact random encrypted root in
`<canonical-signing-key-path>.policy-observer-root.json` before exporting the
configuration. Back up that anchor with the keys. Creation does not initialize
owner history, contact volunteers or start a listener.

A complete anchor can be re-exported with `setup-export SETUP_JSON NEW_CONFIG`,
including after a lost response or partial configuration export. An existing
output is never overwritten. An incomplete anchor is preserved and refused;
do not delete it or rename/copy the signing key to generate another root. The
local guard is not proof that an imported key was never used elsewhere: initial
preparation requires a genuinely new identity. Existing identities need their
original pins and recovery workflow.

Public enrollment contains only public contexts and the signed encrypted genesis.
Verify its context/genesis fingerprints independently before each volunteer runs:

```text
replica-plan PUBLIC_ENROLLMENT MEMBER_KEY STORAGE_KEY REPLICA_DIRECTORY
replica-enroll --approve DIGEST PUBLIC_ENROLLMENT MEMBER_KEY STORAGE_KEY REPLICA_DIRECTORY
replica-serve PUBLIC_ENROLLMENT MEMBER_KEY STORAGE_KEY REPLICA_DIRECTORY PORT
```

Enrollment requires an empty directory and a pinned member key. The service opens
existing state and retains complete certified generations. It binds to loopback;
remote TLS/reverse routing still needs explicit deployment configuration. An
interrupted enrollment can be inspected with `replica-resume-plan` and completed
with `replica-resume --approve DIGEST`, using the same four file/directory
arguments. A missing accepted manifest is never treated as a fresh enrollment.

After volunteers are serving, initialize the owner with its prepared configuration:

```text
initialize-plan CONFIG
initialize --approve DIGEST CONFIG
ready CONFIG
serve CONFIG
```

Initialization planning is offline. Before recreating any missing pristine owner
component, apply requires four fresh unfrozen heads equal to the original root.
Three reachable copies refuse initialization before files are created. If remote
history has advanced, a missing writer/archive needs complete recovery. Retained
unknown partial files also require inspection; do not erase them to retry.
Successful initialization still reports unverified readiness. `ready` obtains
four durable copies; `serve` repeats its fresh check before opening the listener.

## Configuration

### Bounded operator work through outbound links

Initialization, status, readiness, signed advancement and recovery commands accept
the existing `RESONANCE_HISTORY_OPERATOR_TRANSPORT_FILE` environment setting:

```sh
RESONANCE_HISTORY_OPERATOR_TRANSPORT_FILE=/path/operator-transport.json \
  npm run policy-observer --workspace @resonance/relay -- ready /path/observer.json
```

Use the existing [operator transport configuration](v0.4-history-operator-transport.md):
an already encrypted infrastructure identity, five explicitly pinned
history-key/relay-identity mappings, direct authenticated contacts or one explicit
volunteer bridge, and a bounded operation lifetime. The observer's protocol key
and encrypted history remain independent of this infrastructure identity. Never
use a personal account identity for operator links.

The same transport carries discovery, source fencing, freeze/agreement, history
transfer, generation provisioning and pristine-resumption root checks. Supplied
invalid/missing configuration or keys refuse the operation; no direct fallback is
selected. Offline inspection, restoration review/export and initialization review
parse public routing configuration but do not read the infrastructure secret or
open connections. Each command closes its transport and clears its loaded key.

This finite maintenance session is not a continuous service. `serve` and
`replica-serve` refuse an owner operator transport setting. Enrolled volunteers
can already use the [ordinary relay background role](v0.4-history-volunteer-runtime.md)
with their policy-history context. The ordinary relay runtime below provides
continuous observer routing and resource controls; guided desktop activation
remains separate work.

`readPolicyObserverConfigurationFile` accepts a bounded UTF-8 JSON file. It checks
exact fields, signed genesis/continuation roots, deterministic observer-history
context, five distinct history members/endpoints, archive limits and listener
bounds. Local paths resolve relative to the configuration file.

Construct the file from the actual prepared objects; do not generate another
random genesis for a previously used key:

```js
const configuration = {
  version: 1,
  kind: 'policy-observer-configuration',
  context,            // independently pinned five-member policy observer set
  historyContext,     // deterministic history context for this observer
  genesis,            // exact independently retained original encrypted root
  root: genesis,      // or the exact certified root of its restored generation
  members,           // five { publicKey, endpoint } history volunteer pins
  directory: 'owner',
  signingKeyFile: 'observer-key.json',
  storageKeyFile: 'owner-storage.hex',
  limits: { archiveBytes: 67108864, archiveBlocks: 10001 },
  listen: { port: 9101, maxConnections: 4, connectionTimeoutMs: 10000 }
};
```

The signing-key file uses the existing operator `{publicKey, secretKey}` format
with canonical base64url keys. The storage-key file contains 32 bytes encoded as
lowercase hexadecimal. Keep both local and private. They are read into bounded
buffers; temporary copies are cleared after the observer takes ownership. The
configuration contains paths, public pins and encrypted roots, not private keys.

History endpoints use `/history-checkpoint`. Non-loopback network contacts must
use secure transport. The observer listener binds only to `127.0.0.1`; public TLS
and reverse routing require explicit external configuration. Port zero is allowed
for local tests, with the selected endpoint printed at startup. A dynamic local
endpoint does not replace any independently pinned advertised endpoint.

## Commands

Run from the repository with an absolute configuration path, for example:

```sh
npm run policy-observer --workspace @resonance/relay -- status /path/observer.json
npm run policy-observer --workspace @resonance/relay -- ready /path/observer.json
npm run policy-observer --workspace @resonance/relay -- advance /path/observer.json /path/signed-advance.json
npm run policy-observer --workspace @resonance/relay -- serve /path/observer.json
```

- `status` authenticates existing local history and reports its head, pending
  work, conflict evidence, local recovery fence and archive usage. It sends no
  network requests and reports readiness as unverified.
- `ready` explicitly completes pending history and requires four current durable
  copies. It refuses signing readiness for an expired/conflicted/fenced observer.
- `advance` verifies and durably applies the authority's immediate signed
  successor, or completes its exact retry. A conflicting commitment is retained
  as terminal evidence. It never skips a missing predecessor.
- `serve` checks four current copies before opening the bounded listener. Every
  later observation performs a fresh current-head read; startup is not a retained
  permission to sign indefinitely. New policy requests use the same authenticated
  immediate-successor path.

Only one local owner opens the history. A running service must close before an
offline command can inspect or change that same directory. On normal shutdown,
the listener stops accepting requests and waits for admitted work before the
owner closes. A client losing its reply does not undo an accepted update.
Interrupted state, missing journals, changed keys, retained conflicts and local
recovery fences are preserved; startup never replaces them with empty files.

## Reviewed recovery commands

The same entry point also exposes the resumable workflow. Use the configuration
of the original observer, its independently retained genesis and keys, a new
workspace, and an explicit `available` or `unavailable` declaration. `available`
opens and authenticates the source; a failed open never falls back to lost-state
mode. Stop its running service before this local maintenance.

Append these command arguments to the npm entry point above:

```text
recovery-plan CONFIG WORKSPACE available 1
recovery-start --approve DIGEST CONFIG WORKSPACE available 1
recovery-status CONFIG WORKSPACE
recovery-step CONFIG WORKSPACE
recovery-review CONFIG WORKSPACE NEW_DIRECTORY
recovery-restore --approve DIGEST CONFIG WORKSPACE NEW_DIRECTORY
recovery-export CONFIG WORKSPACE RESTORED_DIRECTORY NEW_CONFIG
recovery-resume-plan CONFIG WORKSPACE RESTORED_DIRECTORY
recovery-resume --approve DIGEST CONFIG WORKSPACE RESTORED_DIRECTORY
```

The first digest comes from `recovery-plan`; the restoration digest comes from
`recovery-review`. Neither is a retained signing permission. Each explicit
`recovery-step` performs one bounded phase (or a bounded download step); repeat
until status reports `complete`. Status and workspace reopening transmit nothing.
The source fence, actual agreement selection and retained local evidence floor
are preserved across commands and restarts. No automatic agreement view change
occurs; the positive view is explicitly supplied during planning.

Restoration writes into a new directory and reports readiness as **unverified**.
It can preserve a blocked policy history without pretending that the observer
may sign. Export reconstructs the selected ancestry again and compares the
existing destination's immutable baseline with that independent replay digest.
It can export a complete restoration after a lost command response, and accepts
legitimate later observer updates while preserving the selected baseline. It
refuses a missing writer or a re-encrypted, self-consistent but different baseline.
An occupied output file is never overwritten; retain an interrupted output and
choose a separate path. No export starts a service.

For an interrupted restoration, `recovery-resume-plan` independently replays its
selected ancestry and inspects the exact local files without network requests.
Its digest binds the destination, baseline, file contents, limits and member pins.
An approved `recovery-resume` completes only an authenticated pristine component.
Before creating a missing writer or archive, it requires four fresh, unfrozen
replica heads equal to the certified root. Missing files alone do not demonstrate
that the generation was unused: if replicas have advanced, full history recovery
is required. A missing used archive, retained archive alongside a missing writer,
or local recovery fence also prevents pristine resumption.

Resumption reports readiness as **unverified** and starts no listener. The root
read is not a durable write certificate. After export, use `ready NEW_CONFIG` and
then `serve NEW_CONFIG`; each performs its own fresh quorum check, including any
change after resumption. Desktop controls and private policy
routing remain open.

Three new integration cases include an entire recovery across separate Node CLI
processes, wrong approvals, source fencing, independent export validation,
readiness, later updates, repeated export, changed baseline and explicit source
loss. The combined operation/recovery/restoration group passes **32 tests in four
files in 46.25 seconds**, plus TypeScript. CI remains a separate gate.

The resumption regression group passes **69 tests in four files**; the final
root-budget check passes TypeScript and **23 command/interruption tests** in
31.93 seconds. Tests include 16 real process-death boundaries, stale approvals,
impossible archive budgets and simultaneous writer/archive loss after a remote
update. An insufficient budget is refused before recreating files.

## Validation and limits

### Continuous background operation

After explicit preparation, enrollment and owner initialization, the ordinary
relay can reopen the existing observer alongside its other roles:

```sh
RELAY_POLICY_OBSERVER_FILE=/absolute/path/observer.json \
RELAY_POLICY_OBSERVER_LINKS_FILE=/absolute/path/links.json \
node --import tsx packages/relay/src/main.ts
```

The optional links file uses the existing pinned history routing format (version
1 for direct authenticated relay links, version 2 for an explicit bridge). It
does not contain the finite operator-session identity/deadline fields. The
ordinary relay's retained infrastructure identity authenticates its connections;
configure its passphrase file separately when needed. The five member public
keys must match the observer history. An explicit invalid links file fails
startup without direct fallback. Without a links file, the five independently
pinned direct history endpoints are used and their sockets are metered.

Startup opens existing state only and requires four current copies before
exposing the configured loopback observation listener. The relay's general
`started` diagnostic does not mean the observer is ready: wait for
`policy_observer_ready`. A failed observer startup stops the process. Each later
observation still performs a fresh quorum check; readiness is never cached as
permission to sign indefinitely.

Fresh observation requests, including requests without a policy update, consume
the owner's new-work allowance before decoding or replica fanout. Existing CPU,
power, schedule and total-traffic controls apply through that allowance. Incoming
observer sockets and direct or routed history sockets enter the same traffic
meter. Pausing new observations retains stored evidence. Shutdown stops admitting
observer requests and drains accepted updates before closing their history router;
forced process death may still leave a durable pending update for exact resumption.

Co-hosted history owners share one router only if their complete five-member
key-to-relay/bridge mappings agree. Different mappings are refused instead of
widening either quorum. Requests sharing a socket are serialized within their
existing deadlines and bounded operation budget.

When one pinned member's infrastructure identity is the actual local relay
identity, the router delivers its request to the already-enrolled local role.
It preserves the signed protocol, serialization bounds and shared operation
budget without opening a self-connection. Missing enrollment refuses startup;
an unknown local context or invalid signature still refuses the request. An
explicitly authorized bridge route may also target its own enrolled role.
No peer advertisement can set or replace the local binding. Local delivery
counts as that one member only, not an extra replica: the test advances with
one local plus three remote copies and refuses with only three total copies.
Health labels the configured local route separately from network connections;
neither metric proves current durability.

The finite operator transport deliberately refuses using a target member's own
infrastructure identity. For maintenance while that background role is stopped,
use a separately pinned maintenance identity with explicitly authorized bridge
routes, or independently reachable direct history endpoints. The co-location
test initializes through four remote copies under such a maintenance identity,
then starts the background owner with its own enrolled local member.

For desktop supervision, use `RESONANCE_RELAY_POLICY_OBSERVER_FILE` and optionally
`RESONANCE_RELAY_POLICY_OBSERVER_LINKS_FILE` when launching the GUI. Their paths
are retained across later launches and rendered in all three native service
formats. An explicit empty override disables the selected path; clearing an
observer with retained links requires clearing both. Its history directory stays
in the retained storage inventory. This is configuration persistence, not a
guided activation flow or proof of native service installation on all platforms.

Outbound integration and existing direct/reverse-link regressions pass **50 tests
in six files in 64.10 seconds**, plus TypeScript. A complete observer CLI recovery
uses an explicitly pinned bridge with no reachable direct history endpoints and
outbound-only volunteers. It verifies signed updates before/after restoration,
local source fencing, pristine resumption through fresh root reads and offline
operations with the infrastructure passphrase deliberately unavailable. The
existing bounded operator transport supplies cancellation and handshake deadlines;
no quorum or signing deadline was relaxed.

Initial preparation/enrollment and the shared initialization/recovery regressions
pass **66 tests in six files in 35.22 seconds**, plus TypeScript. One scenario uses
the actual CLI from another working directory, five separately running volunteer
processes, three-copy refusal, fresh initialization/readiness, a signed update
through the observer listener and volunteer restart. Six additional process-death
cases cover empty/partial/complete anchor and export publication; incomplete
anchors remain unchanged. These tests simulate independent processes on one
computer and do not establish independent-device durability or Internet behavior.

Nine integration cases verify strict configuration/input handling, relative
paths, offline inspection, missing-writer refusal, quorum-gated startup, signed
operations, blocked/fenced startup, cancellation, changed key files and shutdown
with an admitted update. The actual Node CLI is launched from a different working
directory for status, signed advancement and service startup. Unix shutdown is
graceful; Windows process termination also exercises ownership recovery.

The new cases pass in 6.01 seconds. The 38 existing observation/protected-history
regressions and TypeScript also pass. Cross-platform CI includes the new file;
its result is a separate completion gate. This local service does not complete
live policy distribution, issuer/wallet integration, private routing or independent
Internet/operator validation.
