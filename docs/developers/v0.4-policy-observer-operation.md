# Operating an existing protected policy observer

This experimental Node entry point operates an observer whose original encrypted
root, owner history and five volunteer histories have already been prepared and
independently pinned. It does not create missing state or choose replacement
members. Guided new-key enrollment, recovery commands, desktop selection,
protected compaction and private application integration remain separate work.

## Configuration

`readPolicyObserverConfigurationFile` accepts a bounded UTF-8 JSON file. It checks
exact fields, signed genesis/continuation roots, deterministic observer-history
context, five distinct history members/endpoints, archive limits and listener
bounds. Local paths resolve relative to the configuration file.

Construct the file from the actual prepared objects; do not generate another
random genesis for a previously used key:

```js
const configuration = {
  version: 1,
  kind: 'policy-observer-configuration',
  context,            // independently pinned five-member policy observer set
  historyContext,     // deterministic history context for this observer
  genesis,            // exact independently retained original encrypted root
  root: genesis,      // or the exact certified root of its restored generation
  members,           // five { publicKey, endpoint } history volunteer pins
  directory: 'owner',
  signingKeyFile: 'observer-key.json',
  storageKeyFile: 'owner-storage.hex',
  limits: { archiveBytes: 67108864, archiveBlocks: 10001 },
  listen: { port: 9101, maxConnections: 4, connectionTimeoutMs: 10000 }
};
```

The signing-key file uses the existing operator `{publicKey, secretKey}` format
with canonical base64url keys. The storage-key file contains 32 bytes encoded as
lowercase hexadecimal. Keep both local and private. They are read into bounded
buffers; temporary copies are cleared after the observer takes ownership. The
configuration contains paths, public pins and encrypted roots, not private keys.

History endpoints use `/history-checkpoint`. Non-loopback network contacts must
use secure transport. The observer listener binds only to `127.0.0.1`; public TLS
and reverse routing require explicit external configuration. Port zero is allowed
for local tests, with the selected endpoint printed at startup. A dynamic local
endpoint does not replace any independently pinned advertised endpoint.

## Commands

Run from the repository with an absolute configuration path, for example:

```sh
npm run policy-observer --workspace @resonance/relay -- status /path/observer.json
npm run policy-observer --workspace @resonance/relay -- ready /path/observer.json
npm run policy-observer --workspace @resonance/relay -- advance /path/observer.json /path/signed-advance.json
npm run policy-observer --workspace @resonance/relay -- serve /path/observer.json
```

- `status` authenticates existing local history and reports its head, pending
  work, conflict evidence, local recovery fence and archive usage. It sends no
  network requests and reports readiness as unverified.
- `ready` explicitly completes pending history and requires four current durable
  copies. It refuses signing readiness for an expired/conflicted/fenced observer.
- `advance` verifies and durably applies the authority's immediate signed
  successor, or completes its exact retry. A conflicting commitment is retained
  as terminal evidence. It never skips a missing predecessor.
- `serve` checks four current copies before opening the bounded listener. Every
  later observation performs a fresh current-head read; startup is not a retained
  permission to sign indefinitely. New policy requests use the same authenticated
  immediate-successor path.

Only one local owner opens the history. A running service must close before an
offline command can inspect or change that same directory. On normal shutdown,
the listener stops accepting requests and waits for admitted work before the
owner closes. A client losing its reply does not undo an accepted update.
Interrupted state, missing journals, changed keys, retained conflicts and local
recovery fences are preserved; startup never replaces them with empty files.

## Validation and limits

Nine integration cases verify strict configuration/input handling, relative
paths, offline inspection, missing-writer refusal, quorum-gated startup, signed
operations, blocked/fenced startup, cancellation, changed key files and shutdown
with an admitted update. The actual Node CLI is launched from a different working
directory for status, signed advancement and service startup. Unix shutdown is
graceful; Windows process termination also exercises ownership recovery.

The new cases pass in 6.01 seconds. The 38 existing observation/protected-history
regressions and TypeScript also pass. Cross-platform CI includes the new file;
its result is a separate completion gate. This local service does not complete
live policy distribution, issuer/wallet integration, private routing or independent
Internet/operator validation.
