# Combined relay/history storage: inventory and remaining enforcement

Status: bounded offline directory/file inventory and pre-output desktop path retention implemented; combined byte reservation and
quota enforcement remain open. Publication quotas and per-generation history
caps continue to apply independently. This document must not be read as a claim
that the combined budget is finished.

## Implemented measurement

In paused desktop maintenance, **Measure stored files** inventories the runtime,
saved owner/volunteer histories, recovery selections, the path registry itself,
and individually retained configuration/enrollment outputs. Successful settings saves
retain previous known locations in `historyStorageDirectories`, bounded to 128
absolute paths. Approved desktop setup/recovery/activation additionally records
history directories in a separate durable `relay-storage-locations/locations.json`
registry before its apply work. Recovery status/step also retain the selected
workspace and destination before opening the resumable coordinator. The registry
preserves both current and previous settings selections, including older settings
without a saved directory list. Its version-two manifest also retains up to 128
explicit output paths. A directory-only version-one manifest is read without
resetting it; its next changed write preserves its directories in version two. Settings-write failure, later selections and
reload cannot silently remove committed locations from the inventory.

The authenticated POST `/api/relay/history/storage` accepts an empty body only.
It uses the same stopped-runtime/control exclusion as history operations, supports
cancel/lock/disconnect and returns aggregate counts only. The command-line version
accepts explicit locations and does not acquire a global stopped-runtime claim:

```sh
node --import tsx scripts/admission-history.ts storage-inventory runtime-directory owner-history-directory volunteer-history-directory recovery-workspace --file owner-config.json --file enrollment.json
```

Pause all writers before using the CLI. Every selected root must exist and be a
directory. Canonical overlapping roots are traversed once; stable device/inode
identities deduplicate hard-linked files. Nested symbolic links and special files
are refused. The scanner reads metadata, never payloads or private keys. It counts
all regular files, including manifests, staged files and temporary files, without
interpreting which may be deleted. It never deletes or compacts anything.

Explicit files are inspected individually; their parent folders are not traversed.
The scanner rejects missing files, symbolic links and directory substitutions,
including a file changed into a directory between selection and traversal. Files
already inside a selected directory and stable hard-link aliases count once.
The aggregate response reports `selectedFiles` and never exposes paths or contents.
Input keys and externally created/copied operator files are not inferred from a
parent directory; explicitly select additional known files in the CLI.

Traversal is incremental, bounded to one million entries and depth 64. A 30-second
scan budget and cancellation are checked between filesystem operations. A blocked
filesystem call itself cannot be interrupted by this application-level deadline.
Metadata changes observed around a visit, missing files, unreadable entries,
changed root resolution and exceeded bounds reject the result. Unknown storage
never becomes a zero-byte success. Filesystem errors in the aggregate result omit
paths and filenames.

`logicalBytes` sums regular-file lengths. `allocatedBytes` sums filesystem-reported
512-byte blocks for unique files and directories when available, otherwise null.
These are different measurements: sparse files, compression and copy-on-write
sharing mean neither is an exact statement of exclusive device use or free space.
A scan is not an atomic filesystem snapshot. Another process may write between
visits even though the desktop-managed relay is paused.

## Explicit coverage boundary

The desktop registry preserves approved operation locations even if the later
settings save fails. A local registry lock serializes updates; paths are canonical
and bounded to 128. First creation flushes its directory before its manifest;
a missing/partial manifest in an existing registry refuses further use. Later
updates flush a new file, atomically replace the manifest and flush the directory
before returning to the caller. A crash before replacement cannot authorize
history creation; after replacement the new root remains registered. Interrupted
temporary replacements are bounded and retained, never used as authority or as
permission to remove old roots. No registry operation removes a committed root.
Windows flushes files but does not provide the POSIX directory-flush guarantee.

This is desktop bookkeeping, not a global writer lease or byte reservation.
Offline CLI operations do not yet share this registry. Existing-history inspections
can still open their own journals/locks before the apply hook; these hooks do not
constitute a complete production-writer map. Desktop configuration, owner setup/
export, owner-limit editing and volunteer activation retain their exact outputs
before writing. This includes configuration-only setup and preserves outputs even
when settings saving fails. Separate input keys and outputs from earlier external
CLI operations remain outside automatic desktop retention. The registry cannot rediscover
historical paths already lost from older settings, external copies, or output
created before pre-output registration was introduced. Loss/rollback of the entire
registry and its directory has no independent local authenticity proof. The CLI can inspect explicitly supplied additional
roots. Missing registered roots or files remain an error, including a planned restoration
destination or output that does not exist yet. No absent directory is treated as reclaimed
capacity or permission to reset accepted history.

This measurement excludes unselected app databases/models/configuration/key files,
filesystem metadata not represented by reported blocks, other applications,
future writes and temporary replacement headroom. It is an observation, not a
space reservation, durability proof, free-space check or enforceable total quota.
The interface states these boundaries. Existing history health remains cheap
cached protocol accounting; the filesystem inventory runs only on explicit demand.

## Bounded resource checkpoints

`relay-owner-budget.json` and `relay-resource-usage.json` now use the same bounded
atomic checkpoint writer. Each current file and its `.next` replacement is at
most 4 KiB: **16 KiB total encoded-file headroom for both components**. This is a
component ceiling, not a reservation against the pending shared budget. Directory
metadata and the runtime claim require separate accounting.

Reads reject oversized, linked, non-regular, changing and invalid inputs. Writes
validate the exact counter schema and safe-integer range before opening output,
handle short writes, flush, replace, and flush the directory on POSIX. Windows
flushes the file but has no directory-flush guarantee here. Changed or deleted
current state refuses reuse. An uncertain write poisons the handle; an owner
policy whose checkpoint failed refuses further new work even if its time window
expires. The committed current file is authoritative after restart. A bounded
interrupted replacement can be overwritten after reopening that valid current
file; an interrupted first checkpoint with no current file refuses initialization.

Backward clock movement and decreasing/unsafe measured counters do not grant a
fresh allowance within an existing window. Counter overflow is an error, never
rounded or reset to zero. The normal relay runtime claim still provides single
writer exclusion; the helper itself is not a cross-process transaction manager.
Complete deletion or coherent rollback of both files has no independent local
proof. Traffic since the last successful checkpoint can be lost on process death.
None of these files authorize recovery or deletion of accepted protocol history.

## Shared reservation authority: core and snapshot integration

The core now provides `openStorageReservationAuthority` and
`withStorageReservationAuthority` through `@resonance/core/storage-reservations`.
This is an internal integration foundation. The managed relay, desktop and CLI do
**not yet enable a combined quota**: adoption of existing files and the remaining
writers below must use the authority before a product control can be offered.

The initial model reserves each component's enforced lifetime peak, including a
simultaneous replacement. Reservations are persisted before returning a lease.
Several components share one total. A smaller later component limit, a closed
handle, missing output or a changed selection never frees a previous reservation.
An exhausted authority refuses new components and increases; existing components
can keep writing within their already reserved ceiling. This trades spare usable
capacity for simple conservative failure recovery. There is no automatic release.

A dedicated directory holds one bounded one-MiB manifest, one bounded replacement
and process-ownership metadata. The authority reserves **2 MiB + 8 KiB** for this
control peak before user components. At most 512 canonical component paths are
retained, subject also to the encoded manifest limit. A process owns the authority
for its whole runtime or maintenance operation. Initial creation refuses any
existing directory; reopen requires the independently retained authority ID and a
valid primary manifest. An interrupted replacement is never used to reconstruct
missing authority. Unknown, linked, oversized or corrupt metadata refuses use.

Each reservation is flushed and atomically published before the caller can create
output. Failed or uncertain writes invalidate all leases until reopen. Metadata
replacement/deletion and path redirection observed on a live lease also refuse
writes. Real process death before publication retains the previous reservation
set; after publication a reservation stays charged even if output/settings never
finish. Windows flushes files but has no POSIX directory-flush guarantee here.

Limit changes require a digest of the current local review and cannot go below
all retained reservations plus control headroom. Another reservation invalidates
a stale review. The digest is a local review binding, not an independent signature
or a rollback-proof remote checkpoint. Coherent restoration of an old complete
ledger is not independently detectable. The authority is local filesystem
bookkeeping, not proof of protocol recovery or permission to delete history.

The shared encrypted snapshot writer now captures its path and byte limit and,
when a managed authority is supplied, reserves **twice the encoded image cap plus
8 KiB of generated lock/recovery metadata** before directory creation or opening.
It retains that lease across async scope exit and refuses later writes when the
authority closes or becomes uncertain. Caller option mutation cannot enlarge the
reserved image cap. Unconfigured call sites retain existing behavior; no relay
configuration or environment flag silently enables partial quota coverage.

A lease alone does not intercept arbitrary filesystem writes. Every component
must still enforce the peak it declares. Existing unknown files, earlier temporary
images, copied outputs and all direct block/journal/control writers need explicit
adoption and integration. The ceiling concerns managed encoded file bytes, not
filesystem blocks, open deleted inodes, filesystem snapshots or whole-device space.

## Direct writer integration under an explicit authority

The operation journal and private replay journal now capture optional leases for
**twice their file cap**, before creating the runtime directory. Replay/cleanup,
append and compaction require that lease. Zero-capacity journals retain their
existing behavior; an unbounded journal cannot enter a managed authority. Resource
checkpoints reserve **8 KiB each**. Diagnostics reserve **two file caps plus 8 KiB**
and drop diagnostic writes if their lease fails, rather than changing accepted
protocol state. Smaller later caps never release previously reserved peaks.

Writer archives, volunteer generations and ancestry downloads reserve ciphertext
and manifest replacement peaks together before creating a directory or lock. The
manifest allocation is the same idempotent allocation used by encrypted snapshots,
not an extra copy. An archive adds its ciphertext ceiling; generation/download
caps already include two manifests, so their total is the configured cap plus
8 KiB of lock metadata. Serial immutable-block publication renames the same inode:
the pending block uses remaining ciphertext capacity. Captured leases survive
scope exit and are rechecked after asynchronous download replies. Pristine genesis
repair retains the original higher allocation, and existing accepted blocks and
freeze/repair headroom remain usable at a full shared budget.

The infrastructure identity reserves **two 4 KiB images** before initialization or
migration. Encoded output is bounded before its temporary is opened; migrating to
encryption preserves the key. The manual single-key spend ledger reserves
**512 bytes per allowed spend**, rejects arithmetic overflow and enforces its row
cap internally. Its captured lease remains required for exact token retries.
Reservation requests are copied so later caller mutation cannot redirect a lease.

## Operator outputs and control headroom

With an explicit authority, exclusive operator exports now reserve their bounded
exact path before opening output. A supplied directory/replacement lease must
cover that output path and its declared cap. This prevents registry/settings
replacements from allocating a fresh permanent entry for every temporary name.
Undefined JSON values and invalid/oversized byte limits fail before output.

Desktop relay settings use a shared atomic writer with one current image and at
most **eight temporary images**, including the active replacement. Each image is
at most 64 KiB, and ownership adds 8 KiB: **584 KiB reserved for settings**. The
writer serializes concurrent saves, recognizes the previous desktop temporary
naming convention, bounds its parent-directory inspection to 4,096 entries, and
preserves interrupted files. If all temporary slots are occupied, another save
refuses without deleting or overwriting the retained files. Later explicit writes
can proceed while fewer than eight interrupted slots remain; ordinary completion
removes only that operation's temporary. A crash leaves a complete old/new primary
plus bounded interrupted output, never authorization to reconstruct missing
protected history. Settings are still independent of the retained-path registry.

The desktop path registry reserves **129 MiB** for its one-MiB primary and at most
128 one-MiB temporary images, plus a separate **8 KiB ownership allocation**. The
previous update path could begin a 129th temporary when 128 interrupted candidates
already existed. It now refuses a changed update at that boundary; unchanged
selection still works. No retained root, file or candidate is discarded.

Standalone local-state ownership reserves **8 KiB** before creating its lock and
recovery files. Snapshot, diagnostic and atomic-settings components reuse their
already included ownership headroom. Ownership reads are bounded to 4 KiB and
refuse changed, nonregular, symbolic-linked or hard-linked files. These local
claims still depend on PID liveness and do not provide an independent anti-rollback
proof. Runtime admission to a managed scope also reserves the **1 KiB maintenance
marker** before work, so using the shared capacity does not consume pause headroom.
Removing a pause marker never frees its allocation.

## Remaining write-budget implementation

The [storage writer map](v0.4-storage-writer-map.md) identifies snapshot, direct
block, journal, control and supervisor writers. It records the bounded replacement
for new service diagnostics and distinguishes unused export APIs from live relay
writes. Exact operator outputs, registry metadata, settings, local locks and maintenance
now have optional reservations. Generated native outputs now use the same bounded atomic writer. Existing-file
adoption, generation publication and shared entry-point integration still need coverage.

A hard combined quota needs a different mechanism from a repeated directory scan:

1. Wire the implemented reservation authority and desktop path retention into
   shared CLI/runtime selection, and adopt existing files before enabling durable
   **byte** reservations across every protected output. Preserve the
   reservation through settings-save failure and process death, bind it to canonical
   roots and serialize competing writers. A recorded path alone allocates no bytes.
2. Account for existing files and the old-plus-new peak of atomic replacements.
   Accepted obligations, pending intents, ancestry, permanent denials and repair
   headroom set floors. Refusing new work must not silently discard those floors.
3. Reserve before every protected write and signed acceptance, including direct
   ciphertext writes as well as encrypted snapshots. Enforce the same authority
   across the relay process and offline CLI; periodically sampling bytes in an
   HTTP stats endpoint is insufficient.
4. Recover interrupted reservations conservatively. Release capacity only after
   authenticated state proves that removal/compaction is safe. Treat unexpected
   files, incomplete recovery and unobservable usage as occupied/unknown.
5. Expose a reviewed total budget only after every production writer is mapped.
   Test simultaneous owner/volunteer roles, multiple workspaces, full capacity,
   changed paths, read-only storage, short writes, flush failures and SIGKILL.

The current known per-file bounds show why ciphertext-only totals are insufficient:

These are source bounds, not measured usage and not a proven combined ceiling.
Runtime publication/mailbox/journal, policy/witness state, locks and temporary

## Fixed generation locations and retained factory authority

A child now stays at one fixed path from initialization through readiness and
later accepted writes. The durable `ready` marker already gates exposure, so
publication does not need a directory rename or a second path allocation.
Authenticated old provision journals migrate to a version 2 location pin before
continuing: old ready histories require the generation directory; old creating
histories may retain their sole staging directory permanently. Ambiguous paths,
missing ready histories and accepted data under a creating marker are preserved
and refused. See [the exact migration rules](v0.4-history-provisioning.md#crash-safe-creation).

An optional authority reserves the **configured generation cap plus 8 KiB** for
ciphertext, two manifest images and ownership metadata before parent activation.
Each successor journal reserves **two 64 KiB images plus 8 KiB** before its slot
directory. Volunteer initialization funds genesis and the first slot before its
root directory; provisioning funds the next child's empty successor slot before
activating the parent. A capacity refusal remains retryable after an explicit
limit increase. Partial successful allocations remain charged even if a later
preflight allocation fails; no child or activation is authorized by that failure.

`captureStorageReservationOperation` lets long-lived factories re-enter their
original authority when later methods open more writers. Provisioner and volunteer
service operations use it, including growth after provisioning. Switching authority
or silently adopting an unmanaged handle is refused. Existing snapshot leases
still guard writes after scope exit and authority closure. Other recovery factories
and runtime/CLI integration remain separate work; no combined product quota is
being exposed by this change.

## Conservative adoption of existing files

The optional authority now exposes `reviewExisting` and `adoptExisting`. Callers
must exclude all cooperating writers throughout review/apply. These APIs inventory
explicit ordinary files/directories without reading payloads. Unknown files and
interrupted temporary images count in full. They are not interpreted as valid
history, deleted, repaired or made available for reuse. The already reserved
authority directory is excluded from an enclosing selection's inventory.

An approved selection contributes a durable byte floor **in addition to** all
future component peaks. This deliberately double-counts a known existing image
when a future writer's peak already covers that image. It is conservative: until
there is a separately verified ownership/reclamation protocol, an unknown file
cannot silently consume another writer's reservation. Repeated adoption retains
the greater of the previous floor and the newly observed bytes. Smaller files,
missing paths and changed selections never release old floors. Overlaps are
normalized within one scan; earlier separately adopted child/parent selections
remain separately charged. The review reports the extra budget required, and a
budget increase invalidates its old approval digest.

Review/apply bind canonical selections, bounded metadata observations and the
current authority bytes/revision. Replaced inodes, file changes, additions, new
reservations and limit changes invalidate approval. Symlinks, hard-linked files,
special files, missing paths, unsafe byte totals and incomplete scans are refused.
The scanner bounds target count (256), entries (default 100,000, maximum 1,000,000),
depth (64), encoded metadata/listing bytes (16 MiB) and elapsed time (30 seconds).
It rechecks observed identities after the complete walk. It is explicitly **not an
atomic filesystem snapshot**: noncooperating writers still require OS-level
isolation beyond this library. It measures encoded file lengths, not physical
blocks, filesystem snapshots, free space or the rest of the device.

Authority payload version 2 retains both writer allocations and adopted floors,
sharing the existing 512-entry and one-MiB manifest ceilings. A version 1 primary matching the independently retained authority ID is read without mutation; the next durable
mutation publishes version 2 with the same authority ID, retained allocations and
monotone revision. An older binary must refuse the new schema rather than omit
its floors. This is local bookkeeping, not a signed or anti-rollback ledger.

## Prepaid maintenance controls

`openReservedStorageControl` opens a read-only view of an independently pinned
authority while its real writer may still be running. It requires an exact copied
allowlist of already committed ordinary control files: at most 16 entries, each
at most one MiB, for operator output, atomic operator output or local ownership.
It cannot allocate new paths, enlarge caps, change limits/adoptions or acquire the
ledger writer lock. It never changes a v1 primary merely to read it.

Each issued lease rechecks the committed primary and its exact selected paths.
Normal monotone allocation growth is permitted; wrong IDs, missing/corrupt or
insufficient metadata, replaced directories and linked/redirected outputs fail
closed. A detected atomic primary replacement is retried at most three times;
there is no cached-proof fallback. Unrelated history paths receive lexical/schema
validation, so their damage does not prevent writing an already funded pause.
Exclusive authorities retain full path validation when reopened for actual work.

This view supplies accounting only. Desktop/output locks and exclusive file
creation still exclude competing writes. The caller must leave its narrow control
scope before acquiring an exclusive maintenance authority. A funded pause marker
is written before stopping the service and survives process death. No bytes are
freed, accepted records changed or authority ownership transferred by writing it.

Compilation and **95 tests / eight files in 13.28 seconds** pass. Tests include
an independent Node owner at exact capacity, a concurrent pause, refusal of a
second ledger writer, SIGKILL and restart refusal while the marker remains;
metadata races, changed allowlists, old primaries and unsafe outputs are covered.

seconds** with 524 captured source/config hashes unchanged. It predates this view.

## Service preparation and ownership handoff

`prepareRelayServiceInstallation` publishes the bounded complete file set while
its caller owns the authority. The caller can then save its settings, close the
authority and leave that scope before invoking the returned `start()` handle.
Desktop control exclusion must span both phases. The unmanaged convenience

## Adopted scopes, explicitly new locations and shared ownership

Opening an existing authority with `requireAdoptedScopes: true` refuses allocations
outside its reviewed file/directory scopes, including allocations retained by an
earlier unrestricted owner. A file scope covers that exact output; a directory
scope covers its descendants. A sibling with a common name prefix, parent
allocation or redirected descendant does not widen it. A legacy authority without
reviewed scopes is refused without an implicit migration or empty adoption.

An absent new output uses a different explicit workflow: `reviewNewScopes` and
`approveNewScopes`. It requires an ordinary existing immediate parent and binds
its identity/metadata, the target's absence and the current ledger. Present files,
including dangling links, must use existing-file review. Any overlap with retained
allocations/adoptions is refused: missing retained history cannot be declared new.
Changed parents, newly created targets, allocations or limits invalidate approval.
Approval records a zero-byte scope, creates no target and grants no writer bytes.
Later writers still reserve their complete peak before creating files. Shared
entry/manifest ceilings apply. No history initialization is authorized by this
storage-only permission; existing protocol recovery rules still apply.

`openRelayStorageOwner` composes explicit authority/runtime pins with adopted
scope enforcement. It funds pause/ownership and selected small desktop controls
before runtime loading. Stopped maintenance requires the durable marker and holds
runtime exclusion across the operation. `run` carries the same authority across
async callbacks; closed owners reject later work. `withRelayStorageControls`
provides a short synchronous read-only scope for prepaid settings/marker/lock
creation, then leaves that scope before an exclusive ownership handoff. Per-output
and desktop locks remain required. This is an internal composition API, with no
new automatic selection, initialization, service configuration or quota UI.

## Durable selection export before product wiring

## Selected runtime, CLI and desktop ownership

The explicitly selected Node entry opens its existing authority **before** diagnostics
and dynamic runtime loading. Selection binds the runtime directory, port and supported
IPv4 host; a changed binding, absent/corrupt document or authority never falls back
to an unmanaged writer. A bounded loopback probe must receive connection refusal
while ownership is held. A live listener without the current runtime lock, a timeout
or a different error does not prove shutdown. The selection is read before and after
acquisition; both its bytes and file identity must remain unchanged. This checks
cooperating local processes and the configured listener, not arbitrary external
writers or independently operated volunteers.

The Node owner remains open until process exit. The history CLI keeps ownership
through asynchronous commands and, for `replica-serve`, through its returned stop
promise. Stop is idempotent and releases ownership after listener/service cleanup,
including reported stop failure. The offline local-spend retirement and legacy
recovery CLIs also honor an explicit selection. Separate authority-policy and
community-issuer tools refuse an explicitly supplied relay budget: their key/policy
and issuer-ledger creation remains outside this relay-managed workflow. Their files
must be prepared separately and adopted where required. They must not silently
claim to charge an authority they never opened.

Selection is opt-in through `RELAY_STORAGE_SELECTION_FILE` for Node and
`RESONANCE_RELAY_STORAGE_SELECTION_FILE` for these maintenance/desktop entry points.
These are low-level integration inputs, **not** an automatic setup procedure or a
complete quota UI. A selection must already have independently pinned authority
identity, adopted scopes and sufficient prepaid controls. Existing unselected
installations retain their previous behavior; removing a configured file is an error.
A saved desktop selection cannot be disabled or changed by an environment override.

Desktop selection additionally requires prepaid exact settings-replacement and
control-lock peaks. Its short read-only control scope ends before taking exclusive
storage ownership. Pausing and saving disabled settings work beside a live owner at
full capacity. Stopped workflows hold runtime exclusion and the selected authority
through their asynchronous work. Normal stop preserves any previously active
maintenance pause. Invalid saved runtime/selection metadata refuses before writing
controls or invoking native commands.

Managed start/reconfiguration follows this order:

1. Validate service paths, selected runtime bindings and owner settings.
2. Publish the funded pause and stop/unregister the old service.
3. Acquire stopped ownership and verify the configured listener is closed.
4. Prepare durable native definitions and save settings under that authority.
5. Release ownership, recheck selection and clear the pause through prepaid controls.
6. Start the previously prepared service outside all storage scopes.

Preparation of a selected native service requires its matching stopped owner;
unmanaged, runtime-only and unrelated ownership cannot publish its definitions.
The one-use start handle rechecks selection identity and all native files before
any native action. Preparation/settings failures preserve the pause. A native-start
failure republishes it. Saving the storage pin preserves already reviewed role paths,
including when obsolete environment role overrides coexist with activation.
Native commands remain mocked in tests; the launched Node children are real.

Evidence: the actual selected Node entry accepts publications, pauses at an exact
full budget, survives SIGKILL and reopens the same identity and records. The serving
CLI accepts a real signed encrypted checkpoint at full capacity, retains it through
restart and releases ownership after SIGTERM. A desktop lifecycle test uses the
actual Node child across three starts, full-capacity maintenance and retained-record
checks. Negative cases include changed file identity, old live listeners, unsupported
bindings, missing pins, unreviewed/unfunded writes, failed settings publication and
an attempted unmanaged selected-service preparation. Compilation passes; broader
and final focused counts are recorded in the completion plan.

### Remaining activation work

The reservation machinery and selected call paths do not replace reviewed initial
adoption. Product bootstrap still must enumerate all retained relay/history/recovery
roots, exact outputs, unknown/interrupted files and old native definitions while
writers are stopped. Explicit new locations require separate absence approval.
Do not adopt an entire app/home directory merely to make a check pass: personal
client stores, independent issuers and OS service databases are separate scopes.

A review/apply flow must also handle ownership metadata changing between requests.
The current inventory binds directory metadata and owned lock files. Releasing and
reacquiring locks between a review and its apply can change that evidence even when
history is unchanged. The bounded review API below keeps ownership across approval. Its desktop
session/approval integration remains required; do not ignore
arbitrary lock/temporary files or weaken stale-review checks. Initialization must
retain an independent authority pin through interruption before automatic reopening
is possible. These are implementation requirements, not reasons to mark the combined
budget item complete. Aggregate health and limit controls follow this activation gate.


## Bounded stopped adoption review

`openRelayStorageAdoptionReview` operates only on an **existing**, independently
pinned authority and an already paused runtime. It reserves the runtime control
headroom, holds the ledger and runtime claims, checks the configured listener is
closed, and keeps both claims through review/apply. This control allocation is a
mutation; the returned inventory is not presented as a wholly read-only command.
It exposes review/apply/close, with no general writer callback and no service start.
Existing-file adoption and explicitly absent new scopes are separate operations.

Targets and review results are copied. Apply rechecks all inventory/absence metadata
and the committed ledger; its attempt closes the handle on success or failure.
A cancelled or abandoned approval releases ownership while preserving the pause,
allocations and files. The default approval window is 60 seconds, configurable from
100 ms to five minutes. Approval must start within that window; the subsequent core
metadata check/commit keeps its existing bounded execution rules. Signal/timer cleanup
attempts both claim releases. Damaged ownership remains for inspection and automatic
cleanup errors do not become uncaught exceptions; later access reports failed cleanup.

Even a refused competing runtime-claim attempt can create/remove a recovery file
and change directory metadata. Such a change invalidates the review. A new attempt
must obtain fresh approval; no lock or temporary pattern is exempted from inventory.
SIGKILL likewise requires new approval after the normal known-dead claim recovery.
The caller still must coordinate other operators and retains responsibility for
complete scope selection. This API does not itself enumerate all desktop paths,
hold the desktop session/control lock, initialize a budget or persist a UI approval.

For initial setup, `openStorageReservationAuthority` now accepts an optional fresh
`authorityId` in `create-new`. The bootstrap caller can generate and durably retain
that pin independently **before** creation. Existing callers still get a random ID.
The supplied pin is validated before creating metadata. A reported failure after
primary publication can be reopened using the independent pin; an incomplete first
publication with only a temporary file remains refused. Neither retrying `create-new`
in the existing directory nor recovering its primary from an uncommitted temporary
is allowed. Saving the initial intent/pin, handling incomplete creation and connecting
this sequence to the desktop remain outstanding bootstrap work.

Validation includes copied selections, held claims, full-budget refusal, changed
files/approval, expiry/cancellation, malformed targets before allocation, damaged
cleanup, live legacy listeners, absent metadata, explicit new outputs and real child
SIGKILL. Initial-publication fault injection covers failure before and after rename
without reading the primary to discover its identity. Current counts are recorded
in the completion plan; none of these tests certify independent volunteers or a
whole-device disk limit.


## Durable desktop bootstrap

The desktop now has authenticated `/api/relay/storage/bootstrap/review`, `/apply`
and `/cancel` operations. Review accepts exactly `{mode: "new", limitBytes}` or
`{mode: "recover"}`; apply accepts the returned `approvalDigest`. These are staged
operator APIs. No quota UI or automatic activation is enabled.

An existing maintenance marker, desktop control claim, stopped runtime claim and
closed configured listener are required. Review retains exclusion for at most one
minute. Cancellation, session locking, changed settings, wrong approval and expiry
invalidate it; a disconnected unfinished review request is cancelled. A completed
HTTP response does not release the pending approval. Startup and maintenance exit
refuse an unfinished unselected bootstrap, including a partial bootstrap directory.

Creation uses fixed sibling directories inside the desktop data directory:
`relay-storage-bootstrap` retains bounded `intent.json` and `attempt.json` files;
`relay-storage-budget` contains the reservation authority. The random authority pin
and original data-directory identity, port and limit are retained and flushed
before the separately flushed creation-attempt fence. Initialization funds both
bootstrap files and the existing pause/runtime/settings/desktop-control peaks.
Those initial control bytes do not imply sufficient capacity for relay operation
or the existing-file adoption floors.

Recovery uses the independent intent, never a pin inferred from the ledger. An
intact intent without an attempt can be reviewed and initialized once; an attempt
always requires opening the existing primary. An incomplete directory, partial
intent/attempt, missing primary, wrong identity, linked metadata or unexpected
bootstrap entries is preserved and refused. No pending primary is promoted and no
history is deleted. Interrupted control funding can finish on reopening without
lowering a later limit or dropping any allocation. These are local crash/restart
guarantees, not an independent rollback proof or a physical filesystem quota.

`collectDesktopRelayStorageScopes` selects known retained runtime/history/recovery
roots and exact saved outputs, bootstrap metadata, the registry and its ownership,
settings and their sidecars, legacy native logs and native definitions. Unknown
namespaced sidecars remain chargeable; another application's native definitions
are not selected. Missing retained roots/exports require recovery. Explicitly
future files whose parents are absent propose the smallest new directory below an
existing parent; no directory is created during collection. Overlapping existing
roots are counted once by the subsequent bounded core inventory. Input-only files
and unrelated independently operated issuer/authority state are not discovered by
scanning the user's home directory.

The collector is not an approval, a writer lock or a complete product activation.
Its caller must hold all cooperating writer exclusion and revalidate the selection
through apply. Production composition still needs restart-safe adoption, selection
export, settings/native preparation and final activation. Existing native commands
remain mocked in tests, and aggregate limit/health UI is not enabled.

Validation: TypeScript and 112 focused tests in ten files (14.73 seconds), including
real HTTP/session ownership, six SIGKILL boundaries, exact control-capacity recovery,
unknown and missing retained files, all three native path layouts, and actual
scoped selection export/native preparation without executing OS service commands.


## Desktop adoption and interrupted commits

Authenticated `/api/relay/storage/adoption/review`, `/apply` and `/cancel` now
compose the known scope collector with the reservation authority. Review accepts
only saved locations and an optional `limitBytes`; apply consumes the returned
approval digest. A shared session controller permits one bootstrap or adoption
review at a time. Locking, expiry, cancellation, changed settings or the wrong
operation type cannot reuse the approval.

Adoption requires the independent attempted bootstrap intent, an existing primary,
fully funded bootstrap controls, a maintenance marker and a closed listener. It
holds desktop, ledger and runtime claims throughout review/apply. The review shows
retained bytes, proposed limit and whether the complete adoption fits. Insufficient
capacity refuses before the first commit. Apply can update the limit, adopt
existing-file floors, then approve new scopes. Each stage preserves previous
commits after failure; a restart requires a new review and never a budget reset.
Filesystem metadata digests are compared between commits independently of the
ledger revision, so an external file or parent change cannot be silently included
in an earlier approval. Those checks are not an atomic filesystem snapshot.

A read-only core scope inspection reports existing coverage and allocations; it
never authorizes writes or reclassifies missing history as unused space. Desktop
retry may reuse reviewed absent *configuration outputs*, still requiring a fresh
absence check. All retained history and exports remain mandatory. Once the storage
registry has a reservation, its absence requires recovery even under a broader
adopted parent. History roots enclosing desktop account data are rejected because
account writers are outside the relay's reservation authority. Independently
selected runtime storage must match any retained desktop bootstrap identity.

between commits, uncertain publication, expiry, and three real SIGKILL boundaries.
