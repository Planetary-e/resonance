# Combined relay/history storage: inventory and remaining enforcement

Status: bounded offline directory/file inventory and pre-output desktop path retention implemented; combined byte reservation and
quota enforcement remain open. Publication quotas and per-generation history
caps continue to apply independently. This document must not be read as a claim
that the combined budget is finished.

## Implemented measurement

In paused desktop maintenance, **Measure stored files** inventories the runtime,
saved owner/volunteer histories, recovery selections, the path registry itself,
and individually retained configuration/enrollment outputs. Successful settings saves
retain previous known locations in `historyStorageDirectories`, bounded to 128
absolute paths. Approved desktop setup/recovery/activation additionally records
history directories in a separate durable `relay-storage-locations/locations.json`
registry before its apply work. Recovery status/step also retain the selected
workspace and destination before opening the resumable coordinator. The registry
preserves both current and previous settings selections, including older settings
without a saved directory list. Its version-two manifest also retains up to 128
explicit output paths. A directory-only version-one manifest is read without
resetting it; its next changed write preserves its directories in version two. Settings-write failure, later selections and
reload cannot silently remove committed locations from the inventory.

The authenticated POST `/api/relay/history/storage` accepts an empty body only.
It uses the same stopped-runtime/control exclusion as history operations, supports
cancel/lock/disconnect and returns aggregate counts only. The command-line version
accepts explicit locations and does not acquire a global stopped-runtime claim:

```sh
node --import tsx scripts/admission-history.ts storage-inventory runtime-directory owner-history-directory volunteer-history-directory recovery-workspace --file owner-config.json --file enrollment.json
```

Pause all writers before using the CLI. Every selected root must exist and be a
directory. Canonical overlapping roots are traversed once; stable device/inode
identities deduplicate hard-linked files. Nested symbolic links and special files
are refused. The scanner reads metadata, never payloads or private keys. It counts
all regular files, including manifests, staged files and temporary files, without
interpreting which may be deleted. It never deletes or compacts anything.

Explicit files are inspected individually; their parent folders are not traversed.
The scanner rejects missing files, symbolic links and directory substitutions,
including a file changed into a directory between selection and traversal. Files
already inside a selected directory and stable hard-link aliases count once.
The aggregate response reports `selectedFiles` and never exposes paths or contents.
Input keys and externally created/copied operator files are not inferred from a
parent directory; explicitly select additional known files in the CLI.

Traversal is incremental, bounded to one million entries and depth 64. A 30-second
scan budget and cancellation are checked between filesystem operations. A blocked
filesystem call itself cannot be interrupted by this application-level deadline.
Metadata changes observed around a visit, missing files, unreadable entries,
changed root resolution and exceeded bounds reject the result. Unknown storage
never becomes a zero-byte success. Filesystem errors in the aggregate result omit
paths and filenames.

`logicalBytes` sums regular-file lengths. `allocatedBytes` sums filesystem-reported
512-byte blocks for unique files and directories when available, otherwise null.
These are different measurements: sparse files, compression and copy-on-write
sharing mean neither is an exact statement of exclusive device use or free space.
A scan is not an atomic filesystem snapshot. Another process may write between
visits even though the desktop-managed relay is paused.

## Explicit coverage boundary

The desktop registry preserves approved operation locations even if the later
settings save fails. A local registry lock serializes updates; paths are canonical
and bounded to 128. First creation flushes its directory before its manifest;
a missing/partial manifest in an existing registry refuses further use. Later
updates flush a new file, atomically replace the manifest and flush the directory
before returning to the caller. A crash before replacement cannot authorize
history creation; after replacement the new root remains registered. Interrupted
temporary replacements are bounded and retained, never used as authority or as
permission to remove old roots. No registry operation removes a committed root.
Windows flushes files but does not provide the POSIX directory-flush guarantee.

This is desktop bookkeeping, not a global writer lease or byte reservation.
Offline CLI operations do not yet share this registry. Existing-history inspections
can still open their own journals/locks before the apply hook; these hooks do not
constitute a complete production-writer map. Desktop configuration, owner setup/
export, owner-limit editing and volunteer activation retain their exact outputs
before writing. This includes configuration-only setup and preserves outputs even
when settings saving fails. Separate input keys and outputs from earlier external
CLI operations remain outside automatic desktop retention. The registry cannot rediscover
historical paths already lost from older settings, external copies, or output
created before pre-output registration was introduced. Loss/rollback of the entire
registry and its directory has no independent local authenticity proof. The CLI can inspect explicitly supplied additional
roots. Missing registered roots or files remain an error, including a planned restoration
destination or output that does not exist yet. No absent directory is treated as reclaimed
capacity or permission to reset accepted history.

This measurement excludes unselected app databases/models/configuration/key files,
filesystem metadata not represented by reported blocks, other applications,
future writes and temporary replacement headroom. It is an observation, not a
space reservation, durability proof, free-space check or enforceable total quota.
The interface states these boundaries. Existing history health remains cheap
cached protocol accounting; the filesystem inventory runs only on explicit demand.

## Bounded resource checkpoints

`relay-owner-budget.json` and `relay-resource-usage.json` now use the same bounded
atomic checkpoint writer. Each current file and its `.next` replacement is at
most 4 KiB: **16 KiB total encoded-file headroom for both components**. This is a
component ceiling, not a reservation against the pending shared budget. Directory
metadata and the runtime claim require separate accounting.

Reads reject oversized, linked, non-regular, changing and invalid inputs. Writes
validate the exact counter schema and safe-integer range before opening output,
handle short writes, flush, replace, and flush the directory on POSIX. Windows
flushes the file but has no directory-flush guarantee here. Changed or deleted
current state refuses reuse. An uncertain write poisons the handle; an owner
policy whose checkpoint failed refuses further new work even if its time window
expires. The committed current file is authoritative after restart. A bounded
interrupted replacement can be overwritten after reopening that valid current
file; an interrupted first checkpoint with no current file refuses initialization.

Backward clock movement and decreasing/unsafe measured counters do not grant a
fresh allowance within an existing window. Counter overflow is an error, never
rounded or reset to zero. The normal relay runtime claim still provides single
writer exclusion; the helper itself is not a cross-process transaction manager.
Complete deletion or coherent rollback of both files has no independent local
proof. Traffic since the last successful checkpoint can be lost on process death.
None of these files authorize recovery or deletion of accepted protocol history.

Package compilation and **13 tests / three files in 1.09 seconds** pass, including
short writes, file/directory flush failures, link refusal, unsafe counters, clock
rollback and real SIGKILL before/after replacement and during first initialization.
Real relay resource-policy, protected-owner startup and desktop-settings checks
pass **12 tests / three files in 24.73 seconds**. This change follows the earlier
complete suite; its new CI result is recorded separately in the completion plan.

## Shared reservation authority: core and snapshot integration

The core now provides `openStorageReservationAuthority` and
`withStorageReservationAuthority` through `@resonance/core/storage-reservations`.
This is an internal integration foundation. The managed relay, desktop and CLI do
**not yet enable a combined quota**: adoption of existing files and the remaining
writers below must use the authority before a product control can be offered.

The initial model reserves each component's enforced lifetime peak, including a
simultaneous replacement. Reservations are persisted before returning a lease.
Several components share one total. A smaller later component limit, a closed
handle, missing output or a changed selection never frees a previous reservation.
An exhausted authority refuses new components and increases; existing components
can keep writing within their already reserved ceiling. This trades spare usable
capacity for simple conservative failure recovery. There is no automatic release.

A dedicated directory holds one bounded one-MiB manifest, one bounded replacement
and process-ownership metadata. The authority reserves **2 MiB + 8 KiB** for this
control peak before user components. At most 512 canonical component paths are
retained, subject also to the encoded manifest limit. A process owns the authority
for its whole runtime or maintenance operation. Initial creation refuses any
existing directory; reopen requires the independently retained authority ID and a
valid primary manifest. An interrupted replacement is never used to reconstruct
missing authority. Unknown, linked, oversized or corrupt metadata refuses use.

Each reservation is flushed and atomically published before the caller can create
output. Failed or uncertain writes invalidate all leases until reopen. Metadata
replacement/deletion and path redirection observed on a live lease also refuse
writes. Real process death before publication retains the previous reservation
set; after publication a reservation stays charged even if output/settings never
finish. Windows flushes files but has no POSIX directory-flush guarantee here.

Limit changes require a digest of the current local review and cannot go below
all retained reservations plus control headroom. Another reservation invalidates
a stale review. The digest is a local review binding, not an independent signature
or a rollback-proof remote checkpoint. Coherent restoration of an old complete
ledger is not independently detectable. The authority is local filesystem
bookkeeping, not proof of protocol recovery or permission to delete history.

The shared encrypted snapshot writer now captures its path and byte limit and,
when a managed authority is supplied, reserves **twice the encoded image cap plus
8 KiB of generated lock/recovery metadata** before directory creation or opening.
It retains that lease across async scope exit and refuses later writes when the
authority closes or becomes uncertain. Caller option mutation cannot enlarge the
reserved image cap. Unconfigured call sites retain existing behavior; no relay
configuration or environment flag silently enables partial quota coverage.

A lease alone does not intercept arbitrary filesystem writes. Every component
must still enforce the peak it declares. Existing unknown files, earlier temporary
images, copied outputs and all direct block/journal/control writers need explicit
adoption and integration. The ceiling concerns managed encoded file bytes, not
filesystem blocks, open deleted inodes, filesystem snapshots or whole-device space.

Compilation and **68 tests / nine files in 11.34 seconds** pass for the authority,
encrypted states, wallet/outbox crash recovery, witness and checkpoint quorum.
After adding the zero-byte component case, the final authority suite passes
**18 tests in 1.06 seconds**. These groups overlap. Tests include real competing
processes, five SIGKILL boundaries, short writes, file/directory flush failures,
missing/corrupt authority, redirected/hard-linked targets, stale limit approval,
and a real encrypted snapshot refused before creating its directory when the
shared budget is exhausted. This is narrower than full production quota coverage.

## Remaining write-budget implementation

The [storage writer map](v0.4-storage-writer-map.md) identifies snapshot, direct
block, journal, control and supervisor writers. It records the bounded replacement
for new service diagnostics and distinguishes unused export APIs from live relay
writes. Exact desktop operator outputs and registry metadata are now inventoried; their
bytes still need shared reservations alongside other control metadata.

A hard combined quota needs a different mechanism from a repeated directory scan:

1. Wire the implemented reservation authority and desktop path retention into
   shared CLI/runtime selection, and adopt existing files before enabling durable
   **byte** reservations across every protected output. Preserve the
   reservation through settings-save failure and process death, bind it to canonical
   roots and serialize competing writers. A recorded path alone allocates no bytes.
2. Account for existing files and the old-plus-new peak of atomic replacements.
   Accepted obligations, pending intents, ancestry, permanent denials and repair
   headroom set floors. Refusing new work must not silently discard those floors.
3. Reserve before every protected write and signed acceptance, including direct
   ciphertext writes as well as encrypted snapshots. Enforce the same authority
   across the relay process and offline CLI; periodically sampling bytes in an
   HTTP stats endpoint is insufficient.
4. Recover interrupted reservations conservatively. Release capacity only after
   authenticated state proves that removal/compaction is safe. Treat unexpected
   files, incomplete recovery and unobservable usage as occupied/unknown.
5. Expose a reviewed total budget only after every production writer is mapped.
   Test simultaneous owner/volunteer roles, multiple workspaces, full capacity,
   changed paths, read-only storage, short writes, flush failures and SIGKILL.

The current known per-file bounds show why ciphertext-only totals are insufficient:

| Component | Existing encoded-file bound / reservation | Source |
| --- | --- | --- |
| Protected spend image | 32 MiB snapshot; replacement also needs a temporary file | `protected-admission-history.ts` |
| Owner writer journal | 40 MiB snapshot plus replacement | `history-checkpoint-quorum.ts` |
| Owner ciphertext archive | Up to 64 MiB ciphertext; 2 MiB manifest plus replacement | `history-writer-archive.ts` |
| Volunteer generation | Two 2 MiB manifests reserved with ciphertext; 256 MiB ancestry ceiling | `history-checkpoint-store.ts` |
| Child provision journal | 64 KiB snapshot per slot plus replacement | `history-generation-provisioner.ts` |
| Recovery coordinator | 4 MiB snapshot plus replacement | `admission-history-recovery.ts` |
| Frozen-history preparation | 96 MiB snapshot plus replacement | `history-checkpoint-recovery.ts` |
| Agreement coordinator | 2 MiB snapshot plus replacement | `history-agreement-coordinator.ts` |
| Historical download | 256 MiB ceiling including two 2 MiB manifests | `history-ancestry-download.ts` |
| Owner provision coordinator | 512 KiB snapshot plus replacement | `history-provision-coordinator.ts` |

These are source bounds, not measured usage and not a proven combined ceiling.
Runtime publication/mailbox/journal, policy/witness state, locks and temporary
publication/restoration files still require the complete writer map. The generic
snapshot writer enforces its encoded byte cap before opening a temporary file,
then flushes, renames and flushes the directory. Its local lock is per file; it is
not currently a cross-role storage reservation.
