# Recoverable admission witnesses and coordinators

## Behavior and trust boundary

A witness decision must survive loss of its working directory. Otherwise the same
infrastructure key could vote for a conflicting use of a previously spent token.
A coordinator also retains its complete four-witness certificate before allowing
the separate local spend. Both roles can now use the existing protected owner
history. Their decisions join the signed policy and spend state in one encrypted,
versioned application image.

The history still requires four durable copies among five independently pinned
volunteers. Those history volunteers are distinct protocol roles from the five
admission witnesses; the names must not be interpreted as evidence of independent
operators. The existing fixed-membership/fault assumptions still apply. Restoring
the same signing key and complete fenced history is not permission to replace a
witness key, change membership or reset a lost unprotected ledger.

The original version-one spend image remains readable with its established field
order and replay digest. Version two also retains an optional witness and optional
coordinator, their exact signed decisions, and permanent issuer-key denials.
Parsers enforce assigned membership, signatures, distinct decisions, four-member
certificates and bounded capacities. Policy and full-state checkpoints must
preserve roles as well as spends. A retirement may replace expired-key decisions
only with a permanent denial; it does not make the token available again.

## Reviewed capture of intact local state

Run these commands with the relay stopped under the existing maintenance workflow.
The local witness/coordinator files must already exist and be readable using the
owner storage key. This workflow does not initialize missing local evidence.

```sh
node --import tsx scripts/admission-history.ts owner-role-capture-plan \
  owner-config.json policy.json owner-storage.hex owner-directory local-role-directory both

node --import tsx scripts/admission-history.ts owner-role-capture --approve <digest> \
  owner-config.json policy.json owner-storage.hex owner-directory local-role-directory both
```

The last argument can be `witness`, `coordinator` or `both`. Review is offline and
reports counts and an approval digest, without spend identifiers or credentials.
Approval binds both local captures, the selected owner history, policy, location
and head. Application first confirms fresh history readiness. Each selected local
file is then atomically replaced with a version-three protection fence containing
its complete captured state and history context. Existing local writer code
rejects that format. Only after these fences does the owner publish the complete
role capture to four volunteers.

Review reports the combined space needed for the capture and one prospective
complete checkpoint. Insufficient archive capacity refuses before either local
role is fenced. The same headroom calculation guards ordinary protected writes.

If the process dies after fencing only one role, the other intact file is retained.
If it dies before history publication, the fences still contain the entire capture.
If a publication or reply is uncertain, the exact encrypted intent remains pending.
Preserve all of these files. Resume `owner-ready` if a protected intent needs to
finish, then obtain a fresh role-capture review and apply its new digest. A repeated
capture may retain newer decisions or permanent retirements already in the history;
it cannot replace a participant or discard the older captured decisions.

Existing storage reservations remain charged. Fences use their existing bounded
encrypted snapshot allocations; the combined image and prospective checkpoint
must fit owner/volunteer limits before an intent is published. Capturing a large
legacy certificate ledger may require retiring eligible old keys first. Physical
filesystem allocation remains separate from logical byte reservations.

## Serving, retries and recovery

A configured protected relay now refuses a requested role absent from its history.
`RELAY_ADMISSION_WITNESS_INITIALIZE` cannot silently create an empty substitute for
that role. Intact local roles need the capture step above. A newly provisioned
role still needs an explicitly initialized initial ledger before capture; reviewed
desktop creation/capture controls remain a separate operational task.

The witness authenticates a request and persists its exact decision on four copies
before its signature leaves the service. Three copies, failed writes or lost
replies return no success. Exact retries resume the pending ciphertext; conflicting
claims cannot replace it. The relay socket awaits this asynchronous durability
step and does not send a promise or an early acknowledgement.

The coordinator retains the exact certificate before authorizing a spend. A relay
that is also a witness waits for its own in-progress decision before writing the
coordinator record, within the existing coordinator deadline. This prevents two
roles from racing the shared single writer. Each role admits at most one active
decision through this adapter; concurrent callers can receive a retryable refusal.

Ordinary owner freeze, agreement, restoration and readiness now replay and restore
the role image too. The same independently backed-up signing/encryption keys,
context, original genesis and authenticated policy remain necessary. The desktop
restoration review includes witness decisions, quorum certificates and permanent
role-denial counts. Losing private keys or unreplicated old role history is not
repaired by creating an empty role under the old identity.

## Protected retirement

```sh
node --import tsx scripts/admission-history.ts owner-role-retirement-plan \
  owner-config.json policy.json owner-storage.hex owner-directory witness <issuer-key-fingerprint>

node --import tsx scripts/admission-history.ts owner-role-retire --approve <digest> \
  owner-config.json policy.json owner-storage.hex owner-directory witness <issuer-key-fingerprint>
```

Use `coordinator` for its certificate history. The active issuer cannot be retired;
the final retry cutoff must have passed. The denial and removed decisions form one
replicated mutation. A backwards local clock cannot clear that retained denial.
Local retirement tools refuse fenced files instead of bypassing this replication.

## Desktop capture of existing roles

In **Prepare protected history**, select **Protect existing admission roles**.
Choose witness, coordinator or both, the protected owner directory and the intact
local role directory. They must use the selected storage key and retained signed
policy. The source can be the existing runtime or the owner directory; the
protected owner remains separate from the runtime. Optional owner transport pins
support the existing direct/outbound/bridge workflow.

Review is offline and displays counts, existing local fences and archive space for
the capture plus a subsequent complete checkpoint. Approval binds canonical paths,
source decisions, configuration/policy/key bytes and transport selection. Apply
requires fresh readiness, fences the originals, then replicates the capture. The
relay stays paused. Missing source files are never initialized. Both directories
remain inventoried even after a settings-save failure; a new review recognizes an
already completed capture. Cancellation during readiness changes neither local
role. Keep original fences after success or interruption.

This operation does not create new signing keys, enroll a key into signed policy,
start a service or solve membership replacement. Private decision payloads are
absent from the review. Nine real-API setup tests pass (18.67s), including capture,
changed inputs, missing source, interrupted settings and cancellation; four UI
tests cover capacity refusal and operation-specific explanations.


## Genuinely new roles

The desktop has **Prepare a new admission role** and **Export a protected role
signing key**. Preparation generates a fresh Ed25519 key after review; it accepts
no existing signing key. Use an absent dedicated directory and the storage key
that will also encrypt the protected owner history. The encrypted 4 KiB preparation
journal retains the new key and a `preparing`/`prepared` stage. An empty encrypted
role ledger must be flushed before the stage becomes prepared; only then can a
public-key file be exported. No usable private key leaves this workflow yet.

Resume can create a missing ledger only while the retained key is still in the
unpublished preparing stage. A missing prepared ledger refuses, including after
private-key export. A crash before the first journal is published leaves no
exported identity; preserve the incomplete directory and choose a new directory
for a new key. Existing or partial public/private outputs are never overwritten:
resume with a new output path.

Enroll the generated public key in an independently signed community policy.
Prepare a protected owner against that policy (or use a valid explicit policy
transition), then capture the intact new role using the desktop capture operation.
Private-key export requires the same prepared key in the protected image, its
original local fence, the exact reviewed selection and four fresh copies. The
signing key is written only to a new private file; API/CLI results contain its
public key and path. The file is compatible with the existing configured witness
or coordinator key input. Retain independent key/storage-key/history-pin backups.
Policy enrollment and membership approval remain explicit community operations.

Shared operator equivalents:

```text
role-setup-plan|role-setup [--approve DIGEST] new|resume witness|coordinator storage.hex role-directory public-output.json
owner-role-key-plan|owner-role-key-export [--approve DIGEST] owner-config.json policy.json storage.hex owner-directory role-directory witness|coordinator private-output.json
```

Both preparation and export retain the storage authority that opened them. New
preparation funds the complete journal, role replacement peak and public output
before creating the directory. Desktop records the source/history/output locations
before apply and keeps the relay paused. Exporting a private key never authorizes
resetting its accepted history.

The final focused group passes **32 tests / four files / 23.21s** with TypeScript
and whitespace checks. It includes the complete real desktop API sequence, quorum
loss before export, budget-scope switching, missing prepared histories, changed
inputs, and seven actual process-death boundaries (five during preparation and two
at private-key publication). Local loopback processes and SIGKILL do not certify
independent volunteer availability or filesystem power-loss durability.
