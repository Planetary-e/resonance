# Reviewed admission history restoration

The opt-in admission API can reconstruct a lost owner's policy, spends and
permanent issuer denials from complete encrypted ancestry, then initialize a
**new directory** under a certified successor generation. It cannot authorize
service from an old snapshot alone. Four fresh acknowledgements of the exact
current head are required before admission becomes available.

This supplies the reconstruction and activation boundary used by operator
integration. [Relay startup](v0.4-protected-admission-operations.md) can now reopen
prepared protected state. This is not yet an enrollment/restore command, witness-ledger
recovery, automatic policy freshness service or safe history compaction.

## Inputs and trust boundary

The caller retains the owner signing key, history encryption key, independently
pinned context and genesis digest, five member identities/endpoints, and a current
authenticated policy. Losing the encryption key cannot be repaired by replicas.
The replicas retain owner-signed ciphertext, not plaintext spend records or bearer
tokens. The existing fixed-membership quorum assumptions still apply; five local
test services do not demonstrate independent volunteer ownership.

Before restoration, use the existing freeze, selection, download, agreement and
provisioning APIs. Agreement must use its **actual selected proposal**, which can
differ from the owner's preferred proposal. Its confirmed certificate authorizes
one deterministic continuation root. Provision that root on the pinned members;
provisioning itself does not establish write readiness. Preserve all ancestor
generations and incompatible tails.

## Semantic reconstruction

`replayAdmissionHistory` consumes a chronological iterable, such as a completed
`createHistoryAncestryDownload(...).blocks()`. It verifies:

1. The independently pinned generation-zero checkpoint, owner signature,
   encryption authentication and baseline signed-policy digest.
2. Every contiguous sequence, predecessor digest and generation boundary.
3. Each continuation's confirmed agreement certificate and the complete selected
   predecessor, including all four frozen anchors.
4. Every admission mutation through the same reducer used by live admission:
   signed policy successors, attributed/unattributed spends, binding conflicts,
   retirement cutoffs and permanent denials.
5. The exact final selected root, head and frozen anchors, with no missing or
   extra records.

An owner-signed snapshot cannot erase spends or denials. Large policy checkpoints
must preserve the preceding state exactly. Historical event times remain owner
assertions, not independent clocks. Legacy recovery records retain locally
verified attribution rather than transferable bearer proofs.

The API returns no partial usable image on failure. Limits are 10,001 total
blocks, 256 MiB total serialized ciphertext, 64 MiB per generation, 65 generations
and 10,000 live spends. Callers can lower those limits. The default local replay
budget is 30 seconds, configurable up to five minutes; network request lifetimes
are unchanged. Replay checks cancellation and yields to the event loop every 32
blocks. Temporary plaintext buffers and the API's key copy are cleared. Parsed
JavaScript objects cannot provide a guaranteed memory-erasure claim.

## Review and new-directory activation

`prepareAdmissionHistoryRestore` verifies the certified continuation and replays
its selected predecessor. It authenticates the requested current policy and its
relationship to the recovered policy. The destination must be absent or empty
at review time. The frozen review reports aggregate counts, policy revisions,
authority/context/root fingerprints, destination and an approval digest. It does
not expose bearer tokens or individual spend/binding identifiers.

The returned preparation also carries an in-process capability. Supply the
original preparation and its approved digest to:

```ts
openProtectedAdmissionSpendHistory({
  // Existing owner, key, context, policy and pinned-member options...
  initialize: true,
  protection: {
    // Existing protected-history options...
    initializeWriter: true,
    restore: { preparation, approvedDigest },
  },
});
```

The ellipses denote required options, not a runnable shell recipe. A fabricated
JSON review, cloned facade, different destination, context, policy or approval
cannot initialize state. A new process reruns preparation from authenticated
source data; serialized review output alone is not an activation capability.

Initialization atomically captures the complete recovered image and continuation
in protected format v4 at the existing `admission-spends-v2.jsonl` path. Format v3
remains the generation-zero protected format. Both reject local-only readers.
The v4 capture includes the authenticated genesis and reconstructed baseline,
bound to the selected proposal by its replay digest. That digest binds the review;
it is not independent freshness evidence.

`ready()` then obtains four fresh exact-head writes before getters or admission
can serve the image. If the requested policy is a valid later successor, it also
replicates that transition before serving. Further spends use the certified new
generation and the normal retained-writer ordering. An exact old token retry
retains its original binding; a different operation cannot reuse it.

## Reopen, crashes and stale backups

Every protected open starts unavailable until explicit `ready()`, including an
ordinary reopen without restoration. The configured verifier already awaits this
gate. A durable cached certificate may finish an interrupted local image update,
but it cannot replace the fresh readiness exchange.

The protected writer requires each counted receipt's current head to equal the
exact target. A receipt acknowledging an older prefix while advertising a newer
head is insufficient. This catches a remote advance between the repair head
query and append, as well as a coherent rollback of all local owner files.
Frozen or divergent histories also refuse readiness. A current four-member
response is a protocol observation, not a promise of future uptime or global
policy freshness.

After a crash following publication of the v4 image, reopen it without a new
restore capability. Explicit pristine writer/archive creation can finish
interrupted setup; it cannot recreate missing committed history. If the process
died before publishing any authoritative image, keep the interrupted directory
for inspection and prepare a separate new destination. There is no automatic
empty reset or deletion of ambiguous files.

## Evidence and limits

The focused restore file passes 29 cases, including malformed/missing/reordered
ancestry, bad pins/keys, bounds, cancellation, semantically destructive but
authentically signed records, review substitution, stale whole-owner backups,
the head-query/append race, and nine SIGKILL boundaries.

The integration scenario uses five real local WebSocket replica services,
authenticated ciphertext download, actual blind tokens and two certified
successor generations. It verifies exact spent-token replay, rejection of a
changed binding, acceptance of a new token, disk reopen and restoration after
deleting the first restored owner directory. Agreement/provisioning setup in
this fixture uses production role APIs through an in-process transport; the
separate agreement/provisioning suites cover their socket paths. No single test
here is a complete external deployment.

TypeScript and the complete local suite pass **149 files / 950 tests** in
**569.17 seconds**, with one worker. All **357 TypeScript source hashes** remained
unchanged during that complete run. This covers both the restore/readiness work
and the preceding large-policy checkpoint compatibility change.

Ancestors remain necessary and consume finite space. This change does not permit
deleting history, resetting capacity, replacing witness membership or reopening
an unavailable quorum. Operator configuration/enrollment/startup/maintenance,
complete witness and policy recovery, safe compaction, resource measurements and
independent volunteer validation remain separate completion requirements.
