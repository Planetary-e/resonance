# Reviewed initial history setup

The desktop maintenance panel now prepares an initial owner and enrolls volunteers
through fixed reviewed operations. Keep the owner and volunteer signing/storage
keys in independently retained files. Key creation, authority trust and selecting
five genuinely independent volunteers are prerequisites; a public key or different
endpoint is not proof of independence.

## Owner preparation

1. Stop the managed relay using **Protected history maintenance**.
2. In **Prepare protected history**, select **Create owner configuration**. Supply
   the owner signing key, pinned authority, current signed policy, five public
   member contacts and a new output file. Review verifies the policy and contacts,
   generates one random history identifier and displays the public pins. Applying
   requires that same identifier, selection and review; it cannot replace a file.
3. Select **Prepare this owner history**. Choose the local owner storage key, a
   dedicated empty history directory and a new enrollment backup file. The
   directory must be separate from the runtime and all input/backup files.
4. Review and approve preparation. The encrypted generation-zero baseline, writer
   and archive are created locally. The exported enrollment contains the exact
   signed encrypted genesis and public context. Preparation never contacts a
   volunteer and reports readiness as unverified.
5. Keep independent copies of the configuration, enrollment and owner keys. Send
   only the enrollment/public pins to the selected volunteers; never share the
   owner's encryption key or signing secret.

The fixed CLI equivalents are:

```sh
node --import tsx scripts/admission-history.ts owner-config-plan owner-private.json authority.pub policy.json members.json owner-config.json
node --import tsx scripts/admission-history.ts owner-config-create --approve <digest> owner-private.json authority.pub policy.json members.json owner-config.json <reviewed-history-id>
node --import tsx scripts/admission-history.ts owner-setup-plan new owner-config.json policy.json owner-storage.hex owner-history enrollment.json
node --import tsx scripts/admission-history.ts owner-setup-apply --approve <digest> new owner-config.json policy.json owner-storage.hex owner-history enrollment.json
```

`resume` and `export` replace `new` for the separate reviewed operations below.
The older explicit setup commands remain available for scripted operators.

## Volunteer enrollment

On each volunteer's desktop, select **Enroll this volunteer**, choose the owner's
independently verified enrollment file, that volunteer's signing/storage keys and
a new dedicated history directory. Review displays the owner, authority, context,
genesis, member identity and current storage limits. Approval enrolls only that
pinned member. A changed selection invalidates approval; an occupied directory
cannot be cleared or enrolled again by this operation.

Enrollment does not start a listener or configure outbound controller pins. Use
the [reviewed volunteer activation panel](v0.4-desktop-volunteer-activation.md)
next to select controller pins, validate retained generations and save service
configuration while paused. It can reopen complete enrollment and provably pristine
successor slots. For an incomplete first genesis write, use the separate reviewed
resumption below. Do not delete an interrupted directory to retry.

## Interrupted volunteer enrollment

Choose **Resume interrupted volunteer enrollment** with the original enrollment,
member key, local storage key and history directory. This is an offline review and
separate approval. It retains the stopped-runtime claim and maintenance pause.

- A complete retained history reopens through the ordinary service validator and
  preserves all accepted blocks, promises and generation barriers. As on ordinary
  startup, that can finish a provably unactivated empty successor slot.
- An authenticated genesis manifest with zero indexed blocks can complete its
  original independently pinned genesis. Review checks that the directory contains
  only expected initial files and displays that the first block remains pending.
  Approval reuses a valid flushed root or atomically publishes that same signed
  root, then publishes the manifest index before ordinary service reopening.
- A missing/corrupt manifest or missing indexed block is refused. No temporary
  snapshot, directory name or unindexed ciphertext is promoted into authoritative
  history. Preserve those files for explicit recovery/inspection. If the first
  authoritative manifest never existed, this workflow cannot prove that from
  absence; it does not authorize reuse of the directory as an empty history.

```sh
node --import tsx scripts/admission-history.ts replica-resume-plan enrollment.json member-private.json member-storage.hex replica-directory
node --import tsx scripts/admission-history.ts replica-resume --approve <digest> enrollment.json member-private.json member-storage.hex replica-directory
```

The approval binds exact file bytes, canonical paths, keys and retained state.
Wrong approvals, changed files, competing owners and cancellation are refused.
Review/lock reopening can remove abandoned encrypted temporary snapshots; it
never creates a genesis manifest. A failure after the complete genesis is installed
requires a fresh review, which then sees retained history. A desktop settings-write
failure leaves that completed history intact and the earlier saved selection
unchanged. Review again and save the resumed selection before separate activation.

Resumption uses the original enrollment defaults. For an already operational
history with enlarged capacity, use the activation panel with its configured
limits. This local mechanism cannot detect a coherent rollback of the entire
manifest/data/settings backup. Membership replacement and recovery of actually lost
accepted history remain distinct requirements.

## Initial readiness and activation

After volunteers are enrolled and reachable, select **Complete initial owner
readiness**. Choose the original enrollment, owner configuration, policy, storage
key and prepared history directory. An optional operator connection file uses
the existing pinned outbound/bridge transport.

Review is offline, authenticates the retained generation-zero image against the
independently pinned genesis and binds its exact state and pristine setup needs.
Approval completes retained work and requires four fresh exact-head copies. Three
copies, stale receipts and a lost reply cannot establish readiness. Cancellation
retains pending evidence. After interruption, review the same directory again.

```sh
node --import tsx scripts/admission-history.ts owner-initial-readiness-plan owner-config.json enrollment.json policy.json owner-storage.hex owner-history
node --import tsx scripts/admission-history.ts owner-initial-ready --approve <digest> owner-config.json enrollment.json policy.json owner-storage.hex owner-history
```

This operation rejects a restored successor, which needs the separate
[recovery-ancestry-bound review](v0.4-restoration-readiness.md). After success,
use [owner activation](v0.4-desktop-history-activation.md), then explicitly leave
maintenance and start. Every start rechecks current readiness.

## Interrupted setup

No output file is overwritten. A partial export remains intact; select a new
export path. **Resume interrupted initial preparation** opens an existing
authenticated baseline and may complete only pristine missing writer/archive
setup. Missing committed components are refused. **Export retained initial
enrollment** reopens existing complete local components and exports the same
genesis; it cannot turn a restored successor into a replacement genesis.

If no authoritative spend image was published, preserve the interrupted directory
and review a separate empty destination. This is initial setup, never recovery of
accepted work. A settings-save failure can leave valid preparation/enrollment
files without a saved form selection; reopening those files does not authorize
another fresh history.

## Owner archive limits

Pause the relay in maintenance, then select **Edit owner archive limits**. Supply
its retained owner configuration, independently retained enrollment, current
policy, storage key, dedicated history folder and a new configuration output.
The desktop accepts 1–64 MiB and 1–10,001 blocks per current generation. Review
shows retained ciphertext and block counts plus the proposed limits.

The offline operation validates the pinned genesis and complete local history.
A smaller limit cannot discard accepted ciphertext or an intent saved before its
ciphertext reached the archive. Pending work is counted even when the archived
block count alone would fit. Full archives fail new work; a reviewed increase
allows the exact retained pending operation to finish, preserving token reuse
checks. The owner key, member pins and history identity remain unchanged.

Approval writes an exclusive new configuration and preserves the original. It
only saves the setup form selection. Select the new file in **Activate protected
owner**, review again and obtain four fresh copies before saving the runtime
paths. This separate step keeps capacity editing from bypassing readiness. The
relay remains paused until explicitly started. Hand-edited configurations also
pass bounded parsing and retained-history checks on runtime startup.

Equivalent CLI commands (paths may be relative in the CLI):

```sh
node --import tsx scripts/admission-history.ts owner-limits-plan owner-config.json enrollment.json policy.json owner-storage.hex owner-history owner-limits.json 64 10001
node --import tsx scripts/admission-history.ts owner-limits --approve <digest> owner-config.json enrollment.json policy.json owner-storage.hex owner-history owner-limits.json 64 10001
```

The optional configuration field is `limits: {archiveBytes, archiveBlocks}`;
existing configurations keep their former defaults. The byte cap covers encoded
encrypted block files, not spend images, writer manifests, old generations,
recovery workspaces, filesystem overhead or other relay roles. Combined storage
budgets and safe compaction remain separate unfinished work.

## Desktop boundary and validation

GET `/api/relay/history/setup` returns the last saved selection. Authenticated POST
accepts only `{action: "review", input}` or `{action: "apply", input,
approvalDigest}`. Paths are absolute, outputs exclusive and directories canonical
and nonoverlapping with the relay runtime. Extra fields and arbitrary commands
are refused. Every operation holds stopped-runtime/control exclusion, retains the
maintenance pause and saves only file paths and public selection, never secrets.

Local tests cover exact approval, file/directory changes, preserved outputs,
pristine resumption, missing committed state, API authentication, failed settings
writes and a complete initial owner/five-volunteer/readiness/activation sequence.
Native service installation is mocked. Package compilation, strict standalone
command checking and **21 tests / four files in 10.41 seconds** passed, including
eight real SIGKILL boundaries. The shared-readiness regression and final genesis
separation guards also passed; overlapping results are recorded in the completion
plan. A manual React/local Node run completed configuration, preparation/export,
reload/unlock and another export of the same genesis using disposable data.
Embedding initialization was stubbed; no native service was installed or started.
These checks do not certify independent
volunteer schedules, Internet behavior, installers or physical power loss.
