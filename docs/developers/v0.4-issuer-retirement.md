# Permanent retirement of an issuer ledger

Status: **implemented for the opt-in v0.4 pilot, 2026-10-01**. This extends the [local admission-history retirement](v0.4-admission-history-retirement.md) work to offline volunteer issuers.

## Decision

An issuer ledger belongs to **one RSA key and one token period**. Removing permit entries while keeping that issuer operational would forget allocated allowances and batch bindings. An old permit could become reusable, or an apparently empty ledger could grant more invitations.

Retirement therefore **permanently closes the entire ledger**. One encrypted atomic snapshot removes its per-permit evidence while retaining its pinned profile, fixed batch size, original maximum allowance, installed signed policy, retirement time and lifetime counters. It rejects new invitations, blind signing, cached response recovery and policy installation afterwards. It has no reset or reactivation operation.

This can release stored permit hashes, batch identifiers and cached blinded signatures. It **does not create spendable capacity** in that issuer. A new key/period needs its own explicitly initialized ledger and budget. No allowance is refunded or transferred; independent issuer keys still do not implement a network-wide quota.

## Eligibility and review

All of the following are required:

- The existing ledger opens with its matching profile and RSA private key. The original private-key-derived encryption domain is unchanged.
- It contains an authenticated, currently valid community policy. The operator separately supplies the pinned authority public key for maintenance.
- Its RSA key is no longer the active issuer in that installed policy. Install the intended signed successor through the existing policy command first.
- The key's **`retryUntil` has passed**. Issuer cached responses are recoverable only until `spendUntil`; waiting through the later retry cutoff deliberately uses the same conservative final boundary as relay history retirement. Policy expiry alone is insufficient.
- No signing or policy-installation operation is in progress. Existing process locks exclude another writer.
- The operator approves the reviewed digest. It binds the resolved ledger path, authority, issuer key, exact installed policy and complete current state. Changed policy/history or a moved file requires a new review. The clock is checked again immediately before writing.

Unused invitations, partially signed batches and completed responses are all removed together. Before retirement, their ordinary reservation and response-recovery rules remain unchanged. An interrupted issuance never releases its allowance.

## Offline operator workflow

Stop other issuer operations. Keep the existing profile, matching PKCS8 private key and authoritative ledger. Use an independently verified `authority.pub`; maintenance never imports a new community policy or initializes missing history.

Review:

```sh
node --import tsx scripts/issue-admission-tokens.ts plan-retirement \
  issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub
```

The report shows the ledger path, issuer/authority fingerprints, policy revision/digest, response and retry cutoffs, record counts, lifetime allocation/binding/completion totals, original budget, unallocated allowance being cancelled and `approvalDigest`. It omits permit hashes/secrets, batch IDs, blinded responses and private keys. Review does not rewrite the ledger; normal lock recovery and stale temporary-file cleanup still apply.

Apply the reviewed result:

```sh
node --import tsx scripts/issue-admission-tokens.ts retire \
  --approve 'sha256:<review-digest>' \
  issuer-profile.json issuer-private.pem issuer-ledger.json authority.pub
```

Inspect the sealed ledger later:

```sh
node --import tsx scripts/issue-admission-tokens.ts status \
  issuer-profile.json issuer-private.pem issuer-ledger.json
```

`status` retains `allocatedPermits`, `boundPermits`, `completedPermits`, `allocatedTokens`, `boundTokens`, `batchSize`, `maxPermits` and `tokenBudget`. It adds `permanentlyRetired: true`, `retainedEntries: 0`, `retiredAt`, and `unallocatedPermitsCancelled`. **`remainingPermits` is always zero after retirement**, even if the original allowance was never fully allocated. Allocation and completion counts describe historical reservations and cached responses, not proof that recipients received tokens.

An empty, valid encrypted ledger can also be sealed: it cancels all remaining allowance and removes zero records. This does not imply a reduction in file size. It differs from a missing, truncated or corrupt file, which refuses maintenance.

## Format, recovery and limits

- Operational ledgers retain the existing version 1 format. Reading or reviewing them does not migrate or prune evidence. Retirement replaces the same path with version 2: empty `entries`, immutable retirement totals/time and the signed policy that authorized closure. Earlier binaries reject version 2 instead of treating it as unused capacity.
- The retained policy is historical evidence after closure. Reopening verifies its signature and that it was current at `retiredAt`, with an inactive issuer and elapsed retry cutoff. Status remains readable after policy expiry or clock rollback. Policy installation is permanently refused, so a later revision cannot reactivate this ledger.
- Counter validation requires `0 ≤ completed ≤ bound ≤ allocated ≤ maxPermits`. A retired snapshot cannot contain permit entries. Missing markers/policy, invalid counters, invalid signatures and impossible retirement times refuse opening.
- The denial marker, aggregate counters and removal are one atomic flushed replacement. A failed write poisons the handle; close and reopen before further use. Recovery sees either the original evidence or the complete sealed ledger. A recovered sealed ledger remains closed even if the previous process did not receive success.
- The existing 8 MiB limit, single-writer lock and file/POSIX-directory flush rules remain. Windows lacks directory flushing. Temporary replacement space is still required. SIGKILL and injected I/O failures do not establish survival of every filesystem or power-loss failure.
- Keep the current authoritative ledger and key. This does not prevent filesystem backup rollback, cloning a ledger, initializing another path under the same RSA key or signing outside the operational issuer API. It does not destroy the private key; the key is still required to decrypt the sealed ledger. No exported permit/request/response files or backups are removed, and physical secure erasure is not claimed.
- This affects only that issuer ledger. It does not revoke already issued tokens at remote relays, compact wallets, remove community policy-key slots, or resolve unattributed legacy relay spends. Other devices still enforce the policies and retirement markers they hold. Admission remains opt-in.

## Validation

Ten new tests cover all three permit states, real token unblinding/verification, unchanged legacy review, exact response recovery before cutoff, preserved lifetime accounting, unused allowance cancellation, a fresh issuer with an independent budget, wrong/missing approval, authority/active-key/deadline refusals, stale review after policy/path changes, live writers, pending signing/policy operations, a clock change before commit, malformed sealed snapshots, both sides of failed file/directory flushes, the actual CLI and SIGKILL recovery. No permanent service or external network is needed for these checks.

Checkpoint: TypeScript compilation and the final complete local suite passed, **108 files / 559 tests**, with one worker. The focused issuer/issuance/policy checks passed **24 tests across five files**. Remote CI runs separately after push.
