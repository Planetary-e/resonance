# Recovering a protected admission owner

Status: experimental operator workflow, 2026-10-17. This composes the existing
freeze, agreement, ancestry download, provision and reviewed restore protocols.
It does not create new volunteer members, restore lost private keys, compact
ancestors or enable admission by default.

## Required independent backups

Retain the owner signing key, payload encryption key (`owner-storage.hex`),
`owner-config.json`, the original `enrollment.json` containing the genesis, and a
current policy authenticated by the independently pinned authority. The history
and its data must still be recoverable from the enrolled volunteers. A new empty
owner configuration is not a replacement for lost pins or keys.

Keep the old owner process stopped. Use a new recovery workspace and a separate
new destination for the reconstructed owner. The commands preserve other files;
they do not stop a running relay or remove an old directory. All commands below
run with `node --import tsx scripts/admission-history.ts` from the repository root.
Keys are read from private files, never supplied as literal command arguments.

## 1. Review the freeze before starting

```sh
node --import tsx scripts/admission-history.ts owner-recovery-plan owner-config.json enrollment.json owner-storage.hex recovery-work 1
```

The final argument is the explicitly selected agreement view, initially `1`.
The command checks the payload key against the signed genesis, discovers certified
activated successors, and prints an aggregate review with `approvalDigest`.
It creates no files and does not freeze a volunteer. The review binds the context,
genesis, selected parent, next generation, view, workspace and local key.
Conflicting observed generation barriers refuse review. The ancestry bound leaves
room for one new child before authorizing a freeze.

Starting requires the exact reviewed digest:

```sh
node --import tsx scripts/admission-history.ts owner-recovery-start --approve <digest> owner-config.json enrollment.json owner-storage.hex recovery-work 1
```

This repeats inspection, verifies the unchanged review, and creates an encrypted
workflow journal. It does not yet send a freeze. The approval authorizes the next
step's **irreversible** old-generation barrier: ordinary writes to that generation
will stop, including exact retries. It is not approval to replace a live ledger or
discard accepted work. Remote capacity and volunteer availability are not promised
by this review; insufficient capacity or quorum leaves recovery unfinished and
preserves its history.

## 2. Advance explicitly and resume the same workspace

```sh
node --import tsx scripts/admission-history.ts owner-recovery-status owner-config.json enrollment.json owner-storage.hex recovery-work
node --import tsx scripts/admission-history.ts owner-recovery-step owner-config.json enrollment.json owner-storage.hex recovery-work
```

Repeat `owner-recovery-step` until status reports `complete: true` and
`phase: review`. A step performs one bounded phase:

1. Persist freeze intent, obtain four compatible frozen histories, and retain one
   exact preferred proposal.
2. Obtain and persist the actual agreement selection. A hidden prepared decision
   can select a different proposal; the workflow uses that selection.
3. Create a cache bound to the selected proposal, then download at most 128 blocks
   per step across every certified ancestor. An incomplete cache cannot confirm.
4. Revalidate the complete cache, repair compatible shorter copies, and collect
   fresh prepare/confirm votes for the selected history.
5. Provision the confirmed successor on four volunteers and retain its receipts.

Reopen and status never transmit. Every component is registered durably before
network work; a registered missing or corrupt journal is refused. If a crash
publishes a component before registering it, the retained creation intent allows
that exact component to be reopened and registered. An absent component with
ambiguous partial files is not silently recreated. Preserve that workspace for
inspection; a separately reviewed new workspace may be needed. No command erases
a partial freeze or promises that an unavailable quorum will return.

The workflow does not automatically raise the agreement view after a timeout.
When a retained higher view prevents progress, keep the old workspace and review
a separate recovery workspace with an explicitly higher view. Existing volunteer
proofs still control the selection; changing the workspace cannot erase them.
Never edit journals or clear witness/replica state to force a vote. Views remain
bounded by the agreement protocol.

Each network phase retains its existing deadline, at most 30 seconds. The entire
recovery may take several commands; it has no unbounded automatic retry loop.
Download, ancestor and component-journal capacities still apply. Workspace files,
replica files, temporary copies and process memory have separate costs; these
bounds are not a complete device resource budget.

## 3. Review and restore a new owner directory

```sh
node --import tsx scripts/admission-history.ts owner-recovery-review owner-config.json enrollment.json owner-storage.hex recovery-work policy.json recovered-owner
node --import tsx scripts/admission-history.ts owner-recovery-restore --approve <restore-digest> owner-config.json enrollment.json owner-storage.hex recovery-work policy.json recovered-owner
```

The first command replays every authenticated policy, spend and permanent denial
from the pinned genesis. It prints counts and a destination/policy/root-bound
restore digest, without spend identifiers or bearer tokens. Review is local and
does not authorize writes. The second reconstructs that review in-process,
requires its exact digest, atomically initializes the new protected image and
requires four **fresh exact-head** acknowledgements before reporting readiness.
A serialized review cannot initialize a ledger by itself.

If readiness fails after the image was published, preserve the new directory:

```sh
node --import tsx scripts/admission-history.ts owner-ready owner-config.json policy.json owner-storage.hex recovered-owner
```

This opens existing protected state, explicitly finishes only a pristine missing
writer/archive, and retries fresh readiness. Readiness also completes exact retained
pending updates and replicates a valid successor policy supplied in `policy.json`.
It never initializes a missing spend
image or recreates a committed missing writer. An interruption before the image
was authoritatively published requires a separately reviewed new destination.
After readiness, configure the relay to use that directory and follow the
[protected startup guide](v0.4-protected-admission-operations.md). Normal startup
rechecks readiness; an earlier success is not permanent permission to serve.

## Evidence and limits

The CLI integration uses five separate volunteer processes. It loses the owner's
working directories and recovery workspaces through three generation changes,
retaining only its keys/configuration/genesis/current policy. Recovery preserves
real blind-token bindings and a permanent denial, refuses conflicting reuse,
accepts genuinely new tokens, and refuses readiness with only three live copies.
The fourth volunteer can return and finish the already published restore.

API tests reopen between phases, download in one-block steps, retain a hidden
earlier confirmation, reject forged approvals and missing/corrupt journals, and
exercise cancellation, three-copy retry and nine SIGKILL boundaries around intent,
component registration, selection, confirmation and provisioning. The integrated
test exposed and corrected volunteer routing of selected-history transfer frames:
the root is inside their authenticated `authorization.request`, not a top-level
checkpoint request. The retained-service tests now exercise that path explicitly.

These are single-computer tests, not proof of independent volunteer uptime,
Internet behavior or power-loss durability. The protocol still assumes at most
one equivocating member and retained honest volunteer state. Independent policy
freshness, same-key witness recovery/replacement, safe compaction, reverse-link
NAT participation, desktop lifecycle, resource budgets and external validation
remain in the [completion plan](v0.4-completion-plan.md).
