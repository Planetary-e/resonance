# Enrolled history in the relay background service

Status: opt-in volunteer runtime, 2026-10-17. This reopens one **already-enrolled**
history in the ordinary relay process. It neither enrolls a new history nor changes
its members, root, keys or accepted evidence. Complete the
[reviewed enrollment](v0.4-volunteer-history-operations.md) first.

## Configuration

Create a private JSON configuration with exactly these fields. Copy the complete
`context` and independently retained genesis ID from the reviewed enrollment;
never reconstruct them from an untrusted peer or damaged local directory.

| Field | Value |
| --- | --- |
| `version` | `1` |
| `context` | Complete existing history context object, including owner, authority, member keys and quorum |
| `genesisId` | Independent `sha256:…` identifier of the enrolled genesis |
| `directory` | Existing enrolled volunteer directory |
| `signingKeyFile` | Existing member signing-key JSON file |
| `storageKeyFile` | Existing 32-byte local encryption key as 64 lowercase hexadecimal characters |
| `controllers` | One to five `{ "relayId": "did:key:…", "endpoint": "wss://…/" } records, with distinct identities and endpoints |
| `limits` | `{ "bytesPerGeneration": 16777216, "blocksPerGeneration": 100, "generations": 8 }`, chosen to fit retained state and the operator's contribution |

The limits example is an explicit configuration, not a network recommendation.
Bounds are more than 4 MiB and at most 256 MiB per generation, 1–10,001 blocks per
generation and 1–65 generations. Two maximum manifests reserve 4 MiB; retained
blocks need additional space. The existing combined ancestry ceiling also applies. A limit
below retained data refuses startup; it does not discard data. These are
per-history bounds, not a single combined disk quota for every relay role.

Paths resolve relative to this configuration file, not the shell's working
directory. Files are bounded regular inputs; malformed private JSON errors omit
their contents. Public Internet contacts require WSS; loopback WS is allowed for
local testing. Extra initialization instructions, duplicate controllers, invalid
pins or missing/corrupt enrolled state are refused before the service listens.

Run the ordinary relay entry point with the configuration path:

```sh
RELAY_HISTORY_VOLUNTEER_FILE=/absolute/path/volunteer.json node --import tsx packages/relay/src/main.ts
```

Other relay settings still apply, particularly `RELAY_DATA_DIR`, public endpoints
and resource controls. The history directory remains the separately configured
enrollment directory. Controller contacts are added to outbound links with their
explicit identity pins; a matching unpinned `RELAY_CONTACTS` entry cannot erase
that pin. Discovery cannot replace history membership. The process advertises no
direct endpoint unless the operator has separately configured one.

The volunteer serves checkpoint, agreement, transfer and provisioning over its
authenticated outbound connections. No dedicated direct history listener is
opened by this mode. A controller's signed socket identity is checked separately
from the history owner's signature on each protocol request.

## Desktop service

Before enabling the relay from the desktop app, launch it with:

```sh
RESONANCE_RELAY_HISTORY_VOLUNTEER_FILE=/absolute/path/volunteer.json npm run app
```

The existing service installer includes the configuration path in the macOS
LaunchAgent, Linux user service or Windows scheduled-task definition. Raw history
signing/storage keys are not copied into the service definition. The chosen path
is retained in local relay settings: reopening the GUI without that environment
variable preserves the enrolled background role. An explicit replacement path
causes the next enable/update operation to reinstall the service configuration.
An explicit empty override disables this role on that update while retaining its
history on disk; it does not transfer obligations to another volunteer.

This is an operator option. There is not yet a desktop enrollment/recovery wizard.
[Protected-owner relay startup](v0.4-history-owner-runtime.md) is available separately
in the Node runtime; its complete desktop configuration remains required.

## Resource and shutdown behavior

History links use the existing relay socket traffic meter. The enrolled role asks
the existing owner policy before accepting **new storage**, charging the logical
request size to the new-work ingress budget. CPU, schedule, power and total-traffic
conditions apply through that policy. Reads and exact retries of retained blocks
remain available when new storage is paused. Total wire accounting includes chunk
and acknowledgement overhead; the logical new-work charge is not that total.

The shared stream budget and protocol/disk limits still apply. Admission of new
history cannot bypass a zero new-work allowance. These controls do not impose a
hard CPU/network kill on reads or existing obligations, and the ordinary
publication storage setting does not replace the separate history limits. Resource
measurement and combined contribution/health reporting remain required.

Startup failures close the enrolled role. Shutdown handlers are installed before
contact discovery, so a silent contact cannot prevent graceful shutdown and key
cleanup. History streams close before relay connections stop; the enrolled role then closes. Returning after an outage
reopens the same authenticated history; there is no missing-state initialization.

## Validation and remaining work

Real Node-process tests cover pinned outbound service, a signed append, graceful
stop/restart, retained readable data, exact retry under a zero new-work budget,
rejection of a new append, missing state and a silent startup contact. Configuration
tests cover wrong keys, unchanged manifests, strict limits/fields and private-error
redaction. Static service-definition tests cover the three OS formats and retained,
replacement and explicitly cleared configuration paths. They do not install or
certify native services on all three operating systems.

Still required: a volunteer
bridge when both sides are outbound-only, full desktop operator workflows,
aggregate history health/storage controls, and independent Internet/TLS/energy
validation. The [reverse-link guide](v0.4-history-reverse-links.md) explains that
remaining topology boundary.
