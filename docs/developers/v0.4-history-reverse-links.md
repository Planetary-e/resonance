# History over authenticated relay links

Status: opt-in library/server integration, 2026-10-17. An enrolled volunteer now
has [runtime/background-service configuration](v0.4-history-volunteer-runtime.md).
Protected-owner startup and complete desktop operation remain required.

An enrolled volunteer can receive history requests on the authenticated connection
it already opened toward a reachable volunteer relay. It does not need to advertise
or accept a direct connection to its own history listener. Both connection
directions carry checkpoint, agreement, selected-history transfer and successor
provisioning messages. The original owner/member signatures, enrollment, generation
barriers, expiry checks and four-of-five durability rules remain authoritative.

## Explicit routing and trust

`HistoryRelayRouter` maps each pinned history member key to one distinct relay
infrastructure identity. It attaches only after the existing challenge/open/accept
handshake authenticates the exact socket. It never learns history membership from
a descriptor or bootstrap contact. An unauthenticated socket or an authenticated
identity absent from the explicit pins cannot allocate a history stream.

Owners supply `members: [{ publicKey, relayId }, ...]`. A volunteer supplies
`acceptedRelayIds` and its existing enrolled service as the handler:

```ts
const historyLinks = new HistoryRelayRouter({
  acceptedRelayIds: [ownerRelayId],
  handler(method, frame) {
    return method === 'agreement'
      ? service.exchange(frame)
      : service[method](frame);
  },
});
const relay = createRelayServer({
  // Existing persistence, resource controls and discovery settings also apply.
  historyLinks,
  relayLinks: { targets: [pinnedOwnerRelayContact] },
});
```

The caller opens the already-enrolled service, starts the relay, then closes the
service/router after stopping it. The router is caller-owned and shared by inbound
and outbound connections. Reconnection installs a fresh stream session and rejects
unfinished requests on the previous socket. There is no transparent resend or
fallback to a different member; the durable protocol layer decides how to retry
the original pending operation. Transport cancellation cannot undo a durable write.

Use the owner's router's `checkpoint` as the protected history transport, and its
`agreement`, `transfer` and `provision` transports for recovery. Existing protocol
endpoint validation still applies to member configuration; this router selects by
the explicit member/relay pins and does not dial those direct endpoints as fallback.
Service authorization and signature validation still run after reassembly.

Relay identities here identify infrastructure, not an application's user account.
Retain the authorized infrastructure identity separately from the owner's working
history, or explicitly update accepted relay pins during recovery. Possession of
an owner signing key alone does not silently change a volunteer's transport pins.
This channel does not remove traffic timing or infrastructure-identity correlation.

## Bounded exchange

The shared relay WebSocket frame limit is unchanged. A separate `relay_history_v1`
frame carries at most one 128 KiB binary chunk, encoded as canonical base64url.
Request and response headers declare their full size. The receiver checks the
method's existing protocol limit and reserves capacity before acknowledging the
header. Each chunk waits for an exact offset acknowledgement. Unknown fields,
wrong offsets, noncanonical bytes, truncated chunks and duplicate stream openings
close that link; role refusals return only a generic error.

- Maximum wire frame: `ceil(128 KiB × 4 / 3) + 1 KiB`, below the existing 1 MiB cap.
- One active request per direction per socket; eight operations across a router.
- At most 64 MiB of reserved send/reassembly buffers across a router. Allocation
  refusal cannot invoke the history role and releases that operation's reservation.
- A maximum 30-second complete-exchange deadline, including transfer and parsing;
  chunk progress cannot extend it. The original protocol's abort/expiry can end it
  earlier. A slow link can therefore refuse a large transfer without changing history.
- At most one unacknowledged chunk per direction and a 256 KiB socket-buffer check.
- Responses retain each action's smaller cap: ordinary checkpoint replies 4 KiB,
  continuation observations 40 KiB, agreement promises 64 KiB, provisioning 1 KiB;
  full reads use the existing bounded envelope limit.

Cancellation/socket loss releases stream buffers and rejects the caller. A handler
already running retains its operation slot until it settles, even after cancellation,
so repeatedly cancelling work cannot evade the concurrency cap. Late results cannot
send or revive a completed operation. Existing relay socket accounting includes all
history bytes. These allocation caps do **not** establish peak RSS, CPU, total
bandwidth, power consumption or Internet performance: JSON/crypto/storage work also
uses resources, and those measurements remain on the roadmap.

## Evidence and remaining integration

Socket tests exercise multi-megabyte UTF-8 payloads in both directions, all four
methods, authentication pins, shared budget exhaustion, stream corruption,
whole-exchange deadlines, cancellation with a delayed role, response caps and loss
of the connection. They also require reservations to be released.

The server integration starts one reachable controller and five outbound-only
volunteer relays on one computer. Their direct history endpoints are deliberately
unreachable. It stores real-token spend evidence, drops to three volunteers,
refuses new work while retaining its pending mutation, reconnects a fourth,
completes that mutation, deletes the owner's working history and performs the
complete freeze/download/agreement/provision/restore workflow over those links.
Both spends survive and the restored owner can accept new work. Unauthenticated
and unpinned-but-authenticated senders cannot reach any history role.

Required follow-up:

1. The enrolled volunteer now has explicit runtime/desktop-service configuration
   and retained controller pins. Complete the protected owner's corresponding
   configuration and desktop recovery flow, preserving the refusal to initialize
   missing history during startup.
2. Separate transport readiness from admission readiness: the current standalone
   owner waits for history quorum before starting its listener. Reverse links need
   their authenticated transport available first. Startup must permit that transport
   while keeping publication/search admission closed until protected readiness;
   simply attaching this router after `ready()` would deadlock that topology.
3. A configured volunteer bridge/topology when both the owner and members are
   outbound-only; this implementation requires a reachable volunteer at the other
   end of a connection. It does not traverse arbitrary NATs or create an always-on
   managed relay.
4. Supervised lifecycle, resource-policy integration and independent Internet/TLS,
   volunteer-overlap and energy validation. Local sockets and simulated outages
   cannot certify those external conditions.
