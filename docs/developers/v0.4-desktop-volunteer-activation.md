# Reviewed volunteer service activation

After [enrollment](v0.4-desktop-history-setup.md), a volunteer can configure its
background relay in **Protected history maintenance → Activate enrolled volunteer**.
The operation retains the maintenance pause. Leaving maintenance and starting the
relay remain explicit actions.

## Select and review

Supply the independently retained enrollment, this member's signing/storage key
files, its existing history directory, an authorized controller file and a new
service configuration output. The controller file is an array of one to five
independently verified infrastructure identities and endpoints:

```json
[{ "relayId": "did:key:<verified-controller-key>", "endpoint": "wss://controller.example/" }]
```

Controllers must have distinct identities and endpoints. Public contacts require
TLS; loopback contacts may use WebSocket without TLS for local testing. This file
pins the relay connection identity; signed history requests still need the owner
key pinned by the enrollment. Review never establishes reachability or a current
quorum.

Choose 5–256 MiB per generation, 1–10,001 blocks per generation and 1–65 retained
generations. Review reopens every retained generation under those limits. It
rejects limits that cannot retain the existing records. The byte count reserves
manifests and ciphertext; it is not a combined disk limit covering every journal,
recovery workspace, temporary file or filesystem allocation.

Review shows public context/genesis/member pins, controllers and aggregate retained
storage. It binds the selected files, canonical locations, settings and complete
retained manifests/provisioning state. Changes to a generation barrier invalidate
approval even if the visible block/byte counts are unchanged. Keys stay in local
files and never enter the browser request or review response.

## Approve and start

Approval creates a new configuration file exclusively and saves its path and
public history binding in desktop settings. It cannot overwrite another file.
The runtime retains this reviewed role across GUI restart and takes precedence
over an obsolete GUI launch variable. Activating the owner role also preserves
an existing reviewed volunteer role, and vice versa.

A later launch checks the retained context, genesis, member and canonical history
directory against the configuration. Changing identities or switching to a copied
directory requires an explicit recovery workflow; it cannot masquerade as a limit
edit. This local binding is not distributed membership governance and does not
detect a coherent rollback of the entire disk/settings backup.

To change limits or authorized controllers, pause the service, review the same
retained history with a new output file and approve again. The service remains
paused after approval. Leave maintenance and start when ready. The runtime then
opens the retained history and connects to the pinned controllers.

## Interruption and refusal

Review uses the ordinary retained-service reopen path. It can finish only an
unactivated empty successor slot whose absence is provably safe; it is not a
strictly read-only filesystem inspection. It never enrolls a missing genesis,
recreates accepted records or contacts peers. Activated missing successor journals,
corrupt history and unknown contents require inspection/recovery.

If writing desktop settings fails after configuration creation, preserve that
configuration and the history. The previous settings remain intact. Select a new
output path and review again. The operation does not start a native service.
Missing/corrupt saved bindings or configurations are refused, rather than silently
detaching the volunteer role.

## API and validation

Authenticated GET `/api/relay/history/volunteer-activation` returns the saved
selection. POST `/review` accepts exactly `{input}`; POST `/apply` accepts exactly
`{input, approvalDigest}`. Both run under stopped-runtime/control exclusion and
require the persistent maintenance pause. Inputs use bounded absolute paths and
fixed operations; arbitrary commands and extra fields are refused.

Validation results are recorded in the [completion plan](v0.4-completion-plan.md).
Tests use disposable histories and real local Node/socket processes; native service
installation is mocked. Independent volunteer availability, Internet/TLS deployment,
combined storage budgets and broader interrupted-enrollment recovery remain open.
