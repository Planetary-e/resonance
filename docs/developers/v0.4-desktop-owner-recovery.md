# Guided desktop owner recovery

The maintenance panel now exposes the existing owner recovery protocol as bounded
reviewed operations. The desktop does not accept a command name, shell arguments
or arbitrary script from the browser. It selects only plan, start, status, step,
restore review, restore, retained-restoration review and readiness completion from
the shared operator implementation.

## Workflow

Stop the managed relay through **Protected history maintenance**. In **Recover
owner history**, select the retained owner configuration, independent enrollment
backup, storage key, current signed policy, recovery workspace, new restored
history folder and optional operator connection file. Keys remain in files.
Start with agreement view 1; raising a view requires an explicitly selected new
workspace, preserving the previous workspace and all volunteer evidence.

**Review new recovery** contacts volunteers to discover authenticated retained
history. It neither creates a workspace nor freezes a generation. The review
binds the original protocol approval to the complete desktop file selection,
normalized operator routing and canonical output locations. Invalid/expired
policy, overlapping folders, occupied restoration destinations, bad views and
malformed input are refused before discovery. Runtime, workspace and restored
history folders must be separate; symlink aliases cannot bypass this check.

**Approve freeze and prepare recovery** repeats inspection and verifies the
unchanged approval. It creates the encrypted workflow journal and saves the
selection. The approval authorizes a later irreversible old-generation freeze:
ordinary writes and exact retries there stop. It does not authorize replacing
witness/coordinator state or discarding accepted records.

**Run next recovery step** performs one existing bounded protocol phase. There is
no automatic retry/view-increase loop. **Resume saved workspace** reopens local
status without network exchange. Saved input and encrypted progress survive
locking or closing the GUI; each call reacquires stopped-runtime/control exclusion.
An interrupted settings write can leave a valid workspace without a saved form
selection. Select that same workspace and resume its status; do not prepare a new
empty history to bypass it.

Once provisioning completes, **Review restoration** reconstructs accepted spends
and denials locally and shows a separate destination/policy-bound approval.
**Approve restoration** initializes the new history and requires four fresh
copies. Success leaves the service paused. Use the separate
[owner activation panel](v0.4-desktop-history-activation.md), then explicitly leave
maintenance and start. Every later start still checks fresh readiness.

## Cancellation and interruptions

Cancel, session lock and client disconnect close outstanding exchanges and keep
the maintenance pause and durable pending work. Exclusion remains held until the
operation settles. Cancellation cannot undo a freeze already accepted by a
volunteer. A timeout does not authorize deleting a workspace or replacing keys.

If restoration published the new image but failed readiness, retain that folder.
Select **Review retained restoration**, then **Approve readiness completion**.
The review replays the workspace ancestry and binds the exact retained image,
policy and any pristine writer/archive setup. Completion requires four fresh
copies and leaves the service paused. See the
[readiness-resumption guide](v0.4-restoration-readiness.md). Do not restore over an
occupied destination. [Initial preparation/volunteer enrollment](v0.4-desktop-history-setup.md)
is also available. Guided volunteer service activation and storage controls still
keep the full desktop workflow roadmap item open.

Resuming a completed workspace checks whether the destination contains files and
shows that fact without claiming readiness. It no longer offers restoration over
an occupied folder. Use activation to validate a completed owner history or the
readiness workflow for an interrupted one.

## Local API

GET `/api/relay/history/recovery` returns the saved selection. POST accepts exact
`{action, input}` or `{action, input, approvalDigest}` for start/restore/ready. Both need
an unlocked session and bearer token. The existing cancellation endpoint cancels
the active in-process operation. Returned progress contains phase, generation and
aggregate restoration counts, never bearer tokens or private key material.

## Validation

Package compilation and **29 tests / seven files in 43.20 seconds** pass. The new
integration uses the real local HTTP API and five enrolled history services:
lost owner, explicit approvals, a failed three-copy freeze, returning fourth
member, lock/unlock and workspace resumption, restoration, separate activation,
accepted-token replay and conflicting-reuse refusal. Negative tests cover input
and directory boundaries, unchanged files on rejection, settings-write failure
after journal creation, and cancel/lock/disconnect during outstanding freeze work.
UI tests distinguish freeze consequences, bounded steps, restoration approval and
later activation. Native service installation remains mocked; these tests do not
certify independent networks, volunteer schedules or power-loss durability.

A manual browser run used the actual React application, local Node API and five
local history services with disposable keys/data. It created/unlocked a test
identity, reviewed and advanced every recovery phase, restored one accepted token,
reviewed/applied activation, reloaded, unlocked again and resumed the saved
workspace. The service remained paused; no native install/start was invoked.
Embedding initialization was stubbed because this scenario tests history recovery,
not model loading or text matching. The run exposed the occupied-destination UI
case above; the final API/UI regression covers its correction.
