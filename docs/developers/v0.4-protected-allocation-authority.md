# Protected allocation authority

The development API can retain new allocation plans and claim assignments on
four of five pinned volunteer devices before returning their signatures. It
extends the existing honest-authority workflow. It does not establish who is
eligible, authorize a second claim, change trust rules or complete K2/K4.

## Identity and initialization

Use `openProtectedAdmissionAllocationAuthority` from the node package. The API
requires explicit `mode: 'create-new'` or `mode: 'open-existing'`. Creation starts
with an empty v2 authority state and creates its owner, writer and archive;
opening never initializes a missing component. Existing local authority journals
cannot be converted or reopened through this API. The local-only API likewise
rejects the protected envelope.

The required protection configuration is:

```ts
{
  context,          // Pinned history identity and five member public keys.
  signingKey,       // History owner key, independently retained.
  members,          // Those members' authenticated endpoint configuration.
  writerDirectory, // Private writer and encrypted payload archive directory.
  timeoutMs,        // Optional bounded maintenance attempt deadline.
  maxArchiveBlocks,
  maxArchiveBytes,
}
```

The top-level options are `path`, `authority`, `secretKey`, `mode`, `protection`
and an optional clock for testing. `authority` and `secretKey` identify the
allocation signer. Its key may differ from the history owner key. Both pins are
checked; role, validation, domains and raw restoration cannot be overridden by
business callers.

The context role is `admission-allocation-authority`. Its `policyDigest` is the
static empty-genesis descriptor returned by `allocationAuthorityHistoryAnchor`:

```ts
historyDigest('resonance:allocation-authority-history-genesis:v1\n' +
  JSON.stringify({ version: 2, authority, manifests: [], assignments: [] }))
```

This binds the authority and empty starting state. It is not a current policy
certificate or evidence of revocation freshness. The protected outer kind and
AEAD domain distinguish the journal from local allocation and protected issuer
files. The shared storage implementation preserves existing issuer formats.

## Enrollment and decisions

Opening is offline and unverified. `enrollment()` returns the pinned context and
signed root for explicit volunteer enrollment through the generic replica
plan/enroll/serve workflow. Call `ready()` after enrollment and on every reopen.
Three available replicas refuse; four fresh exact-head confirmations establish
readiness. A cached certificate alone is insufficient.

The business methods match the local authority API:

- `review(plan)` and `sign(plan, approvalDigest)` retain one immutable signed plan
  for a community epoch.
- `reviewAssignment(request)` and `assignClaim(request, approvalDigest)` reserve
  one issuer permit per claim in that period. A different issuer for the same
  claim is refused.
- `current(community, epoch)` and
  `currentAssignment(community, epoch, claimHandle)` reexport applied records.
- `status()` reports aggregate plan/assignment counts and history readiness,
  pending state and retained head. `close()` releases ownership and wipes key
  copies.

New decisions require readiness and a current issuance window before signing,
before committing and after quorum completion. The commit order is exact local
intent, four durable acknowledgements, local apply, then output. Failure or
process death can leave an uncertain result; reopening and `ready()` complete
that exact retained signature before further decisions. Pending-only records
are never returned by the offline reexport methods.

An applied immutable record remains reexportable offline and after expiry,
including an exact approved retry. Reexport does not renew its validity or make
new decisions available. If the window expires during retention, the new call
refuses output; any already applied record remains retained and independently
subject to the original expiry.

## Bounds and remaining work

Historical parsing authenticates each canonical signature and its allocation,
claim and quota bindings without treating historical expiry as corruption.
Every protected transition is unchanged or appends exactly one plan or one
assignment. Prior entries remain identical and ordered. Reassignment, removal,
combined additions and changed quotas are refused.

Limits remain 64 plans, 2,048 assignments and an 8 MiB plaintext image, plus the
bounded protected owner file and archive. Full snapshots consume archive space;
capacity exhaustion refuses work without pruning or refunding reservations.
This is not sustainable compaction. Preserve both private keys, context,
enrollment, owner, writer and archive.

This first authority API supports intact-owner restart and exact pending
resumption. Authority-specific complete owner-loss recovery and an operator CLI
remain to be implemented and reviewed. Generic ciphertext compaction and
spend-specific recovery commands are not enabled for this role. Do not treat
another independently initialized journal or copied signer key as failover.

The [predeclared experiment](../evals/v04-protected-allocation-authority-2026-10-18.md)
records validation and the operation dependency matrix. New allocations and
assignments require the authority key holder and its history quorum; already
assigned issuance and token redemption gain no new authority-online dependency.
Independent eligibility, malicious-authority governance and actual volunteer
availability remain separate open requirements.
