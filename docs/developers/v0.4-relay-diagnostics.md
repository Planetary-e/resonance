# Bounded managed-relay diagnostics

New desktop service definitions configure `RELAY_DIAGNOSTICS_DIRECTORY` as
`relay-diagnostics` inside the desktop data directory. The relay retains structured
JSON diagnostics in `current.ndjson` and `previous.ndjson`, each at most **1 MiB**.
Rotation replaces only the previous diagnostic file. These files are disposable
operational evidence, never publication, admission, mailbox or recovery authority.
The two-file limit excludes the small process-lock metadata and filesystem
allocation overhead; it is not a whole-app disk quota.

The managed macOS definition sends process stdout/stderr to `/dev/null`, Linux
uses `StandardOutput=null`/`StandardError=null`, and the Windows launcher discards
those streams. This prevents a second unlimited supervisor capture alongside the
bounded structured log. Ordinary CLI execution still prints structured logs to
stdout. Existing installed service definitions and old `relay-service.log` files
are not rewritten or removed by this source change. Apply the new definition
through the existing explicit service installation workflow when deploying it.

## Startup and failure behavior

`main.ts` configures the diagnostic sink before dynamically loading `runtime.ts`.
The previous runtime body is otherwise preserved. A caught module/runtime startup
failure records `relay_startup_failed` and exits with code 1 after flushing queued
console output (or a one-second deadline), even if startup already created handles.
The service manager can then apply its existing restart policy. Uncaught runtime
exceptions are observed without replacing Node's default termination behavior.

Structured startup/runtime events are retained. Arbitrary dependency stdout/stderr,
very early Node/loader failures before this entry point, and service-manager messages
are not captured in these files. Native manager/OS diagnostics may still be needed
for those failures. Do not claim complete capture of every process output.

A dedicated local lock rejects simultaneous diagnostic writers. Startup rejects
unexpected entries, links, multiply linked files and oversized existing output
rather than deleting or following them. Reopening removes only an incomplete final
diagnostic line; it never examines or truncates protocol history. A record larger
than 16 KiB is replaced by a small `diagnostic_record_dropped` marker containing its
original byte length, without its contents.

After a write error or observed output replacement, that sink stops appending and
counts dropped records. A diagnostic failure must not turn a durable accepted
operation into a protocol exception. The existing administrator-authenticated
relay `/stats` endpoint reports `diagnostic_log` with `available`, `maximumBytes`
and `droppedRecords`; it is null when the sink is not configured. No filenames,
record contents or activity are added to public health/discovery responses.
The desktop's aggregate history inventory still excludes this separate diagnostic
folder; its maximum is reported separately, not silently added to history usage.

Diagnostic writes do not require durable acknowledgement. Rotation and orderly
exit close the files; process or power loss may lose the last records. Retained
protocol state continues to use its own flush, signature and recovery rules.

## Validation

Package typechecking and **42 tests / six files in 45.08 seconds** pass. Coverage
includes two-file rotation, reopen after an incomplete line, oversized records,
write failure, competing writers, link/replacement refusal, a real 16,000-record
process flood followed by SIGKILL, and a real early relay startup failure. Signal
and link cases are conditional on platform. Existing real Node owner/bridge/
volunteer startup, activation and capacity/statistics regressions also pass.
Native service installation remains mocked; generated definitions are checked
without installing them on this computer.

A disposable JavaScript-only bundle using the packaging script's relay esbuild
flags started locally, returned HTTP 200 health, reported the 2 MiB diagnostic
limit through authenticated stats, wrote its startup event, and exited cleanly
on SIGTERM. Its data and bundle were removed. No native installer or release was
built. This checks the new dynamic entry point in the bundled format; it does not
certify Windows/Linux installation or independent Internet operation.

The full local suite and current CI result are recorded in the
[completion plan](v0.4-completion-plan.md).

Complete local regression: **1,217 tests / 191 files in 889.02 seconds**. The saved
544-file package TypeScript/declaration manifest and every hash were unchanged
throughout the run. This covers the final runtime source and owner diagnostic
health assertions; it does not certify native installation on three platforms.
